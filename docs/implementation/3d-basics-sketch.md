# 3D 基本機能 設計スケッチ（REQ-MOGRAPH-003）

> **Status**: Sketch — 2026-07-27 — 実装単位は未確定

対象要件: REQ-MOGRAPH-003（優先度 Should）。関連: REQ-MOGRAPH-004、
REQ-GPU-001。

**これは完全な実装計画ではない。** 方向づけと単位の目安までを書き、
詳細は `typography-plan.md`（REQ-MOGRAPH-004）の完了後に埋める。
3D テキスト押し出しが主要ユースケースであり、テキストジオメトリの形が
確定していない段階で詳細を書くと手戻りになるため。

## スコープ

Element 3D / Cinema 4D Lite 相当。**フル 3D シーンは目指さない。**
2D コンポジット内に 3D 要素を配置する。

主要ユースケースはリリックモーションでの 3D テキスト多用。

## 決まっていること

### コンテナ構造は変えない

`docs/specifications/procedural-geometry.md:159` が既に決めている。

> `Geometry` の位置は 2D（`Vec2`）。3D 拡張は**属性型の追加**で行い、
> コンテナ構造は変えない。

つまり `Geometry` を `Geometry3D` に分岐させたり `P` を `Vec3` に
昇格させたりしない。`AttributeType::Vec3` は既にあるので、
**`Pw`（Vec3 の world 位置）を追加属性として持つ**方向になる。

含意:

- 既存の 2D ノード（`geometry.transform`、`field.apply`、`scatter.*`）は
  `P` しか見ないので、3D 属性が乗ったジオメトリも壊さず通過する。
- `Field::sample` は `&[Vec2]` を取る。3D 位置でのフィールドサンプルは
  そのままでは書けない。`per-instance-modulation-plan.md` が
  `FieldSample` 構造体化を入れるので、**そこに `positions_3d` を足す
  余地を残しておく**（変調計画で構造体化する理由の一つ）。
- ラスタライザは `P`（Vec2）しか読まない。3D は投影後の `P` を書く
  ノードが要る（下記）。

### 投影は明示ノードで行う

`camera.project` が 3D 属性（`Pw`）とカメラパラメータから
`P`（Vec2）を計算して書き戻す。これで下流は既存の 2D 経路がそのまま
使える。「3D レンダリング結果が 2D コンポジットに合成される」という
受入条件は、専用の 3D レンダラではなくこの投影で満たす。

深度ソート（`Pw.z` による描画順）はラスタライザ側の対応が要る。

### GPU 方針

3D は GPU が前提だが、**`gpu-resident-geometry-plan.md` の上に載る**。

- 押し出し・ベベルは頂点生成なので GPU に向く。ただし出力形が未決定
  （下記）なので設計できない。
- `camera.project` は全頂点への行列適用で、GPU 常駐ジオメトリなら
  1 カーネル。CPU 常駐だと投影のたびに往復する。
- ライティングはフラグメント段階なので既存のラスタライザ拡張。
- 深度ソートは GPU 側（深度バッファ or ソート）。CPU ソートだと
  インスタンス順の読み戻しが要る。

つまり **3D を CPU 常駐ジオメトリの上に作ると往復だらけになる**。
`gpu-resident-geometry-plan.md` を 3D の前提に置く。

## 未決定（004 完了後に決める）

### 押し出しの出力形

テキスト輪郭 → 押し出しでできるのは**メッシュ**。
現在の `Primitive` は `Path` のみで、`Mesh` は「将来」とだけ書かれている。

選択肢:

1. `Primitive::Mesh` を追加する — コンテナ構造を変えないという方針の
   範囲内かどうかが微妙。`Primitive` の enum を増やすこと自体は
   構造変更ではないが、影響は広い。
2. 押し出しを**前面 / 側面 / 背面のパス集合**として表現する。
   ベベルなしなら側面は四角形パスの集合で表せる。メッシュを導入せずに
   済むが、ライティングの法線をどう持つかが問題になる。
3. 3D はジオメトリパイプラインに載せず、**専用ノード内部で完結**させて
   FrameBuffer を出すブラックボックスにする。既存構造を一切汚さないが、
   「3D テキストがフィールドで歪む」ができなくなる。要件 004 の
   「変換ジオメトリがフィールドの影響を受ける」と相性が悪い。

**004 でテキスト輪郭ジオメトリの形が決まってから選ぶ。**

### ライティングの持ち方

法線属性（`N`: Vec3）を per-point で持つのが素直だが、
2 の表現を選ぶと側面の法線をどこに置くかが決まらない。

### プリミティブ（ボックス / 球 / 円柱 / 平面）の位置づけ

押し出しの出力形が決まれば同じ形で作れる。先に決めることはない。

## リスク

- **既存の 2D 前提が想定より深い可能性**。`bounds()`、`path_sample`、
  `rasterize` の各所が `Vec2` を直接扱っている。単位 1 の着手時に
  棚卸しが要る。
- **「フル 3D を目指さない」の線引きが曖昧**。カメラとライトを入れた
  時点で「なぜシャドウが無いのか」「なぜマテリアルが無いのか」が
  出てくる。要件側でスコープの線を明文化してから実装に入るべき。
- 優先度 Should かつ 004 依存なので、**002 / 005 より後**で構わない。

## 非対象（現時点の想定）

- シャドウ、反射、グローバルイルミネーション
- マテリアル / シェーダグラフ
- 3D モデルのインポート（glTF / OBJ）
- 3D 空間でのパーティクル
- IK / リギング / アニメーションのインポート
