# 3D シーン 実装計画

> **Status**: 単位 1a・1b・2・3 実装済み — 2026-08-02（2026-07-27 のスケッチから
> 昇格、2026-07-29 に決定事項を確定）

対象要件: `docs/requirements/REQ-3D.md`（REQ-3D-001〜009）。
関連: REQ-MOGRAPH-004、REQ-GPU-001、REQ-CORE-010。

ジオメトリ表現の規約は `docs/specifications/procedural-geometry.md`。

## スコープ

Element 3D / Cinema 4D Lite 相当。**フル 3D シーンは目指さない。**

主要ユースケースは**プリミティブジオメトリを使ったモーショングラフィック
表現**（C4D の MoGraph 相当）。立方体や球を規則的に並べ、フィールドで変調して
動かす絵が中心。3D テキストの押し出しは重要だが主導線ではない。

この優先順位が実装順を決める。**プリミティブ（REQ-3D-005）と複製
（REQ-3D-009）は REQ-MOGRAPH-004 に依存しない**ので、タイポグラフィの完了を
待たずに 3D が実用になる。押し出しはテキスト輪郭ジオメトリの形が決まってから。

## 決定事項（2026-07-29 設計セッション）

### 表現は `Primitive::Mesh`。variant を先に入れ、レンダラは後

モデル読み込み（REQ-3D-008）と 3D 破砕（`geometry-fracture-plan.md`）が
視野にあるため、**押し出しをパス集合で表す案は採らない** — 任意の三角形
メッシュを前面 / 側面 / 背面に分解できないので、読み込みをやるなら結局
Mesh が必要になり両方書くことになる。

段取りを分ける根拠は**時間で高くつくものが違う**こと。

| | 今のコスト | 後回しにしたコスト |
|---|---|---|
| enum の網羅 match | `Primitive::Path` 参照 53 箇所 / 7 ファイル | `OPS-1〜13` / `PATH-1〜6` / `TYPE-*` 追加後は 100 箇所超 |
| `P` の次元の網羅 | `as_vec2` 呼び出し 58 箇所 / 12 ファイル | 同上 |
| レンダラ | 変わらない | 変わらない（既存ノードに影響しない） |

よって **variant を先に入れて match の規約を確定させ**、レンダラは 3D 着手時に
実装する。

### Scene はグラフを流れるデータ型

`DataTypeId::SCENE` を追加し、Scene は**オブジェクト・カメラ・ライトの
リスト**を持つ `NodeData` にする。

```text
shape.rect ────┐
               ├─ scene.add(transform) ─┐
mesh.box ──────┘                        ├─ scene.render ─→ FrameBuffer
                    scene.camera ───────┤
                    scene.light ────────┘
```

- 既存の pull 評価・`PortRecord`・キャッシュがそのまま使える
- 複数カメラ / 複数パスが自然に書ける
- Scene を subnet（REQ-LAYER-003）に収めて使い回せる
- 変換の階層は Scene の入れ子で表す（子の Scene を親の `scene.add` に渡す）

**FrameBuffer オブジェクトは複製できない**（REQ-3D-001 の既知の制約）。
`scatter.*` は Geometry のインスタンス機構なので対象外。ビデオウォール的な
表現は v1 では組めない。

### 後回しにしても安い理由（と、そのための制約）

逃げ道 A（Mesh へのテクスチャ割り当て）が必要とするもののうち、**重い部分は
既に本計画に入っている**。

| 必要なもの | 状況 |
|---|---|
| レンダラのテクスチャサンプリング | 単位 4（FrameBuffer オブジェクトのために必須） |
| Mesh の UV 属性 | 単位 5（「法線と UV 相当の属性」） |
| `scene.add` のテクスチャ入力 | 未定。**入力ポートの末尾追加**で済む |

さらに **`Scene` の値は永続化されない**。`.ravprj` に入るのはノード・エッジ・
パラメータで、評価された `Scene` は入らない。よって Scene のオブジェクト
モデルを後から変えても**ファイル移行が発生しない**。入力ポートの末尾追加も
エッジの index を壊さない（`expose_param_port` が末尾に追加する設計理由）。

**そのための制約（単位 4 で守ること）**: テクスチャサンプリングを
「FrameBuffer 用の暗黙 quad 専用」に作らない。**最初から Mesh の UV 属性を
読む形**にし、FrameBuffer の quad はそこに自明な UV を持たせるだけにする。
これを守れば逃げ道 A は純粋にポート追加で済み、守らないと別実装になる。

逃げ道 B（FrameBuffer オブジェクトのインスタンス化）は
`instances` の `source: GeometryRef` の型を広げる必要があり、後からでも安く
ならない。ただし A で同じ絵が出る（テクスチャ付き平面を複製する）ので、
**A を確保しておけば B は不要**になる見込み。

**レイヤー層の概念（AE 式の 3D レイヤー）は採らない。** 「各レイヤーが自分の
ネットワークを所有して FrameBuffer を出す」という REQ-LAYER の根幹と衝突し、
`frame` を出さないレイヤーという例外が Null に続いて 2 つ目になる。

### 位置は `P` の次元をジオメトリごとに許す

`Pw`(Vec3) を別属性にして `P` を投影後の値にする案は**採らない**。位置の
情報源が 2 つになり同期漏れを招く。詳細は仕様書の「位置の次元」。

投影は `scene.render` の内部で行い、`P` を書き換えない。

### 回転はオーサリングと要素で分ける

オーサリング = オイラー角の成分別チャンネル（回転順 ZYX 固定）、
要素属性 = クォータニオン `orient`(Vec4)。統一アニメーションチャネルが
成分ごとに独立補間するため、クォータニオンはキーフレーム対象にできない。
詳細は仕様書の「回転の表現」。

### 描画は不透明 Mesh が深度、半透明と Path がソートの 2 パス

現在の `rasterize.wgsl` は解析的（フラグメントごとにパスセグメントへの最短
距離を評価）で、頂点バッファを使わず `depth_stencil: None`。

- **パス 1**: 不透明 Mesh を深度バッファ有効（write ON / test ON）で描く。
  押し出しテキストの前面と側面の前後関係が正しくなる
- **パス 2**: 半透明と Path を**オブジェクト単位の代表深度**でソートして
  back-to-front、深度 test ON / write OFF。Mesh の背後に隠れるのは正しい

代表深度は**そのオブジェクトの変換を適用し、カメラの view 空間へ移した重心の
z**（同値なら bbox の z 範囲で tie-break）。**`Pw` 属性は存在しない** —
位置は `P`（Vec2 または Vec3）だけで、奥行きは `scene.add` の変換と
カメラ行列から決まる。

ソートがオブジェクト単位であることが「交差する半透明同士を保証しない」理由。
オブジェクト内部で深度が広がっている場合（3D 折れ線、傾いたカード）、
半透明同士の前後は解決できない。不透明 Mesh に対しては深度テストが
フラグメント単位で効くので正しい。

**交差する半透明同士は保証しない**（REQ-3D-007 のスコープ線）。全部を深度
バッファにすると解析的カバレッジのアンチエイリアス縁で背景が抜ける。

### GPU 常駐ジオメトリを前提にしない

スケッチ段階では「3D は `gpu-resident-geometry-plan.md` の上に載る」と
していたが、**この前提を外す**。`GPU-0` は測定で中止しうる判断ゲートであり、
3D をそこに依存させると 3D 自体が測定結果に人質を取られる。

CPU 常駐で実装し、`scene.render` の内部で頂点バッファへアップロードする
（`rasterize` の GPU 経路が既に storage buffer へ属性を上げているのと同じ
形）。GPU 常駐化は入ったら効くが、前提ではない。

**測定（2026-07-29）でこの判断は裏付けられた。** `perf-baseline.md`
「3D の頂点アップロード」より、CPU → storage buffer が **6.5〜7.9 GB/s**
（6.4 MB 以上の転送。1 MB 未満は固定コストの比率が上がり約 5.0 GB/s）。
頂点 32 B 換算、下限 6.5 GB/s で計算:

| 頂点数 / フレーム | アップロード ms | 16.6 ms 予算比 |
|---|---|---|
| 10 万（3.2 MB） | ≈0.5 | 3% |
| 50 万（16 MB） | ≈2.5 | 15% |
| 100 万（32 MB） | ≈4.9 | 30% |

数十万頂点までは毎フレームアップロードで成立する。ただし**条件が 1 つ付く**:

- **静的なメッシュ実体と、毎フレーム動く状態を別バッファに分ける。**

  | バッファ | 中身 | dirty になる条件 |
  |---|---|---|
  | 静的（メッシュ実体） | 頂点位置・インデックス・法線・UV | **その列が変わったときだけ** |
  | 動的（per-instance / per-object） | 変換行列、`P` / `orient` / `scale3`、色 | 毎フレーム可 |

  変換をシェーダで適用し**頂点に焼き込まない**のが前提。焼き込む設計に
  するなら「静的バッファは無い」ことを明記すること — その場合は毎フレーム
  全頂点を上げ直すので、上表の予算がそのまま効く。

  現状の `rasterize` GPU 経路は分離しておらず、毎フレーム
  `create_buffer_init` で全部作り直している（10 万インスタンスで 1.20 ms、
  100 万で 17.08 ms）。単位 4 でこれをそのまま真似すると 100 万頂点級で崩れる。

`GPU-0` は「実施」判断になった（同計画 Status）ので `GpuGeometry` は
いずれ入るが、**単位 4 の着手をそれで待たせない**という判断は変えない。

## 実装単位

単位 1 は 2 つに分ける。`P` の次元と `Primitive` の種別は**独立した軸**で、
それぞれ別の大きな面を持つ。

| 変更 | 影響面 |
|---|---|
| `P` の次元許容（単位 1a） | `as_vec2` 呼び出し 58 箇所 / 12 ファイル |
| `Primitive::Mesh` の variant（単位 1b） | `Primitive::Path` match 53 箇所 / 7 ファイル |

組み合わせは 4 通りすべて意味を持つ。Vec3 の `P` + `Path` は**3D の折れ線**
（押し出しの輪郭、3D 曲線）で Mesh 無しに成立し、Vec2 の `P` + `Mesh` は
**平面を三角形分割したもの**（破砕の中間結果、塗りのメッシュ化）。
1 単位にまとめると 100 箇所超の巨大な単位になってレビューできない。

### 単位 1a: `P` の次元許容（Vec2 | Vec3）✅ 実装済み

`Positions`（`ravel-core/src/geometry/container.rs`）が `P` の読み出しを
一本化し、`Geometry::validate` は Point / Instance ドメインの `P` が
Vec2 か Vec3 であることだけを課す。明示エラーは
`GeometryError::RequiresPlanarP`。分類の結果は仕様書
「`as_vec2` 呼び出しの棚卸し」にある。

- `P` の列型が Vec2 と Vec3 のどちらでもよいことを `Geometry` の不変条件と
  して認める（構築時の検証を緩め、ドメイン内の型一致は維持する）
- `as_vec2` を呼ぶ 58 箇所すべてに、**仕様書の表どおりの挙動**
  （対応 / 次元非依存 / 明示エラー）を実装する。分類表は仕様書
  「`as_vec2` 呼び出しの棚卸し」
- 3D 対応が要るもの: `geometry.transform`（3 成分変換）、`bounds` 系
- 明示エラーにするもの: 弧長・パス前提（`attribute.path_sample` /
  `scatter.path_array`、将来の `resample` / `attribute.curveu`）と
  `rasterize`、`scatter.*` の `center_input`
- 次元非依存で素通しするもの: `attribute.*` / `field.apply` /
  `geometry.merge`（将来の `blast` / `sort` / `switch`）

**完了条件**

- Vec3 の `P` を持つジオメトリを構築・評価できるテスト
- `geometry.transform` が 3 成分を変換するテスト
- 弧長前提ノードが Vec3 で明示エラーになるテスト（**黙って xy に射影しない**
  ことの pin）
- 属性系・要素操作系が Vec3 を素通しするテスト
- `P` が Vec3 の Path ジオメトリ（3D 折れ線）が成立するテスト
- **既存の 2D 挙動が一切変わらないテスト**（既存ゴールデン無改変）

### 単位 1b: `Primitive::Mesh` の追加と網羅規約（レンダラなし）✅ 実装済み

`Primitive::Mesh`（`ravel-core/src/geometry/container.rs`）が三角形メッシュを
表し、インデックスは `Geometry` が 1 本だけ持つ共有列（`Arc<Vec<u32>>`）に
入る。値は `verts.start` からの**相対オフセット**なので、連結は範囲をずらして
列を追記するだけで済む。明示エラーは
`GeometryError::RequiresPathPrimitives`。分類の結果は仕様書
「`Primitive::Path` 参照の棚卸し」にある。

- `Primitive::Mesh { verts: Range<usize>, indices: Range<usize> }` を追加
- インデックス列を `Geometry` に持たせる（`AttributeSet` と同じ `Arc` CoW）
- 既存 53 箇所の `Primitive::Path` 参照すべてに Mesh の腕を入れ、
  **仕様書の表どおりの挙動**を実装する。判断が要るのは 8 箇所で、残り
  45 箇所は Path を構築するだけの箇所・文書・既存テスト
- `Geometry::validate` はインデックス列の範囲・3 の倍数・頂点数未満を検査する
- `rasterize` は Mesh を含むジオメトリで明示エラー（この時点では描けない）

**完了条件**

- Mesh を持つジオメトリを構築・評価できるテスト
- 弧長前提ノードが Mesh で明示エラーになるテスト
- `attribute.*` / `field.apply` が Mesh を素通しするテスト
- Vec2 の `P` + Mesh（平面の三角形分割）が成立するテスト
- **既存の 2D 挙動が一切変わらないテスト**（既存ゴールデン無改変）

### 単位 2: `orient` / `scale3` / `N` 標準属性と回転ユーティリティ ✅ 実装済み

回転数学は `geometry::rotation`（`Quat` は `(x, y, z, w)`、`Mat3` は行優先）が
単独で持つ。オイラーは**外因性 ZYX**（`Rx * Ry * Rz`、固定軸の Z が先）で、
ジンバルロック時は X を 0 として結合分を Z に載せる。4x4 は置かない。

- 予約名を `geometry/names.rs` に追加
- オイラー角（ZYX）⇄ クォータニオンの変換、クォータニオンの合成と slerp
- `scatter.*` が 3D で `orient` / `scale3` を書けるようにする土台

**完了条件**

- オイラー ⇄ クォータニオンのラウンドトリップテスト
- 回転順 ZYX が pin されたテスト（既知の角度で既知の行列になる）
- slerp が最短経路を通るテスト
- ジンバルロック近傍での挙動が定義どおりであるテスト

### 単位 3: `Scene` データ型とカメラ ✅ 実装済み

シーン空間は **+X 右 / +Y 下 / +Z 奥（右手系）** — 2D コンポジション座標と
一致させ、2D→3D 境界で符号反転を起こさないため。glTF / OBJ は +Y 上・
+Z 手前なので**単位 9 の読み込みで変換する**。`Mat4` は列優先で階層は
`parent * child`、回転は `geometry::rotation` に委譲する。深度範囲は
`Camera::clip_range()` が正規化するので、**単位 4 は `near` / `far` を
直接読まずこれを使う**（読み分けると投影行列と深度バッファが食い違う）。

- `DataTypeId::SCENE`、`Scene` の `NodeData` 実装、ポート色
- `scene.add`（Geometry または **FrameBuffer** + 3D 変換 → Scene）、
  `scene.merge`（Scene 結合）。FrameBuffer はテクスチャ付き矩形になる
  （サイズは画像解像度由来、アスペクト比を保つ）
- `scene.camera`（パース / オルソ。位置・注視点・画角・near/far）
- カメラパラメータは統一アニメーションチャネルに乗せる
- Scene の入れ子（`scene.add` が Scene も受ける）

**完了条件**

- Scene にオブジェクトを追加して取り出せるテスト
- 入れ子の変換が合成されるテスト
- カメラの投影行列が既知の値になるテスト（パース / オルソ両方）
- カメラパラメータにキーフレームを打てるテスト
- アスペクト比がコンポジション解像度から決まるテスト

### 単位 4: 三角形レンダラと `scene.render`

単位 3 が用意した土台と、それが課す制約:

- **深度範囲は `Camera::clip_range()` から読む。** `Camera` の `near` / `far`
  フィールドを直接読んではいけない。`clip_range()` は `near` を権威として
  `far` を押し出すことで反転・空の範囲を正規化しており、投影行列もこれを
  通している。深度アタッチメントだけ生の値を読むと**投影行列と深度バッファの
  範囲が食い違う**
- **シーン空間は +X 右 / +Y 下 / +Z 奥（右手系）**、クリップ空間は wgpu
  （xy ∈ [-1,1] で y 上、depth ∈ [0,1]）。view-projection の `m11 = -1` が
  この Y 反転を担っている
- 平坦化は `Scene::flatten() -> Vec<FlatObject { content, world_transform }>`、
  カメラは `Camera::view_projection_matrix_for(&EvalContext)`。カメラの選択は
  `Scene::primary_camera()`（最初にマージされたもの）— 選択パラメータが要る
  ならポート / パラメータの末尾追加で足りる
- 回転行列を自前で書かない。`geometry::rotation`（3x3）と `scene::Mat4` が
  既にあり、オイラーの順序はそこが所有している
- 第 2 のレンダーパイプライン（頂点/インデックスバッファ、深度添付、
  法線補間、**UV と単一テクスチャのサンプリング**）
- **テクスチャサンプリングは Mesh の UV 属性を読む形にする**（FrameBuffer の
  quad 専用にしない）。上記「後回しにしても安い理由」の制約
- 2 パス描画（不透明 Mesh → 半透明と Path）
- Path オブジェクトは既存の解析的経路を Scene 内で使う
- FrameBuffer オブジェクトはテクスチャ付き矩形として描く
- CPU リファレンス経路（三角形の塗りはスキャンライン）

**完了条件**

- 単一の Mesh が期待どおり描かれるゴールデンテスト
- 重なる 2 枚の Mesh で自己遮蔽が正しいテスト
- FrameBuffer オブジェクトが正面から見て元画像と一致するテスト
  （アスペクト比とサンプリングの pin）
- **UV 属性を差し替えるとサンプリング結果が変わるテスト**（quad 専用の
  暗黙 UV になっていないことの pin。逃げ道 A の前提を守る）
- 毎フレーム更新される FrameBuffer が正しく反映されるテスト
- 半透明 Path が不透明 Mesh の背後で隠れるテスト
- Path のアンチエイリアス縁で背景が抜けないテスト
- **交差する半透明同士が不正確であることを明示するテスト**
  （将来の改善で挙動が変わったと分かるように）
- CPU / GPU 一致テスト（許容誤差を明示。既存の merge / transform と同様に
  積和の FMA 縮約を考慮する）
- **変化していないメッシュの静的バッファが 2 フレーム目に再確保も
  再アップロードもされないテスト**（上記「GPU 常駐ジオメトリを前提に
  しない」の条件）。**`ravel_gpu::transfer::stats` では検証できない** —
  あのカウンタは `upload_texture` / `read_texture` だけを数えており、
  `create_buffer_init` によるバッファ生成は素通りする。メッシュバッファ側に
  確保カウンタを置くか、ハンドル同一性（2 フレーム目が同じバッファを
  使い回したこと）を観測する形にする。動的バッファ側は毎フレーム更新されて
  よいので、カウンタは静的バッファに限定する

### 単位 5: 基本プリミティブ（REQ-3D-005）

- `mesh.box` / `mesh.sphere` / `mesh.cylinder` / `mesh.plane`
- 分割数パラメータ、法線と UV 相当の属性
- `ParamRole` を宣言して Viewer のマニピュレータで掴めるようにする
  （`viewer-overlay-manipulator-plan.md` 単位 5）

**完了条件**

- 4 種の頂点数・面数が分割数から期待どおりになるテスト
- 法線が単位ベクトルで外向きであるテスト
- 球の極（縮退する三角形）の扱いが定義どおりであるテスト
- フィールドで変調できる結合テスト

### 単位 6: 3D 複製（REQ-3D-009）

- `scatter.grid` に 3 軸目の分割数を追加
- `scatter.circular` に軸指定を追加
- `scatter.path_array` / `scatter.scatter` を 3D ジオメトリ上で動かす
- インスタンスに `P`(Vec3) と `orient` を書く
- 複製数の上限と超過時の評価エラー

`orient` / `scale3` / `N` の予約名と回転数学は単位 2 で入っている
（`geometry::names` と `geometry::rotation`。クォータニオンは `(x, y, z, w)`）。
**`scale3` と `scale` / `orient` と `rot` の優先関係はこの単位が決める** —
単位 2 は「消費側が決める」として未決にしてある。2D 経路が `rot`(F32) /
`scale`(Vec2) を読み続けることを崩さない形で決めること。

**完了条件**

- 3 軸グリッドの複製数が積になるテスト
- インスタンスが `P`(Vec3) / `orient` を持つテスト
- フィールドで位置・姿勢・スケール・色を per-instance 変調できるテスト
- **2D の既存挙動が変わらないテスト**（`P` が Vec2 のときの回帰）
- 上限超過が評価エラーになるテスト

### 単位 7: ライティング（REQ-3D-006）

- `scene.light`（ディレクショナル / ポイント / アンビエント）
- `scene.render` が `N` と合わせて陰影を計算する
- 色は既存の `Cd` とスタイル属性を使う（マテリアルは非対象）

**完了条件**

- 3 種のライトで既知の陰影になるゴールデンテスト
- ライトが無い Scene でも Mesh が見えるテスト（アンビエント既定）
- `N` を持たないジオメトリ（Path）がライティングで壊れないテスト
- ライトパラメータにキーフレームを打てるテスト

### 単位 8: 押し出しとベベル（REQ-3D-004）

**依存**: `TYPE-*`（テキスト輪郭ジオメトリの形の確定）、
`PATH-0b`（三角形分割器の採用判断）

- パス → Mesh の押し出し。前面 / 背面キャップは三角形分割で埋める
  （`ravel_core::geometry::triangulate`、`PATH-0b` で `earcut` に決着）。
  **出力三角形は入力の巻き方に依らず常に反時計回り**なので、**前面と背面の
  表裏はインデックス順から読み取れない** — 背面キャップは巻きを自分で反転
  させ、`N` も自分で書くこと
- 側面は輪郭に沿って生成し、`N` を書く
- ベベル（幅・分割数）
- 穴あき形状（文字の `o`）のキャップ

**完了条件**

- 穴あき形状のキャップが正しく埋まるゴールデンテスト
- 押し出した Mesh がフィールドで変調できるテスト
- ベベルの分割数 0 が押し出しと一致するテスト
- 法線が生成されライティングに使われるテスト

### 単位 9: モデル読み込み（REQ-3D-008）

**依存**: 単位 4（描けないと確認できない）

- glTF / OBJ からジオメトリと法線を読む（マテリアル・アニメーション・
  スキニングは非対象）
- **基底の変換**: glTF / OBJ は **+Y 上・+Z 手前**、シーン空間は
  **+Y 下・+Z 奥**（単位 3）。読み込み時にここで変換する。**この変換を
  ここに閉じるのが、シーン空間を 2D コンポジション座標に合わせた判断の
  代償**（2D→3D 境界に符号反転を置かない代わりに、import 境界に置く）
- アセット参照はメディアと同じ相対パス解決（REQ-PROJ-001）
- 複数メッシュの階層を Scene の入れ子として表現する
- 読み込み失敗の UI 表示

**完了条件**

- glTF / OBJ の読み込みテスト（小さな固定ファイル）
- **+Y 上のモデルが上下反転せずに描かれるテスト**（法線の向きも含む）
- 階層が Scene の入れ子になるテスト
- 相対パスで永続化されるテスト
- 読み込んだ Mesh を破砕・変調できる結合テスト
- 失敗が UI に出るテスト

## 検証

- `mise run check`
- 単位 1・2・3 は headless（`ravel-core`）で書ける。GPU 不要（実績: 単位 2 が
  25 テスト、単位 3 が `ravel-core` 47 / `ravel-nodes` 24 で、いずれも
  アダプタ不要・ゴールデン画像 0 枚）
- **行列と回転は「実装と同じ式」で検証しない。** 手計算した要素値、または
  実装とコードを共有しないリファレンス実装と比較する。単位 3 では
  view-projection のテストが実装と同じ式を比較していて、投影行列の
  完了条件を実質満たしていなかった
- **「pin したつもり」を変異テストで確かめる。** 符号・順序・閾値を意図的に
  壊してテストが落ちることを確認する。単位 2 / 3 では対角要素だけの検証、
  単軸だけの検証、平行移動だけの入れ子が、それぞれ符号誤り・順序誤り・
  合成順の誤りを見逃していた
- 単位 4 以降は GPU アダプタが必要。CPU リファレンス経路との一致テストを
  既存の `rasterize` と同じ形で持つ
- **ゴールデン画像を増やしすぎない**。数値検証（頂点数、法線の向き、
  既知座標の色）を優先する

## リスク

- ~~**単位 1a / 1b の箇所数が想定より深い可能性**~~ — 解消。分類表を仕様書に
