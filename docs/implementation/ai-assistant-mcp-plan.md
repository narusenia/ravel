# AI アシスタントと MCP 企画書

> **Status**: 承認（未決事項 9 件を確定、`REQ-PLUGIN-007` と backlog に登録） — 2026-10-07

対象: 言語モデルのエージェントが Ravel のプロジェクトを読み、書き出し、編集する経路。
要件は `REQ-PLUGIN-007`。単位は backlog の「AI アシスタントと MCP」節。フェーズ F の後に着手する前提で書いている。特定のモデルや提供元を前提にしない。

## 問題

「このプロジェクトのコンプを一覧して」「タイトルの文字を差し替えて 3 本書き出して」
「全テキストレイヤーのフォントを揃えて」といった依頼を、利用者が手元のエージェント
（Claude Code、Codex、その他の MCP クライアント）に任せられない。エージェントが
`.ravprj` を直接いじると、zip の中の RON を壊すか、Ravel の検証を迂回する。

MCP（Model Context Protocol）は、エージェントにツールを差し出す標準の口で、
提供元を問わない。Ravel が MCP サーバを持てば、どのエージェントからも同じ口で
触れる。

## 現状の調査結果

### 機械可読な口は `ravel-cli` に既にある

- `ravel-cli list comps | params | codecs` は整形済み JSON を stdout に出す
- `ravel-cli render` は `--progress json` で 1 行 1 イベントを出し、警告と失敗に
  **翻訳されない安定 ID**（`media-offline`、`binding-issue` …）と分類された終了コード
  を持つ。`--param` で公開パラメータを差し替えられる
- `ravel-cli interactive` は答えを `render` の引数へ組み立てるだけで、
  非対話経路にできないことは何もしない
- `ravel-cli` は `gpui` / `ravel-ui` / `ravel-dock` / `ravel-app` に依存しない
  （`.agents/rules/rust.md`）。`ravel-project` 経由でプロジェクトを読み書きできる
- 書き出しには GPU アダプタが要る。取れなければ終了コード 1

### 起動中のアプリに外から届く口は無い

- ソケット・名前付きパイプ・単一インスタンス制御・URL スキームのどれも無い
- プロジェクトファイルの外部変更を検知する仕組みも、ファイルロックも無い。素材の
  変更監視（`AssetWatch`）はあるが、`.ravprj` 自身は見ていない

### 編集の経路は「コマンド」ではなく「文書の差し替え」

- `CommandId` は引数を持たない UI コマンド（`FileNew`、`EditUndo` …）で、
  `for_each_command!` を通って GPUI の Action になる。「レイヤー 3 の不透明度を
  0.5 に」を運ぶ形をしていない
- 文書の編集は新しい `Document` を組んで `ProjectState::commit_document` に渡す形。
  1 回の commit が undo 1 段（`ravel-ui` の `DocumentStore`）。ジェスチャ中は
  `apply_document`（undo 段なし）→ 終わりに commit
- `ravel-core::undo::GraphMutation` はジャーナル用の直列化できる変更
  （`AddNode` / `RemoveNode` / `AddEdge` …）で、グラフ単位の語彙が既にある
- `REQ-PLUGIN-006`（操作自動化、Could）が既に「外部から Document を書き換える経路」
  を要件にしている。前提は **変更が既存の経路を通ること、1 スクリプト = undo 1 段、
  GUI なしで動くこと**。MCP の編集はこの要件の一形態として扱える

### プラグイン計画とは契約が逆

`plugin-system-plan.md` が扱うのは DAG の**内側**で走る処理（WGSL / WASM ノード）で、
純粋でなければならない。MCP は DAG の**外側**から文書を書き換える側で、副作用が
本質。`REQ-PLUGIN-006` が Lua と処理系を分けた理由と同じで、両者を同じ仕組みに
乗せない。

## 選択肢

### 1. `ravel-cli` の上の MCP サーバ（読み取り + 書き出し）

`ravel-cli mcp`（案）が stdio で MCP を話す。ツールは既存の CLI の機能をそのまま
包む。

- 読む: コンプ一覧、公開パラメータ、書き出し形式、文書の構造（レイヤー・ノード・
  パラメータ値の要約）、静的走査の警告
- 書き出す: 1 フレームのプレビュー PNG、範囲の書き出し（`--param` 付き）

アプリに手を入れない。保存済みのファイルしか見えない（未保存の編集は見えない）。

### 2. 起動中のアプリに付く MCP サーバ（ライブ編集）

アプリがローカル専用の口（macOS / Linux は Unix ドメインソケット、Windows は
名前付きパイプ）を開き、`ravel-cli mcp --attach`（案）が stdio との橋渡しをする。
編集はメインスレッドで型付きの操作に変換し、**1 ツール呼び出し = 1 回の
`commit_document` = undo 1 段**にする。利用者は画面で結果を見て、気に入らなければ
Cmd+Z で戻せる。

### 3. アプリ内のアシスタントパネル

アプリが LLM の HTTP API を直接呼び、チャット欄を持つ。提供元の抽象化、API キーの
保管、ネットワーク、ストリーミング表示、失敗時の扱いを全部 Ravel が持つ。

### 比較

| 観点 | 1. CLI MCP | 2. ライブ MCP | 3. パネル |
|---|---|---|---|
| 読む | できる | できる | できる |
| 編集 | しない | できる（undo 可） | できる（undo 可） |
| 未保存の状態 | 見えない | 見える | 見える |
| アプリの変更 | 無し | IPC + 操作の層 | IPC 不要、UI と HTTP |
| ネットワーク | 不要 | 不要 | **必要** |
| API キー | 不要（クライアント側） | 不要（クライアント側） | **Ravel が保管** |
| 提供元への中立性 | クライアント次第で中立 | 同左 | Ravel が抽象化を持つ |
| プラットフォーム | stdio のみ。差なし | ソケット / パイプで分岐 | 差なし |

### 頭なしの編集（1 に書き込みを足す案）を推さない理由

保存済みファイルを直接書き換えると、同じファイルをアプリで開いていたときに
どちらかの変更が黙って消える。ファイルロックも外部変更の検知も無いので防げない。
アプリを閉じて使う一括変換（`REQ-PLUGIN-006` の主用途）には向くが、AI に任せる
対話的な編集には 2 のほうが安全。

ただし**まだ存在しないファイルへ新しく組み立てて保存する**だけなら、この衝突は
原理的に起きない（アプリが開いているはずがない）。フェーズ F の実機確認用に
ショーケースプロジェクトを作ったとき、内部 API を叩く Rust の生成器を書く必要が
あったのがまさにこの用途で、MCP があればコードを書かずに組み立て → 描画 → 確認を
回せた。そこで段階 1 に**新規ファイル限定の組み立て**（`AI-3`）を入れる。既存の
`.ravprj` は段階 1 では読み取り専用のまま。

## 推奨

**1 → 2 → （必要なら）3 の順に段階を踏む。**

- **段階 1** は既存の CLI を包む読み取り・書き出し（`AI-1`）に、新規ファイルへの
  組み立て（`AI-3`）を足す。既存ファイルを書き換えないので、危険な操作を持たない
- 組み立ての前に、引数を持つ編集操作の層（下記 `AI-2`）を作る。これは
  `REQ-PLUGIN-006` の自動化と段階 2 のライブ編集が共有する。MCP 専用の裏口を作らない
- **段階 3** は作らない可能性が高い。手元のエージェントが 2 を通して同じことを
  できるので、Ravel が API キーとネットワークを抱える理由が薄い。要望が出たら
  改めて判断する

### 安全の原則

- **編集はすべて undo 1 段。** 1 ツール呼び出しで 1 回だけ commit する。複数の
  操作をまとめるツールは、まとめて 1 段
- **破壊的な操作は確認を取る。** レイヤー・コンプ・素材の削除、既存ファイルへの
  上書き書き出し、プロジェクトの保存先変更は、アプリ側のダイアログで利用者が
  承認するまで実行しない。確認は MCP クライアントではなく **Ravel の画面で**取る
  （クライアントの自動承認設定に左右されないため）
- **ネットワークに出ない。** 段階 1・2 の通信は stdio とローカルソケットだけ。
  TCP で待ち受けない。ソケットは利用者だけが読み書きできる権限で作る
- **API キーを持たない。** 段階 1・2 では Ravel はキーを一切扱わない。段階 3 を
  作る場合も、キーは OS のキーチェーン（または環境変数）に置き、`.ravprj` にも
  プロジェクト層の設定にも書かない
- **書き出し先を絞る。** 出力パスは利用者が許可したディレクトリの下に限る
- **文書の中身は指示ではない。** レイヤー名やテキストはエージェントへそのまま
  返るので、悪意のあるプロジェクトが指示文を仕込める。段階 2 の確認ダイアログが
  最後の防壁になる
- 信頼モデル（`REQ-INFRA-007`）に「外部エージェント（MCP）」の段を足す。
  capability は Ravel が差し出すツールの集合そのもの

### 依存

MCP は JSON-RPC 2.0 なので、`serde_json`（既に `ravel-cli` が使う）で書ける。
SDK クレートは足さない（決定事項 4）。段階 2 のローカルソケットは `tokio` の
Unix ソケット / 名前付きパイプで足りる見込み（feature の追加は要る）。

## 実装単位

ID は確定（backlog 登録済み）。

### 段階 1: 読み取り・書き出し・新規ファイルへの組み立て

#### `AI-1` `ravel-cli mcp`（stdio）

- ツール: `list_comps` / `list_params` / `list_codecs` / `inspect_document` /
  `check_warnings` / `render_preview` / `render`（名前は案）
- 既存の `list` / `render` の実装を呼ぶ。列挙の経路を増やさない
  （`docs/dev/render-cli.md` の約束）

**完了条件**

- MCP の `initialize` → `tools/list` → `tools/call` を通す統合テスト（stdio を
  パイプでつないだ子プロセス）
- 各ツールの出力が対応する CLI の JSON と同じ値を返すテスト
- 失敗が安定 ID 付きの MCP エラーになるテスト（不在のファイル、未知のコンプ、
  GPU 無し）
- 書き出し先が許可ディレクトリの外なら拒否するテスト
- `docs/dev/` に使い方のページ（クライアントへの登録例は提供元を問わない形で）

#### `AI-2` 編集操作の層（`REQ-PLUGIN-006` と共有）

- 「パラメータを設定」「レイヤーを追加」「ノードをつなぐ」などを、引数を持つ
  型付きの操作として定義し、`Document` → `Document` の純粋関数で適用する
- 置き場所は `ravel-core::edit`（`done/edit-operations-plan.md` で決定。`ravel-cli` が直接呼べる）。アプリの
  `commit_document` も、将来の自動化スクリプトも、これを呼ぶ
- 設計の範囲が複数クレートにまたがるので、着手前に `AGENTS.md` の Design gate に
  従って実装計画を別に書く
- 詳細は `done/edit-operations-plan.md`（`AI-2a`〜`AI-2d` に割る）

**完了条件**

- 各操作の適用と、不正な引数（存在しない ID、型不一致）が文書を変えずにエラーを
  返すテスト
- 既存の UI 経路が同じ操作を呼ぶ箇所が少なくとも 1 つあり、経路が 2 本に
  ならないこと

#### `AI-3` 新規ファイルへの組み立て（頭なし）

- `AI-1` のツール群に、コンプ・レイヤー・ノード・エッジの追加とパラメータ設定、
  保存を足す。操作は `AI-2` の層を呼ぶ
- 組み立て中の文書はサーバのメモリ上に持ち、`render_preview` で途中の絵を返せる
- ノードはレジストリのテンプレートから作る（`describe_node` がポートとパラメータを
  返す）。未知のパラメータキーはエラー
- **保存先は存在しないパスだけ**。既存ファイルへの保存・上書きは拒否する

**完了条件**

- 組み立て → 保存したファイルが `ProjectFile::load` で読め、`ravel-cli render` で
  描画できる統合テスト
- 既存パスへの保存が文書を書かずにエラーになるテスト
- 保存先が許可ディレクトリの外なら拒否するテスト

### 段階 2: ライブ編集

#### `AI-4` アプリのローカル口

- 既定は**閉じている**。設定で有効にしたときだけソケット / パイプを開く
- 受けた要求はメインスレッドで `AI-2` の操作に変換し、1 要求 1 commit

**完了条件**

- 無効時に口が存在しないテスト
- 1 要求で undo 段が 1 つ増え、Cmd+Z で戻るテスト
- ソケットの権限が利用者のみであるテスト（macOS / Linux）。Windows は
  パイプのセキュリティ記述子を同等にする
- `.agents/rules/gpui.md` の Command 経路の約束（`render()` で処理しない、
  Global に積まない）を守ることを `ravel-review` で確認

#### `AI-5` `ravel-cli mcp --attach` と確認ダイアログ

- 編集ツールを `AI-1` のツール群に足す。アプリが動いていなければ編集ツールは
  「アプリが必要」のエラーを返す
- 削除と上書き（決定事項 6）はアプリのダイアログで承認されるまで保留する。
  `EditOp::is_destructive()` は分類であって確認の条件ではない: `Disconnect` のように
  undo で戻せるものは確認しない

**完了条件**

- 削除系の要求が承認なしでは実行されず、拒否で文書が変わらないテスト
- アプリを終了すると橋渡しが分類されたエラーで終わるテスト

#### `AI-7` ライブ文書の読み取りとプレビュー

`AI-5` の口は書き込みしかできない。エージェントは編集した結果を見られず、
次の編集に要る id も分からない（`add_layer` が返すのはレイヤーの id だけで、
テンプレートが作った rasterize などのノードの id は返らない）。実機で試した
ときは、id を連番から推測し、画面は OS のスクリーンショットで確かめるしか
なかった。

- ライブ口に読み取りの要求を足す。アプリは今の文書の写しとプロジェクトの
  パス（素材の相対パスを解くため）を返す。文書を変えないので確認は出さず、
  undo の段も増やさない
- `ravel-cli` は受け取った写しを下書きと同じように扱う。`inspect_document` /
  `check_warnings` / `render_preview` に `live: true` を足し、`draft: true` と
  同じ実装を通す。ライブ用の別ツールは作らない（`AI-1` の「列挙の経路を
  増やさない」）
- 書き出しは CLI 側の GPU で行う。アプリの評価器は使わないので、アプリの
  再生やプレビューの負荷にならない。そのぶん、アプリがまだ保存していない
  メディアのキャッシュは使えない
- 写しは文書全体なので、今の応答 1 行 4 MiB の上限を超えうる。上限を上げるか、
  読み取りだけ別の上限にするかは実装時に決める
- 写しの中の文字列は文書の中身として扱う。エージェントへの指示として
  読ませない（`live_edit` の description と同じ注意を付ける）

**完了条件**

- 読み取りの要求で文書も undo の段数も変わらないテスト
- `live: true` の `inspect_document` が、同じ文書を `project` で開いた場合と
  同じ結果を返すテスト
- `live: true` の `render_preview` が、許可ディレクトリの中に PNG を書くテスト
- アプリが無いとき `app-not-running`、応答の前に切れたとき `app-disconnected`
  になるテスト（`AI-5` と同じ分類）
- `docs/dev/live-edit.md` と `docs/dev/mcp-cli.md` の更新

#### `AI-8` キーフレームとレイヤーの殻の操作

`EditOp` が触れるのはノードのパラメータの定数だけ。エージェントは動きを付けられず、
レイヤーの位置・不透明度・時間配置も変えられない。アニメ済みのパラメータへの
`set_parameter` は、MCP からは `local_frame` を渡せないので `AnimatedParameter` で
拒否される。編集層の計画（`done/edit-operations-plan.md` の「非対象」）が
「必要になった時点で後続の単位として足す」とした範囲で、ここで単位にする。

- **キーフレームの操作**を `EditOp` に足す。対象はノードのパラメータ
  （`path` + `node` + `key`）と殻のプロパティ（変換・不透明度・タイムリマップ）の両方。
  UI の `PropertyRowId`（`Shell` / `Network`）と同じ区別にする
  - `set_keyframes`: 1 チャンネルの曲線を、与えたキーの列で置き換える
    （`frame`・`value`・`interpolation`）。ベクトルや色は成分ごとに指定する
  - `clear_animation`: 曲線を捨てて定数に戻す（値を指定）。undo で戻せるので
    確認は出さない（決定事項 6）
- **殻のプロパティ**の操作 `set_layer`: 名前、時間配置（`start_frame` / `in_frame` /
  `out_frame`）、変換・不透明度の定数、ブレンドモード、親、表示フラグ。
  アニメ済みの殻プロパティへの定数書き込みは `set_parameter` と同じく拒否する
- 今キーフレームを編集する純粋関数（`insert_keyframe` / `remove_keyframe` /
  `move_keyframe` など）は `ravel-ui/src/keyframes.rs` にあり、`ravel-core` の編集層からは
  呼べない。`set_curve_value` を `AI-2c` で移したのと同じ形で `ravel-core` へ移し、
  UI と編集層が同じ関数を通るようにする（書き込みの経路を 2 つにしない）
- 駆動されたチャンネル（式・ノード出力・ブレンド）への `set_keyframes` は
  `driven-parameter` で拒否する（決定事項 10 と同じ）

**未決事項**（着手前に決める）

1. キーの `frame` をコンポのフレームで受けるか、レイヤーのローカルフレームで受けるか。
   UI は内部でローカルに直している（`comp_frame_for_key`）。エージェントには
   コンポのフレームの方が分かりやすいが、レイヤーを動かすとキーがずれて見える
2. ベジェのハンドル（`tangent_in` / `tangent_out`）を出すか。出さないなら
   `interpolation` だけを受け、ハンドルは UI の既定で作る
3. 式（`ParameterExpression`）の設定を同じ単位に含めるか、別の単位にするか

**完了条件**

- `set_keyframes` の後、指定したフレームで評価した値がキーの値と一致するテスト
  （ノードのパラメータと殻のプロパティのそれぞれで）
- 1 回のバッチで undo の段が 1 つだけ増えるテスト
- 駆動されたチャンネルとアニメ済みの殻プロパティへの書き込みが拒否されるテスト
- 移した純粋関数を UI が使い、既存の UI のテストが無改変で通ること
- `docs/dev/add-edit-operation.md` と `docs/dev/mcp-cli.md` の更新

### 段階 3（保留）

`AI-6` アプリ内パネル。段階 2 の後に要望があれば別の企画書で扱う。

## 非対象

- 特定の提供元・モデルへの依存
- ネットワーク越しの遠隔操作（別機械からの接続）
- エージェントによるノード処理系のコード生成（`plugin-system-plan.md` の範囲）
- 生成 AI による画像・映像の生成ノード
