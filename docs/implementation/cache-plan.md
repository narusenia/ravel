# キャッシュ実装計画（REQ-CORE-006）

> **Status**: 単位 1〜4 実装済み — 2026-07-31

対象要件: REQ-CORE-006（三層キャッシュ）。関連: REQ-CORE-002（Hybrid Pull）、
REQ-CORE-005（スレッド分離）、REQ-CORE-011（ステートフル評価）、
REQ-CORE-013（スコープ軸）、REQ-GPU-001、REQ-PROJ-001、REQ-RENDER-004。

**この計画の目的は、個々のキャッシュを速くすることではない。** 現状 8 系統の
キャッシュが互いを知らずに存在し、未実装機能が 5 つ、同じ土台を別々の形で
要求している。それらが各計画で独立に実装される前に、キー・予算・無効化・
計測の規約を 1 箇所で決着させる。

**順序**: 単位 1 は `3D-1a` / `3D-1b` と同じ理由（対象箇所が時間で増える）で
フェーズ B。以降の配置は `roadmap.md` を正とする。

## 問題

**要件と実装が既に矛盾している。**

出るが、**テストから読めるカウンタがない**。「キャッシュが効かなくなった」
という回帰を CI で捕まえる手段が現状ゼロ。

## 決定事項

### 三層の実体は「出力段のフレームキャッシュ」として別層に置く

`Evaluator::cache` を多エントリ化して三層に載せるのではなく、**comp /
レイヤー出力を時間でキー付けした層を新設**する。ノード単位キャッシュは
1 ノード 1 値のまま（時間基準化のみ行う）。

- 理由: ノード単位の多エントリ化は、無効化経路（`drop_scope_owner_caches`
  ほか）の全面再検証を伴う。一方、体感（スクラブ・再生・緑バー）に効くのは
  出力段だけ。両者を同時に動かさない。
- ただし**多エントリ化は見据える**。今払うのは次の 3 点に限る。いずれも
  単エントリのままでも独立に価値がある。
  1. 有効判定の条件を `CacheIdentity` に構造体化する（多エントリ化は
     `HashMap<(NodeKey, CacheIdentity), _>` になるだけで、無効化は
     `NodeKey` 部分で今と同じに動く）
  2. `NodeData` にバイト会計を足す（単エントリでも MED-CORE-06 の解に必要）
  3. ヒット / ミスを `CacheIdentity` 単位で計数する（多エントリ化の
     効果測定がそのまま REQ-CORE-006 の受入条件になる）
- 払わないもの: **同一ノードの複数エントリ間の退避順序**（どのフレームを
  残すかの選択）と、ノード値のディスクスピル。多エントリ化を決めてからでも
  同じコスト。ノード**間**の予算退避は `CACHE-3` で入れる（1 ノード 1 値の
  ままでもキャッシュ全体に上限が要るため）。

### 時間キーは量子化 tick

```rust
/// フレーム位置を 1/4096 フレーム単位に量子化したキー。
pub struct TimeKey(i64);

const SUBFRAME_SCALE: f64 = 4096.0;
```

- `f64` のビットパターンを直接キーにしない。`frame / fps` 経由、シャッター
  オフセット演算、タイムリマップは**同じ位置を別の演算順で計算する**ので、
  1 ulp の差で黙って全ミスする。原因も追えない。
- **量子化幅は「衝突しない」ではなく「衝突が起きる条件を宣言できる」ことで
  選ぶ。** モーションブラーのサンプル間隔は
  `シャッター角 / 360 / サンプル数` フレームで、シャッター角が小さいほど
  詰まる。1/4096 は最小シャッター角 11.25°（= 1/32 フレーム）× 128 サンプルで
  ちょうど 1 tick になる値。360°/32 サンプルという典型では 1 tick の 128 倍
  離れる。
- **サンプル間隔が 1 tick を下回る組み合わせは黙って潰さない。**
  `BLUR-4` がシャッター角とサンプル数から間隔を算出し、tick を下回るなら
  サンプル数を tick で決まる上限に丸めて警告する（同一 `TimeKey` の
  サンプルは同じ画になるので、払ったコストが無駄になることをログで示す）。
  この判定は `CACHE-2` が公開する `TimeKey::SUBFRAME_SCALE` を使う。
- 時不変ノードは `TimeKey::TIMELESS`（`i64::MIN`）を使い、フレームを跨いで
  ヒットする現行挙動を保つ。
- 供給元は `EvalContext` の連続フレーム位置（`eval.rs:137` のドキュメント
  コメントが定義している「整数 frame + サブフレームオフセット」）。

### 同一性は `CacheIdentity` に集約する。精度以外は厳密一致

```rust
struct CacheIdentity {
    time: TimeKey,
    resolution: (u32, u32),
    comp_resolution: (u32, u32),  // 座標基準。resolution と同じ軸として扱う
    fps: FrameRate,
    quality: Quality,      // motion-blur-plan.md 単位 3 が導入（未実装）
    precision: Precision,  // 保存精度。要求側は min_precision を出す
    bypassed: bool,
}
```

照合規則は軸ごとに 2 種類しかない。**混ぜないことが重要**なので明記する。

| 軸 | 規則 |
|---|---|
| `time` / `resolution` / `fps` / `quality` / `bypassed` | **厳密一致** |
| `precision` | **順序比較**（`stored >= min_precision` でヒット） |

精度だけ順序なのは、**上位精度の流用は無損失で変換も要らない**から
（`min_precision = F16` の要求が F32 エントリを受け取っても絵は劣化せず、
表示経路は f32 をそのまま扱える）。逆向き（F32 要求が F16 エントリを取る）は
ミスになる。これが書き出しを守る唯一の仕組み。

- proxy の縮小は `ctx.resolution` を下げることで表現し、**scale を別軸に
  しない**。既存の `CacheMiss::ResolutionChanged` がそのまま働く。
- `quality` の導入は `motion-blur-plan.md` 単位 3 と相乗りする。あちらが
  `CacheMiss::QualityChanged` を足す前提を本計画が引き継ぐ。
- **近似ヒット（エントリを縮小・降格して流用する）は採らない。** 対象は
  「上位解像度エントリを縮小して低解像度要求に答える」「上位精度エントリを
  f16 に丸めて渡す」といった**変換を伴う**流用で、上記の精度の順序比較
  （変換なしでそのまま渡す）とは別物。理由は順序の非対称性で、厳密一致を
  先に入れれば近似は後から上に載せられるが、逆順は不可能 — 近似を先に
  入れると厳密の意味を取り戻せない。加えて `quality` は降格不可（ブラーの
  サンプル数が違う画は「同じフレームの粗い版」ではない）で軸ごとに規則が
  違い、緑バーが厳密と近似を区別できず表示が嘘になる。将来方向として
  下記に残す。

### 精度をキーに含め、要求側が最低精度を宣言する

`Precision` は `F32 > F16 > U8` の順序を持ち、要求側が `min_precision` を
宣言する。**保存精度が要求を下回るエントリはミス**として扱う。

- 対話プレビューは `F16`（または `U8`）を要求 → 縮約エントリでヒット。
- 書き出しは `F32` を要求 → 縮約エントリは自動的にミス。**キャッシュの
  有無で成果物が変わる事故が構造的に起きない。**
- 効果: 作業形式は RGBA f32 = 16 byte/px で 1080p 33 MB / 4K 133 MB。f16 なら
  半分。GPU 側は既に `Rgba16Float` に描いている
  （`ravel-nodes/src/rasterize/mod.rs:219`, `:317`）ので、**GPU 常駐値を
  そのまま保持するなら 8 byte/px が変換コストゼロで手に入る**。今 f32 に
  なるのは CPU に読み戻した後だけ。

### `FrameBuffer` を精度多相にする。ただし 2 段に割る

現状 `FrameBuffer.data` は `Arc<[f32]>` 固定（`ravel-core/src/types.rs:174`）、
`PixelFormat` も `RgbaF32` / `MonoF32` のみ（`:29`）。縮約形式を CPU 側で
持つには型を変える必要がある。

- **単位 1（今やる。規約の確定）**: `format` フィールドと
  `as_f32(&self) -> Cow<'_, [f32]>` を導入し、既存の直接添字を
  アクセサ経由へ機械的に置換。**`F32` なら `Cow::Borrowed` でゼロコスト**
  なので既存挙動と性能は不変。
- **単位 Y（実測後。本計画の他の単位はこれに依存しない）**: per-pixel
  ループを format 汎用化し、f16 を展開せずに読む。
- 対象規模: `.data[` 66 箇所、`Arc<[f32]>` 29 箇所、`FrameBuffer {` 構築
  71 箇所 / 21 ファイル。per-pixel ループは 6 ファイルに集中
  （`merge.rs` 7 / `color_correct.rs` 7 / `transform.rs` 6 / `blur.rs` 6 /
  `comp/opacity.rs` 5 / `comp/merge.rs` 5）。
- **REQ-CORE-009 との関係**: 同要件は「内部処理は常に 32bit float」「ビット
  深度変換が入出力時のみ」と書いているが、**GPU 経路は既に `Rgba16Float` で
  描いており（`rasterize/mod.rs:219`）要件は実装と乖離している**。本計画は
  「**演算は f32、キャッシュと GPU 常駐の保存表現は縮約可**」に線を引き直し、
  縮約が演算に漏れない境界（`as_f32()` を通す）を受入条件にする。
  REQ-CORE-009 の改訂は下記「要件の改訂」に含める。
- **今やる根拠**: `FrameBuffer` は `Serialize` を持たない（`types.rs:168` の
  derive は `Clone, Debug` のみ）ので**永続化フォーマットの移行はゼロ**。
  純粋にコードだけの変更で、`VEC-5` / `PARAM-1` と違い `.ravprj` の
  migration が要らない。一方 `FX-1`〜`FX-4`（カラー・ブラー・ディストー
  ション・キーイング）は全部 per-pixel ループを持ち、フェーズ F の後だと
  対象が倍以上になる。`3D-1b` と同じ構図。

### 予算は `CacheBudget` が単一の権威

`ravel-core` に置く（依存方向が `nodes → {core, gpu, media}`、
`{gpu, media, audio, ui} → core`、`core` は何にも依存しないため、全員が
共有できる場所は core だけ）。

```rust
pub enum CacheKind { NodeResult, Frame(Tier), MediaFrame, Sim }
pub enum Tier { Vram, Ram, Disk }
```

- VRAM の保持分も `CacheBudget` が会計し、超過時は古いフレームを落として
  プールへ返す。`TexturePool` の `LruBudget` は「アイドル再利用枠」として
  従属させ、**VRAM 上限を決める箇所を 1 つにする**。
- 会計の単位は `NodeData::byte_size(&self) -> u64`。既定実装は**与えない**
  — 既定 0 は黙って過小会計するので、既存の全実装（テスト用のものを含む）に
  コンパイルエラーで書かせる。`is_gpu_resident()`（`types.rs:107`）の隣に並べる。
- **sim には保護枠を切る**（既定で総額の 25%、設定可変）。通常のフレーム
  キャッシュは sim を追い出せない。sim は追い出されると再計算が
  O(フレーム数) で、他の層と非対称。
- 設定は `SettingsLayer`（`ravel-project/src/settings.rs:105`）に
  `CacheLayer` を足し、グローバル + プロジェクトの 2 段マージに乗せる。
  項目は `root` / 各層の上限 / sim 予約率 / ディスク層の有無。

**調停の形**（「単一の権威」を実際に成立させるための取り決め）:

- 所有者は 1 つ。`Arc<Mutex<CacheBudget>>` を `EvalService` が持ち、
  `TexturePool` と共有デコードキャッシュには構築時に渡す。**予算を新規に
  作れる場所を 1 箇所にする**（`Default` を公開しない）。
- API は `reserve(kind, bytes) -> Reservation` と、`Reservation` の drop に
  よる自動解放。上限超過時は `reserve` が**退避対象のリストを返す**
  （呼び出し側が実際に落とす。GPU テクスチャは pool へ、RAM は drop）。
- VRAM の総額は「キャッシュ保持分 + プールのアイドル枠」で、**アイドル枠は
  残余**（総額 − 保持分）として動的に決まる。`LruBudget` は自分で上限を
  持たず、毎回この残余を渡される。これが「権威が二重にならない」の意味。
- 退避の優先順は `投機で入ったエントリ → 通常エントリ（LRU）→ sim 予約枠`。
  sim 予約枠は最後まで削らない。

**完了条件に「上限を跨ぐケース」を必ず入れる**（下記単位 3 / 5 / 8）。
上限に当たらないテストしかないと、予算コードが死んでいても通る。

### ディスク層はグローバルに統一し、置き場は設定で変えられる

- 既定は `global_config_dir()/cache/frames/<project-key>/`。既存の
  `DiskCache`（`ravel-app/src/media/cache.rs`）と同じ方式に統一する。
  **REQ-CORE-006 と REQ-PROJ-001 の `.ravprj/.cache/` 記述を改訂する**
  （下記「要件の改訂」）。
- 設定で `root` を差し替えられる（別ドライブへ逃がす用途）。
- **フレームのディスク層そのものの実装は測定ゲート付き**。着手条件は
  「RAM 層の既定予算で 1080p / 10 秒の往復スクラブのヒット率が不足する」
  ことを `perf-baseline.md` に記録すること。

### メディアのデコード済みフレームは `ravel-media` の共有サービスが持つ

- アセット単位で共有するので、同じ素材を複数レイヤーが使っても 1 部。
  現状は `MediaProcessor` 内に静止画 1 エントリ（`ravel-nodes/src/media.rs:67`）、
  動画はデコーダだけキャッシュ（`ravel-media/src/decoder.rs:50`）で、
  レイヤーごとに重複する。
- 予算は `CacheKind::MediaFrame` として `CacheBudget` の下に入る。
- ノード単位キャッシュに吸収しない。吸収するとアセット共有の重複排除が
  できず、多エントリ化を先に要求してしまう。

### sim の長期保持は将来「明示キャッシュノード」に寄せる

暗黙 LRU で数百フレームを守り続けるのではなく、ユーザーが明示的に固定
できる形（`util.cache` 相当）を将来方向とする。`render-export-plan.md`
の非対象節が「Write ノードは評価純粋性とディスクキャッシュ設計の問題」として保留
しているので、**同じ議論に合流させる**。本計画では保護枠までを扱う。

### 先読みの規約を今固める（実装は最後の単位）

`EvalService` は専用ワーカー 1 本 + latest-wins 合体（`eval_service.rs:8-13`）。
投機要求を素朴に投げると対話要求を押し出す。規約:

- 投機要求は対話要求と**別キュー**。対話要求が来たら投機は即破棄する。
- 投機は latest-wins の世代番号を進めない。
- 投機の結果はキャッシュに書くだけで、`on_update` を発火しない
  （Viewer の表示を勝手に差し替えない）。
- 予算超過時、**投機で入ったエントリを対話で入ったエントリより先に落とす**。

先読みが無くても緑バーは「再生・スクラブで通った所が残る」形で伸びるので、
機能としては独立している。規約だけ先に固めるのは、後から入れると
`EvalService` の意味論を壊しがちなため。

### 計測はカウンタ API と Timeline のキャッシュ帯で出す

- `cache_stats()` で `CacheMiss` 別件数・ヒット数・層別使用バイトを読める
  ようにし、`GPUCOMP-7`（リードバック回数の回帰テスト）と同じ発想で
  「スクラブ後戻りで `process` が走らない」をテストで固める。
- `cached_ranges(comp, precision, resolution) -> Vec<Range<u64>>` を提供し、
  Timeline に AE 風のキャッシュ帯を描く（RAM = 緑、ディスク = 青相当）。
  厳密一致で照合しているので、帯の意味が一意に決まる。

## 目標構成

```text
                       要求: (path, TimeKey, resolution, fps, quality, min_precision)
                                          │
              ┌───────────────────────────▼───────────────────────────┐
              │  フレームキャッシュ（出力段。comp / レイヤー出力）       │
              │    VRAM: GpuFrameBuffer (Rgba16Float) — ゼロコピー表示  │
              │    RAM : f16 バイト列 — CPU 消費時のみ f32 展開          │
              │    Disk: 測定ゲート後（グローバル、置き場は設定可変）     │
              └───────────────────────────┬───────────────────────────┘
                                    ミス │
              ┌───────────────────────────▼───────────────────────────┐
              │  Evaluator（ノード単位 1 エントリ + CacheIdentity 照合） │
              │    sim は別 map（SimTrack。保護枠）                     │
              └───────────────────────────┬───────────────────────────┘
                                          │ メディア読み
              ┌───────────────────────────▼───────────────────────────┐
              │  共有デコードフレームキャッシュ（ravel-media、アセット単位）│
              └───────────────────────────────────────────────────────┘

  すべての層が 1 つの CacheBudget の下で会計され、cache_stats() で観測できる
```

## 式のキャッシュキー（2026-08-03 追記）

REQ-CORE-014 / REQ-CORE-015 の式が入ると、**`CacheIdentity` に式が参照する
ものが含まれていなければ「式を書き換えても絵が変わらない」形で静かに壊れる**。

`expression-language-plan.md` の `EXPR-3` が、式ソースのハッシュと参照集合を
`CacheIdentity` に加える。本計画側の規約としては次を守る。

- 式は決定的で副作用を持たない（REQ-CORE-014）ので、キーに入れるのは
  **式ソースと参照集合**だけでよい
- `frame` を参照しない式は時不変として扱え、時間軸のキャッシュ再利用に乗る

## 実装単位

### 単位 1 (`CACHE-1`) ✅: `FrameBuffer` の精度多相化（規約のみ）

- `PixelFormat` に `RgbaF16` / `Rgba8` を追加。`FrameBuffer` に `format` を
  持たせ、`data` をバイト列表現に変える。
- `as_f32(&self) -> Cow<'_, [f32]>` を追加し、既存の直接添字 66 箇所を
  アクセサ経由へ機械的に置換。`F32` は `Cow::Borrowed`。
- `new_zeroed` は `F32` を作り続ける（既定は不変）。
- `.data` の直接添字を `scripts/lint-patterns.sh` で禁止。
- **この単位では誰も f16 バッファを生成しない。** 純粋な準備。

**完了条件**

- 既存のノード・合成・書き出しテストが無改変で通る。
- `F32` の `as_f32()` が borrow を返す（コピーしない）ことのテスト。
- f16 バッファを `as_f32()` 経由で読んで期待値に一致するテスト。
- **縮約バッファが演算へ f32 として渡ることのテスト**（REQ-CORE-009 v2 の
  受入条件に対応）。
- `lint-patterns.sh` が直接添字を検出するテスト。
- `perf_baseline.rs` の合成シナリオで**回帰がない**ことの確認。

### 単位 2 ✅ (`CACHE-2`): `CacheIdentity` の抽出と時間基準化

- `TimeKey` と `Precision` を追加。`CacheEntry` の `frame` / `ctx` /
  `bypassed` を `CacheIdentity` にまとめる。
- 有効判定を整数 frame ではなく `TimeKey` で行う（**MED-CORE-03 / BLUR-2 を
  回収**。`motion-blur-plan.md` の単位 2 は本単位に統合する）。
- `resolve_params` をキャッシュ有効判定の**後ろ**へ移す。判定に必要なのは
  `Channel*` / `NodeOutput` ソースのみで、定数の再解決と `PathPoints` の
  clone は不要（**HIGH-03 を回収**）。
- `CacheMiss` に `PrecisionInsufficient` を追加。

**実装時の決定**（コードが正）:

- 丸めは `TimeKey::from_frame_position` 1 箇所（half-away-from-zero）。
  供給元は `EvalContext::sample_frame()`。非有限・範囲外は飽和させ、
  `TimeKey::TIMELESS`（`i64::MIN`）と衝突させない。
- **エントリの `precision` は「そのエントリが満たすと保証された下限」**で、
  生成時の `EvalContext::min_precision` を記録する。物理的に縮約バッファを
  作るのは `CACHE-1` / `CACHE-5` 以降だが、再利用の可否は生成時の保証で
  決まる。既定は `F32` なので現行挙動は不変。
- `quality` 軸は `CacheIdentity` にまだ無い。`motion-blur-plan.md` の
  単位 3（`BLUR-3`）が `CacheMiss::QualityChanged` と一緒に足す。
- `resolve_params` は 2 段に割った。`resolve_channel_params`（判定前。
  グラフを引ける `Channel*` だけ）と `materialize_params`（ミス時のみ。
  定数を clone してキー付き `ResolvedParams` を組む）。**NodeOutput の
  pull 順序は変わらない** — 両者ともパラメータ順に走り、定数は何も pull
  しないため。

**完了条件**

- 同一 `TimeKey` の再要求がヒットするテスト。
- 整数フレーム送りの既存キャッシュ挙動が変わらないテスト。
- サブフレーム位置の異なる 2 要求が**別扱い**になるテスト
  （BLUR-3〜5 の前提）。
- `min_precision = F32` が f16 エントリを拒否するテスト。
- `min_precision = F16` が **F32 エントリでヒットし、変換が起きない**テスト
  （精度軸だけが順序比較であることの回帰）。
- キャッシュヒット経路で `PathPoints` の clone が起きないテスト。
- 演算経路の違う 2 つの時間計算（`frame / fps` とシャッターオフセット）が
  同じ `TimeKey` になるテスト。

### 単位 3 (`CACHE-3`): `CacheBudget` と退避

- `NodeData::byte_size()` を追加（既定実装なし。全実装に書かせる）。
- `CacheBudget`（総額 / 層別会計 / sim 予約枠 / 投機フラグ）を `ravel-core` に
  追加。`SettingsLayer` に `CacheLayer` を足す。
- `Evaluator::cache` に上限を入れ、LRU で退避（**MED-CORE-06 を回収**）。
- `scope_owners` / `scope_bindings` の pruning と、`register()` の全走査
  除去（**MED-CORE-07 を回収**）。
- `TexturePool` の `LruBudget` を `CacheBudget` に従属させる。
- `cache_stats()` を追加。

**完了条件**

- 予算超過で最古のエントリが落ち、使用バイトが上限以下に収まるテスト。
- sim 予約枠が通常エントリの圧力で削られないテスト。
- レイヤー削除後に `scope_owners` / `scope_bindings` が残らないテスト。
- `register()` がキャッシュ全走査をしないことのテスト（大きなキャッシュで
  呼び出し回数か走査量を観測）。
- `cache_stats()` の件数が実際のヒット / ミスと一致するテスト。
- VRAM 上限を跨ぐ連続評価でプールが枯渇しないテスト。

### 単位 4 (`CACHE-4`): スコープ無効化の粒度修正

- `cache.retain(|k, _| !k.path.starts_with(&path))` がスコープ内の**全**
  キャッシュを捨てる問題を解消（**MED-CORE-02 を回収**）。`net.in` の
  `source` ポートに依存しないノードは、調整レイヤーの下のスタックが
  変わっても生き残るべき。
- インターフェースノードのポート単位キャッシュをバインディング識別子で
  キー付けする（`issues/medium/core-evaluator.md` の方針）。

**完了条件**

- 調整レイヤー配下で `source` に依存しないノードが、下のスタック変更で
  再計算されないテスト。
- `source` に依存するノードは正しく再計算されるテスト（逆方向の回帰）。
- 毎フレーム同一内容の再評価でヒット率が 1 に漸近するテスト。

### 単位 5 (`CACHE-5`): フレームキャッシュ層（comp 単位の無効化）

- `EvalService` 側に出力段のフレームキャッシュを新設。キーは
  `(comp path, CacheIdentity)`。
- VRAM 層は `GpuFrameBuffer`（`Rgba16Float`）をそのまま保持。RAM 層は
  f16 バイト列。
- 無効化は**影響 comp の全フレーム破棄**。まず正しさを確保する。
- 依存: `gpu-compositing-plan.md` の GPU 常駐出力（f16 テクスチャを
  そのまま保持するため）。

**完了条件**

- スクラブ後戻りで `process` が 1 度も走らないテスト（`take_timings` が空）。
- VRAM ヒット時に GPU→CPU 転送が発生しないテスト（`GPUCOMP-7` の
  リードバック計数を流用）。
- 編集後に該当 comp のエントリが全て落ち、他 comp が残るテスト。
- 予算超過で古いフレームがプールへ返るテスト。
- 書き出し相当の `min_precision = F32` 要求がプレビューエントリを
  拾わないテスト。

## 検証

- 単位 1 は挙動不変。**既存テストの無改変通過と `perf_baseline` の
  回帰なしが完了条件**。
- 単位 2 の「サブフレーム位置の異なる 2 要求が別扱いになる」テストが
  BLUR-3〜5 のゲート。これが無いと「実装したのにブレない」形で静かに壊れる。
- 単位 5 の「スクラブ後戻りで `process` が走らない」が本計画の核心。
- 予算に関わる単位（3 / 5 / 8）は**上限を跨ぐケースを必ずテストする**。
  上限に当たらないテストしかないと、予算コードが死んでいても通る。
- `perf-baseline.md` に記録する数値: 往復スクラブのヒット率、1080p /
  4K での層別使用バイト、f32 / f16 の合成時間、デコード回数。

## 非対象

- **ノード単位キャッシュの多エントリ化**。準備（`CacheIdentity` /
  `byte_size` / 計数）だけ行う。着手判断は、フレームキャッシュのヒット率が
  測れるようになった後、precomp 再利用のミスが実測で支配的な場合。
- **近似ヒット**（上位解像度・上位精度からの降格流用）。将来方向として、
  「厳密ヒットが無いときだけ / `resolution` 軸だけ / GPU 経路だけ」に
  限定して足せる。`quality` 軸は降格不可。
- **明示キャッシュノード**（`util.cache` 相当）。`render-export-plan.md` の
  Write ノード議論に合流させる。
- **コンパイル済みシェーダのディスクキャッシュ**（REQ-GPU-001 の受入条件。
  未実装）。台帳には載せるが本計画では扱わない。HIGH-06（検証がハッシュ照合の
  前 / パイプライン共有なし）は **#193 で解決済み**で、シェーダとパイプラインの
  メモリキャッシュは既に効いている（残るのは上限が無いことだけ）。
- **sws スケーラのキャッシュ**（HIGH-17）。同上。
- **CPU→GPU 変換結果のキャッシュ**（`MED-GPU-05`）。同上。
- **UI 側のメモ化 3 件**（`issues/low/backlog.md` のグラデーション・
  エッジ整形文字列・Viewer bbox）。同上。
- **gpui 内部のキャッシュ**。予算を持てない。
- **`.ravprj` 内へのキャッシュ格納**。展開ディレクトリ運用（REQ-PROJ-001）が
  前提になり、コンテナ層の大工事になる。

## 要件の改訂

REQ-CORE-006 の現行記述に対する変更点:

| 現行 | 改訂後 |
|---|---|
| 三層をノード評価結果のキャッシュとして定義 | **出力段のフレームキャッシュ**として定義。ノード単位は 1 エントリ + 同一性照合 |
| ディスクキャッシュは `.ravprj` 内の `.cache/` | **グローバル**（`global_config_dir()/cache/`）。置き場は設定可変。zip 除外の話は不要になる |
| （精度の言及なし） | **精度をキーに含め、要求側が最低精度を宣言**。精度だけ順序比較、他の軸は厳密一致。書き出しは常に F32 を要求 |
| 「LRU ベースのエビクションが各層で機能する」 | 単一 `CacheBudget` が層をまとめて会計。sim に保護枠 |
| 「キャッシュヒット率がモニタリング可能」 | `cache_stats()` API + Timeline のキャッシュ帯 |

REQ-CORE-009（32bit float 内部処理）も同時に改訂する。現行の「内部フレーム
バッファは常に 32bit float」「ビット深度変換は入出力時のみ」は、**GPU 経路が
既に `Rgba16Float` で描いている**実装と乖離しており、フレームキャッシュの
縮約保持とも両立しない。「**画素演算は f32、保存表現は縮約可、演算へ渡る
境界で f32 として読み出す**」に線を引き直す。

REQ-PROJ-001 は `.cache/` をプロジェクト構造から外し、「派生キャッシュは
グローバル（未保存プロジェクトでも効かせるため）」に改める。
`architecture.md` のキャッシュ節とプロジェクトファイル構造も同様。
