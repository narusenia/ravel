# キャッシュ実装計画（REQ-CORE-006）

> **Status**: 単位 1〜10 実装済み — 2026-08-10
> （残りは `CACHE-11` ディスク層、`CACHE-Y`）

対象要件: REQ-CORE-006（三層キャッシュ）。関連: REQ-CORE-002（Hybrid Pull）、
REQ-CORE-005（スレッド分離）、REQ-CORE-011（ステートフル評価）、
REQ-CORE-013（スコープ軸）、REQ-GPU-001、REQ-PROJ-001、REQ-RENDER-004。

**この計画の目的は、個々のキャッシュを速くすることではない。** 現状 8 系統の
キャッシュが互いを知らずに存在し、未実装機能が 5 つ、同じ土台を別々の形で
要求している。それらが各計画で独立に実装される前に、キー・予算・無効化・
計測の規約を 1 箇所で決着させる。

**順序**: 単位 1 は `3D-1a` / `3D-1b` と同じ理由（対象箇所が時間で増える）で
フェーズ B。以降の配置は `roadmap.md` を正とする。

## 決定事項

### 三層の実体は「出力段のフレームキャッシュ」として別層に置く

`Evaluator::cache` を多エントリ化して三層に載せるのではなく、**comp /
レイヤー出力を時間でキー付けした層を新設**する。ノード単位キャッシュは
1 ノード 1 値のまま（時間基準化のみ行う）。

- 理由: ノード単位の多エントリ化は、無効化経路（`drop_scope_owner_caches`
  ほか）の全面再検証を伴う。一方、体感（スクラブ・再生・緑バー）に効くのは
  出力段だけ。両者を同時に動かさない。
- ただし**多エントリ化は見据える**。今払うのは次の 3 点に限る。いずれも
  単エントリのままでも独立に価値がある。
  1. 有効判定の条件を `CacheIdentity` に構造体化する（多エントリ化は
     `HashMap<(NodeKey, CacheIdentity), _>` になるだけで、無効化は
     `NodeKey` 部分で今と同じに動く）
  2. `NodeData` にバイト会計を足す（単エントリでも MED-CORE-06 の解に必要）
  3. ヒット / ミスを `CacheIdentity` 単位で計数する（多エントリ化の
     効果測定がそのまま REQ-CORE-006 の受入条件になる）
- 払わないもの: **同一ノードの複数エントリ間の退避順序**（どのフレームを
  残すかの選択）と、ノード値のディスクスピル。多エントリ化を決めてからでも
  同じコスト。ノード**間**の予算退避は `CACHE-3` で入れる（1 ノード 1 値の
  ままでもキャッシュ全体に上限が要るため）。

### 時間キーは量子化 tick

```rust
/// フレーム位置を 1/4096 フレーム単位に量子化したキー。
pub struct TimeKey(i64);

const SUBFRAME_SCALE: f64 = 4096.0;
```

- `f64` のビットパターンを直接キーにしない。`frame / fps` 経由、シャッター
  オフセット演算、タイムリマップは**同じ位置を別の演算順で計算する**ので、
  1 ulp の差で黙って全ミスする。原因も追えない。
- **量子化幅は「衝突しない」ではなく「衝突が起きる条件を宣言できる」ことで
  選ぶ。** モーションブラーのサンプル間隔は
  `シャッター角 / 360 / サンプル数` フレームで、シャッター角が小さいほど
  詰まる。1/4096 は最小シャッター角 11.25°（= 1/32 フレーム）× 128 サンプルで
  ちょうど 1 tick になる値。360°/32 サンプルという典型では 1 tick の 128 倍
  離れる。
- **サンプル間隔が 1 tick を下回る組み合わせは黙って潰さない。**
  `BLUR-4` がシャッター角とサンプル数から間隔を算出し、tick を下回るなら
  サンプル数を tick で決まる上限に丸めて警告する（同一 `TimeKey` の
  サンプルは同じ画になるので、払ったコストが無駄になることをログで示す）。
  この判定は `CACHE-2` が公開する `TimeKey::SUBFRAME_SCALE` を使う。
- 時不変ノードは `TimeKey::TIMELESS`（`i64::MIN`）を使い、フレームを跨いで
  ヒットする現行挙動を保つ。
- 供給元は `EvalContext` の連続フレーム位置（`eval.rs:137` のドキュメント
  コメントが定義している「整数 frame + サブフレームオフセット」）。

### 同一性は `CacheIdentity` に集約する。精度以外は厳密一致

```rust
struct CacheIdentity {
    time: TimeKey,
    resolution: (u32, u32),
    comp_resolution: (u32, u32),  // 座標基準。resolution と同じ軸として扱う
    fps: FrameRate,
    quality: Quality,      // motion-blur-plan.md 単位 3 (BLUR-3) が導入済み
    precision: Precision,  // 保存精度。要求側は min_precision を出す
    bypassed: bool,
    expressions: u64,      // パラメータ式のダイジェスト（EXPR-3 が追加）
}
```

照合規則は軸ごとに 2 種類しかない。**混ぜないことが重要**なので明記する。

| 軸 | 規則 |
|---|---|
| `time` / `resolution` / `fps` / `quality` / `bypassed` / `expressions` | **厳密一致** |
| `precision` | **順序比較**（`stored >= min_precision` でヒット） |

精度だけ順序なのは、**上位精度の流用は無損失で変換も要らない**から
（`min_precision = F16` の要求が F32 エントリを受け取っても絵は劣化せず、
表示経路は f32 をそのまま扱える）。逆向き（F32 要求が F16 エントリを取る）は
ミスになる。これが書き出しを守る唯一の仕組み。

- proxy の縮小は `ctx.resolution` を下げることで表現し、**scale を別軸に
  しない**。既存の `CacheMiss::ResolutionChanged` がそのまま働く。
- `quality` の導入は `motion-blur-plan.md` 単位 3 と相乗りする。あちらが
  `CacheMiss::QualityChanged` を足す前提を本計画が引き継ぐ。
- **近似ヒット（エントリを縮小・降格して流用する）は採らない。** 対象は
  「上位解像度エントリを縮小して低解像度要求に答える」「上位精度エントリを
  f16 に丸めて渡す」といった**変換を伴う**流用で、上記の精度の順序比較
  （変換なしでそのまま渡す）とは別物。理由は順序の非対称性で、厳密一致を
  先に入れれば近似は後から上に載せられるが、逆順は不可能 — 近似を先に
  入れると厳密の意味を取り戻せない。加えて `quality` は降格不可（ブラーの
  サンプル数が違う画は「同じフレームの粗い版」ではない）で軸ごとに規則が
  違い、緑バーが厳密と近似を区別できず表示が嘘になる。将来方向として
  下記に残す。

### 精度をキーに含め、要求側が最低精度を宣言する

`Precision` は `F32 > F16 > U8` の順序を持ち、要求側が `min_precision` を
宣言する。**保存精度が要求を下回るエントリはミス**として扱う。

- 対話プレビューは `F16`（または `U8`）を要求 → 縮約エントリでヒット。
- 書き出しは `F32` を要求 → 縮約エントリは自動的にミス。**キャッシュの
  有無で成果物が変わる事故が構造的に起きない。**
- 効果: 作業形式は RGBA f32 = 16 byte/px で 1080p 33 MB / 4K 133 MB。f16 なら
  半分。GPU 側は既に `Rgba16Float` に描いている
  （`ravel-nodes/src/rasterize/mod.rs:219`, `:317`）ので、**GPU 常駐値を
  そのまま保持するなら 8 byte/px が変換コストゼロで手に入る**。今 f32 に
  なるのは CPU に読み戻した後だけ。

### `FrameBuffer` を精度多相にする。ただし 2 段に割る

現状 `FrameBuffer.data` は `Arc<[f32]>` 固定（`ravel-core/src/types.rs:174`）、
`PixelFormat` も `RgbaF32` / `MonoF32` のみ（`:29`）。縮約形式を CPU 側で
持つには型を変える必要がある。

- **単位 1（今やる。規約の確定）**: `format` フィールドと
  `as_f32(&self) -> Cow<'_, [f32]>` を導入し、既存の直接添字を
  アクセサ経由へ機械的に置換。**`F32` なら `Cow::Borrowed` でゼロコスト**
  なので既存挙動と性能は不変。
- **単位 Y（実測後。本計画の他の単位はこれに依存しない）**: per-pixel
  ループを format 汎用化し、f16 を展開せずに読む。
- 対象規模: `.data[` 66 箇所、`Arc<[f32]>` 29 箇所、`FrameBuffer {` 構築
  71 箇所 / 21 ファイル。per-pixel ループは 6 ファイルに集中
  （`merge.rs` 7 / `color_correct.rs` 7 / `transform.rs` 6 / `blur.rs` 6 /
  `comp/opacity.rs` 5 / `comp/merge.rs` 5）。
- **REQ-CORE-009 との関係**: 同要件は「内部処理は常に 32bit float」「ビット
  深度変換が入出力時のみ」と書いているが、**GPU 経路は既に `Rgba16Float` で
  描いており（`rasterize/mod.rs:219`）要件は実装と乖離している**。本計画は
  「**演算は f32、キャッシュと GPU 常駐の保存表現は縮約可**」に線を引き直し、
  縮約が演算に漏れない境界（`as_f32()` を通す）を受入条件にする。
  REQ-CORE-009 の改訂は下記「要件の改訂」に含める。
- **今やる根拠**: `FrameBuffer` は `Serialize` を持たない（`types.rs:168` の
  derive は `Clone, Debug` のみ）ので**永続化フォーマットの移行はゼロ**。
  純粋にコードだけの変更で、`VEC-5` / `PARAM-1` と違い `.ravprj` の
  migration が要らない。一方 `FX-1`〜`FX-4`（カラー・ブラー・ディストー
  ション・キーイング）は全部 per-pixel ループを持ち、フェーズ F の後だと
  対象が倍以上になる。`3D-1b` と同じ構図。

### 予算は `CacheBudget` が単一の権威

`ravel-core` に置く（依存方向が `nodes → {core, gpu, media}`、
`{gpu, media, audio, ui} → core`、`core` は何にも依存しないため、全員が
共有できる場所は core だけ）。

```rust
pub enum CacheKind { NodeResult, Frame(Tier), MediaFrame, Sim }
pub enum Tier { Vram, Ram, Disk }
```

- VRAM の保持分も `CacheBudget` が会計し、超過時は古いフレームを落として
  プールへ返す。`TexturePool` の `LruBudget` は「アイドル再利用枠」として
  従属させ、**VRAM 上限を決める箇所を 1 つにする**。
- 会計の単位は `NodeData::byte_size(&self) -> u64`。既定実装は**与えない**
  — 既定 0 は黙って過小会計するので、既存の全実装（テスト用のものを含む）に
  コンパイルエラーで書かせる。`is_gpu_resident()`（`types.rs:107`）の隣に並べる。
- **sim には保護枠を切る**（既定で総額の 25%、設定可変）。通常のフレーム
  キャッシュは sim を追い出せない。sim は追い出されると再計算が
  O(フレーム数) で、他の層と非対称。
- 設定は `SettingsLayer`（`ravel-project/src/settings.rs:105`）に
  `CacheLayer` を足し、グローバル + プロジェクトの 2 段マージに乗せる。
  項目は `root` / 各層の上限 / sim 予約率 / ディスク層の有無。

**調停の形**（「単一の権威」を実際に成立させるための取り決め）:

- 所有者は 1 つ。`Arc<Mutex<CacheBudget>>` を `EvalService` が持ち、
  `TexturePool` と共有デコードキャッシュには構築時に渡す。**予算を新規に
  作れる場所を 1 箇所にする**（`Default` を公開しない）。
- API は `reserve(kind, bytes) -> Reservation` と、`Reservation` の drop に
  よる自動解放。上限超過時は `reserve` が**退避対象のリストを返す**
  （呼び出し側が実際に落とす。GPU テクスチャは pool へ、RAM は drop）。
- VRAM の総額は「キャッシュ保持分 + プールのアイドル枠」で、**アイドル枠は
  残余**（総額 − 保持分）として動的に決まる。`LruBudget` は自分で上限を
  持たず、毎回この残余を渡される。これが「権威が二重にならない」の意味。
- 退避の優先順は `投機で入ったエントリ → 通常エントリ（LRU）→ sim 予約枠`。
  sim 予約枠は最後まで削らない。

**完了条件に「上限を跨ぐケース」を必ず入れる**（下記単位 3 / 5 / 8）。
上限に当たらないテストしかないと、予算コードが死んでいても通る。

### ディスク層はグローバルに統一し、置き場は設定で変えられる

- 既定は `global_config_dir()/cache/frames/<project-key>/`。既存の
  `DiskCache`（`ravel-app/src/media/cache.rs`）と同じ方式に統一する。
  **REQ-CORE-006 と REQ-PROJ-001 の `.ravprj/.cache/` 記述を改訂する**
  （下記「要件の改訂」）。
- 設定で `root` を差し替えられる（別ドライブへ逃がす用途）。
- **フレームのディスク層そのものの実装は測定ゲート付き**。着手条件は
  「RAM 層の既定予算で 1080p / 10 秒の往復スクラブのヒット率が不足する」
  ことを `perf-baseline.md` に記録すること。

### メディアのデコード済みフレームは `ravel-media` の共有サービスが持つ

- アセット単位で共有するので、同じ素材を複数レイヤーが使っても 1 部。
  現状は `MediaProcessor` 内に静止画 1 エントリ（`ravel-nodes/src/media.rs:67`）、
  動画はデコーダだけキャッシュ（`ravel-media/src/decoder.rs:50`）で、
  レイヤーごとに重複する。
- 予算は `CacheKind::MediaFrame` として `CacheBudget` の下に入る。
- ノード単位キャッシュに吸収しない。吸収するとアセット共有の重複排除が
  できず、多エントリ化を先に要求してしまう。

### sim の長期保持は将来「明示キャッシュノード」に寄せる

暗黙 LRU で数百フレームを守り続けるのではなく、ユーザーが明示的に固定
できる形（`util.cache` 相当）を将来方向とする。`done/render-export-plan.md`
の非対象節が「Write ノードは評価純粋性とディスクキャッシュ設計の問題」として保留
しているので、**同じ議論に合流させる**。本計画では保護枠までを扱う。

### 先読みの規約を今固める（実装は最後の単位）

`EvalService` は専用ワーカー 1 本 + latest-wins 合体（`eval_service.rs:8-13`）。
投機要求を素朴に投げると対話要求を押し出す。規約:

- 投機要求は対話要求と**別キュー**。対話要求が来たら投機は即破棄する。
- 投機は latest-wins の世代番号を進めない。
- 投機の結果はキャッシュに書くだけで、`on_update` を発火しない
  （Viewer の表示を勝手に差し替えない）。
- 予算超過時、**投機で入ったエントリを対話で入ったエントリより先に落とす**。

先読みが無くても緑バーは「再生・スクラブで通った所が残る」形で伸びるので、
機能としては独立している。規約だけ先に固めるのは、後から入れると
`EvalService` の意味論を壊しがちなため。

### 計測はカウンタ API と Timeline のキャッシュ帯で出す

- `cache_stats()` で `CacheMiss` 別件数・ヒット数・層別使用バイトを読める
  ようにし、`GPUCOMP-7`（リードバック回数の回帰テスト）と同じ発想で
  「スクラブ後戻りで `process` が走らない」をテストで固める。
- `cached_ranges(comp, &EvalContext) -> Vec<Range<u64>>` を提供し、
  Timeline に AE 風のキャッシュ帯を描く（RAM = 緑、ディスク = 青相当）。
  厳密一致で照合しているので、帯の意味が一意に決まる。

## 目標構成

```text
                       要求: (path, TimeKey, resolution, fps, quality, min_precision)
                                          │
              ┌───────────────────────────▼───────────────────────────┐
              │  フレームキャッシュ（出力段。comp / レイヤー出力）       │
              │    VRAM: GpuFrameBuffer (Rgba16Float) — ゼロコピー表示  │
              │    RAM : f16 バイト列 — CPU 消費時のみ f32 展開          │
              │    Disk: 測定ゲート後（グローバル、置き場は設定可変）     │
              └───────────────────────────┬───────────────────────────┘
                                    ミス │
              ┌───────────────────────────▼───────────────────────────┐
              │  Evaluator（ノード単位 1 エントリ + CacheIdentity 照合） │
              │    sim は別 map（SimTrack。保護枠）                     │
              └───────────────────────────┬───────────────────────────┘
                                          │ メディア読み
              ┌───────────────────────────▼───────────────────────────┐
              │  共有デコードフレームキャッシュ（ravel-media、アセット単位）│
              └───────────────────────────────────────────────────────┘

  すべての層が 1 つの CacheBudget の下で会計され、cache_stats() で観測できる
```

## 式のキャッシュキー（2026-08-03 追記）

REQ-CORE-014 / REQ-CORE-015 の式が入ると、**`CacheIdentity` に式が参照する
ものが含まれていなければ「式を書き換えても絵が変わらない」形で静かに壊れる**。

`expression-language-plan.md` の `EXPR-3` が、式ソースのハッシュと参照集合を
`CacheIdentity` の `expressions` として追加済み。規約は次のとおり。

- 式は決定的で副作用を持たない（REQ-CORE-014）ので、キーに入れるのは
  **式ソースと参照集合**だけでよい
- 時間軸（`frame` / `time`）を参照しない式は時不変として扱い、時間軸の
  キャッシュ再利用に乗せる。`time` は `frame / fps` で同じ軸なので、
  どちらか一方でも参照していれば時変
- 式を持たないノードのダイジェストは `0`。式が無いグラフのキーは不変

- `.data` の直接添字を `scripts/lint-patterns.sh` で禁止。
- **この単位では誰も f16 バッファを生成しない。** 純粋な準備。

**完了条件**

- 既存のノード・合成・書き出しテストが無改変で通る。
- `F32` の `as_f32()` が borrow を返す（コピーしない）ことのテスト。

### 単位 2 ✅ (`CACHE-2`): `CacheIdentity` の抽出と時間基準化

- `TimeKey` と `Precision` を追加。`CacheEntry` の `frame` / `ctx` /
  `bypassed` を `CacheIdentity` にまとめる。
- 有効判定を整数 frame ではなく `TimeKey` で行う（**MED-CORE-03 / BLUR-2 を
  回収**。`motion-blur-plan.md` の単位 2 は本単位に統合する）。
- `resolve_params` をキャッシュ有効判定の**後ろ**へ移す。判定に必要なのは
  `Channel*` / `NodeOutput` ソースのみで、定数の再解決と `PathPoints` の
  clone は不要（**HIGH-03 を回収**）。
- `CacheMiss` に `PrecisionInsufficient` を追加。

**実装時の決定**（コードが正）:

- 丸めは `TimeKey::from_frame_position` 1 箇所（half-away-from-zero）。
  供給元は `EvalContext::sample_frame()`。非有限・範囲外は飽和させ、
  `TimeKey::TIMELESS`（`i64::MIN`）と衝突させない。
- **エントリの `precision` は「そのエントリが満たすと保証された下限」**で、
  生成時の `EvalContext::min_precision` を記録する。物理的に縮約バッファを
  作るのは `CACHE-1` / `CACHE-5` 以降だが、再利用の可否は生成時の保証で
  決まる。既定は `F32` なので現行挙動は不変。
- `quality` 軸は `motion-blur-plan.md` の単位 3（`BLUR-3`）が
  `CacheMiss::QualityChanged` と一緒に追加済み。既定は `Quality::Final`
  （精度の `F32` 既定と同じ理由 — 軸を知らない経路が黙って劣化しない）で、
  Viewer 経路だけが `Preview` へ降ろす。降格不可なので `Quality` は
  `PartialOrd` を導出せず、順序比較を書けなくしてある。
- `resolve_params` は 2 段に割った。`resolve_channel_params`（判定前。
  グラフを引ける `Channel*` だけ）と `materialize_params`（ミス時のみ。
  定数を clone してキー付き `ResolvedParams` を組む）。**NodeOutput の
  pull 順序は変わらない** — 両者ともパラメータ順に走り、定数は何も pull
  しないため。

**完了条件**

- 同一 `TimeKey` の再要求がヒットするテスト。
- 整数フレーム送りの既存キャッシュ挙動が変わらないテスト。
- サブフレーム位置の異なる 2 要求が**別扱い**になるテスト
  （BLUR-3〜5 の前提）。
- `min_precision = F32` が f16 エントリを拒否するテスト。
- `min_precision = F16` が **F32 エントリでヒットし、変換が起きない**テスト
  （精度軸だけが順序比較であることの回帰）。
- キャッシュヒット経路で `PathPoints` の clone が起きないテスト。
- 演算経路の違う 2 つの時間計算（`frame / fps` とシャッターオフセット）が
  同じ `TimeKey` になるテスト。

### 単位 5 (`CACHE-5`): フレームキャッシュ層（comp 単位の無効化）

**設計時の記述**（2026-07-31。下の「実装時の決定」が上書きした箇所がある）:

- `EvalService` 側に出力段のフレームキャッシュを新設。キーは
  `(comp path, CacheIdentity)`。
- VRAM 層は `GpuFrameBuffer`（`Rgba16Float`）をそのまま保持。RAM 層は
  f16 バイト列。
- 無効化は**影響 comp の全フレーム破棄**。まず正しさを確保する。
- 依存: `gpu-compositing-plan.md` の GPU 常駐出力（f16 テクスチャを
  そのまま保持するため）。

**実装時の決定**（コードが正。`ravel-core/src/runtime/frame_cache.rs`）:

- スロットは `(CompId, TimeKey)`。**ノード id はキーに入れない** — コンパイル
  済みシェルグラフは再コンパイルのたびに新しいノード id を持つので、ノードで
  キー付けすると到達不能なエントリが残り、`cached_ranges` がそれを報告する
  （帯が嘘をつく）。照合はエントリが持つ `CacheIdentity` に委ね、評価器と
  同じ規則（精度だけ順序、他は厳密一致）をそのまま使う。
- 無効化は `InvalidationHint` ではなく **`set_document` と同じ文書差分**で
  引く。多くの文書コミットが `InvalidationHint::None` を渡して評価器側の
  差分に頼っており、ヒント駆動にすると**それらの編集に古い絵を返す**。
  `Document::compositions` は `Arc<Composition>` なので、触っていないコンプは
  ポインタ一致で無料。コンプ切り替え（`Structural` だが文書は不変）では
  帯が残る。
- **キャッシュするのは `finalize` 後の値**。`GpuEvalHooks::finalize` が
  ビューア向けに GPU フレームを読み戻す唯一の地点なので、ヒットは
  `process` もリードバックも払わない。層は**保存した値**の
  `is_gpu_resident()` で決まる。表示が GPU テクスチャから行われるように
  なれば（フェーズ 4）、この コードを変えずに VRAM 層が動き出す。
  **計画書の「VRAM 層は `GpuFrameBuffer` をそのまま保持」からの逸脱**:
  今それをやると、読み戻し済みで誰も参照しないテクスチャが VRAM を占有し、
  `headroom = 上限 − 保持分` が縮んでテクスチャプールのアイドル枠を
  食い潰す（1080p `Rgba16Float` は約 16.6 MB/フレーム、既定 1 GiB を
  60 フレームで埋める）。評価経路を遅くするキャッシュは無いより悪い。
- 予算の各層は評価器のノード結果と**共有**なので、退避リストは相手の id を
  含みうる。落とさなかった id は予算の過小計上になるため、
  `Evaluator::take_foreign_evictions` / `drop_evicted` と
  `SharedFrameCache` の対を worker が突き合わせる。`CACHE-8` の共有デコード
  キャッシュが 3 つ目の参加者として加わり、突き合わせは
  `settle_evictions`（`eval_service.rs`）の 1 パスに統合された。
- RAM 層の f16 化は**宣言された下限**にだけ従う（`min_precision <= F16` の
  ときだけ `RgbaF16` へ縮約）。ビューアは今も `F32` を要求するので実際には
  眠っている — ビューアの下限を下げるのは製品判断で、本単位の仕事ではない。

**完了条件**（実装に合わせて 2026-08-10 に改訂。改訂理由は各項目に併記）

- スクラブ後戻りで `process` が 1 度も走らないテスト（`take_timings` が空）。
- **キャッシュヒット時に GPU→CPU 転送が発生しないテスト**（`GPUCOMP-7` の
  リードバック計数を流用）。
  - 旧: 「**VRAM ヒット時に** GPU→CPU 転送が発生しない」。
    キャッシュするのは `finalize` 後の値で、`finalize` こそがリードバックの
    唯一の地点なので、**保証すべきはヒットがリードバックを払わないこと**。
    今は `finalize` が GPU フレームを読み戻すため VRAM 層にエントリは載らず、
    「VRAM ヒット」という状態自体が存在しない。**満たしていない条件を
    満たしたことにしないため文面を実装に合わせた。**
  - VRAM 層の条件は**表示が GPU テクスチャから行われるようになったとき**の
    もので、そのときは `finalize` が `GpuFrameBuffer` を返し、層は保存値の
    `is_gpu_resident()` で決まるのでこのコードを変えずに載る。
    そこで初めて「VRAM ヒットで転送ゼロ」が意味を持つ。担当は
    `gpu-compositing-plan.md` のゼロコピー表示。
- 編集後に該当 comp のエントリが全て落ち、他 comp が残るテスト。
- 予算超過で古いフレームが**破棄される**テスト（GPU 常駐値ならその破棄が
  プールへの返却になる。返却そのものは `GpuFrameBuffer` の `Drop` の責任で、
  `ravel-gpu` 側のプールテストが担保する）。
- 書き出し相当の `min_precision = F32` 要求がプレビューエントリを
  拾わないテスト。
- `finalize` が失敗した値がキャッシュされず、次の要求で再試行されるテスト
  （ヒットは `finalize` を再実行しないので、一度の失敗が恒久化しうる）。

### 単位 6 (`CACHE-6`): Timeline のキャッシュ帯と統計

- `cached_ranges(comp, &EvalContext)` を追加。
- Timeline にキャッシュ帯を描く（RAM = 緑、将来のディスク = 青）。
- 予算・ヒット率のログ出力を整える。

**実装時の決定**（コードが正）:

- `cached_ranges` の絞り込みは **`CacheIdentity::mismatch` そのもの**で、
  軸の部分集合ではない。品質・fps・コンプ解像度も解像度や精度と同じように
  ヒットを決めるので、1 つでも落とすと「帯は緑なのにスクラブで再計算される」
  フレームが出る（スロットにノード id を入れないのと同じ理由）。引数が
  `EvalContext` なのはそのため — ビューアが次に投げる文脈をそのまま渡す。
- `cached_ranges` は**整数フレームだけ**を返す。サブフレーム位置
  （シャッターサンプル）は再生ヘッドが乗れないので、丸めて帯にすると
  「当たらないフレームを当たると言う」ことになる。
- 帯の画素化は `TimelinePanel::cache_band_spans`（`ravel-ui`）で、
  `loop_range_span` — ルーラーが閉区間をピクセルに直す唯一の場所 — を
  そのまま通す。ヘッドレステストはここに置く。
- 帯は**購読しない**。`CacheBandState` グローバルへは**範囲が変わったときだけ**
  書き（比較はマップを clone する**前**に行う）、Timeline は再生ヘッドや文書の
  更新で走る再描画のついでに読む。
  購読すると評価完了ごと（＝再生中は毎フレーム）に notify が増え、
  `HIGH-21` と同じ形になる。再生中は再生ヘッドの再描画が毎フレーム走るので、
  帯はそれに乗って伸びる。
- 帯は**今表示している解像度・精度**で引く。別の解像度のエントリを緑にすると
  スクラブで当たらないので帯が嘘になる。
- `cached_ranges` は全走査 + ソートなので、UI スレッドは
  `SharedFrameCache::version()`（挿入と破棄でだけ動くカウンタ）を先に見て、
  **キャッシュヒットだけだった評価では走査そのものを飛ばす**。帯を消す経路は
  記録した version も捨てる（他コンプの編集などで version が動かないまま
  帯だけ空になった状態から復帰できなくなるため）。
- 編集時は**その場で**帯を消す。評価完了を待つと、編集の notify で走る再描画が
  編集前の帯を出す。評価が走らない経路（空コンプ、コンパイルエラー）も塞ぐ。
- 色は緑（`success`）のみ。`cached_ranges` は層を返さず、ディスク層
  （青）は層自体が `CACHE-11` なので、今 2 色にするのはデータが守れない約束。

**完了条件**

- 帯の範囲が `cached_ranges` の返り値と一致するヘッドレステスト。
- `cached_ranges` が報告するフレームが、実際に `get` でヒットするフレームと
  一致するテスト（品質・fps・コンプ解像度の違うエントリを混ぜて確認）。
- 編集で帯が消える / 再生で伸びるテスト。編集の側は**評価完了を待たずに**
  消えること。
- 帯の描画が再生中の Timeline 再描画コストを増やさないこと
  （`HIGH-21` の回帰を作らない）。

### 単位 7 ✅ (`CACHE-7`): 無効化を時間範囲に絞る

- `InvalidationHint::Params(node_ids)` から所有レイヤーを引き、
  `[start_frame, start_frame + (out_frame - in_frame))`
  （`ravel-core/src/composition/mod.rs:186-190`）に交差するフレームだけを
  落とす。
- 親コンプへの伝播（precomp が入っている場合）を含む。

**実装時の決定**（コードが正。`ravel-core/src/runtime/frame_cache.rs` の
`invalidation_plan`）:

- **どのコンプを落とすかは今も文書差分**（`CACHE-5` の決定）。ヒントが決める
  のは**そのコンプのどのフレームを落とすか**だけ。絞り込みは安全側の既定の
  上に載る最適化で、置き換えではない。
- 絞り込むのは、**合体された全要求が `Params` を持っていて**、かつ**名前の
  付いた全ノードが所有レイヤーに解決できた**ときだけ。どちらかが欠ければ
  従来どおりコンプ全破棄。
  - 「全要求が」を worker 側で別途数えているのは、`InvalidationHint::merge`
    が `None` を `Params` に吸収するため。`None` は「何も変わっていない」と
    書かれているが、実際には殻の編集（transform / opacity）が文書と一緒に
    投げてくる。合体後の `Params` からは、説明の付かない編集が相乗りしたか
    どうかを読み取れない。
  - ノードが解決できないのは、コンパイル済み殻グラフの合成ノードのように
    文書に存在しない id のとき。**置ける場所が分からないヒントで絞るのは
    古い絵を返すことなので、絞り込み自体を止める。**
  - 差分に出たのにヒントがどのノードも置いていないコンプも全破棄
    （`Arc` が動いた理由をヒントが説明していない）。
- レイヤーの範囲は `[start_frame - 1, end_frame + 1)`。**前後 1 フレームの
  余裕**は、モーションブラーのシャッターサンプルがフレームの間に落ちるため。
- 落とす範囲には、**編集レイヤーに親子付けされたレイヤーの範囲**も含める。
  transform チャネルは `ChannelSource::NodeOutput` でネットワーク内のノードを
  参照できるので、親の範囲外のフレームでも子の絵が変わる。
- **`layer.ref` は範囲を広げない**（`ravel-nodes/src/layer_ref.rs` は
  **参照先の** `[in, out)` で打ち切る）ので、参照元を辿る必要はない。
- **precomp 経由の伝播は新規の修正**で、絞り込みとは独立に効く。子コンプを
  編集しても**親コンプの `Arc` は動かない**ため、`CACHE-5` のままでは親が
  編集前の絵を返し続けていた。親が落とすのは**その precomp ノードを持つ
  レイヤーの範囲全体**で、子の影響範囲を親のタイムラインへ写像はしない
  — `precomp` のプロセッサはまだ存在せず、写像を書けばコードのどこも
  実行していない時間関係を先に固定してしまう。レイヤー自身の範囲は殻の
  時間ゲートが保証している上界なので、そこで止める。
- 伝播は不動点まで回すが、コンプ数で上限を切ってある。循環の拒否は
  `validate_precomp_cycles` の仕事で、**キャッシュは検証を通っていない文書
  でも停止しなければならない**。

**完了条件**

- レイヤーの時間範囲外のフレームが**生き残る**テスト。
- 範囲内のフレームは落ちるテスト。
- precomp 経由で親 comp の該当範囲も落ちるテスト。
- 単位 5 の「comp 単位で全破棄」と結果が矛盾しない（絞り込みが
  取りこぼさない）ことの比較テスト。

### 単位 8 ✅ (`CACHE-8`): 共有デコードフレームキャッシュ

- `ravel-media` にアセット単位の共有キャッシュを追加。予算は
  `CacheKind::MediaFrame`（**HIGH-16 を回収**）。
- 静止画・画像シーケンスの複数エントリ化（**MED-MED-02 の後半を回収**。HW
  デバイス作成の回避は issue 側に残る）。
- キーにパスを含め、リリンク後に stale ヒットしないこと。

**実装時の決定**（コードが正）:

- 置き場は `crates/ravel-media/src/frame_cache.rs`、`ffmpeg` フィーチャの
  **外**。デコードした主体が誰であれフレームは同じもので、注入されたリーダー
  しか無いビルドでもキャッシュは効く必要がある。
- キーは `(解決済みパス, 入力色空間, ストリーム番号, フレーム番号)`。
  **入力色空間がキーに入るのはフェーズ CM の帰結** — 取り込み時に伝達関数を
  外すようになったので、保持しているのは変換後の絵であり、同じファイルを
  別の入力色空間で読んだ結果は「古いコピー」ではなく**別の絵**。パスを含む
  ことがリリンク後の stale ヒットを構造的に不可能にする。
- **mtime はキーに入れない。** 毎フレームの `stat` を払うことになり、
  置き換えた既存キャッシュも見ていなかった。同一パスの上書きは検出しない。
- 所有者は評価ワーカー（`GpuEvalHooks`）で、`processor_for_node` /
  `register_all_processors` がテクスチャプールと同じ形で各 `media`
  プロセッサへ渡す。プロセッサ側に残るのは開いたリーダー 1 本だけ。
- 退避は `CacheBudget` に一任し、**このキャッシュは独自の LRU を持たない**。
  ヒットで `touch` するので順序は least-recently-*used*。
- Ram 層は `CacheKind::NodeResult` / `CacheKind::Frame` と共有なので、
  `reserve` の退避リストには**他の消費者の id が混ざる**。読み飛ばすと漏れる
  — `reserve` は返す前に勘定から外すので、飛ばした id は二度と退避対象に
  ならず実体は生き続ける。**`CACHE-5` の受け渡しに乗せた**: 自分のものでない
  id は捨てずに預かり（`MediaFrameCache::take_foreign_evictions`）、worker の
  `settle_evictions` が 3 者の預かり分を 1 パスで持ち主へ配る。デコード
  キャッシュは `EvalWorkerHooks::reconcile_evictions` から参加する — 評価器の
  中に居ないため、hooks が唯一の到達点。3 つ目の方式は作っていない。

**完了条件**

- 逆方向スクラブで GOP を再デコードしないテスト（デコード回数を観測）。
- 同じ素材を使う 2 レイヤーがデコード結果を共有するテスト。
- 予算超過で古いフレームが落ちるテスト。
- シーケンスで直近 N フレームがヒットするテスト。
- リリンク後に古いパスのエントリがヒットしないテスト。

### 単位 9 ✅ (`CACHE-9`): 先読み（投機充填）

- `EvalRequest` に投機フラグを追加。別キュー・世代番号を進めない・
  `on_update` を発火しない・予算では先に落ちる。
- アイドル検出（対話要求が一定時間来ていない）でプレイヘッド前方を充填。

**実装時の決定**（コードが正。`ravel-core/src/runtime/eval_service.rs`）:

- **投機フラグは `EvalRequest` のフィールドではなく、キューそのもの**。
  入口は `EvalService::request_speculative`（`&self` で、返り値なし）で、
  worker 側の `Job::Speculative` に落ちる。フィールドを足すと「どちらの
  キューに入れたか」と「フィールドの値」の 2 つが同じことを言うので、
  言う場所を 1 つにした。`&self` であること自体が**世代番号を進めない**
  ことの型による表明でもある。
- **アイドル検出は実時間のサンプリングではなくチャネルの待ち**。両キューが
  空になったときの `select!` に `default(idle)` を付け、それが発火したら
  「対話要求が `idle` の間来ていない」と読む。**タイマーも時計もポーリング
  も無い**ので、テストは `idle = Duration::ZERO` を渡すだけで「worker が
  暇になった」という決定的なイベントとして扱える。
- **しきい値は 250 ms、先読みは 24 フレーム**（`ReadAhead::DEFAULT_IDLE` /
  `DEFAULT_FRAMES`）。250 ms は、数十 ms 間隔で要求を投げるスクラブが
  絶対に踏まない幅であり、かつプレイヘッドから手を離してから充填が始まる
  までが体感で待ちにならない幅。24 フレームは 24–30 fps でおよそ 1 秒。
- **先読みは既定で切ってある**（`EvalService::spawn` /
  `spawn_with_budget`）。要求したフレームだけを評価する呼び出し側 —
  レンダー、ベンチマーク、`process()` を数えるテスト — の意味論を
  変えないため。入れるのは `EvalServiceConfig` を取る
  `spawn_with_config` で、実際に入れているのは
  `ravel-app` の Viewer 用サービス 1 箇所だけ。
- 先読みが投げる要求は、**直前の対話要求の文脈をそのまま持ち、時間軸だけ
  動かす**（`EvalContext::with_frame`）。解像度・品質・精度・座標基準が
  1 つでもずれると「帯は伸びるがスクラブでは当たらない」— 帯が嘘をつく。
  完了条件の帯テストが `cached_ranges` だけでなく**実際のヒット**まで
  確かめているのはそのため。
- 充填済みかの判定は `SharedFrameCache::contains`（**ヒットもミスも記録
  しない**）。投機は誰も出していない要求なので、`hit_rate` を動かすと
  ログとテストが読む数字がずれる。
- **投機ランクは評価器のノード結果にも通す**（`Evaluator::set_read_ahead`）。
  フレームだけを投機扱いにすると、投機評価が作ったノード結果が対話用の
  エントリを追い出せてしまい、完了条件が半分しか成立しない。
  対象外なのは**共有デコードキャッシュ**（`CACHE-8`）で、こちらはアセット
  単位で対話評価と共有される — 同じデコード結果を対話側も使うので、
  投機が触れたという理由で先に捨てるのは誤り。
- **投機は中断可能**。キューの破棄だけでは、すでに `evaluate_at` に入った
  1 フレームが最後まで走り、重いフレームがそのままスクラブの遅延になる。
  `Evaluator::set_read_ahead` が渡す述語を**各ノードの `process()` の直前**で
  引き、対話要求が来ていれば `EvalError::Cancelled` で抜ける。
  - 判定は**チャネルが空かどうか**（`!rx.is_empty()`）。実時間は見ない。
  - 引く場所を `eval_node` の入口ではなく `process()` の直前にしたのは、
    プルが上から下へ走るため。ノードの入口で引くと、入力を辿る前に済んで
    しまい、要求が届く頃には通過済みになる。
  - **純粋性は壊れない**: 途中まで計算済みのノード結果はどれも完全で正しい
    値なので、そのままキャッシュに残る。捨てられるのは「答え」だけで、
    フレームキャッシュへの挿入は `Ok` でしか起きない。
  - **簿記も壊れない**: 打ち切りは早期 return を増やさず、退避の突き合わせ
    （`settle_evictions`）は Ok / Err にかかわらず同じ位置で走る。

**完了条件**

- 投機中に対話要求が来たら投機が即破棄されるテスト。
- 投機が latest-wins の世代番号を進めないテスト。
- 投機の結果が Viewer の表示を差し替えないテスト。
- 予算圧で投機エントリが対話エントリより先に落ちるテスト。
- 投機によって帯が伸びるテスト。
