# カラーマネジメント実装計画（REQ-RENDER-003 / REQ-CORE-009）

> **Status**: Planned — 2026-08-06

対象要件: REQ-RENDER-003（OCIO + GPU LUT カラーマネジメント）、
REQ-CORE-009（32bit float 内部処理のリニア前提）。
引き受ける issue: `HIGH-25`（合成が display-referred 空間で行われている）。

## 問題

**パイプラインがリニアではない。要件はリニアだと書いている。**

実装を辿ると、色空間変換のコードがリポジトリに 1 行も無い。

| 経路 | 現状 | 場所 |
|---|---|---|
| 取り込み | `data[offset] as f32 / 255.0` | `ravel-media/src/decoder.rs:921` |
| Viewer 表示 | `(v.clamp(0.0, 1.0) * 255.0 + 0.5) as u8` | `ravel-app/src/panels/mod.rs`（`reference_bgra`） |
| 動画書き出し | `(px.clamp(0.0, 1.0) * 255.0) as u8` | `ravel-media/src/encoder.rs:160` |
| 連番書き出し | 同上（`EXPORT-1`） | `ravel-media/src/encode/sequence.rs` |

どこにも伝達関数が無い。つまり **sRGB エンコード済みの値が 0–1 に正規化された
まま合成に入り、そのまま出ていく**（display-referred）。3 経路が同じ素朴変換で
揃っているので**自己整合はしていて、取り込み → 書き出しは恒等**になる。
今すぐ壊れて見えるものは無い。

壊れているのは**合成の数学**である。

- **不透明度・ブレンド**: sRGB エンコード値の線形補間は物理的に誤り。
  黒と白の 50% 合成が中間グレー（`0.5` → 表示 128）になるが、正しくは
  リニアで `0.5` → 表示 188 付近
- **ブラー・ダウンサンプル**: 明部の重みが不足し、縁が暗く沈む
- **プリマルチプライド合成**: アルファとの積が非線形空間で行われる

そして要件が食い違っている。REQ-CORE-009 は
「OCIO（REQ-RENDER-003）も 32bit float **リニア空間**での処理を前提」と
書いているが、実装はリニアではない。REQ-RENDER-003 は **Must なのに計画が
無かった**（`backlog.md` の未計画要件表）。本計画がそれを引き受ける。

### 今やる理由

ロードマップの**基準 1**（移行コストが時間で増える単位を先に）が最も強く
効く単位。パイプラインをリニアにすると、作者が指定した色の意味が変わるので
`.ravprj` の移行が要る。

- **リリースタグがゼロ**、CD ワークフローも無い（`.github/workflows/` は
  `ci.yml` のみ）。AGENTS.md も「パッケージング手順はまだ無い」と書いている
- したがって**世に出た `.ravprj` は実質存在しない**。移行は今なら限りなく安い
- 後回しにするほど、変換対象のプロジェクトと「見た目が変わった」の苦情が増える

**フェーズ C4 の直後**に置く。C4（書き出し）は基準 0（成果物が出せない）で
先行し、その次に基準 1 のこれが来る。C2（キャッシュ本体）より前にする理由は、
フレームキャッシュが「どの色空間の絵を持っているか」を軸に持つことになり、
後から色変換を入れると `CacheIdentity` の再検討が発生するため。

**`EXPORT-*` のエンコーダは書き直しにならない。** 出力変換はエンコーダの
**手前に段を挿す**だけで、`Encoder` トレイトも連番の実装も変わらない。

## 決定事項（2026-08-06 設計セッション）

### 骨格を自前の固定変換で先に入れ、OCIO は後段

`ocio-rs`（0.2.1、BSD-3-Clause、OCIO 2.5.2 のバインディング）が実在し、
`.ocio` 読み込み・CPU/GPU 両経路・**GPU シェーダ抽出**まで揃っている。
要件が求める「GPU 3D LUT にベイクして wgpu シェーダで適用」がそのまま乗る。

それでも**最初の 5 単位は自前の固定変換で組む**。理由:

1. **この仕事の難所は変換の数式ではない。** 難所は「入力色空間を素材ごとに
   持ち、作業空間をリニアにし、表示と出力に変換を挿し、既存プロジェクトを
   移行する」構造の側で、そこは OCIO を使っても自前でも同じ量の作業になる
2. **切り分けが効く。** リニア化の移行と C++ のビルドを同時に背負うと、
   絵がおかしいときに「色の実装が悪いのか OCIO のビルドが悪いのか」が
   分からない
3. **CI のコストを後ろに倒せる。** `ocio-rs` の `bundled` は OCIO を
   ソースからビルドする。このリポジトリは既に CI キャッシュが逼迫している
   （10GB 上限に `target/` 3 本が競合し macOS 分が毎回 evict される — `#211`）
4. **抽象の形を推測で決めずに済む。** `ocio-rs` の API を見てから
   バックエンド境界を切れる

`ocio-rs` は単独メンテナの若いクレート（初版 2026-05-13、月間 570 DL 程度、
自称「release hardening 進行中」）なので、**後段に置くこと自体がリスク
緩和になる**。`CM-6` に着手する時点で改めて採否を判断でき、落としても
`CM-1`〜`CM-5` の骨格は残る。

### 作業空間はリニア Rec.709 原色

ACEScg ではなく、**伝達関数だけリニアにして原色は据え置く**。

- 移行が**純粋な伝達関数の変換**で済み、色域変換が一切発生しない
- 色域外の値とガマットマッピングの設計判断を最初から抱え込まない
- ACEScg は `CM-7`（`.ocio` 読み込み）で作業空間の選択肢として入る

### 一斉切替。作業空間のフラグを持たない

プロジェクト単位で display-referred / linear を切り替えるフラグは**作らない**。

守るべき既存ユーザーがいない（リリースゼロ）状態で二重の作業空間を持つのは
純粋なコストで、評価・キャッシュ・書き出しの全経路に条件分岐が増える。
`.ravprj` を v7 → v8 に上げ、**作者が指定した色を一度だけ変換する**。

### 移行は型付きパス。manifest 連鎖ではない

`ravel-project/src/migration.rs` の既存の規約に従う。manifest の連鎖
（`migrate_v7_to_v8`）は**バージョン印を進めるだけ**にし、内容の変換は
ロード後の型付きパスとして `ProjectFile::from_archive` から適用する
（`v4 → v5` の `Document::upgrade_curve_params` が先例）。

変換対象は `ravel_core::types::Color { r, g, b, a }` のうち **`r` / `g` / `b`
だけ**。アルファは伝達関数を持たないので変換しない。

### 素材の入力色空間は素材ごとに持つ

「全部 sRGB」と決め打たない。`AssetRef` に入力色空間を持たせ、既定を
sRGB にする。EXR / 連番 float は既にリニアなので、決め打つと
**リニア素材に二重に伝達関数がかかる**。

### 表示変換は 1 箇所

`GPUCOMP-9`（#284）が f32 → BGRA 変換を評価ワーカーへ移し、変換点が
1 箇所に集約されている。表示変換はそこに入れる。Viewer の各所に散らさない。

## 目標構成

```text
素材（sRGB / Rec.709 / linear EXR …）
   │  入力変換（素材ごとの入力色空間 → 作業空間）
   ▼
作業空間: linear Rec.709 primaries, 32bit float
   │  合成・ブラー・不透明度・ブレンドはここで行う
   ├─────────────── 表示変換 ──▶ Viewer（linear → sRGB、GPU LUT）
   └─────────────── 出力変換 ──▶ Encoder（linear → 出力色空間）
```

`CM-6` 以降で、入力・表示・出力の 3 つの変換の**中身**が OCIO 由来に
差し替わる。構造は変わらない。

### CM-1 色空間の型と変換関数

`ravel-core` に置く。**純粋関数だけの単位**で、副作用も I/O も持たない。

- `ColorSpace` 型（`Srgb` / `Rec709` / `LinearRec709` / `Rec2020` / `AcesCg`）
- 伝達関数の往復（sRGB の区分関数、Rec.709 の OETF、恒等）
- 原色行列（`CM-1` では Rec.709 間の恒等のみ使うが、`CM-7` が使う形で置く）
- `.cube` 形式の 3D LUT の読み込みと三重線形補間

**完了条件**

- 伝達関数の往復がすべての入力で誤差 1e-6 以内に戻るテスト
- sRGB の区分関数の**継ぎ目**（`0.04045` / `0.0031308` 近傍）で不連続が
  無いテスト
- 定義域外（負値、1 超）で panic せず、単調性を保って外挿するテスト
- 原色行列の往復が恒等に戻るテスト
- `.cube` の読み込みと補間が既知の LUT で期待値を返すテスト
- **既存の絵が変わらないこと**（この単位は呼び出し側を持たない）

### CM-2 素材の入力色空間とデコードの線形化 + `.ravprj` v8

- `AssetRef` に入力色空間を持たせる。既定 `Srgb`。**EXR と float 連番は
  `LinearRec709`** を既定にする（二重適用を避ける）
- `ravel-media` のデコード経路で、`u8 → f32 / 255.0` の直後に入力変換を挿す
- **`.ravprj` v7 → v8**。`migration.rs` の連鎖はバージョン印のみ。
  内容変換は `Document` への型付きパスとして、作者が指定した `Color` の
  `r` / `g` / `b` に `srgb_to_linear` を適用する

**完了条件**

- sRGB 素材の取り込みがリニア値になるテスト
- **EXR / float 連番に伝達関数が二重適用されない**テスト
- v7 の `.ravprj` が v8 に上がり、**作者が指定した色の見え方が変わらない**
  テスト（移行後の色をリニア → sRGB で戻すと元の値に一致する）
- アルファが変換されないテスト
- v8 を古いビルドで開くと `MigrationError::TooNew` になるテスト
- 移行が冪等であるテスト（二度かけても値が変わらない）

### CM-3 Viewer の表示変換

- `GPUCOMP-9` が集約した f32 → BGRA 変換点に、作業空間 → 表示色空間の
  変換を挿す
- 表示色空間は当面 sRGB 固定（選択は `CM-8`）
- **`quality` / `ViewerResolution` と直交**させる（`BLUR-3` の軸と混ぜない）

**完了条件**

- リニア値がガンマ補正されて表示されるテスト
- **合成の結果が物理的に正しくなる**ことの回帰テスト（黒と白の 50%
  不透明度合成が、表示上 128 ではなく 188 付近になる）
- 変換が 1 箇所に閉じ、Viewer の他の描画経路が素の値を u8 化していない
  ことの確認（lint か grep で担保する）
- 表示変換が `quality` と `ViewerResolution` のどちらにも影響されない
  テスト

### CM-4 書き出しの出力変換

- `EXPORT-1` の `Encoder` の**手前に**変換段を置く。`Encoder` トレイトも
  連番の実装も変えない
- PNG / 動画: 作業空間 → sRGB
- **EXR: 作業空間のまま（リニア）で書く。** ここで初めて EXR の
  「リニア 32bit float をそのまま出せる」が事実になる
- `EXPORT-1` が入れた「この値は scene-linear ではない」という doc コメントを
  撤回する

**完了条件**

- PNG の書き出しが Viewer の表示と一致するテスト
- **EXR がリニア値を保持し、PNG とは異なる値になる**テスト
- sRGB 素材を取り込んで PNG に書き出すと**ビット単位で元に戻る**テスト
  （入力変換と出力変換が往復する）
- 動画書き出しと PNG が同じ値になるテスト
- `render-export-plan.md` の v1 出力形式表の根拠が事実と一致すること

### CM-6 `ocio-rs` の導入とビルド戦略

**この単位は着手前に採否を判断する。** `ocio-rs` は若いクレートなので、
`CM-5` 完了時点で成熟度を再評価する。落とす判断も選択肢に残す。

- `bundled`（ソースビルド・静的リンク）と システムインストール のどちらを
  採るか決める。**CI のキャッシュ予算（`#211`）への影響を測ってから決める**
- `stub` 既定（色管理が無効になる）を**踏まない**ビルド構成にする。
  feature の入れ忘れが黙って色管理を殺す経路を塞ぐ
- **BSD-3-Clause の帰属表示義務**: OCIO と推移依存（expat / yaml-cpp /
  Imath / pystring / ZLIB / minizip-ng）の notice をリリースバンドルに
  同梱する必要がある。AGENTS.md がフォントで抱えている債務と同じ種類なので、
  **同じ場所に記録する**

**完了条件**

- 3 OS でビルドが通る
- CI の所要時間とキャッシュ使用量の増加を測定し記録する
- `stub` モードでビルドされた場合に**ビルドエラーになる**（黙って
  無効化されない）テストまたはビルド時チェック
- 帰属表示の一覧が `AGENTS.md` の該当箇所に載る

### CM-7 `.ocio` の読み込みと GPU シェーダ抽出

- `.ocio` 設定ファイルをプロジェクトに読み込む
- 入力・作業・表示の各色空間を設定から選ぶ
- `ocio-rs` の GPU シェーダ抽出を wgpu 経路に接続し、3D LUT をテクスチャに
  ベイクする。**LUT の再生成は設定変更時のみ**
- `CM-1` の自前変換は、OCIO 設定が無いときの既定として残す

**完了条件**

- `.ocio` 設定ファイルを読み込めるテスト
- 入力/作業/表示カラースペースを設定できるテスト
- ACES / Rec.709 / sRGB / Rec.2020 の変換が既知の値で正確に動作するテスト
- ビューア表示に GPU LUT が適用されるテスト
- LUT が設定変更時にのみ再生成されるテスト
- OCIO 設定が無いプロジェクトが `CM-1` の既定経路で動くテスト

## 検証

- `CM-1` は純粋関数なので単体テストで完結する
- `CM-2` の移行は**往復テスト**で担保する（移行後の値をリニア → sRGB で
  戻すと元に一致）
- `CM-3` / `CM-4` は**表示と書き出しが一致すること**を軸に検証する。
  「正しい絵」の絶対的な基準は持たず、4 つの出口（Viewer / PNG / EXR /
  動画）の相互一致で担保する
- 既存のゴールデンテストは**この計画で意図的に変わる**。`CM-3` の時点で
  更新し、更新の理由をコミットメッセージに残す

## 非対象

- **HDR 出力**（PQ / HLG のディスプレイ出力）。伝達関数は `CM-1` に置くが、
  HDR ディスプレイへの出力経路は別
- **トーンマッピング**。ACEScg を作業空間に選べるようになる `CM-7` の後
- **カラーグレーディングのノード**（リフト/ガンマ/ゲイン、カラーホイール）。
  REQ-MOGRAPH の `FX-1` が担当し、フェーズ F
- **ディスプレイのプロファイル取得**（OS のモニタ ICC）。`CM-8` の後
- **作業空間をプロジェクト単位で切り替えるフラグ**。決定事項のとおり作らない
