# カラーマネジメント実装計画（REQ-RENDER-003 / REQ-CORE-009）

> **Status**: `CM-1`〜`CM-5` 実装済み（骨格はリニア化まで完了）/
> `CM-6`〜`CM-8`（`ocio-rs` の導入以降）は未着手 — 2026-08-06 起案

規範は [`../specifications/color-management.md`](../specifications/color-management.md)。
以下の「問題」節は着手前の状況の記録として残してある。

対象要件: REQ-RENDER-003（OCIO + GPU LUT カラーマネジメント）、
REQ-CORE-009（32bit float 内部処理のリニア前提）。
引き受ける issue: `HIGH-25`（合成が display-referred 空間で行われている。
`CM-1`〜`CM-4` で解決済み、`issues/closed/` へ移した）。

## 問題

**パイプラインがリニアではない。要件はリニアだと書いている。**

実装を辿ると、色空間変換のコードがリポジトリに 1 行も無い。

| 経路 | 現状 | 場所 |
|---|---|---|
| 取り込み | `data[offset] as f32 / 255.0` | `ravel-media/src/decoder.rs:921` |
| Viewer 表示 | `(v.clamp(0.0, 1.0) * 255.0 + 0.5) as u8` | `ravel-app/src/panels/mod.rs`（`reference_bgra`） |
| 動画書き出し | `(px.clamp(0.0, 1.0) * 255.0) as u8` | `ravel-media/src/encoder.rs:160` |
| 連番書き出し | 同上（`EXPORT-1`） | `ravel-media/src/encode/sequence.rs` |

どこにも伝達関数が無い。つまり **sRGB エンコード済みの値が 0–1 に正規化された
まま合成に入り、そのまま出ていく**（display-referred）。3 経路が同じ素朴変換で
揃っているので**自己整合はしていて、取り込み → 書き出しは恒等**になる。
今すぐ壊れて見えるものは無い。

壊れているのは**合成の数学**である。

- **不透明度・ブレンド**: sRGB エンコード値の線形補間は物理的に誤り。
  黒と白の 50% 合成が中間グレー（`0.5` → 表示 128）になるが、正しくは
  リニアで `0.5` → 表示 188 付近
- **ブラー・ダウンサンプル**: 明部の重みが不足し、縁が暗く沈む
- **プリマルチプライド合成**: アルファとの積が非線形空間で行われる

そして要件が食い違っている。REQ-CORE-009 は
「OCIO（REQ-RENDER-003）も 32bit float **リニア空間**での処理を前提」と
書いているが、実装はリニアではない。REQ-RENDER-003 は **Must なのに計画が
無かった**（`backlog.md` の未計画要件表）。本計画がそれを引き受ける。

### 今やる理由

ロードマップの**基準 1**（移行コストが時間で増える単位を先に）が最も強く
効く単位。パイプラインをリニアにすると、作者が指定した色の意味が変わるので
`.ravprj` の移行が要る。

- **リリースタグがゼロ**、CD ワークフローも無い（`.github/workflows/` は
  `ci.yml` のみ）。AGENTS.md も「パッケージング手順はまだ無い」と書いている
- **ただしこれは「配布していない」ことの証拠であって、「`.ravprj` が存在
  しない」ことの証拠ではない。** 開発者の手元・テスト資産・共有された
  ファイルは残りうる。リリースメタデータから在庫を推論しない
- したがって決めるのは在庫の推測ではなく**方針**である（下記）
- 後回しにするほど変換対象は増える。方針が「変換して開く」である以上、
  対象が少ないうちに入れるほうが安い

**サポート方針を明示する。** v7 を開いたときの挙動を次に固定する。

- v7 は**変換して開く**（拒否しない）。変換内容は `CM-2` の移行規則
- **変換できない構成は変換せずに開き、警告を出す**（式で駆動される色など。
  `CM-2` 参照）。黙って値を変えるより、変わらなかったことを伝える
- 変換後は v8 として保存される。v8 を古いビルドで開くと
  `MigrationError::TooNew` で**拒否**される（既存の規約どおり）

**フェーズ C4 の直後**に置く。C4（書き出し）は基準 0（成果物が出せない）で
先行し、その次に基準 1 のこれが来る。C2（キャッシュ本体）より前にする理由は、
フレームキャッシュが「どの色空間の絵を持っているか」を軸に持つことになり、
後から色変換を入れると `CacheIdentity` の再検討が発生するため。

**`EXPORT-*` のエンコーダは書き直しにならない。** 出力変換はエンコーダの
**手前に段を挿す**だけで、`Encoder` トレイトも連番の実装も変わらない。

## 決定事項（2026-08-06 設計セッション）

### 骨格を自前の固定変換で先に入れ、OCIO は後段

`ocio-rs`（0.2.1、BSD-3-Clause、OCIO 2.5.2 のバインディング）が実在し、
`.ocio` 読み込み・CPU/GPU 両経路・**GPU シェーダ抽出**まで揃っている。
要件が求める「GPU 3D LUT にベイクして wgpu シェーダで適用」がそのまま乗る。

それでも**最初の 5 単位は自前の固定変換で組む**。理由:

1. **この仕事の難所は変換の数式ではない。** 難所は「入力色空間を素材ごとに
   持ち、作業空間をリニアにし、表示と出力に変換を挿し、既存プロジェクトを
   移行する」構造の側で、そこは OCIO を使っても自前でも同じ量の作業になる
2. **切り分けが効く。** リニア化の移行と C++ のビルドを同時に背負うと、
   絵がおかしいときに「色の実装が悪いのか OCIO のビルドが悪いのか」が
   分からない
3. **C++ のビルドを必要になるまで払わない。** `ocio-rs` の `bundled` は
   OCIO と推移依存（expat / yaml-cpp / Imath / pystring / ZLIB /
   minizip-ng）をソースからビルドする。**`sccache` が覆うのは Rust の
   コンパイラ呼び出しなので、cmake の `CMAKE_C_COMPILER_LAUNCHER` に
   自分で通さない限り自動では効かない**
4. **抽象の形を推測で決めずに済む。** `ocio-rs` の API を見てから
   バックエンド境界を切れる

> **理由 3 は当初「CI キャッシュが 10GB 上限で逼迫している（`#211`）」と
> 書いていたが、`ci-cache-plan.md` の `CICACHE-1` / `CICACHE-2`
> （2026-08-08、sccache + Cloudflare R2）で解消済み。**
> 残るのは C++ ソースビルドそのもののコストなので、上のとおり書き直した。

`ocio-rs` は単独メンテナの若いクレート（初版 2026-05-13、月間 570 DL 程度、
自称「release hardening 進行中」）なので、**後段に置くこと自体がリスク
緩和になる**。`CM-6` に着手する時点で改めて採否を判断でき、落としても
`CM-1`〜`CM-5` の骨格は残る。

### 作業空間はリニア Rec.709 原色

ACEScg ではなく、**伝達関数だけリニアにして原色は据え置く**。

- 移行が**純粋な伝達関数の変換**で済み、色域変換が一切発生しない
- 色域外の値とガマットマッピングの設計判断を最初から抱え込まない
- ACEScg は `CM-7`（`.ocio` 読み込み）で作業空間の選択肢として入る

### 一斉切替。作業空間のフラグを持たない

プロジェクト単位で display-referred / linear を切り替えるフラグは**作らない**。

守るべき既存ユーザーがいない（リリースゼロ）状態で二重の作業空間を持つのは
純粋なコストで、評価・キャッシュ・書き出しの全経路に条件分岐が増える。
`.ravprj` を v7 → v8 に上げ、**作者が指定した色を一度だけ変換する**。

### 移行は型付きパス。manifest 連鎖ではない

`ravel-project/src/migration.rs` の既存の規約に従う。manifest の連鎖
（`migrate_v7_to_v8`）は**バージョン印を進めるだけ**にし、内容の変換は
ロード後の型付きパスとして `ProjectFile::from_archive` から適用する
（`v4 → v5` の `Document::upgrade_curve_params` が先例）。

**変換対象は `Color` ではない。** 作者が指定した色は
`ParameterValue::Channel3` / `Channel4`（`AnimationChannel` の配列、
`graph.rs:215`）として永続化される。`ravel_core::types::Color` は評価中の
値型であって保存形式ではない。したがって移行はチャネルを辿る必要があり、
次の 3 つが順に難しくなる。

| チャネルのソース | 扱い |
|---|---|
| `Constant(f32)` | 値に `srgb_to_linear` を適用する |
| `Keyframes(curve)` | **各キーの値に適用する。** ただし補間の意味が変わる（リニア補間 ≠ sRGB 補間）ので、キー上の値は一致するが中間フレームはずれる。**この事実を警告として報告する** |
| `Expression` / `NodeOutput` / `Blend` | **変換できない。** 値は評価時に決まる。変換せず、解決不能として報告する |

**どの `Channel3` / `Channel4` が色かは値から判別できない。** ポートの宣言型
（`COLOR` か `VEC3` / `VEC4` か）で決まるので、移行はノードテンプレートの
ポート型を引いて判定する。テンプレートが見つからないノード（未知のノード型を
含むプロジェクト）は**変換せず警告する**。

アルファは伝達関数を持たないので変換しない（`Channel4` の第 4 成分）。

### 素材の入力色空間は素材ごとに持ち、優先順位を決める

「全部 sRGB」と決め打たない。`AssetRef` に入力色空間を持たせる。EXR / 連番
float は既にリニアなので、決め打つと**リニア素材に二重に伝達関数がかかる**。

ただし「EXR なら必ずリニア」も決め打ちである。EXR は別の色空間の値を
入れて配布されうるので、**優先順位を定める**:

1. `AssetRef` の明示指定（ユーザーが設定したもの）— 常に勝つ
2. ファイルのメタデータ（EXR の `chromaticities`、PNG の `iCCP` / `gAMA`）
3. 拡張子ごとの既定（float 形式 → `LinearRec709`、整数形式 → `Srgb`）

**2 と 3 は推定なので、どちらを採ったかを UI とログで見えるようにする。**

### 量子化の規則を 1 つに定める

**現状ここが割れている。** Viewer は最近接（`panels/mod.rs:623`、`:1063` の
`(v.clamp(0,1) * 255.0 + 0.5) as u8`）、FFmpeg エンコーダは切り捨て
（`encoder.rs:160-163` の `(px.clamp(0,1) * 255.0) as u8`）。**今すでに
表示と動画書き出しが最大 1 LSB ずれている。**

共有の変換関数を 1 つ置き、Viewer / PNG / 動画がそれを使う。**最近接に
揃える**（切り捨ては 1.0 を 255 に写せず、往復が壊れる）。EXR は float の
まま量子化しない。

これは `HIGH-25` の一部として直す。この規則が無いと `CM-4` の
「ビット単位で往復する」完了条件が、伝達関数が正しくても落ちる。

### 表示変換は 1 箇所

`GPUCOMP-9`（#284）が f32 → BGRA 変換を評価ワーカーへ移し、変換点が
1 箇所に集約されている。表示変換はそこに入れる。Viewer の各所に散らさない。

## 目標構成

```text
素材（sRGB / Rec.709 / linear EXR …）
   │  入力変換（素材ごとの入力色空間 → 作業空間）
   ▼
作業空間: linear Rec.709 primaries, 32bit float
   │  合成・ブラー・不透明度・ブレンドはここで行う
   ├─────────────── 表示変換 ──▶ Viewer（linear → sRGB、GPU LUT）
   └─────────────── 出力変換 ──▶ Encoder（linear → 出力色空間）
```

`CM-6` 以降で、入力・表示・出力の 3 つの変換の**中身**が OCIO 由来に
差し替わる。構造は変わらない。

### CM-1 色空間の型と変換関数

`ravel-core` に置く。**純粋関数だけの単位**で、副作用も I/O も持たない。

**原色と伝達関数を別々にモデル化する。** 1 つの列挙に混ぜると
「`Rec2020` の伝達関数は何か」「`AcesCg` は線形か」が型に現れず、`CM-2` と
`CM-7` が符号化済みと線形を区別できなくなる。

```text
ColorSpace { primaries: Primaries, transfer: Transfer }

Primaries : Rec709 | Rec2020 | ApOne        （ACEScg は AP1）
Transfer  : Linear | Srgb | Rec709 | Pq
```

これで `sRGB`（Rec709 原色 + sRGB 伝達）、`ACEScg`（AP1 + Linear）、
作業空間（Rec709 + Linear）がすべて同じ形で表せる。よく使う組み合わせは
定数として名前を与える。

- 伝達関数の往復（sRGB の区分関数、Rec.709 の OETF、PQ、恒等）
- 原色行列（`CM-1` では Rec.709 間の恒等のみ使うが、`CM-7` が使う形で置く）
- `.cube` 形式の 3D LUT の読み込みと三重線形補間
- **共有の量子化関数**（決定事項「量子化の規則を 1 つに定める」）

**完了条件**

- 伝達関数の往復がすべての入力で誤差 1e-6 以内に戻るテスト
- sRGB の区分関数の継ぎ目での**跳びが有界**であるテスト。
  **「不連続が無い」ことは要求しない** — 規格の `0.04045` と `0.0031308` は
  丸めた値で厳密には交わらないので、適合実装でも微小な段差が出る。
  実装が厳密な交点を使うと宣言するか、跳びの上限を定めるかのどちらかにする
- 定義域外（負値、1 超）で panic せず、単調性を保って外挿するテスト
- 原色行列の往復が恒等に戻るテスト
- **`Primaries` と `Transfer` の全組み合わせが構成でき、往復するテスト**
- `.cube` の読み込みと補間が既知の LUT で期待値を返すテスト
- 量子化が 0.0 / 1.0 / 中点 / 境界で期待値を返すテスト

**「既存の絵が変わらないこと」はこの単位では検証しない。** `CM-1` は純粋
関数だけで呼び出し側を持たないので証明しようがない。その基準は `CM-2` /
`CM-3` / `CM-4` が持つ。

### CM-2 素材の入力色空間とデコードの線形化 + `.ravprj` v8

- `AssetRef` に入力色空間を持たせ、決定事項の**優先順位**（明示指定 →
  メタデータ → 拡張子ごとの既定）で解決する
- `ravel-media` のデコード経路で、`u8 → f32 / 255.0` の直後に入力変換を挿す
- **`.ravprj` v7 → v8**。`migration.rs` の連鎖はバージョン印のみ。
  内容変換は `Document` への型付きパスとして、決定事項の表に従って
  `Channel3` / `Channel4` を辿る。**変換できなかった箇所は集計して返し、
  ロード後に警告として出す**

**完了条件**

- sRGB 素材の取り込みがリニア値になるテスト
- **EXR / float 連番に伝達関数が二重適用されない**テスト
- 優先順位のテスト: 明示指定がメタデータに勝つ / メタデータが拡張子既定に
  勝つ / メタデータが無いとき既定に落ちる
- `Constant` の色が v8 で変換され、**リニア → sRGB で戻すと元の値に一致する**
- **`Keyframes` の色が各キーで変換され、中間フレームがずれることが警告に出る**
- **`Expression` / `NodeOutput` / `Blend` で駆動される色が変換されず、
  解決不能として報告される**
- **ポート型が `VEC3` / `VEC4` のチャネルが変換されない**（色だけを変換する）
- テンプレートが引けないノードが変換されず警告に出る
- アルファが変換されないテスト
- v8 を古いビルドで開くと `MigrationError::TooNew` になるテスト
- 移行が冪等であるテスト（二度かけても値が変わらない）

### CM-3 Viewer の表示変換

- `GPUCOMP-9` が集約した f32 → BGRA 変換点に、作業空間 → 表示色空間の
  変換を挿す

- **`quality` / `ViewerResolution` と直交**させる（`BLUR-3` の軸と混ぜない）

**完了条件**

- リニア値がガンマ補正されて表示されるテスト
- **合成の結果が物理的に正しくなる**ことの回帰テスト（黒と白の 50%
  不透明度合成が、表示上 128 ではなく 188 付近になる）
- 変換が 1 箇所に閉じ、Viewer の他の描画経路が素の値を u8 化していない
  ことの確認（lint か grep で担保する）
- 表示変換が `quality` と `ViewerResolution` のどちらにも影響されない
  テスト

### CM-4 書き出しの出力変換

- `EXPORT-1` の `Encoder` の**手前に**変換段を置く。`Encoder` トレイトも
  連番の実装も変えない
- PNG / 動画: 作業空間 → sRGB
- **EXR: 作業空間のまま（リニア）で書く。** ここで初めて EXR の
  「リニア 32bit float をそのまま出せる」が事実になる
- `EXPORT-1` が入れた「この値は scene-linear ではない」という doc コメントを
  撤回する

**完了条件**

- PNG の書き出しが Viewer の表示と**ビット単位で一致する**テスト
  （両者が同じ量子化関数を通ることの担保）
- **EXR がリニア値を保持し、PNG とは異なる値になる**テスト
- **EXR を sRGB へ変換すると PNG と一致する**テスト（出口の等価性は
  「同じ値」ではなく「共通の色空間へ変換したあと一致」で定義する）
- sRGB 素材を取り込んで PNG に書き出すと**ビット単位で元に戻る**テスト
  （入力変換と出力変換が往復する）
- 動画書き出しと PNG がビット単位で一致するテスト
- `done/render-export-plan.md` の v1 出力形式表の根拠が事実と一致すること

### CM-7 表示変換を GPU で行う（自前の固定変換 + ユーザー提供の `.cube`）

> **2026-08-10 に再定義。** 旧 `CM-7`（`.ocio` の読み込みと `ocio-rs` の
> GPU シェーダ抽出）は `CM-6` の判断待ちなので、**OCIO を必要としない部分を
> ここへ切り出した**。中身は `CM-9` へ移してある。

依存は **`CM-5`**（`CM-6` ではない）。OCIO 抜きで着手できる。

- **表示変換を wgpu の経路で行い、CPU の per-pixel 処理を無くす。**
  今の変換は `ViewerImage::from_frame_buffer` の CPU 側にある
- **3D LUT である必要は今は無い。** 現在の変換は伝達関数だけで原色行列は
  恒等なので、**シェーダで直接計算すれば足りる**（GPU の `pow` は安く、
  LUT の補間誤差も入らない）。3D LUT が要るのは任意の変換が来る `CM-9` から
- **ユーザー提供の `.cube` を適用できるようにする。** 読み込みと三重線形補間は
  `CM-1` が実装済みなので、GPU 側に載せる作業だけが残る
- **出口の等価性を壊さないこと。** GPU 経路と CPU 経路（書き出しが通る
  `to_output_space` + `quantize_u8`）が**共通の表示色空間で一致する**ことを
  テストで固定する。GPU 側は丸めが違いうるので、**厳密なビット一致を
  要求するのか許容差を定めるのかをこの単位で決めて書く**

**完了条件**

- リニア値が GPU 経路でガンマ補正されて表示されるテスト
- **GPU 経路と CPU 経路の出力が、定めた基準（ビット一致または許容差）で
  一致するテスト**
- `.cube` を与えると表示に反映され、外すと既定に戻るテスト
- 表示変換が `quality` と `ViewerResolution` のどちらにも影響されないテスト
- CPU 側の per-pixel 表示変換が経路から消えたことの確認
  （`raw-pixel-quantisation` lint と、変換点が 1 箇所である担保は維持する）

**非対象**: リードバックそのものの除去（`HIGH-09` の残り＝ゼロコピー表示）。
これは GPU で変換しても残る別の作業で、引受先は未定。

### CM-9 `.ocio` の読み込みと GPU シェーダ抽出

依存: `CM-6`（`ocio-rs` の採否）と `CM-7`（GPU の表示変換経路）。
**`CM-6` のゲートが開くまで着手しない。**

- `.ocio` 設定ファイルをプロジェクトに読み込む
- 入力・作業・表示の各色空間を設定から選ぶ
- `ocio-rs` の GPU シェーダ抽出を wgpu 経路に接続し、3D LUT をテクスチャに
  ベイクする。**LUT の再生成は設定変更時のみ**
- `CM-1` の自前変換は、OCIO 設定が無いときの既定として残す
- **`CacheIdentity` に色管理の同一性を足す。** 入力・作業・表示の色空間と
  `.ocio` の内容が変われば、キャッシュ済みの絵は無効になる。`BLUR-3` の
  `quality` と同じく**等値照合の軸**として載せる（別の色空間で作った絵は
  「粗い版」ではなく別の画）。`.ocio` はファイル全体のハッシュで同一性を
  取る（パスや mtime ではない — 内容が同じなら同じ絵になる）
- `AssetRef` の入力色空間の変更も、その素材に依存するノードを dirty にする

**完了条件**

- `.ocio` 設定ファイルを読み込めるテスト
- 入力/作業/表示カラースペースを設定できるテスト
- ACES / Rec.709 / sRGB / Rec.2020 の変換が既知の値で正確に動作するテスト
- ビューア表示に GPU LUT が適用されるテスト
- LUT が設定変更時にのみ再生成されるテスト
- **表示色空間を切り替えるとキャッシュが無効化されるテスト**
- **`.ocio` の内容が変わるとキャッシュが無効化され、内容が同じなら
  パスが変わってもヒットするテスト**
- **`AssetRef` の入力色空間を変えると、その素材に依存するノードだけが
  再評価されるテスト**
- OCIO 設定が無いプロジェクトが `CM-1` の既定経路で動くテスト

## 検証

- `CM-1` は純粋関数なので単体テストで完結する
- `CM-2` の移行は**往復テスト**で担保する（`Constant` の色は移行後の値を
  リニア → sRGB で戻すと元に一致）。変換できない構成は**「変換されずに
  報告される」ことをテストする**
- `CM-3` / `CM-4` は出口の**等価性**を軸に検証する。「正しい絵」の絶対的な
  基準は持たない

  **等価性の定義**: 4 つの出口（Viewer / PNG / EXR / 動画）は
  **共通の表示色空間（sRGB）へ変換したあとにビット単位で一致する**。
  素の値の一致ではない — EXR はリニアのまま書くので PNG とは数値が違う。
  Viewer / PNG / 動画の 3 つは同じ量子化を通るので素の値でも一致する
- 既存のゴールデンテストは**この計画で意図的に変わる**。`CM-3` の時点で
  更新し、更新の理由をコミットメッセージに残す

## 非対象

- **HDR 出力**（PQ / HLG のディスプレイ出力）。伝達関数は `CM-1` に置くが、
  HDR ディスプレイへの出力経路は別
- **トーンマッピング**。ACEScg を作業空間に選べるようになる `CM-7` の後
- **カラーグレーディングのノード**（リフト/ガンマ/ゲイン、カラーホイール）。
  REQ-MOGRAPH の `FX-1` が担当し、フェーズ F
- **ディスプレイのプロファイル取得**（OS のモニタ ICC）。`CM-8` の後
- **作業空間をプロジェクト単位で切り替えるフラグ**。決定事項のとおり作らない
