# 評価スコープ軸とグラフ内反復 実装計画（REQ-CORE-013）

> **Status**: Planned — 2026-07-27
> **REQ-CORE-013 の「v1 では採用しない」決定を覆す。** 根拠は下記「なぜ今か」。

対象要件: REQ-CORE-013（グラフ内反復）。関連: REQ-CORE-002（Hybrid Pull）、
REQ-CORE-006（キャッシュ）、REQ-CORE-011（ステートフル評価）、
REQ-LAYER-003/007。

**順序**: `stateful-eval-plan.md`（SIM-1）**より前**。理由は下記。

## 問題

### キャッシュは 1 ノードにつき値を 1 つしか持てない

```rust
struct NodeKey {
    path: Vec<PathSegment>,
    node: NodeId,
}

struct CacheEntry {
    frame: u64,
    ctx: EvalContext,
    bypassed: bool,
    value: Arc<dyn NodeData>,
}
```

`frame` / `ctx` / `bypassed` は**キーではなく検証条件**
（`CacheMiss::FrameAdvanced` / `ResolutionChanged` / `FpsChanged` /
`BypassToggled`）。合致しなければ再計算して**上書き**する。

したがって「同一ノードの複数の評価結果を同時に保持する」ことが
構造的にできない。

### それを必要とする機能が 3 つ、すべて計画済み

| 機能 | 必要なこと | 現行キーでの帰結 |
|---|---|---|
| `effects-library-plan.md` FX-5 タイムリマップ | 下流が frame `f` のまま上流を `f'` で評価 | 正しさは検証条件が守るが、`f` と `f'` の要求が**互いを上書きし続けて再計算**する |
| `stateful-eval-plan.md` SIM-3 sim キャッシュ | フレーム連続区間を保持 | 不可能。**同計画は別 map（`sim_cache`）の新設で回避している** |
| 本計画 グラフ内反復 | 同一サブグラフの N 回評価 | 不可能 |

**3 つが同じ制約に別々の回避策で当たっている。** このまま進めると
評価エンジンに互いを知らないキャッシュ機構が 3 つ生える。

### 一方で、正しい軸は既にある

`path: Vec<PathSegment>` は**「同じノードを別スコープで評価する」ための
既存の次元**で、レイヤーネットワークと subnet のネストがこれに乗っている
（REQ-LAYER-003/007）。3 機能が必要としているのはまさにこの軸の拡張。

## なぜ今か

**`stateful-eval-plan.md` の SIM-1 が「今すぐ着手できる」状態にある。**
あの計画は sim キャッシュを別 map で持つと書いてあり、着手すれば
分裂の 1 個目が既成事実になる。3 機構が揃ってからの統合は、
評価エンジンのキャッシュ経路を全面的に再検証する作業になる。

軸を先に決めれば、SIM-3 と FX-5 は同じ仕組みに乗り、反復は
**新しい機構を足さずに**入る。

REQ-CORE-013 が「初期リリースでは採用しない」と判断した理由は
「評価エンジンの静的 DAG 前提を維持する」ことだった。本計画はその前提を
**壊さない** — 反復は動的なグラフ書き換えではなく、静的な DAG を
異なるスコープで複数回 pull するだけ。REQ-LAYER-003 の subnet が既に
やっていることの一般化にすぎない。当時の懸念は解消している。

## 決定事項

### `PathSegment` にスコープ次元を足す

```rust
pub enum PathSegment {
    Layer(CompId, LayerId),
    Subnet(NodeId),
    Comp(CompId),
    /// 反復ノードの i 回目の評価（本計画）。
    Iteration(NodeId, u32),
    /// 時間シフトノード配下の評価（FX-5）。上流を別フレームで
    /// 評価する区間を、シフト元ノードとシフト後フレームで識別する。
    /// **タイムリマップ専用**（下流が `f` のまま上流だけ `f'` = 同時に
    /// 2 つ要る）。モーションブラーは逐次サンプリングなのでこれを使わない
    /// （`motion-blur-plan.md` 参照）。レイヤー殻の `time_remap` も
    /// レイヤー全体が同一時刻になるので不要（`layer-shell-wiring-plan.md`）。
    TimeShift(NodeId, u64),
}
```

- キー空間が自然に分かれるので、**キャッシュ・dirty・無効化の
  既存経路がそのまま効く**。新しい map を作らない。
- 既存の無効化（`drop_scope_owner_caches`）はパス接頭辞で動くので、
  反復ノードや時間シフトノードを dirty にすれば配下の全スコープが落ちる。

### sim キャッシュだけは別扱いを残す

SIM のフレーム連続区間は「N 個の独立した結果」ではなく
「**順序に意味がある系列**」で、`[last+1, t]` の逐次充填という
別のアクセスパターンを持つ。`PathSegment` に `Frame(u64)` を足して
汎用キャッシュに載せると、スクラブのたびに数百エントリが
LRU を汚す。

したがって sim は専用の `SimTrack` を維持する。ただし
**キーは `NodeKey` を共有**し、独自のキー型を作らない。
`stateful-eval-plan.md` はこの点だけ修正する。

### 反復の対象は「要素」ではなく「ピース」

Houdini の for-each には要素単位と piece 単位があるが、
**要素単位（1 ポイントごとに N 回評価）は採用しない**。
10 万ポイントで 10 万回のサブグラフ評価はキャッシュを破壊する。

採用するのは **piece 単位**: 整数属性（既定 `piece`）の値ごとに
ジオメトリを分割し、値の種類数だけ評価する。分割数は
`max_iterations` で上限を切り、超過は評価エラー（黙って切らない）。

要素ごとの変調は従来どおり属性 + フィールドで行う。反復は
「属性では書けない構造的な操作を、部分集合ごとに適用する」ためのもの。

### 反復は 1 段。ネスト不可

`stateful-eval-plan.md` が sim の多段を禁じているのと同じ理由。
`PathSegment::Iteration` が 2 つ以上積まれたら評価エラー。

### 要素スコープ（group 相当）は属性規約とする

Houdini の group に相当する専用の型は導入しない。**Bool 属性を
group として扱う**（Houdini 自身の内部表現と同じ）。

ジオメトリドメインの op は `group` 文字列パラメータを取る規約にする。

- 空文字列 = 全要素（既定、後方互換）
- 属性名 = その Bool 属性が true の要素のみに作用
- 対象外の要素は**入力の値をそのまま通す**（削除しない）

`field.apply` の `amount` は soft な重み付けとして残り、`group` は
hard な適用可否として直交する。両方指定した場合は
「group 内の要素にのみ `amount` を適用」。

**この規約を先に決めるのが目的**で、group を作る / 合成する専用
ノードと UI は本計画の対象外。当面は `attribute.set` で Bool 列を
作れば足りる。

## 目標構成

```text
                        ┌─ Iteration(node, 0) ─→ 部分ジオメトリ 0 ─┐
geometry ─→ iterate ────┼─ Iteration(node, 1) ─→ 部分ジオメトリ 1 ─┼─→ merge ─→ Geometry
              │         └─ Iteration(node, n) ─→ 部分ジオメトリ n ─┘
              └── 内部ネットワーク（net.in / net.out、subnet と同型）
```

`subnet` の評価経路をそのまま使い、`path` に `Iteration(node, i)` を
積んで i 回 pull する。内部ネットワークは `net.in` から
「そのピースのジオメトリ」と「反復インデックス」を受け取る。

## 実装単位

### 単位 1 ✅: `PathSegment` のスコープ次元（挙動不変）

- `Iteration` / `TimeShift` バリアントを追加。
- 既存の `match` を網羅（コンパイルエラーで漏れが出る）。
- 無効化経路がパス接頭辞で新バリアントを含めて落とすことの確認。
- **この単位では新バリアントを誰も生成しない。** 純粋な準備。

**完了条件**

- 既存の評価・キャッシュ・無効化テストが無改変で通る。
- 新バリアントを含むパスで `NodeKey` が別エントリになるユニットテスト。
- パス接頭辞での無効化が新バリアント配下も落とすテスト。

### 単位 2: 時間シフト経路（FX-5 の土台）

- `EvalContext.frame` を差し替えて上流を pull するヘルパ。
  `path` に `TimeShift(node, f')` を積む。
- 同一グラフを `f` と `f'` の両方で保持できることの検証。

**完了条件**

- 同一上流ノードを `f` と `f'` で評価し、**両方がキャッシュに残る**
  テスト（現行キーでは不可能だったことの回帰）。
- `f` 側の pull が `f'` 側のエントリを壊さないテスト。
- 時間シフトノードを dirty にすると配下の全スコープが落ちるテスト。

`effects-library-plan.md` の FX-5 はこの上に載る。

### 単位 3: `geometry.iterate` ノード

- piece 分割（整数属性の値ごと）。`max_iterations` 上限と超過エラー。
- 内部ネットワーク（`net.in` / `net.out`）。`subnet` の実装を流用。
- `net.in` が「ピースのジオメトリ」と「反復インデックス」を出す。
- 結果の結合は `geometry.merge` と同じ規則（属性列の和集合、
  型衝突はエラー）。
- ネスト検出 → 評価エラー。

**完了条件**

- piece 属性 3 値のジオメトリで内部ネットワークが 3 回評価される
  テスト。
- ピースごとに異なる結果が出るテスト（反復インデックスが効くこと）。
- 結合結果の要素数が各ピースの総和に一致するテスト。
- `max_iterations` 超過が**エラーになる**テスト（切り捨てない）。
- ネストが評価エラーになるテスト。
- 同一入力で 2 回評価して同一結果（決定性）テスト。
- 上流編集で全反復スコープが落ちるテスト。

### 単位 4: 要素スコープ規約の適用

- `group` パラメータを既存のジオメトリ op に追加:
  `field.apply` / `attribute.set` / `attribute.promote` /
  `geometry.transform`。
- 空文字列 = 全要素。対象外要素は入力値を通す。
- registry テンプレートとロケール。

**完了条件**

- `group` 未指定で既存テストが無改変で通る（後方互換）。
- group 内のみ変化し、group 外が**バイト等価で不変**であるテスト。
- 存在しない group 名 / Bool でない属性の扱いのテスト
  （エラーではなく「全要素」にフォールバックし警告）。

### 単位 5: 文書更新

- `docs/requirements/REQ-CORE.md`: REQ-CORE-013 の「採用しない」を
  撤回し、優先度と受入条件を書き直す。**撤回の理由を残す。**
- `docs/specifications/procedural-geometry.md`: 「グラフ内反復」節を
  書き換え、要素スコープ規約と標準属性 `piece` を追記。
- `docs/implementation/stateful-eval-plan.md`: `SimTrack` が
  `NodeKey` を共有する旨に修正。
- `docs/implementation/effects-library-plan.md`: FX-5 が単位 2 に
  載る旨に修正。
- `docs/implementation/backlog.md` / `README.md`。

## 検証

- 単位 1 は挙動不変。**既存テストの無改変通過が唯一の完了条件**。
- 単位 2 の「両方がキャッシュに残る」テストが本計画の核心。
  これが通れば 3 機能の共通土台ができている。
- 反復は決定性テストを必ず入れる。ピースの分割順が
  `HashMap` の反復順に依存しないこと（属性値でソートする）。
- パフォーマンス: `max_iterations` の既定値を決めるため、
  ピース 10 / 100 / 1000 で 1 評価の時間を測り `perf-baseline.md` に記録。

## 非対象

- **要素単位の反復**。piece 単位のみ。
- **反復のネスト**。1 段。
- **`while` 相当の条件反復 / 収束ループ**。回数は入力から静的に決まる。
- **group の作成・合成ノードと UI**。規約だけ決め、当面は
  `attribute.set` で Bool 列を作る。
- **動的なグラフ書き換え**。静的 DAG を複数スコープで pull するだけで、
  ノードの生成・削除は行わない。
- **sim キャッシュの汎用キャッシュへの統合**。アクセスパターンが違うので
  `SimTrack` は残す（キー型のみ共有）。
