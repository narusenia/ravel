# 公開パラメータ宣言 実装計画（REQ-PROJ-006）

> **Status**: In progress — 2026-08-03（`EXPO-1` 済み #294）

対象要件: REQ-PROJ-006（公開パラメータ宣言）。
関連: REQ-RENDER-005、REQ-PLUGIN-002、REQ-PLUGIN-004、REQ-PLUGIN-005、
REQ-GPU-003、REQ-LAYER-002、REQ-LAYER-003。
前提計画: `network-interface-editing-plan.md`。

## 問題

**同じものを 4 回設計しかけていた。**

| 用途 | 要件 | 必要なもの |
|---|---|---|
| CLI のテンプレート入力（`--param 名前=値`） | REQ-RENDER-005 | 名前・型・既定値の宣言 + 内部パラメータへの束縛 |
| サブグラフテンプレートの公開パラメータ（HDA / Gizmo 相当） | REQ-PLUGIN-005 | 同じ |
| ネットワークインターフェース（`net.in` / `net.out`） | REQ-LAYER-002 / -003 | 同じ |
| シェーダノードの入出力とユニフォーム宣言 | REQ-GPU-003、REQ-PLUGIN-002 | 同じ |

4 つ目は既に要件として存在していた（REQ-GPU-003「入出力テクスチャと
ユニフォームパラメータを宣言的に定義」）。3 つ目は評価側が完成済みで
編集手段が無い（`network-interface-editing-plan.md`）。

**1 つの機構として切り出さないと、4 回実装して 4 回別の仕様になる。**

## 決定事項（2026-08-03 設計セッション）

### 宣言は「名前による契約」で、パスによる参照ではない

CLI が `--param Title.headline=...` のようにレイヤー名やノードパスで指定する形は
採らない。レイヤーを改名すれば壊れ、ネットワークの内部構造がそのまま外部契約に
なってしまう。

宣言側が名前・型・既定値・説明を持ち、束縛先を内部に隠す。**改名・再配線で
外部契約が壊れないこと**が受入条件になる。

### `network-interface-editing-plan.md` が先に来る

評価側は完成している（`net.in` がカスタム出力ポートを評価し、`subnet` が
外側ピンを内部 In に名前で束縛して再帰評価する）。だが**ポートを生やす経路が
無い**。`NETIF-1`〜`7` がそれを作る。

本計画はその上に「宣言の層」を載せる。順序を逆にすると、ポートモデルが
無い状態で宣言の束縛先を設計することになり、二度手間になる。

**`NETIF-1`〜`5` は完了済み**（2026-08-03 時点）。ポートの追加・削除・改名・
型変更・並び替えと Subnet のピン同期が入ったので、`EXPO-1` の前提は満ちている。
残るのは `NETIF-6`（Collapse / Extract）で、これは `EXPO-6` の前提。

### 値の範囲は定数 + 素材参照に限る

`ParameterValue` は `Float` / `Int` / `Bool` / `String` / `Channel1〜4` /
`PathPoints` / `Curve`（`graph.rs:138-162`）。このうち外部契約に出すのは
**定数として解釈できるもの**だけにする。

- 数値・ベクトル・色・bool・文字列 → 対象
- 素材参照（メディアファイル）→ 対象。**ただし `ParameterValue` に
  メディア参照のバリアントが無い**ので、束縛先はメディアノードのアセット参照とし、
  宣言側の型として別に持つ
- `Channel1〜4` の**チャネル丸ごと**（キーフレーム・式）→ 非対象
- `PathPoints` / `Curve` → 非対象

理由は互換性。外部から渡す形式が `.ravprj` の内部表現に寄ると、内部表現を
変えるたびに CLI の引数形式が壊れる。

### 宣言は既定値を与える位置に立つ

宣言された入力は、統一アニメーションチャネル（REQ-CORE-007）の値ソースを
**置き換えない**。定数ソースの値を差し替える位置に立つ。これにより
「テンプレートで文字を差し替えたらキーフレームが消えた」が起きない。

## 目標構成

```text
宣言（名前・型・既定値・説明）
   │  束縛
   ▼
内部パラメータ（ノードのパラメータ / メディアノードのアセット参照）

利用者:
  REQ-RENDER-005   CLI --param 名前=値          （プロジェクト単位の宣言）
  REQ-PLUGIN-005   サブグラフテンプレート        （サブグラフ単位の宣言）
  REQ-LAYER-002/3  net.in / net.out             （ネットワーク単位の宣言）
  REQ-PLUGIN-002   シェーダ manifest            （プラグイン単位の宣言）
```

## 実装単位

| ID | 単位 | 依存 |

### EXPO-1 宣言の型と永続化

- 宣言は名前（一意）・型・既定値・説明・束縛先を持つ
- **`.ravprj` のフォーマットバージョンを上げる。** 旧ファイルは
  「宣言ゼロ」として読み、往復する
- 名前の一意性と、型と既定値の整合を不変条件として検証する

**完了条件**

- 宣言を持つプロジェクトが保存・読み込みで往復するテスト
- 旧バージョンの `.ravprj` が宣言ゼロで読めるテスト
- 名前の重複が拒否されるテスト
- 既定値の型が宣言の型と一致しない場合に拒否されるテスト
- `docs/dev/` の永続化変更手順（`.ravprj` フォーマット）を更新

### EXPO-2 束縛の解決と適用

- 束縛先を「ノード ID + パラメータキー」で持つ。**ノード ID なので
  ノードの改名・再配線に強い**
- **ただしパラメータキー自体の改名には追従が必要。**
  `network-interface-editing-plan.md` の「改名は 4 箇所を 1 つの操作で書き換える」
  （In のカスタムポート名がポート名・同名パラメータのキー・Properties の
  `custom.<name>`・subnet の promote 名を兼ねている）に**宣言の束縛を 5 番目として
  加える**。部分適用を作らない
- 束縛先が消えた宣言の扱いを決める（宣言は残し、解決不能として報告）
- 与えられた値を適用して `Document` を作る経路。**評価前に一度だけ**行い、
  評価中に宣言を解決しない（キャッシュの同一性に宣言が混ざらないため）

**完了条件**

- 宣言に値を与えると束縛先のパラメータが変わるテスト
- **束縛先ノードを改名しても宣言が生き続ける**テスト
- 束縛先を再配線しても宣言が生き続けるテスト
- 束縛先が削除された宣言が解決不能として報告され、評価が落ちないテスト
- 型不一致の値が適用前に拒否されるテスト
- 定数ソース以外（キーフレーム・式）が束縛先の場合の挙動が定義されている

**実装で判明したこと・決めたこと**（`ravel_core::exposed::apply`）

- **定数ソース以外は成分単位で据え置く。** 値ソースを差し替えず、
  `ChannelSource::Constant` の値だけを書き換える。キーフレーム・式・
  `NodeOutput` の成分は元のまま残り、`BindingIssueReason::AnimatedComponents`
  として報告する。`Vec2` の `x` がキーフレーム、`y` が定数なら `y` だけ入り、
  **入らなかった `x` も `Applied::issues` に出る**（部分適用も必ず報告する。
  黙って書くと `ExposedListing` の `resolved` が `true` になり、機械可読な
  契約が嘘をつく）。「テンプレートで文字を差し替えたらキーフレームが消えた」を
  防ぐのが目的
- **既定値は適用しない。** `apply` は与えられた名前だけ書く。全宣言の既定値を
  書くと「公開した時点の値で凍る」ことになり、以後の GUI 編集が
  レンダのたびに巻き戻る。既定値は列挙（`EXPO-3`）で読ませる値
- **改名の追従が要るのは 1 箇所だけ。** 永続状態としてパラメータキーを
  書き換えるのは `Graph::rename_port` の経路のみ
  （`network-interface-editing-plan.md` の実測表）。`rename_custom_port` が
  `PortEdit`（グラフ + `KeyRename`）を返し、Document コミットが
  `follow_key_rename` を同じスナップショットで適用する
- **束縛先の探索は文書全体。** ノード ID は文書全域で一意（REQ-LAYER-009）
  なので、フラットグラフ・各レイヤーネットワーク・任意深さの subnet を辿る。
  書き込みは 1 パスにまとめてある（`composition::graph_walk` を再利用）

### EXPO-3 宣言の機械可読な列挙

REQ-RENDER-005 の「宣言の一覧を機械可読形式で取得できる」を満たす。

- 名前・型・既定値・説明を列挙する API
- GUI を起動せずに読める層に置く（`render-export-plan.md` の単位 0 で
  抽出する永続化クレート）

**完了条件**

- 宣言一覧が機械可読形式で出るテスト
- GUI 非依存クレートから呼べること（`ravel-app` に依存しない）

**実装で判明したこと・決めたこと**（`ravel_core::exposed::listing`）

- **列挙は永続形式ではない。** 束縛（ノード ID + キー）を落とし、値を
  Rust の enum 表現ではなくネイティブに書く（`float` は数値、`vec3` は
  3 要素配列、`media` はパス文字列）。型名は `ExposedType` の `Display`
  （`"float"` / `"vec2"` / `"media"`）＝ コマンドラインで打つ綴り。
  永続形式をそのまま出すと、内部表現を変えるたびに CLI の契約が壊れる
- **解決不能な宣言も列挙し、`resolved: false` を付ける。** 隠すと
  「そんな名前は無い」と「その名前の裏側が壊れている」を呼び出し側が
  区別できない
- 置き場所は `ravel-core`。`ravel-project` が `gpui` に依存せず
  `.ravprj` を読めるので、アーカイブ → `Document` → 列挙 → JSON が
  GUI 非依存経路になる（テストは `ravel-project` 側にある）

### EXPO-4 素材参照の宣言と差し替え

- 宣言の型としてメディア参照を持つ
- 束縛先はメディアノードのアセット参照
- 解決は REQ-PROJ-005 の変数・相対パス規約に従う
- **不在の素材は明示的な失敗**にする（黙って空フレームにしない）

**完了条件**

- 素材を差し替えて評価結果が変わるテスト
- 不在の素材が明示的な失敗になるテスト
- 相対パス・変数を含む参照が解決されるテスト
- 差し替えた素材の寸法・尺が元と違う場合の挙動が定義されている

**実装で判明したこと・決めたこと**（`ravel_core::exposed::apply` の Media 経路）

- **差し替えは参照の置換だけ。寸法・尺の違いは補正しない。** コンポの解像度・
  尺、レイヤーの in/out・トランスフォームは一切変えない。渡したファイル次第で
  レイアウトが変わるならテンプレートではない。新素材の終端より後ろのフレームは、
  そのネットワークにおける通常の範囲外読み出しと同じ挙動
- **アセット ID は宣言名から決定的に導く**（`exposed:<宣言名>`）。同じ値を
  2 回適用しても同じ文書になる（冪等）。差し替え前のエントリは**残す** —
  他のノードやレイヤーの `AudioSource` が参照している可能性があり、
  apply は GC ではない
- **導出 ID が既存エントリと衝突したら適用前に拒否する**（`AssetIdTaken`）。
  例外は「束縛先ノードが既にその ID を指している」場合＝同一宣言の再適用のみ。
  無条件に上書きすると、その ID を読む別ノードや `AudioSource` の素材まで
  一緒に差し替わる
- **メタデータは取らない。** 幅・高さ・尺はデコーダが要るが `ravel-core` に
  無いので、登録するエントリは空メタデータ + 拡張子から推定した `AssetKind`。
  同じ理由で**連番画像シーケンスは宣言できない**（`AssetKind::Sequence` の
  prefix/padding/範囲は import の probe しか知らない）
- **不在の素材は `apply` を失敗させる**（`MediaNotFound`）。解決自体が
  できない場合（未保存プロジェクトの相対パス、未知の `${VAR}`）は
  `MediaUnresolved` と区別する。どちらも書き込み前に判定する
- **束縛先はメディアノードの `asset_id` に限る。** それ以外は報告して書かない
  （ノード違いは `NotAMediaNode`、キー違いは `NotAnAssetReference`）。
  「String である」ことと「資産参照である」ことは別で、メディアノードの
  別の文字列パラメータに書くと、プロセッサが読む参照は変わらないまま
  そのパラメータだけ壊れ、しかも成功として報告されてしまう
- `apply` は素材解決の文脈（プロジェクトルート + 変数表）を引数に取る
  （`AssetContext`）。メディア宣言が無ければ `AssetContext::default()`

## 検証

- EXPO-1〜4、6 はヘッドレス
- EXPO-5 は実機
- **改名・再配線に対する頑健性が本計画の要点。** EXPO-2 の 2 つのテスト
  （改名・再配線）が通らなければ、パス参照と同じ脆さを持つことになる

## 非対象

- **キーフレーム・カーブ・パス形状の丸ごと差し替え**。内部表現を外部契約に
  露出させるため。必要になったら別要件
- **宣言のグループ化・階層化**。v1 はフラットなリスト
- **宣言の型に対する範囲制約（min / max / ステップ）**。Properties の
  パラメータエディタが持つ情報と重複するので、そちらとの統合を別途決める
- **プラグイン manifest の実装**（REQ-PLUGIN-004）。`plugin-system-plan.md`
- **CLI そのもの**。`render-export-plan.md`
