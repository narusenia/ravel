## 着手順（提案）

**この順は roadmap を置き換えない。** 上記の項目に限った並びで、
根拠は「リリースを塞ぐか」「他の修正に相乗りできるか」の 2 つ。

### 1. `HIGH-29`（Windows のメニュー）

**唯一のリリース阻害。** 他の何とも依存が無く、単独で着手できる。
Windows 実機での確認が要るので、実機を触れるときに回す。

### 2. `HIGH-28` + `LOW-APP-07` + `MED-APP-30` をまとめて

**3 つとも「保留中のコミットを、それを運ぶ入れ物ごと捨てている」**という
同じ欠陥。別々に直すと同じ穴が残る側が出る。

- `HIGH-28` — スクラブの `Commit`
- `LOW-APP-07` — デバウンスされた色のコミット
- `MED-APP-30` — 同じ再構築経路が毎マウス移動で走る

`MED-APP-30` は着手前に「バンドが毎 move で選択を公開しているか」を
確かめること（起票時に特定できていない）。

### 3. `HIGH-27`（Subnet のキーフレーム）

**`MED-APP-25` を先に直すか同時に直す。** `MED-APP-25`（Subnet のコピペが
内部 `NodeId` を複製しない）が残っていると、行を bare `NodeId` で
アドレスする前提が崩れる。理由は `HIGH-27` の個票に書いた。

### 4. 残りの medium / low

`MED-APP-26` は分岐 1 つ、`MED-APP-27` は位置を渡すだけで、どちらも小さい。
`MED-APP-29` は `NETIF-2` の型の文脈依存に乗るので、そこを読んでから。

## 設計ゲートの 3 件について

計画書は書けている（`backlog.md` に単位も登録済み）。着手可能なのは
`DISK-1` / `AID-1` / `PGRP-1` / `PGRP-5`。

**フォーマット版は逐次採番**と決めた。3 件（+ `CM-2`）が `v8` を取り合うので、
