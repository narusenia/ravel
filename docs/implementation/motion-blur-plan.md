# モーションブラー実装計画（REQ-RENDER-004）

> **Status**: Planned — 2026-07-27
> **REQ-RENDER-004 を新設する。** 従来この機能は要件にも仕様にも存在しなかった。

対象: レイヤー単位のモーションブラー。関連: REQ-CORE-002（Hybrid Pull）、
REQ-CORE-006（キャッシュ）、REQ-CORE-007（アニメーションチャネル）、
REQ-CORE-009。

## 問題

モーショングラフィックスの標準機能でありながら、**コードにも要件にも
一言も存在しない**。高速に動く要素がストロボ状に見える。

実装しようとすると、評価エンジン側に 3 つの障害がある。すべてコードで確認済み。

### 1. キーフレームが整数フレームでしか評価できない

`AnimationChannel::evaluate(frame: u64, ctx)` → `KeyframeCurve::sample(frame: u64)`
（`animation/channel.rs:86,126`）。

`EvalContext` は `frame: u64` と `time: f64` を**両方持っており**、
`media.rs:154` は既に `ctx.time`（連続時間）を読んでいる。したがって
サブフレーム評価すると**動画素材は正しく再サンプルされるが、キーフレームで
動かした Transform やシェイプパラメータは N 個の同一サンプルになる**。
一番ブラーが要るものに効かない。

### 2. キャッシュ有効性が整数フレームを見ている

```rust
Some(entry) if time_dependent && entry.frame != ctx.frame => CacheMiss::FrameAdvanced
```
（`eval.rs:1028`）

`ctx.time` だけ振って `ctx.frame` を据え置くと、2 サンプル目以降が
**すべてキャッシュヒット**する。**「実装したのにブレない」形で静かに壊れる。**

### 3. 品質段階の概念が無い

16 サンプルではスクラブが実用にならず、2 サンプルでは書き出しが汚い。
Viewer は既に長辺 1024 へ縮小して評価しているが（`project_state.rs:51`
`viewer_resolution`）、これはハードコードでモデル化されていない。

## 決定事項（2026-07-27 設計セッション）

### 2 つのモードを持ち、v1 は `Sampled` のみ実装する

```rust
pub enum MotionBlurMode {
    /// シャッター区間を N 分割して評価し積算する。正確。
    Sampled { samples: u32 },
    /// 要素の速度から方向性のあるにじみを作る。安いが回転ブラーは近似。
    Velocity { scale: f32 },   // v1 では未実装
}
```

ユーザーが明示的にモードを選ぶ形にする。「プレビューは速度ベース、
書き出しはサンプル」と**システムが黙って差し替える**設計は採らない。
プレビューと書き出しが違う絵になる問題を、モード選択の明示性で回避する。

### レイヤー単位でサンプルする

殻の合成チェーン（`compile.rs`: 時間変換 → Transform → Opacity → Merge）に
synthetic な `comp.motion_blur` を 1 段挟む。`adjustment` が
`comp.merge.adjustment` として実装済みなのと同じ形。

コンポジション全体を N 回評価する方式は採らない。mograph のコンプは
「動く前景 + 静止した重い背景」が普通で、全体方式だと背景も N 倍払う。

`layer.ref` 越しの参照はブレない。AE と同じ挙動で、必要ならプリコンプで回避する。

### ネットワーク全体をサンプルする（殻の Transform だけではない）

理由が 2 つある。

1. **主要ユースケースが殻だけでは成立しない。** リリックモーションの
   文字アニメーションは `text.layout` の per-char 属性を `field.time` で
   駆動する = **レイヤーネットワークの内部**で起きる。殻の Transform は
   静止したままなので、殻だけサンプルすると「文字が高速に飛び込むのに
   ブレない」ことになる。
2. **コストが N 倍にならない。** 評価器は既にノード単位で時変性を判定して
   おり（`eval.rs:992` の `is_time_dependent() || node_has_animated_params(..)`）、
   時不変ノードはフレームを跨いでキャッシュから返る。したがって N 倍払うのは
   **時変サブグラフだけ**で、フォント輪郭・静止シェイプ・読み込み済み画像は
   1 回で済む。この最適化のために新規に書くものは無い。

### 評価スコープ軸（`PathSegment`）は使わない

ブラーのサンプリングは**逐次**（t0 で評価 → 積算 → t1 で評価 → 積算）で、
同一ノードの複数結果を*同時に*保持する必要がない。`ctx` を振るだけでよい。

`evaluation-scope-plan.md` の `PathSegment::TimeShift` は
**タイムリマップ専用**（下流が `f` のまま上流を `f'` で評価する = 同時に
2 つ要る）。両者は別物なので混同しない。

### サンプル分布は一様。ジッタは入れない

確率的ジッタはバンディングを減らすがノイズを持ち込み、**決定性を壊す**。
本リポジトリは決定性を強く要求しており（乱数は `seed` + `id` ハッシュのみ、
`Date` / 乱数グローバル禁止）、ゴールデンテストもそれに依存している。
一様サンプルのバンディングはサンプル数で対処する。

### 積算は 32bit float リニアでの単純平均

内部処理が常に 32bit float リニア（REQ-CORE-009）なので、
ガンマを意識せず平均してよい。

### パーティクルは v1 でブレない

sim はサブフレーム状態を持たないため、N 回評価しても同じ値が返る。
`Velocity` モード（`velocity` 属性が予約済み）を後から足すときに解決する。
**v1 ではその旨をドキュメントに明記する**（黙って効かないのを避ける）。

## 実装単位

### 単位 1 ✅: アニメーションチャネルの連続時間化

**モーションブラー以外にも効く前提工事。**

- `KeyframeCurve::sample(f64)`、`AnimationChannel::evaluate(frame: f64, ctx)`。
  キーフレーム自体は整数フレームに置いたまま、**サンプリングだけ連続**にする。
  引数の単位は**秒ではなく小数フレーム**。`KeyframeCurve` は fps を持たず、
  キーフレームはフレームに固定されているため。連続コンプフレームは
  `EvalContext::sample_frame()`（整数 `frame` + `time` 由来のサブフレーム
  差分。オングリッド時は `frame` にビット一致）、レイヤーローカル化は
  `Layer::local_frame_continuous` で得る。整数版 `Layer::local_frame` は
  キーフレームの表示・書き込み用に残す。
- 補間はもともと連続の数学なので、変更は主にシグネチャと境界処理
  （`Interpolation::Step` の半開区間の扱いを明示する）。
- 呼び出し元（`eval.rs` のパラメータ解決、カーブエディタ、Properties）を移行。

副次的な効果:

- `per-instance-modulation-plan.md` が「`sample` が `u64` しか取らず量子化
  される」ことを理由に採った時間オフセットの回避設計が不要になる。
- FX-5 のタイムリマップが整数フレームに丸めずに済む。
- 24fps コンプに 30fps 素材を載せたときの補間が正しくなる。

**完了条件**

- 整数フレームでの評価結果が移行前と**ビット等価**（既存テスト無改変）。
- 分数フレームでリニア / ベジェ補間が期待値を返すテスト。
- `Step` 補間の境界（キー上と直前直後）のテスト。

### 単位 2: キャッシュ有効性を `time` 基準へ

- `eval.rs:1028` の判定を `entry.ctx.time != ctx.time` に変更。
  `frame` はキーフレーム参照と UI 用の整数インデックスとして残す。

**完了条件**

- **同一 `frame`・異なる `time` で再評価されるテスト**（本計画で最も
  重要な回帰テスト。これが無いと「実装したのにブレない」に気づけない）。
- 同一 `time` の再要求がキャッシュヒットするテスト。
- 既存のフレーム送りキャッシュ挙動が変わらないテスト。

### 単位 3: 品質段階（`EvalContext.quality`）

- `Quality { Preview, Final }` を `EvalContext` に追加。
- キャッシュ有効性に参加させる（`resolution` / `fps` と同じパターン。
  `CacheMiss::QualityChanged` を追加）。
- Viewer は `Preview`、書き出しは `Final` を要求する。
- 既存のハードコード 1024 縮小（`viewer_resolution`）をこの概念に吸収する。

**完了条件**

- 品質切替でキャッシュが無効化されるテスト。
- Viewer が `Preview`、レンダーワーカーが `Final` を要求するテスト。
- 既存の `viewer_resolution` テストが等価な形で通る。

### 単位 4: `comp.motion_blur` と殻フィールド

- `Layer` 殻に `motion_blur: Option<MotionBlurMode>`。永続化とマイグレーション。
- Composition に `shutter_angle`（既定 180°）と `shutter_phase`、
  `motion_blur_samples`（Final 時のサンプル数）。Preview のサンプル数は
  別値（既定 2）。
- `compile.rs` が殻フィールドから `comp.motion_blur` を挿入。
- プロセッサ: シャッター区間 `[t - angle/720/fps + phase, t + angle/720/fps + phase]`
  を N 分割し、上流を各時刻で評価して平均。

**完了条件**

- コンパイルトポロジのスナップショットテスト。
- 等速直線運動する矩形が期待どおりの範囲ににじむゴールデンテスト。
- **回転する図形が回転方向にブレる**ゴールデンテスト（`Velocity` モードでは
  出せない絵で、`Sampled` を選んだ理由の検証）。
- **ネットワーク内部で動く要素（`field.time` 駆動）がブレる**ゴールデン
  テスト。単位の目的そのもの。
- `samples = 1` で無効時と一致するテスト。
- 時不変サブグラフが 1 回しか評価されないことを `timings` で検証するテスト。

## 検証

- ゴールデンテストは CPU 経路。GPU 不要。
- **単位 2 の回帰テストを最優先**。これが無いと機能が沈黙して壊れる。
- パフォーマンス: `samples = 8` のコンプで、時変ノード数に比例した評価
  回数になっていることを `timings` で確認し `perf-baseline.md` に記録。

## 非対象

- **`Velocity` モードの実装**。モードの型は v1 で定義するが実装は後。
- **パーティクルのブラー**。`Velocity` モードとセット。
- **コンポジション全体のブラー**。レイヤー単位のみ。
- **3D モーションブラー**、シャッター形状（ボックス以外）、
  適応サンプリング。
- **ジッタ / 確率的サンプリング**。決定性を優先する。
