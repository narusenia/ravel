# パーティクル実装計画（REQ-MOGRAPH-002）

> **Status**: Planned — 2026-07-27

対象要件: REQ-MOGRAPH-002（優先度 Should）。関連: REQ-CORE-010（属性）、
REQ-CORE-011（ステートフル評価）、REQ-CORE-012（フィールド）、
REQ-GPU-001。

**前提**:
- `done/stateful-eval-plan.md`（REQ-CORE-011）— sim キャッシュが無いと成立しない。
- `done/per-instance-modulation-plan.md` — フォースはフィールドとして接続する。

## 問題

パーティクルは**属性付きポイントジオメトリのフレーム逐次シミュレーション**
として実装する（要件 v2 の決定。v1 の「2D フレームバッファ上の処理」制約は
REQ-MOGRAPH-004 のジオメトリ相互作用と両立しないため撤回済み）。

現状、ポイントジオメトリの器（`Geometry` の Point ドメイン、`age` / `life` /
`velocity` / `id` の予約属性名）とポイントスプライト描画
（`rasterize/mod.rs` の `pscale` / `Cd` / `alpha` 対応）は既にあるが、
**時間発展させる機構が無い**。

## 決定事項

### パーティクルノードは 1 つ。エミッタとフォースは入力

Houdini の POP ネットワークのようなサブネットは作らない。

```text
emitter geometry ─→ ┐
                    ├─→ particle.simulate ─→ Geometry (points) ─→ rasterize
force fields ──────→ ┘
```

`particle.simulate` が唯一のステートフルノードで、
`StatefulProcessor` を実装する。これで spec の「多段接続は 1 段に制限」に
自然に収まる。

### エミッタは形状ではなく「任意ジオメトリ」に一本化

要件は「ポイント/ライン/エリア/任意ジオメトリ」を挙げるが、
ポイント・ライン・エリアは既存の `shape.*` + `scatter.scatter` で作れる。
`particle.simulate` の emitter 入力は **`Geometry` を取るだけ**にし、
発生位置はそのポイント/インスタンス位置からサンプルする。

テキスト変換ジオメトリ（`text.to_path`）をそのまま挿せるのが要点で、
受入条件「エミッタ形状を選択できる」はこれで満たす。

### フォースはフィールド入力の可変ポート群

重力・アトラクタ・ドラッグ・ノイズ・タービュランスを個別ノードにしない。
`field.*`（既存 9 種 + 変調計画の 3 種）を可変入力グループに繋ぎ、
各フィールドを**加速度のスカラー場**として解釈する。

ベクタ方向は「フィールド値 × 方向パラメータ」で与える。
フィールドがスカラー場である設計（変調計画の決定事項）を崩さない。

重力のような一様な力は `field.constant` + 方向パラメータで表現できる。

### 描画は既存のポイントスプライト経路を使う

`pscale` / `Cd` / `alpha` は既にラスタライザが読む。
専用の描画ノードは作らない。

### CPU で始め、GPU 経路を単位 6 として明示的に持つ

パーティクルは REQ-MOGRAPH 群のなかで **GPU が本当に効く唯一の場所**。
理由は他のジオメトリノードと性質が違うため。

| | 他のジオメトリノード | パーティクル |
|---|---|---|
| 評価頻度 | キャッシュが効き、変更時のみ | **毎フレーム必ず step** |
| キャッシュ | 温キャッシュで 0.007 ms | sim なので飛ばせない |
| 要素数 | 数百〜数千 | **10 万点以上を狙う** |

ただし v1 は **CPU（rayon）で実装する**。理由は 2 つ。

1. `procedural-geometry.md` の GPU 方針が「v1 は CPU SoA」と決めており、
   フィールドの WGSL 評価は REQ-GPU-003 の将来拡張とされている。
2. GPU シミュレーションは `gpu-resident-geometry-plan.md`（GPU 常駐
   ジオメトリ）を前提にする。それが無いと毎フレーム読み戻しになり、
   GPU を使う意味が消える。

単位 1〜5 を CPU で完成させ、`gpu-resident-geometry-plan.md` が
「実施」判断になった後に単位 6 を足す。**CPU 経路は参照実装として残す**
（`rasterize` の先例と同じ）。

#### 測定（2026-07-29）が示したこと: 律速は step ではなく描画

`perf-baseline.md`「パーティクルの CPU / GPU 判断」。`particle.simulate` の
代用として、同じ属性列に対する明示 Euler ステップを毎フレーム回した。

| 点数 | step のみ（rayon） | 描画の `flatten` + `upload` |
|---|---|---|
| 10 万 | **0.16〜0.27 ms** | 2.29 + 0.99 = 3.28 ms |
| 100 万 | 1.19〜1.57 ms | 19.10 + 8.11 = 27.2 ms |

**CPU ステップは 10 万点で 60fps 予算の 1〜2%。** 上表の「10 万点以上を狙う」は
CPU で成立する。よって:

- **v1 を CPU（rayon）で作る方針は実測で裏付けられた。**
- **単位 6 の根拠はステップの高速化ではない。** 完了条件の「10 万点で step が
  16.6 ms を大きく下回る」は CPU が既に満たしている。GPU sim の価値は
  状態を VRAM 常駐にして**描画側の CPU 展開とアップロードを消す**ことで、
  それは `gpu-resident-geometry-plan.md` の単位 1 と単位 5 が担う。
- GPU 常駐状態の読み戻しは 10 万点で **≈1.35 ms**（submit + map の固定
  レイテンシ律速。unified memory）。100 万点＝16 MB では ≈2.0 ms で
  サイズにも効き始める。下の「スクラブ中は CPU / 再生中は GPU」は
  帯域面では成立する。

**したがって単位 6 の位置づけを変える**: 「10 万点を出すために必要な単位」
ではなく、「`GpuGeometry` が入った後に、CPU 参照実装と一致させながら
sim を GPU へ移す単位」。10 万点の実用性は単位 1〜5 で足りる。

### sim キャッシュと VRAM の衝突（決着: 2026-11-10、チェックポイント）

`procedural-geometry.md` は sim キャッシュを**RAM に保持し、単一のバイト
予算の中に保護枠を持つ**と決めている（`cache-plan.md`）。GPU
シミュレーションだと状態は VRAM 常駐になり、
300 フレーム巻き戻すために GPU バッファ 300 本を保持することになる。
10 万点 × 6 属性 × 4 byte × 300 フレーム ≈ **720 MB**。現実的でない。

**決定: キーフレーム化（チェックポイント）。** SIM が既に持つ機構を
そのまま使う。`SimTrack` は予算を超えると保持フレームを `stride` ごとの
疎なチェックポイントへ間引き、間のフレームは最寄りのチェックポイントから
`step` し直す（`done/stateful-eval-plan.md` の追補）。GPU の状態も同じ規則で
保持し、課金先を VRAM 側（`VramAllowance`）にするだけで、間引きと再 step の
論理は CPU と共有する。

- **採らない: RAM へのスピル。** 毎フレームの読み戻しが GPU の利点を削る。
  チェックポイントだけを RAM に置く併用は、VRAM 予算が足りないと分かって
  から足せる（規則は同じまま課金先が変わるだけ）
- **採らない: スクラブ CPU / 再生 GPU の使い分け。** step を 2 実装持ち、
  両者のビット一致を保ち続ける保守コストが最も高い。決定性（`seed` + `id`）
  の検証も 2 倍になる

理由は保守: 間引き・再 step・予算の機構が 1 つで済み、CPU 経路のテストが
GPU 経路の保持規則もそのまま検証する。

### 決定性は `seed` + `id` のみ

spec の規約どおり。`id` は発生順の通し番号で、寿命を通じて安定。
`index` は毎フレーム振り直される配列添字なので**区別する**
（`names.rs` が既に両方を予約している）。

## 目標構成

```text
particle.simulate
  入力: emitter (Geometry) / forces (Field, 可変グループ)
  パラメータ: rate / life / life_variance / initial_velocity /
              initial_spread / drag / seed / max_points
  状態: Vec<Particle> 相当を SoA の Geometry として保持
  出力: Geometry (Point ドメイン)
```

per-point 属性:

| 属性 | 型 | 由来 |
|---|---|---|
| `P` | Vec2 | 積分結果 |
| `velocity` | Vec2 | 積分結果 |
| `id` | I32 | 発生順（寿命を通じ安定） |
| `index` | I32 | 配列添字（毎フレーム振り直し） |
| `age` | F32 | 経過フレーム |
| `life` | F32 | 寿命（発生時に決定） |
| `pscale` / `Cd` / `alpha` | F32 / Color / F32 | カーブ/フィールド制御 |

寿命・サイズ・色は `age / life` を駆動値にした
`field.attribute` → `field.curve_remap` → `field.apply` で制御する。
パーティクル専用のカーブ UI は作らない（変調計画の資産を使う）。

## 実装単位

### 単位 1: `particle.simulate` の骨格

- `StatefulProcessor` 実装。発生（rate × フレーム時間）、
  積分（前進オイラー）、寿命による削除。
- `max_points` で上限を切り、超過時は発生を抑制して `log::warn!`。
  **黙って切り捨てない**。
- SoA のまま扱う（`Geometry` の列を直接伸縮）。

**完了条件**

- rate から期待される発生数になるテスト。
- 寿命超過で削除されるテスト。
- `id` が寿命を通じて安定し、`index` は詰め直されるテスト。
- 同一 seed で 2 回評価して完全一致するテスト。
- `max_points` 到達時に警告が出て発生が止まるテスト。

### 単位 2: エミッタジオメトリからの発生

- ポイント / インスタンス位置からのサンプル。
- パス プリミティブがあれば弧長サンプル（既存の `path_sample`）。
- 発生位置のジッタと初速の方向（法線 / ランダム / 固定）。
- エミッタの属性（`Cd` 等）を発生パーティクルへ継承。

**完了条件**

- ポイント / パス / インスタンスの各エミッタで発生位置が
  ジオメトリ上にあるテスト。
- エミッタ属性が継承されるテスト。
- エミッタが空でもエラーにならないテスト。

### 単位 3: フィールドフォース

- 可変入力グループでフィールドを受け、各フレームで
  全パーティクル位置をバッチサンプルして加速度に加算。
- **向きの規則は 1 本（決定）**: `Vec2` のフィールドは加速度そのもの、スカラーの
  フィールドは `force_direction`（ノードに 1 つ）に掛ける大きさ。`radial` は専用
  モードにせず `field.direction_to` × `field.falloff` で書く。理由: 可変入力の
  スロットはスロットごとのパラメータを持てず、規則が 1 本なら単位 6 のカーネルも
  1 経路で済む。
- ドラッグは速度に比例する減衰としてパラメータで持つ
  （フィールドにしない）。

**完了条件**

- `field.constant` + 下向き方向で自由落下になるテスト
  （解析解との比較、許容誤差付き）。
- `field.falloff` によるアトラクタで中心に集まるテスト。
- `field.noise` で決定的に同じ軌跡になるテスト。
- フォース未接続でも等速直線運動するテスト。

### 単位 4: スクラブ耐性と他ノードへの流用

- sim キャッシュ（`done/stateful-eval-plan.md`）との結合確認。
- パーティクル出力を `scatter.*` の `instance_source` ではなく
  **複製元ポイント**として使う経路の確認。
  （`scatter` は Geometry を入力に取るので、追加実装は不要な想定。
   通らなければここで直す。）

**完了条件**

- 前方再生 → 巻き戻し → 再生で同一結果になるテスト。
- 前方ジャンプで暫定表示 → 確定値になるテスト。
- パーティクルポイントを `scatter` のソースにしてシェイプが
  各パーティクル位置に立つゴールデンテスト。
  **受入条件「他ノードのソースに使える」の検証。**

### 単位 6: GPU シミュレーション（実施と決定。前提つき）

**前提**: `gpu-resident-geometry-plan.md` が「実施」判断になっていること
（2026-07-29 に「実施」で確定）。
**前提**: 同計画の単位 1（`GpuGeometry`）と単位 5（`rasterize` が常駐
ジオメトリを直接読む）が入っていること。**単位 5 が無いと状態を VRAM に
置いても描画のために毎フレーム読み戻すので、GPU sim の意味が消える。**
**前提**: 上記「sim キャッシュと VRAM の衝突」— 決着済み（チェックポイント）。

- `particle.simulate` の step を WGSL compute カーネル化。
  状態は `GpuGeometry` として VRAM 常駐。
- フォースは `gpu-resident-geometry-plan.md` 単位 2 の WGSL フィールドを
  そのまま使う。
- 発生と削除（可変長配列の圧縮）は GPU 側で prefix sum が要る。
  ここが実装上の山場。

**完了条件**

- 単位 1〜4 の全テストを GPU 経路で再実行して CPU と一致。
  **とくに同一 seed での完全一致**（浮動小数の演算順が変わるため、
  許容誤差の設定を明示する）。
- **10 万点の end-to-end（step + 描画）が 16.6 ms を下回ることの実測。**
  step 単体の比較では意味がない — CPU が既に 0.2 ms 前後で通っており
  （`perf-baseline.md`）、単位 6 が回収するのは描画側の展開と
  アップロード（10 万点で 3.28 ms、100 万点で 27.2 ms）。
- **100 万点で CPU 経路より速いことの実測。** CPU の律速がステップではなく
  描画なので、差が出るのはこの規模から。
- スクラブ・巻き戻しが決着した方式で破綻しないことの実機確認。

## 検証

- すべて CPU。GPU パーティクルは非対象。
- **自由落下の解析解比較**を入れる。積分が壊れていることを
  「なんとなく変」ではなく数値で検出するため。
- パフォーマンス: `max_points` の既定値を決めるため、
  1 万点 / 10 万点で 1 フレームの `step` 時間を `perf-baseline.md` の
  手順で 1 回測る。

## 非対象

- **GPU シミュレーションの v1 実装**。単位 6 は**実施と決定**したが
  （2026-07-29）、`gpu-resident-geometry-plan.md` の単位 1 / 5 が前提
  （VRAM キャッシュ方式はチェックポイントで決着済み）。単位 1〜5 は CPU SoA（rayon）で
  完成させる。**10 万点の実用性は CPU 経路で足りる**（実測 0.2 ms 前後/step）。
- **衝突判定**（ジオメトリとの衝突、パーティクル同士の衝突）。
- **サブフレームエミッション**。発生はフレーム境界のみ。
  高速移動時の粒の飛びは許容する。
- **多段シミュレーション**（sim の下流に sim）。spec の v1 制約。
- **トレイル / ストリーク描画**。パーティクルの軌跡を線で描くのは
  別ノードで、本計画には含めない。
- **パーティクル専用の Properties UI**。既存のパラメータ UI で扱う。

## 実装メモ（単位 1〜5）

計画との差と、実装して初めて決まったこと。仕様は
`procedural-geometry.md`「パーティクル」、型と地図は `agent-api-reference.md`。

- **実装は `ravel-nodes/src/particle.rs`**（`ParticleSimulate: StatefulProcessor`）。
  状態は Point ドメインだけの `Geometry`（SoA 列）と、発生の繰り越し（`f64`）・次の
  `id`・警告の「入った瞬間」フラグ。`output` は `Geometry` を clone する
  （列は `Arc` 共有なので安い）。GPU 版（単位 6）は同じ列を 1 要素 1 呼び出しで
  動かせる形にしてある（ステップは要素ごとの式）。
- **フォースの向きは「フィールドごと」ではなくノード 1 つに 1 つ**
  （`force_direction`。単位 3 に決定として記載）。アトラクタのテストは
  `field.direction_to` × `field.falloff` × 強さ（`field.multiply` が
  スカラーをベクタへ拡げる）。
- **積分は前進オイラー**（位置が前フレームの速度で動く）。自由落下は離散解
  `y_n = g·dt²·n(n−1)/2` と一致し、解析解 `½ g t²` とは `g·t·dt/2` だけずれる
  （テストはこの誤差上限で比べる）。定数の大きさのアトラクタは中心でチャタリング
  するので、ドラッグと強さを釣り合わせる（`terminal speed = a / drag`）。
- **`max_points` の既定は 100000**（`PARTICLE_MAX_POINTS_DEFAULT`、テンプレートと
  プロセッサの既定の食い違いを避けるため 1 箇所）。測定は `perf-baseline.md`
  「`particle.simulate` 実測」。**rayon は載せなかった**（`ravel-nodes` の本番依存が
  増える。10 万点で serial 0.5 ms 前後で、100 万点で効く話は単位 6 の領分）。
- **警告は `tracing::warn!`**（`log` ではなく。コードベースの慣例）で、**条件に
  入った瞬間に 1 回**（上限に居続けても毎フレームは出さない）。同じ扱いが
  3D / Mesh のエミッタと、加速度でないフォースの答えにある。
- **エミッタ**: `emit_from` = `auto` / `points` / `path` / `instances`。パスは最初の
  1 本だけ（`PathArcTable`）。継承する属性は、点 = その点の行、パス = 最寄りの頂点の行、
  インスタンス = そのインスタンスの行。発生位置・向きは `seed` と `id` のハッシュだけ。
- **単位 4 の「scatter のソース」**: `scatter.*` には**ポイント入力からインスタンスを
  作る経路が無く**、計画の「追加実装は不要な想定」は通らなかったので、ここで
  `scatter.points`（copy-to-points）を足した（`scatter/points.rs`）。`P` / `rot` /
  `scale` は粒から取り、`pscale` は一様スケールとして掛け、他の属性はインスタンス
  ドメインへ引き継ぐ。`Vec3` の `P` は当初評価エラーとし、3D 複製（3D-6）の
  マージ時に `orient` / `scale3` を書く 3D の配置へ置き換えた。
  ゴールデン `tests/particle_scatter_golden.rs` は「粒ごとにシェイプが立つ」を検証する。
- **寿命・サイズ・色**は専用 UI 無し。`age` / `life` を `field.attribute` /
  `@age` / `@life` 式で読み `field.apply` で書く（テストは `pscale = 4(1 − age/life)`）。
