# PathChannel 設計書 — パスアニメーション（REQ-UI-011 単位 8）

ペンツールで描いたカスタムパス（`shape.custom_path`）を時間軸で変化させる
仕組みの設計メモ。**実装は行わない**（実装計画の単位 8 の成果物）。
難問は「点数が変化するキーフレーム間の補間」（頂点対応問題）であり、
本書は段階的な解決方針を定める。

## 前提（v1 の構造、#147 / #149 で確定済み）

- パスは `ParameterValue::PathPoints(Vec<PathPoint>)` に保持（**定数のみ**）。
  `PathPoint { p, in_tan, out_tan }`、接線は `p` からのオフセット、
  ゼロ = コーナー。閉路は別パラメータ `closed: Bool`（離散値）。
- 評価: `resolve_params` が `ResolvedValue::PathPoints` として素通しする。
- 描画: geometry 上の `in_tan`/`out_tan` 点属性を rasterize が共有
  フラット化（comp 空間 0.25px 固定 tolerance、CPU/GPU 同一折れ線）。
- undo / 永続化: Document スナップショット、RON、journal v6（bincode）。
- 編集: ペンツールのセッション確定・点/ハンドル編集は 1 操作 = 1 undo。

## 目標と非目標

- **v2 の目標**: 同一点数のパス同士のモーフィング（点ごとの線形補間）
  と、ペンツールによるキーフレーム編集（編集 = 現フレームにキー挿入）。
- **非目標（v3 以降）**: 点数変化モーフィングの全自動化、複数プリミティブ
  間のモーフィング、パスブーリアン演算。

## データモデル（推奨案）

`ParameterValue::PathChannel(PathChannel)` を新設する。

```rust
struct PathKeyframe {
    frame: u64,
    points: Vec<PathPoint>,   // キーごとに点数を保持
    interpolation: PathInterpolation, // v2: Linear | Step
}
```

- 代替案（`PathPoints` のままキー列を Graph 外に持つ）は Document 由来の
  undo・永続化・評価キャッシュの既存経路に乗らないため却下。パラメータ
  値として持つのがチャネル規約（REQ-LAYER-004）とも一致する。
- variant 追加は bincode journal のレイアウト変更 — **実装時に
  `JOURNAL_FORMAT_VERSION` bump（v7 想定）**。
- 既存の `PathPoints` 値は定数として存続させ、自動変換しない。初めての
  キー作成操作で `PathChannel` 化する（チャネルの Constant → Keyframes
  遷移と同じ規約）。

## 補間セマンティクス（v2）

- **同点数キー間**: 点 i ↔ 点 i で `p` / `in_tan` / `out_tan` を線形補間。
  始点インデックスの回転対応（closed パスの位相合わせ）は v2 では
  行わない — 編集 UI が点数と順序を維持する運用で担保する。
- **点数不一致キー間**: Step（手前キーの値を保持）。v2 のペン編集は
  点の移動・接線編集のみをキー対象とし、点の追加/削除（v1.5 機能）を
  キーフレーム済みパスに行った場合は新しい点数がそのキーにのみ記録
  される、で矛盾しない。
- **`closed`**: 離散。常に Step。
- 時間方向の Bezier 補間（`tangent_in`/`tangent_out` 規約）は既存
  チャネルと同じ構造を使えるが v2 対象外（Linear/Step のみ）。

## 点数変化モーフィング（v3 の設計方針）

頂点対応問題: パス P0（n 点）と P1（m 点）の間の写像をどう決めるか。

- **(a) 弧長リサンプリング（推奨）**: 両パスを共有フラット化で折れ線化
  → 弧長で正規化 → 同一サンプル数 N に再標本化 → 点ごと補間。接線は
  対応点同士で補間するか、補間後に再推定する。コーナー点数が一致する
  場合はコーナー同士を優先対応させるヒューリスティックで角の劣化を
  抑える。限界: トポロジ差（穴・複数プリミティブ）では破綻する。
- (b) 対応点マーカー（AE のマスク頂点マッチ相当）: 表現力は高いが
  UI コストが大きく、v3 でも採用しない。
- (c) 全キーで点数を強制一致させる編集モデル（点追加/削除を全キーに
  反映）: 実装は容易だが表現力を大きく削る。採用しない。

評価時コスト: (a) はキー間ごとにフラット化＋再標本化が走るため重い。
キー間キャッシュ（両キーの内容ハッシュ → リサンプル済み対応列）を
evaluator 側に持つ設計が必要になる。

## 既存サブシステムへの影響

- **評価**: `resolve_params` が `PathChannel` をフレーム評価して
  `Vec<PathPoint>` を生成し `ResolvedValue::PathPoints` に帰着させる。
  flatten / rasterize / processor は**変更不要**。
- **ペンツール**: キーフレーム済みパスの編集は現フレームへのキー挿入
  （`edited_float_param` の PathPoints 版が必要。layer-local 時刻規約
  REQ-LAYER-006 に従う）。
- **Timeline**: パスキーは既存のキーフレーム行（◆）に乗る。
- **Properties**: read-only 表示を「N points（K keys）」程度に拡張。
- **選択/bbox/移動**: PathPoints の制御多角形 AABB 規約を補間後の値に
  適用するだけでよい。

## 未解決の問い（実装時に再訪）

- closed パスの始点インデックス回転を UI が誘導なしに許すと、v2 の
  点 i ↔ 点 i 対応が意図とずれる。編集操作で検出・警告するか。
- 接線の線形補間は中間フレームで自己交差を増やしうる。許容か、
  接線長の単調性を制約するか。
- 将来パス点に `Cd` 等の点属性が付いた場合、リサンプリング時の
  属性補間規約が別途必要。
