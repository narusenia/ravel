# 評価・描画パフォーマンス baseline（Phase 0 計測結果）

> **Status**: Reference — measurement record

計画: `done/eval-render-performance-plan.md`。計測日: 2026-07-17。
環境: Apple M5 / macOS 26.3 / release ビルド / 512×512 RGBA f32。

## 計測方法

- 計測ハーネス: `crates/ravel-nodes/examples/perf_baseline.rs`
  （`cargo run -p ravel-nodes --release --example perf_baseline`）。
  `NodeEditorPanel` の UI スレッド処理のうち評価系
  （`apply_property_change` → `sync_processors` → `evaluate_for_viewer`）を
  ヘッドレスに再現し、計装済み `tracing` span（`evaluate` /
  `node_process` / `gpu_upload` / `gpu_readback` / `cpu_rasterize` /
  `register_processors`）を集計する。
- 除外している UI 側処理（ウィンドウが必要なため）: ノードサイズ再計算、
  undo push、`ViewerFrame` Global 発行、GPUI notify/paint。いずれも
  CPU 軽量だが、in-app 計測での上乗せ分として留意。
  （`ViewerFrame` 発行はかつて f32→BGRA 変換をここで抱えていて軽量ではなく、
  それが `HIGH-08` だった。`GPUCOMP-9` で変換を評価ワーカーへ移した後は
  実際に `Arc` の移動だけ — 下記「表示変換を評価ワーカーへ移した後」）
- グラフ: `source(512×512 グラデーション) → blur → color_correct →
  merge.A`、`source → merge.B`（GPU 3 ノード経由のビューア出力を模す）。
- 転送回数は `ravel_gpu::transfer::stats` のプロセス毎カウンタで検証。
- シナリオ (d) 無操作アイドルは、ヘッドレスでは評価パスが一切走らない
  ことの確認に留まる（アイドル時の再描画コストは UI 側の別問題）。

## 結果

### (a) ノード選択切替（グラフ不変・キャッシュ温）

| 指標 | 値 |
|------|----|
| wall/iter | ~0.00 ms（20 iters） |
| 転送 | 0 uploads / 0 readbacks |

選択切替そのものはキャッシュヒットで完結し、評価コストはほぼゼロ。
選択時の体感カクつきの犯人は評価ではなく、選択に伴う再描画・
Properties 再構築・（Geometry 選択時の）アドホック rasterize 側にある。

### (b) blur radius スクラブ 3 秒（90 ticks、現行 UI 経路）

Change 毎に evaluator を作り直し（`sync_processors` 相当）、`merge` を
再評価。radius は 1.0→23.25 を掃引。

| 指標 | 値 |
|------|----|
| wall/tick | **mean 14.62 ms**（min 10.42 / max 18.30） |
| 転送/90 ticks | 360 uploads (1.51 GB) / 270 readbacks (1.13 GB) |

| span | calls | mean ms |
|------|-------|---------|
| evaluate（全体） | 90 | 14.03 |
| node_process:blur | 90 | 7.21 |
| node_process:merge | 90 | 3.74 |
| node_process:color_correct | 90 | 3.07 |
| gpu_readback | 270 | 2.37 |
| gpu_upload | 360 | 0.43 |
| register_processors | 90 | **0.57** |

1 tick あたり読み戻し 3 回 (7.1 ms) + アップロード 4 回 (1.7 ms) =
**約 8.8 ms（~60%）が CPU↔GPU 往復**。各 GPU ノード内の dispatch 毎
`ctx.wait()`（ブロッキング）も node_process に含まれる。
一方 evaluator 再構築（`register_processors`、パイプライン再生成込み）は
0.57 ms と軽い — shader モジュールがハッシュキャッシュされるため。

### (b') 同スクラブ、変更ノードのみ再登録（evaluator・キャッシュ維持）

processor はパラメータを構築時に取り込むため、radius 変更には blur
processor の再生成・再登録が必要（`register` が dirty 化し、下流は
freshness 伝播で再計算、source はキャッシュ利用）。

| 指標 | 値 |
|------|----|
| wall/tick | mean 15.06 ms（min 10.88 / max 22.10） |
| 転送/90 ticks | (b) と同一: 360 uploads / 270 readbacks |

**(b) との差はノイズ範囲（±0.5 ms）。「processor 全再構築が高い」仮説は
棄却**。転送回数も不変 — 各 GPU processor が CPU 入力を毎回アップロード
し直すため、evaluator キャッシュを維持しても往復は 1 回も減らない。
スクラブコストの本体は GPU 往復と同期待ちそのもの。

### (c) scatter count=500 の Geometry チェーン選択

`shape.rect → scatter.grid(25×20=500)`。evaluator は構築済み・キャッシュ温
（選択では processors を再構築しない実挙動に合わせる）。Viewer 用の
アドホック rasterize（`evaluate_for_viewer` と同経路、キャッシュ無し）を
毎回実行。

| 指標 | 値 |
|------|----|
| wall/iter | **mean 38.02 ms** |
| cpu_rasterize | mean 37.75 ms（ほぼ全部） |
| evaluate（geometry 部分、温） | 0.007 ms |

Geometry ノードを選択するたびに UI スレッドが 38 ms ブロックする。
犯人は CPU ラスタライズ単体（キャッシュされないため毎選択で発生）。

### paint プロキシ（run-merge 走査、512×512）

| コンテンツ | quads | 走査 wall |
|-----------|-------|-----------|
| フラット形状（scatter 出力） | 402 | — |
| グラデーション（merge 出力） | **262,144（= 全ピクセル）** | 0.26 ms |

run-merge はフラット塗りには有効だが、グラデーション・実写系
FrameBuffer では 1 ピクセル 1 quad に退化する。GPUI への 26 万 quad
提出コストは本計測の範囲外（ヘッドレス不可）だが、メディア表示では
paint_quad 経路が支配的コストになることが確実。

## 計画との突き合わせと Phase 順序の判断

計画の推定（§問題）は概ね実測と一致:

1. 「同期評価が UI をブロック」 — 実測 14.6–38 ms/操作（フレーム予算
   16.6 ms 前後〜2 倍超）で**確定**。
2. 「ノード単位の CPU↔GPU 往復」 — スクラブ時間の約 60% で**確定**。
   さらに (b') により、往復は evaluator キャッシュの持ち方と無関係に
   processor 内部で発生することを確認（Phase 2 の設計対象そのもの）。
3. 「paint_quad・CPU rasterize は相対的に小」 — **部分修正**:
   CPU rasterize はインスタンス 500 で 38 ms と大きい（Phase 3 の
   価値を裏付け）。paint_quad はフラット形状では小さいが、
   グラデーション/メディアでは per-pixel quad に退化する
   （Phase 4 の価値はメディア再生の文脈で急上昇する）。

想定外だった点: `sync_processors`（evaluator 再構築 0.57 ms）は軽く、
「processor 再登録の回避」単体はスクラブ最適化として効果がない。

**結論: Phase 順序は計画どおり 1 → 2 → 3 → 4 を維持。**

- Phase 1（バックグラウンド評価）が最優先 — どのシナリオでも
  14.6–38 ms を UI スレッドから排除でき、体感カクつきを直接解消。
- Phase 2（GPU 常駐）はスクラブ評価時間の ~60% を削り、再生
  （TASK-013）のフレーム予算に必須。
- Phase 3（GPU ラスタライズ）は 38 ms/eval の解消。
- Phase 4 は最低ライン（読み戻し 1 回 + RenderImage）をメディア
  対応前に入れる価値がある（per-pixel quad 退化のため）。

## 制約・未計測

- GPUI の実 paint コスト（quad 提出・レイアウト）と
  `rebuild_widgets` は in-app 計測が必要。span は仕込み済みだが、
  アプリの fmt subscriber は span close を出力しないため、取得には
  タイミング集計レイヤ（本ハーネスの `TimingLayer` 相当）または
  `FmtSpan::CLOSE` の有効化が別途必要。
- 計測はプロセス単発実行。GPU ドライバ状態によるばらつきは
  min/max の幅（(b) で 10.4–18.3 ms）として記録。

## Phase 完了時の再計測

Phase 1/2/4 の完了条件の再計測はこのファイルに追記する。

### Phase 1（バックグラウンド評価）完了時

シナリオ (b'') = (b) と同じ 90 tick スクラブを `EvalService` 経由で実行
（ハーネスに追加済み）。

| 指標 | Phase 0 (b) | Phase 1 (b'') |
|------|------------|---------------|
| UI スレッド wall/tick | 14.62 ms | **~0.00 ms（要求投函のみ）** |
| 評価回数/90 ticks | 90 | **1**（think time なし投函のため全て coalesce） |
| 転送/評価 1 回 | 4 uploads / 3 readbacks | 同（Phase 2 の対象のまま） |

実スクラブ（Change 間隔 ~33 ms）ではワーカーが追従できる限り毎 tick
評価されるが、UI スレッドはブロックしない。評価 1 回あたりの GPU 往復
（4 up / 3 down、~8.8 ms）は Phase 2 で削減する。

### Phase 2（GPU 常駐パイプライン）完了時

GPU 4 ノードが `GpuFrameBuffer` を入出力し、dispatch 毎の `ctx.wait()` を
除去。読み戻しは Viewer 境界（`GpuEvalHooks::finalize`）の 1 回のみ。

計測注記: Phase 2 以降の evaluate は GPU 作業を投入するだけで完了を
待たない。表の「評価 wall/tick」は評価スレッドの占有時間（投入まで）、
「end-to-end」は 90 tick 分の GPU 完了（`ctx.wait()`）込みの実測。

| 指標（(b) 90 ticks） | Phase 0/1 | Phase 2 |
|------|-----------|---------|
| 評価 wall/tick（投入まで） | 14.62 ms | 1.41 ms |
| **end-to-end /tick（GPU 完了込み）** | 14.62 ms | **1.45 ms（-90%）** |
| readbacks | 270（3/tick） | **0** |
| uploads | 360（4/tick） | 180（2/tick、CPU ソースの GPU チェーン流入点のみ） |
| node_process:blur | 7.21 ms | 0.50 ms（ブロッキング待ち消滅） |

- 中間読み戻しゼロは `gpu_resident_pipeline.rs` の転送カウンタテストで
  担保（`GpuContext::transfer_stats` — カウンタはコンテキスト毎に分離）。
- 常駐経路と CPU 経由ステージング経路の画素等価テスト済み（誤差 <1e-5）。
- evaluator キャッシュ上の GPU ハンドルは drop で共有プールに自動返却
  （テストで担保）。プール予算は eval ワーカー共有で 512 MiB。
  **既知の制約**: LRU 予算が束縛するのはアイドル（返却済み）テクスチャ
  のみで、キャッシュが保持する常駐ハンドルの総量は未束縛。三層フレーム
  キャッシュ（REQ-CORE-006）設計時に GPU 対応のキャッシュ eviction と
  合わせて解決する。
- 残る uploads 2/tick は CPU ソース（将来のメディアデコード出力が GPU
  常駐になれば 0）。Viewer 表示の読み戻し ~1.9 ms/フレームは Phase 4
  （RenderImage / ゼロコピー）の対象。

### Phase 3（GPU ラスタライズ）完了時

`rasterize` の通常ノードを instanced-quad render pass（non-zero winding +
edge distance の fragment 評価、triangulation 不要）に置換。Composition
synthetic ノードと Viewer ad-hoc は golden 互換の CPU zeno 経路を維持。

| 指標（scatter 500 instances、512×512、release） | CPU (zeno) | GPU |
|------|-----------|-----|
| rasterize / 評価 | 50.2 ms | **2.6 ms（GPU 完了込み、~19×）** |
| + RGBA32Float 読み戻し | — | 3.0 ms |

GPU/CPU 等価: 自己交差パス 100.000%（0.1 許容内画素）/ coverage Δ0.004%、
開閉路 99.479% / Δ0.012%、ネスト instance + pscale/rot/scale/Cd/alpha
100.000% / Δ0.037%。しきい値: 画素一致 >99%、coverage Δ<2%。

### 再生（`done/playback-foundation-plan.md` 実装単位 3）完了時

シナリオ (e) = 30 fps × 90 フレーム（3 秒）の再生。`PlaybackClock` を
フレーム間隔で tick し、フレームが進んだときだけ `EvalService` に
`EvalContext::frame` 実値付きの要求を投函する（PlaybackController の
tick ループをヘッドレスに再現、ハーネスに追加済み）。デモグラフに
time-dependent ノードがまだ無いため、blur radius をフレーム毎に
アニメーションさせて毎フレーム実仕事を発生させている。

| 指標 | 値 |
|------|----|
| UI スレッド wall/公開フレーム（フレーム算出 + 要求投函） | **mean 0.01 ms** |
| 実測レート | 90 フレーム / 3.02 s、**27.4 fps 評価** |
| 公開フレーム | 83（tick ジッタによるスキップ 7） |
| latest-wins coalesce | **0**（評価 ~1.5 ms/フレーム、ワーカーは余裕で追従） |
| 転送/フレーム | 2 uploads / **0 readbacks**（Phase 2 の常駐維持） |

- tick ジッタのスキップは設計どおり「フレーム落ち」になり、クロックは
  ドリフトしない（90 フレームを 3.02 s で走破 = 実時間精度維持）。
  スキップ数は `Transport::dropped_frames` として PlaybackController が
  カウントし、停止/終端到達時に tracing へ記録する。
- 評価が 1 フレーム時間（33 ms）を超えるグラフでは coalesce 数が
  増えて表示 fps が落ちるが、UI スレッドは要求投函（~0.01 ms）のみで
  ブロックしない（Phase 1 の保証を引き継ぐ）。
- Viewer 表示側の読み戻し・`RenderImage` 変換コストは Phase 4 の表の
  とおり（フレーム更新毎の BGRA 変換のみ）。

### Phase 4（Viewer の image 表示、最低ライン）完了時

paint_quad ランマージを `RenderImage` + `img` 要素に置換。GPUI の実
paint コストはヘッドレスで測れないため、提出プリミティブ数で比較:

| コンテンツ（512×512） | paint_quad 経路 | RenderImage 経路 |
|----------------------|----------------|------------------|
| フラット形状 | 402 quads / render | **1 textured quad** |
| グラデーション/実写 | **262,144 quads / render**（ピクセル毎に退化） | **1 textured quad** |
| CPU 側前処理 | run-merge 走査 0.26 ms × **render 毎** | BGRA u8 変換 ~O(n) × **フレーム更新毎のみ** |

読み戻し（~1.9 ms/フレーム）は評価ワーカー側 finalize に留めたまま
（UI 非ブロッキング）。ゼロコピー共有（ストレッチ）は未着手 — メディア
再生で変換・読み戻しがボトルネック化した時点で再評価する。

### RESP-3（シェーダ・パイプライン共有）完了時

計測日: 2026-07-28。環境: Apple M5 / macOS 26.3 / release ビルド / 512×512。
`done/ui-responsiveness-plan.md` RESP-3（issue HIGH-06）。
同一ツリーの変更前コミットを `git worktree` で並べ、同じハーネスの
シナリオ (b) を各3回走らせて比較した（`register_processors` は
`Structural` 相当の全プロセッサ再登録スパン）。

| 指標 | 変更前（3回） | 変更後（3回） |
|------|--------------|--------------|
| `register_processors` mean/tick | 0.304 / 0.296 / 0.323 ms | **0.015 / 0.015 / 0.018 ms** |
| wall/tick | 1.31 / 1.27 / 1.35 ms | **1.02 / 1.03 / 1.17 ms** |

`register_processors` は約20分の1（−95%）。tick 全体は約 −18% で、
その差はほぼ `register_processors` の差分と一致する。

**読み方の注意（2点）**:

1. 上の 2026-07-17 のシナリオ (b) は wall/tick **14.62 ms**、readback 270 回と
   記録しているが、今日の**変更前**の同シナリオは 1.31 ms / readback 0 回。
   Phase 2〜4 の GPU 常駐化が間に入っているため、14.62 ms との差を
   RESP-3 の効果として読んではいけない。上表の比較のみが RESP-3 の効果。
2. シナリオ (b) は毎 tick 全プロセッサを再登録するので、RESP-3 のうち
   「検証をハッシュキャッシュの後ろへ」と「パイプライン共有」を測っている。
   「状態を持たないプロセッサは再登録せず invalidate だけ」（実 UI の
   `Params` 経路）はこのシナリオでは走らないため、実アプリの編集ティックでは
   さらに減る。

HIGH-06 は「編集中の体感を最も悪化させている要因」と書いていたが、
測定はそれを支持しない。変更前でも `register_processors` は tick の
約23%（0.31 / 1.31 ms）で、残りは `gpu_upload` と GPU ノードの
`node_process`。編集時の体感の主因は依然として第2段（HIGH-04 / HIGH-05 の
CPU↔GPU 往復とシェル合成の CPU per-pixel）側にある。

### GPU シェル合成チェーン baseline

計測日: 2026-07-28。環境: Apple M5 / macOS 26.3 / release ビルド / 512×512。
`gpu-compositing-plan.md` の最初の測定単位として、各レイヤーネットワークが
`source → blur → net.out`（末尾は GPU 常駐）となる Composition を
`compile_composition` で構築した。各シェルは非 identity transform、opacity 0.8、
Normal / Add / Multiply / Screen / Overlay の混在 merge を通る。

スクラブは既存 (b'') と同じく think time 無しで90要求を投函するため、
latest-wins により完成評価は1回。レイヤー数の定数を既定10と比較用3に変えて
別々に実行した。

| 指標 | 10 layers | 3 layers |
|------|-----------|----------|
| wall/iter（要求投函） | mean 0.00 ms（min 0.00 / max 0.00） | mean 0.00 ms（min 0.00 / max 0.00） |
| 完成評価 | 1 | 1 |
| uploads | 10（41.9 MB） | 3（12.6 MB） |
| **readbacks** | **10（41.9 MB）** | **3（12.6 MB）** |
| end-to-end / 90 ticks | 73.88 ms | 34.22 ms |

30 fps 再生形では、tick ジッタとワーカーの latest-wins により完成評価数が
実行ごとに異なるため、総数と評価1回あたりを併記する。

| 指標 | 10 layers | 3 layers |
|------|-----------|----------|
| wall/iter（要求投函） | mean 0.00 ms（min 0.00 / max 0.01） | mean 0.01 ms（min 0.00 / max 0.04） |
| playback | 90 frames / 3.07 s | 90 frames / 3.04 s |
| 完成評価 | 78（25.4 fps） | 76（25.0 fps） |
| uploads | 10（41.9 MB） | 3（12.6 MB） |
| **readbacks** | **780（3271.6 MB）** | **228（956.3 MB）** |

読み戻しはスクラブ、再生ともに厳密に **N 回 / 完成評価** であり、
HIGH-05 の「GPU 常駐レイヤーごとに shell transform がブロッキング readback」
を再現した。span 集計には追加計装なしで `node_process:comp.transform`、
`node_process:comp.opacity` と全5種の `node_process:comp.merge.*` が現れ、
短絡せずシェルチェーンが実走していることも確認した。

#### ハーネスは両レイヤー数を1回の実行で回す

上の2表はレイヤー数の定数を書き換えて別々に走らせた結果だが、その後
`SHELL_LAYER_COUNTS = [3, 10]` を導入し、**両方が1回の実行で出る**ようにした。
完了条件「readback 回数がレイヤー数に比例」をコード編集なしで確認できる。
同一実行での確認値:

| シナリオ | 3 layers | 10 layers |
|---|---|---|
| (f) スクラブ readbacks（完成評価1回） | **3** | **10** |
| (g) 再生 readbacks / 完成評価 | 249 / 83 = **3** | 680 / 68 = **10** |
| (g) 評価レート | 27.4 fps | 22.4 fps |

#### コストの分解（同日、別機会の再実行 10 layers / 再生形）

同じハーネスを別に1回走らせた結果（完成評価 71、23.3 fps、readbacks 710）で
内訳を見ると、`evaluate` 合計 3052 ms のうち:

| 内訳 | 合計 | 評価1回あたり |
|------|------|--------------|
| `node_process:comp.transform` | 2396 ms（**78%**） | 33.7 ms（10 レイヤー分） |
| うち `gpu_readback` | 1589 ms | 22.4 ms |
| transform の CPU ループ（差分） | 約 807 ms | 約 11.3 ms |
| `node_process:comp.merge.*` 5種合計 | 480 ms | 6.8 ms |
| `node_process:comp.opacity` | 156 ms | 2.2 ms |

**HIGH-04 と HIGH-05 のどちらか一方では足りない**ことがこの分解から読める。
transform 1回 3.4 ms の内訳はブロッキング readback 約 2.2 ms +
CPU per-pixel ループ約 1.1 ms で、readback だけ速くしても per-pixel ループが、
per-pixel ループだけ消しても readback が残る。
GPU 化（HIGH-05）は readback の**回数**を N→1 にするので両方に効く —
だから計画の着手順は HIGH-05 が先で正しい。

読み戻し帯域は 512×512 で 2978 MB / 3.05 s ≈ 976 MB/s。
`VIEWER_MAX_DIM = 1024` では面積4倍なので単純計算で約 3.9 GB/s に達する。
この上限が対話評価の解像度キャップの実体。

#### ステージング確保はフレーム数に比例しない

`HIGH-04` の受入条件 2 つめ。ハーネスは
`TransferSnapshot::staging_buffers_created` の差分を出力する:
ウォームアップ 1 回の後の 20 フレームで **0**（1080p / 4K 両方）。
`transfer.rs` の `repeated_readbacks_allocate_no_staging_buffer` が
同じことをテストで pin する（初回 1 → 以降 16 回で 0）。

プールの置き場所は `GpuContext`（`staging.rs` の `StagingPool`、
バイトサイズをキーにした素直な HashMap + `LruBudget`）。**アイドル許容量は
共有 `CacheBudget` に載せていない**: ステージングは `MAP_READ` すなわち
ホスト可視メモリで、VRAM ティアに計上すると*デバイス*テクスチャを
*ホスト*バッファのために evict する誤った取引になる。RAM ティアに載せるには
`GpuContext` が予算ハンドルを持つ必要があり、それは
`from_handles`（デバイス共有経路）まで含む構築 API の変更になる。
現状はプール自身の 256 MiB 上限（4K 127 MiB + 1080p 32 MiB が同時に
収まる最小の切りの良い値）で、RAM ティアへの統合は予算ハンドルを
渡す者の仕事として残す。

#### 二重コピーの除去をどう固定したか

コピー回数は直接観測できないので**フルフレームサイズのヒープ確保数**を数える。
`ravel-gpu/tests/readback_allocations.rs` はテストバイナリ専用の
グローバルアロケータでスレッドローカルに集計し、
`to_frame_buffer` 1 回のフレームサイズ確保が **1**（フレーム自身の
`Arc<[u8]>` だけ）であることを assert する。旧経路を一時的に戻すと
**3**（`Vec<u8>` → `Vec<f32>` → `Arc<[u8]>`）になり、このテストは落ちる
（実際に確認済み）。行パディングの除去ループは残す — wgpu が返す行は
`COPY_BYTES_PER_ROW_ALIGNMENT` 単位なので詰める処理自体は必要で、
消したのはその後の作り直しだけ。1080p / 4K の RGBA32F は行が
既にアラインされているため、マップ範囲から `Arc<[u8]>` へ**1 回**の
コピーで着地する。

#### 完了判定のプリミティブ（Windows CI 由来の差し替え）

`PendingReadback` の完了判定は当初 `device.poll(PollType::Poll)` だったが、
**submit index 指定の `Wait` をタイムアウト 0 で使う形に差し替えた**
（`is_complete()` = `wait_timeout(Duration::ZERO)`）。動機は Windows CI で
「10,000 回ポーリングしても完了しない」テストが落ちたこと。原因は
バックエンド差ではなく**回数上限が実質タイムアウトだった**ことで、
実際に下表の `checks/frame` は 1080p で **6,689 回**、4K で **21,102 回**
＝ネイティブ Metal の実機でも 4K は旧上限を超える。テストは回数ではなく
時間で区切る形に直した（`a_pending_readback_completes_within_a_bounded_wait`）。

タイムアウト 0 の `Wait` は全バックエンドで非ブロッキングであり
（DX12 は `WaitForSingleObject(event, 0)`、Metal は sleep 前に status 判定、
Vulkan は `timeout_ns = 0`）、かつ**タイムアウトしても wgpu はフェンスを
読んで完了済み submission を回収し map コールバックを発火する**
（`wgpu-core/src/device/resource.rs` の `Device::maintain`）。つまり
`Poll` の進行作用を含んだ上位互換で、加えて「この submission が終わったか」
を submission 単位で答えられる。

#### 内訳: GPU コピー待ちと CPU コピー（`GPUCOMP-10` の判断材料）

ハーネスは同じ readback を `begin_readback()` + `is_complete()` の
スピンで分割しても測る。前半は GPU のコピー完了待ち（非同期化すれば
次フレームの評価と重ねられる分）、後半はマップ範囲から CPU バッファへの
コピー（重ねられない分）。

| 解像度 | GPU コピー待ち | CPU コピー | 分割の合計 | ブロッキング待ちの wall | checks/frame |
|---|---|---|---|---|---|
| 1920×1080 | 0.64 / 0.66 / 0.71 ms | 0.61 / 0.72 / 0.71 ms | 1.25 / 1.38 / 1.42 ms | 2.36 / 2.44 / 2.53 ms | 6,689 |
| 3840×2160 | 2.77 / 2.28 / 2.13 ms | 3.14 / 2.87 / 2.86 ms | 5.91 / 5.15 / 4.99 ms | 7.58 / 6.23 / 6.41 ms | 21,102 |

（3 回の実行値をスラッシュ区切りで併記。`checks/frame` は実行 (3) の値で、
プリミティブ差し替え後に追加した列）

**分割の合計が wall より 1.1 ms 前後小さい理由は wgpu-hal の Metal 実装**。
`to_frame_buffer` の待ちは `PollType::Wait { timeout: None }` で、Metal の
`Fence` 待ちは「コマンドバッファの status を見る → 未完了なら
`thread::sleep(1ms)`」のループ（`wgpu-hal/src/metal/device.rs`、
`Device::wait`）。したがってブロッキング経路は待ち時間が **1 ms 刻みに
切り上がる**: 1080p はコピー 0.71 ms が 1 回の sleep で ~1 ms に、
4K はコピー 2.13 ms が 3 回の sleep で ~3 ms になる。実測の wall
（2.53 / 6.41 ms）は「切り上げた待ち + CPU コピー + submit と確保の分」で
説明が付く。

これは**バックエンド実装の粒度で、GPU の本来のレイテンシではない**。
スピン（タイムアウト 0 の連続判定）なら 0.71 / 2.13 ms で拾えるが、
その間 1 コアを焼くので「待つ代わりに他の仕事をする」形でなければ
意味がない。スピンとブロックの中間（数百 µs スピン → ブロック）で
1080p 約 1 ms を回収できる見込みはあるが、評価ワーカーのコアを
焼く判断を伴うので本単位では実装せず、`GPUCOMP-10` を判断する際の
選択肢として記録するに留める。

#### 判断: `GPUCOMP-10`（非同期リードバック）は現時点では不要

根拠:

1. **1080p で 2.4–2.5 ms/フレーム**。60 fps 予算 16.7 ms の 15%（変更前は
   6.1 ms = 37%）。しかもアプリの対話評価は `VIEWER_MAX_DIM = 1024` に
   制限されているので、実際の表示経路はこれより小さい解像度で動いている。
2. **非同期化で隠せるのは wall から CPU コピーを引いた分**、つまり
   1080p で 1.8 ms / 4K で 3.4–4.4 ms。残る CPU コピー（1080p 0.6–0.7 ms、
   4K 2.9–3.1 ms）はどう並べ替えても消えない。さらにその 1.8 ms のうち
   **約 1 ms は Metal のフェンス待ちが 1 ms 刻みという wgpu-hal 実装の
   粒度**（上記）で、非同期化を持ち出さずスピンでも拾える性質のもの。
   純粋に「GPU がコピーしている時間」は 1080p 0.7 ms しかない。
   フレーム N のリードバック中に N+1 を評価する形はステージングの
   多重化・表示の 1 フレーム遅延・`GpuEvalHooks` のフレーム境界の作り直しを
   要求する。**費用対効果が合わない。**
3. 4K は 6.2–7.6 ms で、30 fps 予算の 19–23%、60 fps 予算の 37–45%。
   ここは「不要」と言い切れる余裕ではないが、**現在 4K を毎フレーム
   リードバックする経路は存在しない**（ビューアは 1024 上限、書き出しは
   リアルタイム制約なし）。

再評価の条件（このどちらかが入った時点で測り直す）:

- `GPUCOMP-11` / `GPUBK-9` で `VIEWER_MAX_DIM` を撤廃し、表示解像度が
  実解像度に追随するようになったとき
- 4K を 60 fps でスクラブする要求が立ったとき

実装コストの見積りに影響する点として、**非同期の器は既にある**:
`PendingReadback`（`begin_read_texture` / `GpuFrameBuffer::begin_readback`）が
`map_async` もコールバックも外に出さない形で完了状態を表し、
`is_complete()`（非ブロッキング）と `wait_timeout()`（有界待ち）の両方を
持っているので、`GPUCOMP-10` に踏み込む場合の追加は「いつ取りに行くか」の
スケジューリングだけで、公開 API の作り直しは要らない。

### 表示変換を評価ワーカーへ移した後（GPUCOMP-9 / HIGH-08）

> **`CM-7` 以降、このハーネスは無い。** 表示変換は GPU（リードバック前の
> 1 パス）へ移り、`ViewerImage::from_frame_buffer` と
> `measure_display_conversion_cost` / `reference_bgra` は削除された。
> 以下は**当時の記録**であって、再現できるコマンドではない。

引き受けた issue:
[HIGH-08](../../issues/closed/HIGH-08-ui-thread-f32-to-bgra-conversion.md)。
計測日: 2026-08-05。環境: Apple M5 / macOS 26.3 / release ビルド。
ハーネス: `crates/ravel-app/src/panels/mod.rs` の
`measure_display_conversion_cost`（`#[ignore]`、
`cargo test -p ravel-app --release --lib measure_display_conversion_cost --
--ignored --nocapture`）。1 サイズあたり 40 フレームの平均、3 回実行。

**変更前をどう測ったか**: 旧変換（1 ピクセル 4 回の `Vec::push`）は
同じテストモジュールに `reference_bgra` として**バイト単位で同一のまま**
残してある（ピクセル不変を固定するテストが同じ関数を使う）。したがって
変更前・変更後は**同一バイナリ・同一実行**の中で測っており、機種差・
ビルドプロファイル差は入らない。旧経路の UI スレッド側はこれに
`Arc::new(fb.clone())`（publish 時）と `RenderImage` の包み込みが加わる。

| 解像度 | 変更前の UI スレッド占有 | 変更後の UI スレッド占有 | 変換自体（ワーカー） |
|---|---|---|---|
| 1024×576（対話評価の上限） | **1.21 / 1.21 / 1.22 ms** | **0**（`Arc` の移動のみ） | 0.49 / 0.49 / 0.50 ms |
| 1920×1080 | **4.35 / 4.32 / 4.31 ms** | **0**（同上） | 1.70 / 1.67 / 1.69 ms |

- **UI スレッドからは全部消えた**。変換は評価ワーカーの `on_update`
  コールバック内（`EvalService` がワーカースレッドで呼ぶ）で走り、UI スレッドが
  受け取るのは出来上がった `RenderImage` の `Arc`。60 fps 予算 16.7 ms に対し、
  1024×576 で 7%、1080p で 26% を占めていた分がそのまま空く
- **変換自体も約 6 割速い**（1.21 → 0.49 ms / 4.32 → 1.70 ms）。バイトごとの
  `push` をやめ、確保済みバッファへ添字で書くようにした分
- `Arc::new(fb.clone())` は**測定上 0.000 ms**。`FrameBuffer::data` は
  `Arc<[u8]>` なので、この clone は初めから浅いコピーだった
  （HIGH-09 と計画書が「メインスレッドでフルフレーム複製」と読んでいた点は
  事実ではない）。現在は `FrameBuffer` 自体を UI スレッドへ運ばないので、
  この確保も無くなっている

**未計測**: 動作中のアプリのメインスレッドを直接プロファイルはしていない。
`perf_baseline.rs` は「ウィンドウを要する経路（notify / paint / ViewerFrame 発行）は
対象外」と明示しており（本ドキュメント冒頭の制約）、UI スレッドを実測する
ハーネスは存在しない。上表は**移した仕事そのものの実測**で、
再生 1 フレームあたり UI スレッドから外れる時間の上限ではなく実額（変換 1 回）。

ハーネス: 同 `perf_baseline.rs`（`# GPU-0` と `# Particle proxy` 節）。

### 直列化とパイプライン化

上表は毎フレーム `gpu.wait()` するので CPU と GPU が直列になる。待たずに

1M でパイプライン化が**遅くなる**のは、待たずに 5 フレーム分の
100 MB 級バッファを積むためにメモリ圧が上がるから。100k までは
パイプライン化が効く。

### 実行間のばらつき（5 回実行）

絶対値はマシンの状態で最大 1.7 倍ぶれる。**比率はぶれない。**

| 実行 | D / 100k 直列 | 同 パイプライン | `flatten` が CPU 側に占める比 |
|---|---|---|---|
| 1 | 19.51 | — | 77% |
| 2 | 18.24 | 13.59 | 77% |
| 3 | 31.36 | 15.02 | 79% |
| 4 | 25.60 | 19.54 | 76% |
| 5 | 19.91 | 12.64 | 75% |

上の各表は**最も軽かった実行（2 回目）**の値。判断に使う行は
**5 回すべてで予算 16.6 ms を超えている**（18.24〜31.36 ms）ので、
ばらつきは結論を変えない。パイプライン化した値は 12.64〜19.54 ms で、
**予算を跨いでいる**（4 回中 2 回が超過）。

### 判断: 実施（`GPU-0` = 実施）

計画の基準は「D の end-to-end が 10 万インスタンスで 16.6 ms を超えるなら
実施」。**5 回すべてで超過**（最速の実行でも 18.24 ms、min 16.82 ms）。
パイプライン化すると最速の実行では 13.59 ms で予算内に入るが、これは
**512×512・単一レイヤー・シェル合成なしの条件**で、1080p では GPU 側の
フラグメントコストが約 8 倍になり、レイヤーが増えれば CPU 側も比例する。
遅い実行ではパイプライン化しても 19.54 ms で超過する。

**ただし優先順は計画の想定と違う。**

- 計画は「CPU 評価 vs アップロード」で単位の優先を決める想定だった。
  実測では**どちらでもなく `raster_flatten`（CPU でのインスタンス展開）が
  支配的**（100k で 77%）。
- したがって「アップロードの差分化だけ（単位 1 のみ）に縮小」は**足りない**。
  100k で回収できるのは 18.24 ms のうち 1.20 ms。
- CPU フィールド評価（C の 100k で 1.17 ms）は 100k では問題ではない。
  1M で 11.92 ms になるので、WGSL フィールド評価（単位 2）が効くのは
  50 万要素超、またはフィールド段数が増えたとき。

## パーティクルの CPU / GPU 判断（`particle-plan.md` 単位 6）

`particle.simulate` は未実装なので、**同じ属性列に対する明示 Euler の
手書きステップ**を代用にした（proxy であることを明記する）。
点ドメイン（プリミティブなし）＝ラスタライザが円スプライトで描く形。

### 結果（ms / フレーム）

| 点数 | ステップ | wall（直列） | パイプライン | step のみ | flatten | upload |
|---|---|---|---|---|---|---|
| 10k | serial | 1.63 | 0.37 | 0.05 | 0.15 | 0.13 |
| 10k | rayon | 1.81 | 0.69 | 0.17 | 0.18 | 0.13 |
| 100k | serial | 5.09 | 4.02 | 0.41 | 2.29 | 0.99 |
| 100k | rayon | 6.53 | 3.60 | 0.35 | 2.40 | 0.98 |
| 1M | serial | 44.25 | 32.80 | 4.04 | 20.83 | 9.24 |
| 1M | rayon | 37.20 | 33.30 | 1.01 | 19.10 | 8.11 |

上表の「step のみ」は描画ループの中で計った値で、ジオメトリを毎フレーム
`Arc` に包んで渡すため属性列が一時的に共有される。**共有の影響を排除した
ステップ単体**も別に測った（描画に一切渡さない状態で回す）:

| 点数 | serial ms | rayon ms |
|---|---|---|
| 10k | 0.04 | 0.07〜0.11 |
| 100k | 0.38〜0.45 | **0.16〜0.27** |
| 1M | 4.15〜5.32 | 1.19〜1.57 |

**ステップ自体は安い。** 10 万点で rayon 0.2 ms 前後（予算の 1〜2%）、
100 万点でも 1.2〜1.6 ms。10k で rayon が serial より遅いのは、この規模では
スレッド起動コストが仕事量を上回るため。

**律速は描画経路**。10 万点で `flatten` 2.29 ms + `upload` 0.99 ms で、
ステップの 10 倍以上。インスタンス（D の 8.75 ms / 100k）より安いのは、
点はソースジオメトリを展開しないため（インスタンス展開が約 4 倍高い）。

### GPU 常駐状態の読み戻し

ステージングバッファは**計測区間の外で 1 回だけ確保**している（毎フレーム
読み戻す実装はバッファを使い回すため）。マップ後は 64 バイトおきに走査して
実際にページを触っている。

| 点数 | バイト数 | 読み戻し ms（3 回実行） |
|---|---|---|
| 10k | 160 KB | 1.28〜1.37 |
| 100k | 1.6 MB | 1.34〜1.36 |
| 1M | 16 MB | 1.91〜2.14 |

**1.6 MB までは submit + map の固定レイテンシ（≈1.3 ms）が支配的**で
サイズに依らない。16 MB では +0.7 ms 増えるので、そこから先はサイズにも
効く（増分だけ見れば約 23 GB/s）。GPU sim の状態を毎フレーム CPU 側へ
戻すコストは、10 万点で 16.6 ms 予算の約 8%、100 万点で約 12%。

> **2026-08-05: このハーネスは削除した（再計測できない）。** 上表は
> `perf_baseline.rs` の `state_readback_ms` が `GpuContext::device()` で
> 直接バッファを作って測ったもので、`GPUBK-4` がその生ハンドルを閉じた。
> `ravel-gpu` の転送抽象は**テクスチャしか扱わない**ので、同じ量を測り直す
> 口が無い。テクスチャ読み戻しへ置き換えると測る量が変わる
> （タイル解除を伴う `copy_texture_to_buffer`、256 B 行パディング、
> マップ範囲の疎な走査ではなくフルコピー）ので、上表と比較できなくなる。
> **数値を作り替えるより測れないことを記録する方を選んだ。** 再計測には
> バッファ読み戻しの抽象が要り、それは消費者（`GPU-1` の `GpuGeometry`）が
> 現れてから形を決める。

### 判断: 単位 6（GPU sim）の根拠はステップコストではない

`particle-plan.md` は単位 6 の完了条件に「10 万点で 1 フレームの step が
16.6 ms を大きく下回ること」を置いているが、**CPU 側が既に 0.2 ms 前後で
下回っている**。よって:

- **単位 1〜5 を CPU（rayon）で作る方針は実測で裏付けられた。** 10 万点なら
  CPU ステップで 60fps 予算の 1〜2% しか使わない。
- **GPU sim の価値はステップの高速化ではなく、状態を VRAM 常駐にして
  `flatten` + `upload`（10 万点で 3.3 ms、100 万点で 28 ms）を消すこと。**
  つまり単位 6 の実質的な前提は `GPU-1`（`GpuGeometry`）であり、
  計画がそう書いているとおり。ステップの WGSL 化は副産物。
- 読み戻しが 10 万点で ≈1.35 ms（固定レイテンシ律速）なので、
  「スクラブ中は CPU / 再生中は GPU」の使い分けは帯域面では成立する。
  100 万点だと ≈2.0 ms でサイズにも効き始める。VRAM とキャッシュの衝突
  （同計画の未解決節）は別問題として残る。

## 3D の頂点アップロード（`3d-scene-plan.md` 単位 4）

同計画は「GPU 常駐ジオメトリを前提にせず、`scene.render` の内部で頂点
バッファへアップロードする」と決めている。その前提が成立する規模を
`raster_upload` のスループットから読む。

| 転送 | 実測 |
|---|---|
| アップロード（6.4 MB 以上） | 6.5〜7.9 GB/s |
| アップロード（0.6 MB） | 約 5.0 GB/s（固定コストの比率が上がる） |
| 読み戻し（buffer → CPU） | 16 MB で 1.41 ms（実効 11 GB/s）。1.6 MB でも 1.32 ms なので**固定レイテンシ律速**で、帯域は測れていない |

頂点 32 B（位置 + 法線 + UV 相当）換算、上表の下限 6.5 GB/s で計算:

| 頂点数 / フレーム | アップロード ms |
|---|---|
| 10 万（3.2 MB） | ≈0.5 |
| 50 万（16 MB） | ≈2.5 |
| 100 万（32 MB） | ≈4.9 |

**数十万頂点までは毎フレームアップロードで成立する**（16.6 ms 予算の
3〜15%）。100 万頂点を毎フレーム上げると単一メッシュで予算の 30% を使う。
`3D-4` の実装時に**静的メッシュを毎フレーム上げ直さない**
（変更のないメッシュはバッファを保持する）ことを条件に入れれば、
`GPU-1` を待たずに済む。この点で 3D を `GPU-0` に依存させない判断は妥当。

## wgpu 抽象の取り分（`GPUBK-14` 判断ゲート）

計測日: 2026-08-06。環境: Apple M5 / macOS 26.3 / release ビルド / 10 コア /
512×512 Rgba32Float。base コミット `5e8fd70`。
loadavg は開始 1.81 → 終了 1.64（同時に別セッションの `codex` が 1 コア弱を
使っていた。A/B は各ラウンド内で交互に取っているので、緩やかな背景負荷は
両者に等しく乗る）。ハーネスは `crates/ravel-gpu/examples/metal_overhead_probe.rs`
（使い捨てのプローブ。`#[cfg(target_os = "macos")]`）。

**これは狭いプローブであり、10 レイヤー合成チェーンの Metal 再実装ではない。**
何を測っていないかは末尾の「このプローブで言えないこと」に書く。

### 測る対象を決めた実測: 評価 1 回あたりの記録パス数

`GPUBK-2` の記録は「submit 29 → 0.48 / 評価」だが、**submit 数とディスパッチ数は
別物**なので、`dispatch_stats()` に記録パス数（`dispatches`、`ComputeDispatch` と
`QuadDraw` 1 件ごとに 1）を足して数え直した。

| シナリオ | 記録パス | 完成評価 | パス / 評価 | submit / 評価 |
|---|---|---|---|---|
| `(g)` 10 レイヤー 30 fps 再生形 | 2330 | 77 | **30.26** | 0.48 |
| `(g)` 3 レイヤー 30 fps 再生形 | 690 | 76 | 9.08 | 0.14 |
| `(f)` 10 レイヤー スクラブ形（冷キャッシュ 1 回） | 50 | 1 | 50 | 1.00 |

プローブのチェーン長 1 / 10 / 30 / 50 はこの実測から採った（30 = 再生形、
50 = スクラブ形の冷評価）。

### (1) 完了済みディスパッチ 1 件のブロッキング待ち（µs）

| ラウンド | wgpu `PollType::Wait` | Metal `waitUntilCompleted` | Metal status スピン |
|---|---|---|---|
| 1 | 1518.4 | 202.5 | 211.9 |
| 2 | 1531.0 | 262.9 | 215.0 |
| 3 | 1523.0 | 200.3 | 199.0 |
| **中央値** | **1523.0** | **202.5** | **211.9** |

**wgpu 経由のブロッキング待ちは 1 回あたり約 1.32 ms 余分に払う。**
`GPUCOMP-10` の分析（`wgpu-hal` Metal の `Device::wait` が status 判定 →
未完了なら `thread::sleep(1ms)`）が予測したとおりの量で、実測はその 1 ms 刻みに
wgpu-core の `maintain` 分が乗った値。

**重要な追加事実: Metal の `waitUntilCompleted` はスピンと同じ速さ**
（202.5 vs 211.9 µs）。つまりここは「1 コアを焼くか 1 ms 待つか」の
トレードオフではない。**ブロックしたまま 1 ms を回収できる**ので、
`GPUCOMP-10` の記録にある「スピンなら拾えるがコアを焼く」という但し書きは
Metal では緩む。これは wgpu-hal の実装粒度の問題であり、上流修正でも
`wait_timeout` を使った有界スピンでも取れる。

### (2) N パスのチェーンを記述して submit する CPU 時間（µs、各3ラウンドの中央値）

| チェーン長 | wgpu パス/ディスパッチ | wgpu 単一パス | Metal エンコーダ/ディスパッチ | Metal 単一エンコーダ |
|---|---|---|---|---|
| 1 | 21.8 | 22.4 | 5.3 | 3.8 |
| 10 | 84.0 | 28.8 | 8.5 | 5.4 |
| 30 | 177.9 | 28.4 | 19.9 | 8.0 |
| 50 | 269.8 | 26.9 | 18.6 | 17.8 |

パスあたりの傾き（1 → 50 の差 / 49）:

| 経路 | µs / パス |
|---|---|
| wgpu、ディスパッチごとに 1 コンピュートパス（**現行の実装**） | **5.06** |
| wgpu、1 パスに N ディスパッチ | **0.09** |
| Metal、ディスパッチごとに 1 エンコーダ | 0.27 |
| Metal、1 エンコーダに N ディスパッチ（serial） | 0.29 |

**この項目のコストはほぼ全部「ディスパッチごとに新しいコンピュートパスを開く」
という我々のコードの構造から来ており、wgpu の抽象そのものではない。**
`ComputePipeline::dispatch`（`crates/ravel-gpu/src/compute.rs`）が
`begin_compute_pass` を 1 ディスパッチごとに呼んでいる。同じ wgpu で
1 パスに畳むと傾きは 5.06 → 0.09 µs/パス、つまり **56 分の 1** になる。
バックエンドを書かずに取れる。

再生形の 30.26 パス / 評価に当てはめると:

**内訳は基準を 1 つに固定して読むこと。** 4 つの計測列があるので、
どの 2 列の差かを書かないと足し合わせが成立しない。下表は native 側の基準を
**`Metal エンコーダ/ディスパッチ`**（wgpu の現行と同じくディスパッチ毎に
区切る形）に固定している:

| 差 | どの 2 列の差か | 評価1回あたり |
|---|---|---|
| **A: 全体** | `wgpu パス/ディスパッチ` − `Metal エンコーダ/ディスパッチ` | 158 µs |
| **B: wgpu の内側で取れる分**（1 パスに畳む） | `wgpu パス/ディスパッチ` − `wgpu 単一パス` | 149.5 µs |
| **C: バックエンドを書かないと取れない分** | `wgpu 単一パス` − `Metal エンコーダ/ディスパッチ` | **8.5 µs** |

この基準なら **A = B + C**（149.5 + 8.5 = 158.0）で閉じる。

**native 側を `Metal 単一エンコーダ` に取ると C は約 20 µs になる。**
差の 11.5 µs は Metal 自身のエンコーダ刻みの費用で、**wgpu の取り分ではない**
（下の (3) では刻み方の差が全チェーン長で誤差内）。**`C = 8.5 µs` と
`C' = 20 µs` を内訳として並べないこと** — 基準が違うので合計が合わない。
どちらの値でも 60 fps 予算 16.7 ms の **0.1% 未満**で、`GPUBK-10` の判定は
変わらない。

固定費（チェーン長に依らない submit 1 回分の差）は約 18 µs で、
チェーンを伸ばしても増えない。

### (3) GPU 完了まで含めたチェーンの wall（ms、各3ラウンドの中央値）

| チェーン長 | wgpu | Metal エンコーダ/ディスパッチ | Metal 単一エンコーダ | wgpu − Metal |
|---|---|---|---|---|
| 1 | 1.532 | 0.225 | 0.225 | +1.307 |
| 10 | 1.602 | 0.320 | 0.324 | +1.282 |
| 30 | 1.746 | 0.569 | 0.575 | +1.177 |
| 50 | 1.762 | 0.833 | 0.827 | +0.929 |

**差はチェーン長にほぼ依存せず約 1.0〜1.3 ms 一定**で、これは (1) のフェンス待ち
1 回分と一致する。**バリアの粒度による差は測れなかった**: Metal 側の
「ディスパッチごとに 1 エンコーダ」（＝ wgpu と同じ構造、エンコーダ境界ごとに
フルバリア）と「1 エンコーダに N ディスパッチ serial」が全チェーン長で
誤差内（0.225/0.225、0.320/0.324、0.569/0.575、0.833/0.827）。

**したがって「wgpu が自動でバリアを挿む分」の取り分は Metal では実質ゼロ。**
Apple GPU のコンピュートエンコーダ境界が十分に安いことを示しており、
`GPUBK-14` が容疑に挙げた 3 項目のうち 3 番目は**空振り**。

### フレーム全体への積み上げ（推定）

アプリの実経路は評価 1 回あたりブロッキング読み戻し 1 回を払う
（`crates/ravel-app/src/eval_hooks.rs` の `finalize` が `to_frame_buffer()` を
呼ぶ。なお `perf_baseline` の `BenchHooks` はこれをしないので、
シナリオ `(g)` の `readbacks` は 0 で、**ハーネスは再生形のフェンス待ちを
含んでいない**）。

| 項目 | 評価1回あたりの wgpu の取り分 | wgpu の内側で取れるか |
|---|---|---|
| フェンス待ちの粒度 | 約 1.32 ms（読み戻し 1 回分） | **取れる**（上流修正 / 有界スピン） |
| ディスパッチの encode | 158 µs | **149.5 µs は取れる**、20 µs は取れない |
| 自動バリア挿入 | 測定誤差内（0） | — |
| **合計** | **約 1.48 ms** | **約 1.46 ms が wgpu 内で取れる** |

**バックエンドを書いて初めて取れるのは約 20 µs / 評価**。
60 fps 予算 16.7 ms の **0.1%**。

### このプローブで言えないこと

完了条件の「wgpu 経由と直叩きで**同じ処理**を回す」からは外れている。
**逸脱として明記する:**

- **10 レイヤー合成チェーンの忠実な再現はしていない。** 測ったのは
  512×512 Rgba32Float のテクスチャ2枚を往復する自明なカーネル
  （読んで定数倍して書く）のチェーンで、実際の
  `network → transform → opacity → merge` ではない。WGSL → MSL の移植も
  していない（Metal 側はプローブ用に書いた別のカーネル）。
  **したがって上の「フレーム全体への積み上げ」は原価項目の差の積算による
  推定であり、フレーム全体を両経路で回して得た差ではない。**
- ノードプロセッサ側の CPU（パラメータ評価、`ensure_gpu`、プールの貸し出し）は
  両経路で共通なので測っていない。参考として、上のパス数を数えた
  `perf_baseline` の実行（同日、loadavg 2.96 の汚れた条件なので絶対値は
  当てにしない）では再生形の `evaluate` が 132.94 ms / 完成評価 77 回 =
  1.73 ms だったが、プローブの数字はその内訳ではない。
- シェーダのコンパイル結果（naga 経由の MSL と手書き MSL）の実行時間差は
  測っていない。カーネルが自明なので GPU 実行時間はどちらも
  メモリ帯域律速に張り付いており、**シェーダ品質の差はこの構成では出ない**。
- パイプライン / バインドグループの**作成**コストは測っていない。両経路とも
  事前に作って使い回している（`dispatch.rs` のキャッシュが定常状態で
  そうなっているのに合わせた）。
- 測ったのは **macOS / Metal のみ**。D3D12 / Vulkan で wgpu が吸収している量が
  同じ保証は無いので、この数字を横流ししない（`gpu-backend-plan.md` の
  `GPUBK-14` 節に明記）。
- タイムスタンプクエリは未使用。GPU 時間は wall から読んでいる。

## ビューア経路の表示解像度（`GPUBK-9` / `GPUCOMP-11` 判断ゲート）

計測日: 2026-08-06。環境: Apple M5 / macOS 26.3 / release ビルド /
10 レイヤーのシェルチェーン。`perf_baseline` の
「Viewer path at display resolutions」節と「Frame readback at display
resolutions」節を**同一実行**で突き合わせ、BGRA 変換だけ別に測った。
各 20 フレーム、3 ラウンド。

`VIEWER_MAX_DIM = 1024`（`crates/ravel-app/src/project_state.rs`）は
「シェル合成が CPU でレイヤーごとに readback する」ことへの譲歩として入った。
その前提は既に消えている（`GPUCOMP-2/3/4/9`、`GPUBK-6`）ので上限を見直す。

### 生の値

ビューア経路（評価 + ブロッキング読み戻し）。`readbacks/frame` は 1.00:

| ラウンド | loadavg | 解像度 | mean ms | min ms | max ms | 読み戻し窓 ms |
|---|---|---|---|---|---|---|
| 1 | 3.35 | 1024x576 | 5.38 | 4.20 | 6.88 | 4.10 |
| 1 | 3.35 | 1920x1080 | 17.91 | 14.90 | 26.66 | 13.23 |
| 2 | — | 1024x576 | 4.88 | 3.90 | 5.68 | 3.84 |
| 2 | — | 1920x1080 | 14.24 | 12.91 | 15.66 | 11.13 |
| 3 | — | 1024x576 | 4.94 | 4.04 | 5.89 | 3.86 |
| 3 | — | 1920x1080 | 14.15 | 12.75 | 16.99 | 11.16 |

**ラウンド 1 は捨てる。** 3 ラウンドとも 1 回目だけ悪く（1080p で 17.91 対
14.24 / 14.15）、ウォームアップの分。中央値は定常のラウンド 2 / 3 から取る:
`1024x576` **4.94 ms**、`1920x1080` **14.2 ms**。

同一実行の単独読み戻し（`to_frame_buffer` のみ。GPU コピー + CPU コピー）:

| 解像度 | MB/frame | mean ms（中央値） |
|---|---|---|
| 1024x576 | 9.4 | 1.52 |
| 1920x1080 | 33.2 | 2.04 |
| 3840x2160 | 132.7 | 5.54 |

BGRA 変換（`ViewerImage::from_frame_buffer`、`ravel-app`。RGBA f32 →
BGRA u8 の毎ピクセル CPU ループ。20 回の中央値）:

| 解像度 | mean ms（中央値） |
|---|---|
| 1024x576 | 0.75 |
| 1920x1080 | 1.63 |
| 3840x2160 | 6.44 |

### 内訳（1080p、10 レイヤー）

**「読み戻し窓」の列は転送コストではない。** `to_frame_buffer` は
コピーが着くまでブロックするので、**評価が投げた GPU 仕事の完了待ちを丸ごと
含む**（ハーネスのコメントにもそう書いてある）。`submits/frame = 1.00` なので、
10 レイヤー分のディスパッチはこの 1 回の待ちで drain される。
単独読み戻しの実測（2.04 ms）と引き算して分ける:

| 成分 | ms | 割合 | 消える条件 |
|---|---|---|---|
| CPU 評価（ディスパッチ記述・パラメータ） | 約 3.1 | 20% | 評価の短縮 |
| **GPU 計算（10 レイヤー、待ちに畳まれる）** | **約 9.1** | **58%** | **評価の短縮** |
| GPU→CPU 転送 | 2.04 | 13% | ゼロコピー表示 |
| BGRA 変換 | 1.63 | 10% | ゼロコピー表示 |
| GPUI 再アップロード / present | **未測定** | — | ゼロコピー表示 |
| 測定済み合計 | **約 15.8** | | |

`1024x576` は同じ分解で約 **5.7 ms**（4.94 + BGRA 0.75）。

### 判定

1. **1080p 常時 60 fps は現時点では届かない。** 測定済みで 15.8 ms、予算
   16.7 ms に対し残りは 0.9 ms で、そこに GPUI のアップロード（1080p BGRA で
   8.3 MB）と present が入るとは考えにくい。**ただし余裕が無いだけで桁は違わない** —
   30 fps 予算 33.3 ms なら大きく余る
2. **ゼロコピー表示だけでは足りない。** 消えるのは転送 2.04 + 変換 1.63 =
   **3.7 ms + 未測定のアップロード**で、合計の約 23%。**支配項は GPU 計算
   9.1 ms（58%）で、これはゼロコピーでは減らない**
3. **読み戻しの回数はもう減らせない。** `readbacks/frame` は既に 1.00
4. **転送と変換はどちらも帯域律速。** 9.4 → 33.2 MB（3.5 倍）に対し転送は
   1.52 → 2.04（1.3 倍。固定費が大きい）、変換は 0.75 → 1.63（2.2 倍）。
   4K では転送 5.54 + 変換 6.44 = 11.98 ms が出口だけで掛かる

したがって**「常時フル解像度」を目標に置かない**。`VIEWER_MAX_DIM` という
隠し定数をやめ、**解像度係数をユーザー制御にする**（`Full` / `1/2` / `1/4` +
操作中は自動で落とす適応解像度。After Effects / Nuke / Fusion と同じ形）。
`1/2` が現行 1024 相当のコストで編集中の既定になり、`Full` は手を止めたときの
品質確認に使える。**この形なら、フル解像度での確認能力はゼロコピー表示を
待たずに手に入る** — ゼロコピーは前提ではなく後からの最適化になる。
計画は別途（設計ゲート対象）。

### この数字で言えないこと

- **GPUI 側のアップロードと present は測っていない。** 上の 15.8 ms は
  「評価してから CPU 上に表示可能なビットマップが出来るまで」で、
  画面に出るまでではない。**実際の表示レートは実機でしか確認できない**
- ヘッドレス直接評価なので、`EvalService` のスレッド往復とキャッシュヒット率は
  反映されていない
- 10 レイヤー固定。レイヤー数で GPU 計算だけが伸びるので、レイヤーが増えると
  ゼロコピーの相対的な効き目はさらに下がる
- `GPUCOMP-10`（非同期リードバック）の再評価条件は「`VIEWER_MAX_DIM` 撤廃時」。
  隠し定数をユーザー制御へ置き換える形はそれに当たるので、その計画で読み直すこと。
  ただし隠せるのは転送 2.04 ms で、GPU 計算の 9.1 ms は隠せない
- loadavg 3.35 前後で測っている。この機体の平常値がそこ（WindowServer と
  ブラウザ）で、1.8 以下は待っても来ない。**ラウンド内は同一条件なので
  内訳の比は頑健**だが、絶対値は空いた機体ならもう少し良い

## フィールド式の要素数スケーリング（`expression-language-plan.md` `EXPR-5`）

計測日: 2026-08-07。環境: Apple M5 / macOS 26.3 / release ビルド。
ハーネス: `crates/ravel-core/examples/field_expression_scaling.rs`
（`cargo run -p ravel-core --release --example field_expression_scaling`）。

`EXPR-5` の完了条件「要素数に対して線形であることの測定」の記録。

### 計測方法

- `ExpressionField::sample` を 1e3 / 1e4 / 1e5 要素で直接呼ぶ。
  評価器・グラフ・キャッシュは通さない（測る対象は sample のループだけ）。
- **3 サイズをラウンドロビンで回す**（サイズごとに全ラウンドを回すのではなく、
  1 ラウンドで 3 サイズを 1 回ずつ）。負荷スパイクが 1 サイズだけに乗るのを
  避けるため。9 ラウンドの中央値を取り、同ラウンド群の max/min も併記する。
- 各サイズにつき計測前に 1 回空打ちして、出力 Vec の初回確保のページ
  フォールトを最初のラウンドに払わせない。
- 位置は 1920×1080 に決定的に散らした `Vec2`。

### 結果（中央値、9 ラウンド）

| 式 | 1e3 | 1e4 | 1e5 | ns/要素（1e5） | 1e5÷1e3 の単価比 |
|---|---|---|---|---|---|
| `@P.x * 2 + @P.y` | 0.009 ms | 0.10 ms | 0.97 ms | 9.7 | 1.13x |
| `sin(@P.x * 0.1) * cos(@P.y * 0.1) * 100` | 0.025 ms | 0.25 ms | 2.44 ms | 24.4 | 0.98x |
| `noise(@P.x * 0.1, time) * (1 - @P.y / res.height)` | 0.023 ms | 0.23 ms | 2.34 ms | 23.4 | 1.02x |

**単価比が 1.0 前後に張り付いているので線形。** 2 回目の実行（同条件）は
それぞれ 1.06x / 0.97x / 1.04x で、実行間のばらつきは 5% 程度。

要素あたり 10〜25 ns は「AST ノードごとのディスパッチ」の桁で、パースが
ループに入っていれば µs 桁になる。仕様書の例（`noise` 版）が 1e5 要素で
2.3 ms。

### 測定条件（そのまま読まないこと）

- **loadavg 3.6〜6.1 で測っている。** 同じ機体で別の実装単位のビルドが
  2 本並行しており、アイドルは待っても来なかった。**絶対値は空いた機体なら
  もう少し良い**。ラウンドロビンにしてあるので**サイズ間の比（＝線形性の
  主張）は頑健**だが、ns/要素をそのまま他の環境と比べないこと。
- 1e3 の `@P.x * 2 + @P.y` だけ max/min が 1.5〜1.75x に開く。9 µs の
  計測でスケジューラのノイズが相対的に大きいだけで、中央値は安定している。
- 変数スライス（`expression::field_values`）はバッチにつき 1 回しか作らない。
  したがって要素数が小さいほど固定費の取り分が大きく見える。
- **測った 3 式はすべて `@P` を参照しているので、要素ごと評価の経路に乗る。**
  `ExpressionField::sample` は `@P` の成分を 1 つも参照しない式では
  **バッチにつき 1 回だけ評価して結果をブロードキャストする**ので、
  `sin(time)` のような式は要素数に対して定数時間になる。上の線形性は
  「位置を読む式のコスト」であって、フィールド式一般の上限ではない。

## 表示変換のコスト（フェーズ CM 完了時）

パイプラインがリニアになったので、f32 バッファを 8bit にするときに**伝達関数を
掛ける**ようになった（`ravel_core::color::to_display_rgba8`）。それ以前は
`clamp * 255 + 0.5` だけだったので、この単位はコストを追加している。

当初の実装は色成分ごとに `f64` の `powf` を 1 回呼ぶ直列ループで、
1920×1080 に 35 ms 前後かかっていた。それを 2 段で削った結果が下の数字。

1. **境界表**（`ravel_core::color` の `DISPLAY_CODE_THRESHOLDS`）。8bit の
   出口は 1 チャネル 256 値しかなく写像は単調なので、伝達関数は
   「255 個の境界のうち何個を超えたか」しか決めていない。表を引けば
   `powf` は 1 回も要らない。**出力は元の実装とビット単位で同一**
   （境界は理想の逆関数ではなく、元の式が `k` を返す最小の `f32` を
   ビット列の二分探索で求めてある）
2. **rayon**（`ViewerImage::from_frame_buffer`）。画素ごとに独立なので
   計算式を一切変えずに並列化できる

### 計測方法

- **スカラー変換のみ**: `ravel-core` の
  `color::tests::measure_display_transform_cost`（`--release --ignored`）。
  1920×1080 相当（2,073,600 画素 × RGBA）に対し、量子化のみ / `powf` /
  境界表の 3 経路を**1 ラウンドずつ交互に 6 ラウンド**、中央値を取る。
  2 つの変換が同じバイト列を返すことをテスト内で assert している
- **Viewer の変換関数全体**: `ravel-app` の
  `panels::viewer_image_tests::measure_display_conversion_cost`。BGRA 並べ替えと
  `RenderImage` 生成まで含めて、旧実装 / 同じ計算の直列版 / 現行（rayon +
  境界表）を**40 回のあいだ 1 回ずつ交互に**測る

### スカラー変換のみ（1920×1080、中央値）

| 経路 | 1 フレーム | 対 `powf` |
|---|---|---|
| 量子化のみ（変換が無料でもここが床） | 2.06 ms | — |
| 伝達関数を `powf` で評価（旧） | 34.24 ms | 1.0× |
| 境界表（現行） | 13.59 ms | **2.5×** |

### Viewer の変換関数全体（`from_frame_buffer`、40 回平均）

> **`CM-7` 以降、このハーネスは無い。** 表示変換は GPU（リードバック前の
> 1 パス）へ移り、`ViewerImage::from_frame_buffer` と
> `measure_display_conversion_cost` / `reference_bgra` は削除された。
> 以下は**当時の記録**であって、再現できるコマンドではない。

| 経路 | 1920×1080 | 1024×576 |
|---|---|---|
| 旧（直列 + `powf`） | 38.2–39.3 ms | 10.8–11.3 ms |
| 境界表のみ（直列） | 16.4–16.8 ms | 4.6–4.9 ms |
| 境界表 + rayon（現行） | **3.71–3.90 ms** | **1.15–1.43 ms** |

- rayon 単体の取り分は **4.3×**（1920×1080）。10 コア（性能 6 / 効率 4）で
  loadavg 10 前後なので、コア数どおりには伸びない
- 合計 **10.1×**（1920×1080）、**8.4×** 前後（1024×576）

### 読み方

- **境界表の取り分は見込みより小さい。** 「`powf` を消せば桁が変わる」という
  当初の見立てに対し、実測は 2.5× にとどまった。255 要素の二分探索は
  `powf` より安いだけで**定数時間ではない**（1 チャネルあたり 8 回の
  依存した比較）。しかも量子化のみの床が 2.06 ms あるので、**変換が完全に
  無料になっても上限は 17×** で、桁の改善は CPU のスカラー経路には
  そもそも無かった。数字を作らずそのまま記録しておく
- **`CM-7` の GPU 3D LUT の価値は変わらない。** 境界表は `powf` を消すだけで
  変換の定義を変えていないので、precision-first の判断とも矛盾しない。
  GPU に焼けばこのコストは削れるのではなく**無くなる**
- 伝達関数を `f32` の `powf` で評価する案（かつて 28% の節約と記録して
  いた）は**用済み**。境界表がそれより速く、しかも定数を二重に持たない
- **UI スレッドではない。** `GPUCOMP-9` 以降この変換は評価ワーカーで走るので
  操作が固まることはなく、効くのはプレビューのスループット。Viewer は
  `ViewerResolution` の対話用上限で評価するので、実効値は 1024×576 側
- **書き出し側は速くなっていない。** レンダーは
  `to_output_space`（f32 のまま表示空間へ符号化）→ `quantize_u8` の 2 段で、
  `to_display_rgba8` を通らない。境界表は「リニア f32 → 8bit コード」を
  1 段で解く仕掛けなので、途中に f32 を挟むこの経路には効かない。
  EXR は作業空間のままなので元から払っていない

### 測定条件（そのまま読まないこと）

- M 系ラップトップ（10 コア: 性能 6 / 効率 4）、`--release`。
  **loadavg 4.8〜6.1**（スカラー変換）、**10.2〜13.4**（Viewer 全体）。
  この機体は再起動しない限り静穏にならないので、静穏を待たずに測っている
- **妥当性は測り方で担保している**: どの経路も**交互に**測っており
  （スカラーは 6 ラウンド、Viewer 全体は 40 回）、負荷の揺れは全経路に
  等しく乗る。**見るべきは比で、絶対値ではない**
- rayon の取り分は特に負荷に依存する。loadavg 10 での 4.3× は下限側の値で、
  空いた機体ではこれより伸びる

## 表示変換を GPU へ移したあと（`CM-7`）

計測日: 2026-08-10。環境: Apple M 系 / macOS / `--release`。ハーネス:
`crates/ravel-nodes/tests/display_transform.rs` の
`measure_display_transform_cost`（`#[ignore]`、
`cargo test -p ravel-nodes --release --test display_transform
measure_display_transform_cost -- --ignored --nocapture`）。
1920×1080、1 ラウンドで旧経路と新経路を**交互に**測って 20 ラウンドの平均、
3 回実行。**loadavg 10.8〜14.2**（この機体は静穏にならない）。

旧経路は `CM-7` が置き換えたものを逐語で再現してある: リードバック
（1 画素 16 バイト）＋ `to_display_rgba8` の rayon ループ。新経路は
`DisplayTransform::run` — 1 ディスパッチ＋ 1 画素 4 バイトのリードバック。

**上の「表示変換のコスト（フェーズ CM 完了時）」の 3.71〜3.90 ms と直接
比べないこと。** あちらは `from_frame_buffer` の中だけを測っていて
リードバックを含まない。`CM-7` はリードバック量そのものを変えるので、
ここでの比較対象は**フレームが画面に届くまで**（読み戻し＋変換）にしてある。

| 入力の在処 | 旧 | 新 | 比 |
|---|---|---|---|
| **GPU 常駐**（Viewer の通常経路） | 5.98 / 6.09 / 7.18 ms | 2.01 / 2.04 / 1.89 ms | **2.97× / 2.99× / 3.79×** |
| CPU 常駐 | 3.40 / 3.70 / 4.32 ms | 6.16 / 6.17 / 5.90 ms | 0.55× / 0.60× / 0.73× |

**CPU 常駐のフレームは遅くなった。** 旧経路はアップロードを払わなかったが、
新経路は 1 画素 16 バイトを上げてから 4 バイトを下ろす。**この事実ごと
残す**: 合成チェーン（`comp.merge` / `comp.transform` / `comp.opacity`）と
`rasterize` は GPU 実装を持つので Viewer の出力は通常 GPU 常駐だが、
出力ノードが CPU 専用の処理系だと 1080p でおよそ 1.7 倍の時間が掛かる。
変換点を 2 つに戻せば避けられるが、それは `CM-7` が消したものそのもの。

**リードバックの往復は残っている。** 削れたのは画素ごとの CPU 計算と
転送量であって、GPU → CPU → GPUI の往復ではない（`HIGH-09` の残り）。

## 残った往復の内訳（`ZC-1`、判断ゲート）

計画: `zero-copy-viewer-plan.md`。計測日: 2026-08-10。
環境: Apple M 系 / macOS / `--release`。ハーネス:
`crates/ravel-app/tests/viewer_roundtrip.rs` の
`measure_viewer_roundtrip_breakdown`（`#[ignore]`）。

```text
cargo test -p ravel-app --release --test viewer_roundtrip \
    measure_viewer_roundtrip_breakdown -- --ignored --nocapture
```

**loadavg 2.53〜2.58**（1 分値。ハーネスが開始時に出力した値）。上の `CM-7`
節と違い、この計測は他のビルドやベンチが走っていない静穏時のもの。
1 セルにつき**ウォームアップ 1 巡**（パイプラインの初回コンパイルと、その
サイズのステージングバッファ確保。`perf_baseline.rs` のリードバック計測が
同じ扱いをしている）の後、20 ラウンド。各ラウンドで 3 つの計測を**交互に**
取り、その平均。**3 回実行**。

### 段の定義

`CM-7` の後、GPU 常駐のフレームが画面に届くまでの 4 段:

1. **表示変換** — `DisplayTransform::run` の 1 ディスパッチ。
   **ゼロコピーにしても残る**
2. **リードバック** — 4 バイト/画素の GPU → CPU。**消える**
3. **CPU 側の包み** — `ViewerImage::from_display_frame`。共有リードバック
   バッファから `RenderImage` が持つ `Vec` への 1 コピー。**消える**
4. **GPUI のアップロードとアトラス churn** — **消えるが測れない**

**段 4 は測定できない。** gpui-ce の内部にあり、ウィンドウ無しには計測
できず、このリポジトリに UI スレッドのハーネスは存在しない（この文書
冒頭の「除外している UI 側処理」と同じ制約）。よって **段 2 + 段 3 を
ゼロコピーの得の推定値**として扱う。段 4 は推定値に上積みされるだけなので、
未測定でも判断の向きは変わらない。

### 「下界」ではなく「推定」である理由

**段 2 は `run` が読み戻すテクスチャではなく、同じキーで別に確保した
テクスチャで単独計測している。** しかも `run` が自分のリードバックで
ブロックし終わった**後**に走るので、`run` の中のリードバックが抱えている
ディスパッチ待ちを含まない。段 2 は `run` の中のリードバックの**代理値**で
あって、測定経路から切り出した一片ではない。だから下界とは呼べない。

**代理値の妥当性は表の最終列で検算している。** 段 1+2 から段 2 を引いた差は
ディスパッチ 1 回分に収まらなければならず、実際 4K Full を除く全セルで
**|差| ≤ 0.09 ms**（符号が負のセルもある — 代理値の誤差そのもの）。
4K Full だけ 1.47〜1.60 ms で、これは 830 万画素のディスパッチが実際に
掛かる時間。**推定値の誤差はディスパッチ 1 回分の内側**と読むこと。

### 結果（3 回分を `/` 区切り、単位 ms）

| 合成解像度 | factor | 実寸 | 段 1+2 | 段 2 | 段 3 | **推定（2+3）** | 検算（1+2 − 2） |
|---|---|---|---|---|---|---|---|
| 1920×1080 | Full | 1920×1080 | 1.669 / 1.719 / 1.680 | 1.616 / 1.688 / 1.662 | 0.345 / 0.347 / 0.330 | **1.962 / 2.035 / 1.992** | 0.053 / 0.031 / 0.018 |
| 1920×1080 | Half | 960×540 | 1.574 / 1.583 / 1.612 | 1.545 / 1.586 / 1.569 | 0.085 / 0.095 / 0.084 | **1.630 / 1.681 / 1.654** | 0.029 / −0.003 / 0.043 |
| 1920×1080 | Quarter | 480×270 | 1.544 / 1.519 / 1.537 | 1.535 / 1.563 / 1.565 | 0.039 / 0.036 / 0.036 | **1.574 / 1.599 / 1.601** | 0.008 / −0.044 / −0.028 |
| 3840×2160 | Full | 3840×2160 | 3.680 / 3.976 / 3.590 | 2.206 / 2.377 / 2.073 | 1.407 / 1.500 / 1.223 | **3.613 / 3.877 / 3.296** | 1.474 / 1.599 / 1.518 |
| 3840×2160 | Half | 1920×1080 | 1.766 / 1.702 / 1.701 | 1.678 / 1.694 / 1.668 | 0.819 / 0.802 / 0.350 | **2.498 / 2.496 / 2.018** | 0.088 / 0.008 / 0.033 |

**推定と検算の列は丸める前の値から出している**ので、表示されている段 2 と
段 3 を足しても末尾 1 桁が合わないセルがある。

転送回数はどのセルも **20 ラウンドで 40 リードバック / 0 アップロード**
（`run` の中で 1 回、段 2 の単独計測で 1 回。ウォームアップ 1 巡は計数の
外）。入力フレームはラウンドが始まる前に GPU へ上げてあるのでアップロード
は 0。**負荷は時間を動かすが回数は動かさない**ので、回数はこの表の妥当性の
チェックに使える。

### 判断: **続行**

しきい値は 60 fps 予算 16.7 ms の 5% = **0.835 ms**。

**全 18 セルが段 2 + 段 3 だけでしきい値を超えている。**

- 最小セル（1080p Quarter）: 1.574〜1.601 ms = **1.88×**
- 最大セル（4K Full）: 3.296〜3.877 ms = **3.95〜4.64×**
- Viewer の既定に近い 1080p Full: 1.962〜2.035 ms = **2.35×**

**往復を消して得られる時間**は、1080p Quarter でも 1.5 ms 以上、
4K Full で 3.3〜3.9 ms。**この数字は推定値だが、しきい値に対する余裕
（最小セルでも 1.88 倍）が分解の不確かさ（ディスパッチ 1 回分、小さいセルで
0.09 ms 以下）より一桁大きい**ので、推定であることは結論を揺らさない。
段 4（GPUI のアップロードとアトラス churn）は未測定だが、**消える側にしか
効かない**ので、上積みされることはあっても差し引かれることはない。
よって計画を凍結する条件（得が 0.835 ms を下回る）は満たされず、
**`ZC-2` 以降へ進む**。

**内訳は ingest が支配的。** `decode_video_frame` の中で段ごとに計時すると、
8.1〜8.2 ms は **ingest 7.2〜7.3 ms + scale 0.33 ms + デコード約 0.5 ms** で、
**ingest が全体の約 89%**。`HIGH-32` 節の u8 PQ の 7.211 ms と一致する
（あの節の初出値が 3 倍過大だったことは同節の訂正に書いた。この一致は補正後の
値でのみ成立する）。

HIGH-17 は色変換そのものを変更していないので **ingest の床はそのまま残る**。
1080p / 8bit で削れるのは 1920×1080 の YUV420P → RGBA BILINEAR コンテキスト 1 個の
構築費用、実測で **0.06〜0.10 ms（約 1%）** にとどまる。
**票が「デコード経路の CPU 時間を支配する」と書いていたのは実測では成立しない。**
支配しているのは ingest であり、それは `HIGH-32` が既に 6〜7 倍速くした後の残りである。
バイアスを取り除いた結果、この結論はむしろ強まった。

なお 1 枚ごとに decoder を open / drop する経路（`crates/ravel-media/src/image_seq.rs`
の静止画・画像シーケンス、`crates/ravel-app/src/media/thumbnail.rs` のサムネイル）は
decoder が 1 フレームしか生きないので、scaler cache の恩恵をまったく受けない。

## 往復を消した後（`ZC-2`〜`ZC-4`、macOS）

計画: `zero-copy-viewer-plan.md`。記録日: 2026-08-11。

**時間の実測は載せない。載せられない。** `ZC-1` が分解した 4 段のうち、
ゼロコピーで消えるのは段 2（リードバック）・段 3（CPU 側の包み）・
段 4（GPUI のアップロードとアトラス churn）で、**段 4 は gpui-ce の内部に
あってウィンドウ無しには測れない**（`ZC-1` 節に同じ制約を書いた）。
「消えた時間」を主張すれば、測れない段を含んだ数字になる。

`ZC-1` の推定はそのまま有効: 段 2 + 段 3 が **1.70〜4.70 ms**（18 セル）で、
これが消えた分の下限。段 4 はそこに上積みされる。

### 代わりに何で確認したか — 回数

計画書の検証節が「**時間ではなく回数を pin する** — 時間は負荷で動くが回数は
動かない」と定めており、そちらで固定した。

| 観測 | 手段 |
|---|---|
| ゼロコピー経路のリードバックが **0 回** | `crates/ravel-nodes/tests/display_surface.rs` の `the_surface_path_removes_the_readback_and_the_fallback_keeps_it` |
| フォールバック経路は **1 回**（退行検出のため両方見る） | 同上 |
| 絵が変わらない | 同ファイル `both_roads_produce_the_same_display_bytes`（両経路のバイト列が**完全一致**） |
| フレーム跨ぎの取り違えが無い | 同ファイル `consecutive_surface_frames_keep_their_sequence` |
| 実機で破綻しない | 平面レイヤーを 299 フレーム再生、ティアリング・パニック・フォールバック警告なし（`ZC-4`） |

**0 回と 1 回の両方を固定しているのが要点。** ゼロコピー側だけを見ると、
フォールバックが壊れて両方 0 になった場合に気づけない。

### この節が「測り直し」を載せていない理由

2026-08-11 に `measure_viewer_roundtrip_breakdown` を回したが、
**その数字は破棄した**。ハーネス（`crates/ravel-app/tests/viewer_roundtrip.rs`）は
ゼロコピー経路を有効化しないので CPU 経路を測っており、しかも直前の
release ビルドで loadavg が 14 まで上がっていた（`ZC-1` 時は 2.5 前後）。
**ゼロコピー後の時間を測るには、その経路を通すハーネスを別に書く必要がある。**
