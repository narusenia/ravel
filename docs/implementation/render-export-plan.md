# 書き出し実装計画（REQ-RENDER-001 / REQ-RENDER-005）

> **Status**: Planned — 2026-07-27（**2026-08-03 改訂**: CLI 先行、音声を対象化）

対象要件: REQ-RENDER-001（キューベースバックグラウンドレンダリング）、
REQ-RENDER-005（CLI ヘッドレスレンダリング）。
関連: REQ-CORE-005、REQ-CORE-009、REQ-MEDIA、REQ-PROJ-006。
前提計画: `motion-blur-plan.md`（品質段階）、`done/exposed-parameters-plan.md`（`--param`）。

## 2026-08-03 改訂の要点

| 変更 | 理由 |
|---|---|
| **CLI を GUI ダイアログより先に出す**（単位順の入れ替え） | CLI が先なら書き出し経路の全体をヘッドレステストで検証できる。GUI は後から薄いダイアログを載せるだけになる |
| **永続化の抽出を単位 0 として追加** | `.ravprj` の load / save が `ravel-app`（GPUI バイナリクレート）にある。CLI はこれを避けられない。`.agents/rules/rust.md` も「persistence logic must work without a live UI」と定めている |
| **音声を対象に入れる**（旧「非対象」を撤回） | 前提だった `HIGH-10`（seek の時間基準）/ `HIGH-11`（トリム）はフェーズ A3 で解決済み。`Mixer::mix(&self, offset, count)` は純関数でデバイスと結合していないので、オフラインミックスダウンは構造的にほぼ無料 |
| **フレーム範囲分割の保証を追加** | 連番出力のファイル名を絶対フレーム番号にするだけで、外部から N プロセスに分割してレンダーファームが組める。実装コストはほぼゼロ |

## 問題

**作ったものをファイルにできない。** REQ-RENDER-001/002/003 が丸ごと未実装で、
`plan.md` も「a complete render queue/export workflow ... not implemented」と
記録している。

`ravel-media` には FFmpeg ベースのエンコード機能があるが、**アプリ層の
導線が無い**。モーショングラフィックスの機能をいくら足しても成果物が出せない。

## 決定事項（2026-07-27 設計セッション）

### 専用レンダーワーカー + 専用 `Evaluator` + 共有 `GpuContext`

対話用の `EvalService` は再利用できない。**キューに溜まったリクエストを
latest-wins で捨てる**（`eval_service.rs:161`）ので、全フレームが必要な
レンダリングには使えない。

一方で `GpuContext { inner: Arc<GpuContextInner> }`（`ravel-gpu/src/device.rs:24`）
は安価にクローンでき、wgpu の device / queue は共有される。したがって
2 本目の `Evaluator` を立てても複製されるのは **CPU 側キャッシュと
プロセッサ登録だけ**。

キャッシュ分離はむしろ利点で、フレーム 500 のレンダリングが対話中の
フレーム 10 の結果を追い出さない。

### ドキュメントスナップショットでレンダー中の編集を許す

`EvalRequest.document: Option<Arc<Document>>` が既にスナップショット。
ジョブ投入時の `Arc<Document>` を保持すれば、**レンダー中にユーザーが
編集しても出力は投入時の状態のまま**になる。追加機構は要らない。

### 永続化を GUI から出す

計画時点では `crates/ravel-app/src/project/mod.rs:418,426` に `.ravprj` の
save / load があった。`ravel-app` は GPUI バイナリクレートなので、CLI が
ここに依存すると GPUI をリンクすることになる。**`EXPORT-0` で
`crates/ravel-project`（GUI 非依存）へ抽出済み。**

**抽出は機械的。** `project/*.rs` の依存は `ravel_core` + `ravel_ui` +
`thiserror` だけで、**gpui を一切 import していない**。`zip` / `ron` /
`serde_json` / `dirs` も移設可能。ただし `ravel_ui::layout_doc::LayoutDocument`
に依存する（`.ravprj` が UI レイアウトを含む）ので、CLI も `ravel-ui` を引く
（ヘッドレスなので無害）。

### CLI を GUI ダイアログより先に出す

レンダーワーカーは GUI と CLI の共有部品（REQ-RENDER-001）。CLI を先に作ると
**書き出し経路の全体がヘッドレステストで検証できる**（フレーム数・決定性・
キャンセル・部分出力の削除・音声の同期）。GUI ダイアログはその上に載る
薄い層になり、実機確認の対象が「ダイアログの操作」だけに縮む。

逆順にすると、GUI 経由でしか検証できない状態が先にでき、CLI を足すときに
テストを書き直すことになる。

### 音声を含める

旧計画は音声を非対象にしていた。前提が解消されたので撤回する。

- `HIGH-10`（`decode_audio_chunk` の seek が時間基準を誤る）と
  `HIGH-11`（要求位置までトリムしない）は**フェーズ A3 で解決済み**
  （`issues/closed/`）。範囲レンダリングが音声ファイルへ seek しても正しい位置に着く
- `Mixer::mix(&self, frame_offset, frame_count) -> Vec<f32>`
  （`ravel-audio/src/mixer.rs:240`）は `&self` の純関数で、CPAL や
  リアルタイムクロックと結合していない。**再生経路の issue
  （`HIGH-12`〜`15`）を踏まない**
- 制約: `Track::new(id, samples: Arc<[f32]>, channels)` は全サンプルを
  メモリに持つ（`MAX_DECODE_BYTES` 128MiB 上限）。長尺では効いてくるので
  受入条件に上限超過時の挙動を入れる

出力の形は「**常に音声を生成し、形式に応じて多重化または併置**」。
動画コンテナなら mux、連番なら同じ範囲の WAV を併置する。`--range` 分割時も
各プロセスが自分の範囲の WAV を出すので整合する。

### Write ノードは v1 に入れない

REQ-RENDER-002 の Write ノードは「評価結果をディスクに焼いて次回以降
そこから読む」使い方が本命で、それは三層キャッシュ（REQ-CORE-006、
ディスク層が未実装）の領域。単なる「ファイルに書く副作用ノード」として
作ると `process()` が副作用を持ち、評価の純粋性を壊す。

v1 の書き出しは**評価グラフの外側**に置く。レンダーワーカーがフレームを
回してエンコーダに渡すだけ。

### 品質は `Final` を要求する

`motion-blur-plan.md` の単位 3 が `EvalContext.quality { Preview, Final }` を
導入する。レンダーワーカーは `Final` を要求し、Viewer の 1024 縮小や
低サンプルのモーションブラーを踏まない。**この計画は品質段階に依存する。**

**精度も併せて要求する。** `cache-plan.md` はキャッシュエントリに精度
（f32 / f16 / 8bit）を持たせ、要求側が最低精度を宣言する規約にしてある。
レンダーワーカーは `min_precision = F32` を要求するので、プレビュー用に
縮約された f16 エントリは**自動的にミスになる**。これにより
「キャッシュが温まっているかどうかで成果物が変わる」事故が構造的に
起きない。キャッシュを共有するか分離するかに関わらず、この宣言は必要。

### 既存の出力への上書きは既定で拒否する

`Encoder::abort` は**自分が作っていないファイルを消さない**（`EXPORT-1`）。
正しい挙動だが、既存の連番へ再レンダーして途中で中断すると、到達した
フレームだけ新内容・残りは旧内容という**混在した連番が、名前の上では
正常な顔で残る**。

したがってレンダーワーカーは、**ジョブを始める前に**出力先を調べ、
同じ名前のファイルが 1 つでもあれば**1 フレームも評価せずに失敗させる**。
上書きは `RenderJob` のフラグ（`OverwritePolicy::Replace`）による
明示的なオプト・インでのみ許す。

判定は**ファイル名単位**で行う。ディレクトリが空かどうかで判定すると、
下記の `--range` 分割保証（N プロセスが同じ出力ディレクトリへ互いに素な
範囲を書く）と正面衝突する。同じ理由で「一時ディレクトリへ書いて
`finish` で入れ替える」案も採らない。

### コーデックは実行時に列挙する

**コンパイル時に決め打ちできない。** 同じバイナリでも macOS では
VideoToolbox 経由で ProRes / H.264 が出せて、最小構成の FFmpeg しかない
Linux では出せない。

- 起動時（または書き出しダイアログを開いた時）に、FFmpeg のエンコーダ
  一覧とプラットフォーム API の有無を問い合わせる
- **UI は実際に使えるものだけを有効表示**し、使えないものは理由付きで
  無効表示する（「この環境の FFmpeg に libaom がない」）
- **連番画像だけは FFmpeg 非依存**で実装し、常に利用可能な保証された
  経路にする

### v1 の出力形式

| 形式 | 扱い | 根拠 |
|---|---|---|
| **PNG 連番** | 常時利用可。**v1 の必須土台** | 特許・ライセンス問題なし。アルファ保持 |
| **EXR 連番** | 常時利用可 | 32bit float の値を精度を落とさず出せる。ただし**値はリニアではない**（下記） |
| **VP9 / AV1** | 利用可能なら露出 | ロイヤリティフリー、実装も BSD 系 |
| **ProRes** | **macOS + VideoToolbox が取れた時のみ** | エンコードには Apple のライセンスが要る。FFmpeg のリバースエンジニアリング実装を「ProRes 対応」と称するのは商標・ライセンス上グレー |
| **H.264** | **OS / HW エンコーダがある時のみ** | 特許は Via LA のプール。x264 は GPL で `.agents/rules/rust.md` の「配布バイナリに GPL を課さない」に抵触。OS/HW 経由なら license は OS / ハードウェアベンダー側 |
| **H.265** | **扱わない** | プールが Via LA / Access Advance / Velos に分裂し、未参加権利者もいる |

これは法務判断ではないので、配布前に別途確認が要る。**計画としては
「連番を必ず動く土台にし、動画コンテナは環境依存として扱う」構造**を採る。

**EXR の値はリニアではない。** 当初この行の根拠を「32bit float リニア
（REQ-CORE-009）をそのまま出せる」と書いていたが、実装はそうなっていない。
取り込み（`ravel-media` のデコーダ）も Viewer も既存の FFmpeg エンコーダも
伝達関数を適用しておらず、バッファは display-referred（sRGB エンコード済みの
0–1）で自己整合している。EXR が保証するのは**精度**（f32 が劣化しないこと）
だけで、色空間の正しさは REQ-RENDER-003（OCIO、計画未着手）の担当。それが
入るまでは Viewer / PNG / EXR / 動画の 4 経路が一致することを優先する。

## 目標構成

```text
  CLI (ravel render)  ─┐
                       ├─→ RenderJob ─→ RenderQueue ─┐
  書き出しダイアログ  ─┘   (Arc<Document> + comp /   │
                            range / encoder / params) ▼
                                              レンダーワーカー
                                         （専用 Evaluator、GpuContext 共有）
                                            │ フレームごと     │ 範囲まとめて
                                            ▼                 ▼
                                    映像 Encoder        音声 Mixer → Encoder
                                    （連番 or 動画）      （mux or WAV 併置）

すべて GUI 非依存クレートに置く（永続化・ワーカー・エンコーダ）。
GUI ダイアログと CLI は同じ層の利用者。
```

- ジョブは順次実行（プロセス内並列レンダリングは非対象）
- **`--range` で分割でき、連番のファイル名は絶対フレーム番号**。外部から
  N プロセスに分けてレンダーファームが組める
- 進捗・キャンセル・失敗は、GUI では UI に、CLI では機械可読出力と
  終了コードに返す
- キャンセルは**フレーム境界で**行い、書きかけのファイルは削除する

### 単位 2: レンダーワーカーとキュー（`ravel-core`）

**`ravel-core` だけで完結する。** `runtime::render` に置き、GUI 非依存を保つ
（`EXPORT-3` の CLI がここを通るため）。`ravel-app` への配線は `EXPORT-5` の
担当で、この単位の時点では呼び出し側はテストだけ。

- `RenderJob { document: Arc<Document>, comp: CompId, range, encoder, output,
  overwrite }`。`overwrite` は既定 `Refuse`（下記「既存の出力への上書き」）。
- 専用 `Evaluator`（`GpuContext` 共有）でフレームを順次評価し
  `Quality::Final` を要求。
- 進捗・完了・失敗・キャンセルのイベント。UI スレッドを塞がない。
- 中断・失敗のいずれでも `Encoder::abort` を通り、部分出力を残さない。

**完了条件**

- 10 フレームのジョブが 10 枚出力するヘッドレステスト。
- **レンダー中にドキュメントを編集しても出力が投入時の内容であること**の
  テスト（スナップショットの検証）。
- キャンセルがフレーム境界で効き、部分出力が削除されるテスト。
- 評価失敗時にジョブが失敗として報告され、他のジョブが継続するテスト。
- 対話用 `EvalService` のキャッシュがレンダーで汚れないテスト。
- 出力先に既存フレームがあるジョブが、**1 フレームも評価せずに**失敗する
  テスト（ファイルが増えていないことではなく、評価が走っていないことを
  確かめる）。
- 明示的な上書き許可を与えたときは同じジョブが通るテスト。
- 互いに素な範囲を同じディレクトリへ書く 2 ジョブが、衝突拒否に
  引っかからないテスト。
- ワーカーが `Quality::Final`（と `Precision::F32`）を要求していることの
  テスト。`motion-blur-plan.md` の `BLUR-3` がこの検証を残していた。

### 単位 3: CLI（`ravel render`）

**この単位でユーザーが映像の成果物を出せるようになる。** ただし
**REQ-RENDER-005 の回収は `EXPORT-4`（音声）まで**。要件は音声出力を
必須にしているので、`EXPORT-3` 単独では受入条件のうち音声 2 項目が未達。
`EXPORT-3` の完了時点では「音声トラックを持つプロジェクトに警告を出す」ことで
黙って音を落とさない状態にし、`EXPORT-4` で埋める。

- サブコマンドと引数（プロジェクト / コンプ / 範囲 / 形式 / 出力先 /
  `--param 名前=値`）
- 公開パラメータの適用（`EXPO-2`）と、宣言一覧の表示（`EXPO-3`）
- `.ravprj` は**読み取り専用**。マイグレーション結果も書き戻さない
- 連番ファイル名を**絶対フレーム番号**にする
- 既存の出力を上書きするための明示的な引数（`--overwrite` 相当）。
  既定は拒否で、無指定なら開始前に理由付きで失敗する
- 分類された終了コード（引数不正 / ロード失敗 / パラメータ不一致 /
  評価失敗 / エンコード失敗 / 中断）
- 進捗と結果の機械可読出力

**完了条件**

- 10 フレームのジョブが 10 枚出力するテスト
- `--range 100-199` の出力ファイル名が絶対フレーム番号になるテスト
- 範囲を 2 分割した 2 回の実行が、1 回で通した出力とビット等価になるテスト
- 宣言に無い `--param` 名と型不一致が**開始前に**失敗するテスト
- **`.ravprj` が書き換わらない**テスト（旧バージョンを読んでも保存しない）
- 各失敗系が期待した終了コードを返すテスト
- 利用不可なコーデック指定が開始前に理由付きで失敗するテスト
- 中断で部分出力が残らないテスト
- 既存の出力があるとき、上書き引数なしでは**開始前に**失敗するテスト
- 音声トラックを持つプロジェクトで警告が出るテスト（`EXPORT-4` までの暫定挙動）

## 検証

- 単位 0〜4 はヘッドレス。単位 5 は実機。
- **決定性**: 同一ドキュメント・同一範囲で 2 回書き出して**ビット等価**に
  なることを PNG 連番で検証する。これが崩れると原因追跡が不可能になる。
- **分割の等価性**: 範囲を分けた複数回の出力が、1 回で通した出力と
  一致すること（映像・音声とも）。これが REQ-RENDER-005 の分割保証の実体。

## 非対象

- **Write ノード**（REQ-RENDER-002）。評価純粋性とディスクキャッシュ設計の
  問題。`cache-plan.md` が「明示キャッシュノード」を将来方向として同じ議論に
  置いているので、**着手するならそちらと一緒に決める**。
- **OCIO / カラーマネジメント**（REQ-RENDER-003）。
- **プロセス内並列レンダリング**、分散レンダリングの制御層。
  `--range` 分割は保証するが、分割・投入・結合は呼び出し側の責任。
- **H.265**、および OS/HW エンコーダの無い環境での H.264。
- **動画コンテナ出力の分割**。連番のみ分割できる（結合が別問題）。
- **プロキシ / 低解像度書き出し**。品質段階は Preview/Final の 2 値のみ。
- **操作自動化スクリプト**（REQ-PLUGIN-006）。CLI は `--param` による
  差し替えまでで、任意の Document 操作は扱わない。
