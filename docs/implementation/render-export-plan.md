# 書き出し実装計画（REQ-RENDER-001）

> **Status**: Planned — 2026-07-27

対象要件: REQ-RENDER-001（キューベースバックグラウンドレンダリング）。
関連: REQ-CORE-005、REQ-CORE-009、REQ-MEDIA。

## 問題

**作ったものをファイルにできない。** REQ-RENDER-001/002/003 が丸ごと未実装で、
`plan.md` も「a complete render queue/export workflow ... not implemented」と
記録している。

`ravel-media` には FFmpeg ベースのエンコード機能があるが、**アプリ層の
導線が無い**。モーショングラフィックスの機能をいくら足しても成果物が出せない。

## 決定事項（2026-07-27 設計セッション）

### 専用レンダーワーカー + 専用 `Evaluator` + 共有 `GpuContext`

対話用の `EvalService` は再利用できない。**キューに溜まったリクエストを
latest-wins で捨てる**（`eval_service.rs:161`）ので、全フレームが必要な
レンダリングには使えない。

一方で `GpuContext { inner: Arc<GpuContextInner> }`（`ravel-gpu/src/device.rs:24`）
は安価にクローンでき、wgpu の device / queue は共有される。したがって
2 本目の `Evaluator` を立てても複製されるのは **CPU 側キャッシュと
プロセッサ登録だけ**。

キャッシュ分離はむしろ利点で、フレーム 500 のレンダリングが対話中の
フレーム 10 の結果を追い出さない。

### ドキュメントスナップショットでレンダー中の編集を許す

`EvalRequest.document: Option<Arc<Document>>` が既にスナップショット。
ジョブ投入時の `Arc<Document>` を保持すれば、**レンダー中にユーザーが
編集しても出力は投入時の状態のまま**になる。追加機構は要らない。

### Write ノードは v1 に入れない

REQ-RENDER-002 の Write ノードは「評価結果をディスクに焼いて次回以降
そこから読む」使い方が本命で、それは三層キャッシュ（REQ-CORE-006、
ディスク層が未実装）の領域。単なる「ファイルに書く副作用ノード」として
作ると `process()` が副作用を持ち、評価の純粋性を壊す。

v1 の書き出しは**評価グラフの外側**に置く。レンダーワーカーがフレームを
回してエンコーダに渡すだけ。

### 品質は `Final` を要求する

`motion-blur-plan.md` の単位 3 が `EvalContext.quality { Preview, Final }` を
導入する。レンダーワーカーは `Final` を要求し、Viewer の 1024 縮小や
低サンプルのモーションブラーを踏まない。**この計画は品質段階に依存する。**

### コーデックは実行時に列挙する

**コンパイル時に決め打ちできない。** 同じバイナリでも macOS では
VideoToolbox 経由で ProRes / H.264 が出せて、最小構成の FFmpeg しかない
Linux では出せない。

- 起動時（または書き出しダイアログを開いた時）に、FFmpeg のエンコーダ
  一覧とプラットフォーム API の有無を問い合わせる
- **UI は実際に使えるものだけを有効表示**し、使えないものは理由付きで
  無効表示する（「この環境の FFmpeg に libaom がない」）
- **連番画像だけは FFmpeg 非依存**で実装し、常に利用可能な保証された
  経路にする

### v1 の出力形式

| 形式 | 扱い | 根拠 |
|---|---|---|
| **PNG 連番** | 常時利用可。**v1 の必須土台** | 特許・ライセンス問題なし。アルファ保持 |
| **EXR 連番** | 常時利用可 | 32bit float リニア（REQ-CORE-009）をそのまま出せる |
| **VP9 / AV1** | 利用可能なら露出 | ロイヤリティフリー、実装も BSD 系 |
| **ProRes** | **macOS + VideoToolbox が取れた時のみ** | エンコードには Apple のライセンスが要る。FFmpeg のリバースエンジニアリング実装を「ProRes 対応」と称するのは商標・ライセンス上グレー |
| **H.264** | **OS / HW エンコーダがある時のみ** | 特許は Via LA のプール。x264 は GPL で `.agents/rules/rust.md` の「配布バイナリに GPL を課さない」に抵触。OS/HW 経由なら license は OS / ハードウェアベンダー側 |
| **H.265** | **扱わない** | プールが Via LA / Access Advance / Velos に分裂し、未参加権利者もいる |

これは法務判断ではないので、配布前に別途確認が要る。**計画としては
「連番を必ず動く土台にし、動画コンテナは環境依存として扱う」構造**を採る。

## 目標構成

```text
書き出しダイアログ ─→ RenderJob ─→ RenderQueue ─┐
  (範囲/形式/出力先)   (Arc<Document> +          │
                        comp / range / encoder)  ▼
                                          レンダーワーカー
                                     （専用 Evaluator、GpuContext 共有）
                                                │ フレームごとに
                                                ▼
                                          Encoder（連番 or 動画）
```

- ジョブは順次実行（並列レンダリングは非対象）
- 進捗・キャンセル・失敗は UI に返す
- キャンセルは**フレーム境界で**行い、書きかけのファイルは削除する

## 実装単位

### 単位 1: エンコーダ抽象と実行時列挙（`ravel-media` / `ravel-core`）

- `Encoder` トレイト: `begin` / `write_frame(FrameBuffer, index)` / `finish` /
  `abort`。
- PNG / EXR 連番の実装（FFmpeg 非依存）。
- 利用可能エンコーダの列挙（FFmpeg のエンコーダ問い合わせ +
  プラットフォーム API 検出）。**不在の理由を持つ**列挙結果。

**完了条件**

- PNG / EXR 連番の書き出しと読み戻し一致テスト。
- アルファ付き PNG のテスト。
- EXR がリニア 32bit float を保持するテスト。
- 列挙が「利用不可 + 理由」を返すテスト（FFmpeg 無し環境をモック）。
- 中断時に書きかけファイルが残らないテスト。

### 単位 2: レンダーワーカーとキュー（`ravel-core` / `ravel-app`）

- `RenderJob { document: Arc<Document>, comp: CompId, range, encoder, output }`。
- 専用 `Evaluator`（`GpuContext` 共有）でフレームを順次評価し
  `Quality::Final` を要求。
- 進捗・完了・失敗・キャンセルのイベント。UI スレッドを塞がない。

**完了条件**

- 10 フレームのジョブが 10 枚出力するヘッドレステスト。
- **レンダー中にドキュメントを編集しても出力が投入時の内容であること**の
  テスト（スナップショットの検証）。
- キャンセルがフレーム境界で効き、部分出力が削除されるテスト。
- 評価失敗時にジョブが失敗として報告され、他のジョブが継続するテスト。
- 対話用 `EvalService` のキャッシュがレンダーで汚れないテスト。

### 単位 3: 書き出し UI

- 書き出しダイアログ: 対象コンプ / フレーム範囲 / 形式 / 出力先 /
  （動画時）ビットレート等。
- 利用不可な形式を理由付きで無効表示。
- レンダーキューパネル: ジョブ一覧・進捗・キャンセル。
  `PanelKind::RenderQueue` は**既に enum に存在する**ので、
  `panel-placement-plan.md` 完了後なら View メニューから到達できる。
- コマンド（`File ▸ Export…`）、キーバインド、ロケール。

**完了条件**

- ダイアログからジョブが投入されるテスト。
- 無効な範囲（out < in）が弾かれるテスト。
- 実機で 1080p 100 フレームを PNG 連番で書き出す確認。

### 単位 4: 文書更新

- `docs/requirements/REQ-RENDER.md`: 001 の受入条件を更新。
  Write ノード（002）と OCIO（003）が別スコープである旨を注記。
- `docs/implementation/plan.md`: 「export not implemented」を更新。
- `docs/specifications/ui-spec.md`: レンダーキューパネル。

## 検証

- 単位 1・2 はヘッドレス。単位 3 は実機。
- **決定性**: 同一ドキュメント・同一範囲で 2 回書き出して**ビット等価**に
  なることを PNG 連番で検証する。これが崩れると原因追跡が不可能になる。

## 非対象

- **Write ノード**（REQ-RENDER-002）。評価純粋性とディスクキャッシュ設計の問題。
- **OCIO / カラーマネジメント**（REQ-RENDER-003）。
- **並列レンダリング**、分散レンダリング。
- **H.265**、および OS/HW エンコーダの無い環境での H.264。
- **音声のミックスダウン書き出し**。`audio-plan.md` に音声書き出しが
  非対象として残っており、v1 の書き出しは映像のみ。
- **プロキシ / 低解像度書き出し**。品質段階は Preview/Final の 2 値のみ。
