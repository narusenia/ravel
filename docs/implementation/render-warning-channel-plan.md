# レンダーが黙って間違わないための警告経路 実装計画

> **Status**: Planned — 2026-08-21

対象: `ravel-core` の識別子パラメータの解決（`eval` / `graph` / `composition`）、
`ravel-cli` の `Warning` とレポート、`assets/locales`。
要件文書は無い（`HIGH-34` / `HIGH-35` の 2 件の欠陥を、共有する 1 つの経路として
片付ける）。`roadmap.md` の**基準 0（出力の誤りを先に）**に該当する。

## 問題

### 1. オフラインの素材はレンダー結果を黙って透明にする（`HIGH-34`）

`media` ノードは素材が解決できないとき透明フレームを返して評価を続ける。
これは意図的な設計（1 つの素材で合成全体を失敗させない）だが、
**その事実が機械可読な出力に一切出ない**。`ravel-cli render` の `Warning` には
音声側（`AudioNotRendered` / `AudioSourceSkipped`）しか無いので、
CLI は成功終了し、真っ黒なフレームを書き出し、レポートにも `--json` にも
何も出ない。気づけるのは `tracing` を読んだ人だけ。

音声側は同じ状況を `AudioSourceSkipped` で「絵は残す、しかし無言にはしない」と
扱っている。**映像側だけが無言**という非対称。

### 2. 参照 ID のパラメータをフレームごとに動かせる（`HIGH-35`）

`composition::validate::is_identifier_parameter` が列挙する 3 つ
（`layer.ref` の `layer`、`precomp` の `comp_id`、`media` の `asset_id`）は
参照先の**生の ID** であって数値ではない。にもかかわらず、
**フレームごとに違う参照先を指す状態を作れる。** 経路は 2 つあり、
`HIGH-35` の個票はうち 1 つしか書いていない（着手時に実測して分かった）。

**(a) ワイヤ経由（`layer.ref` の `layer` と `precomp` の `comp_id`）。**
`Graph::expose_param_port` はこれを普通の `SCALAR` 入力として受け、
Scalar を繋ぐと `param_port_overlay`（`eval.rs`）が `ResolvedValue::Int` に
変換するので、評価のたびに参照先 ID が変わる。

**(b) `StringSteps` 経由（`media` の `asset_id`）。** `asset_id` は
`ParameterValue::String`（`AssetId` の 10 進表記を持つ文字列）で、
`param_port_overlay` は `String` / `StringSteps` に `None` を返すので
**ワイヤでは動かない** — 個票の「3 つとも Scalar で駆動できる」は誤り。
代わりに `DISK-2` が足した `StringSteps` が同じ状態を作る:
`eval.rs` は `StringSteps` をフレームごとに `sample` して
`ResolvedValue::Str` にし、`media` プロセッサは `str_or("asset_id", "")` で
それを読む。一方 `composition::node_asset_reference` は
`ParameterValue::String` **だけ**を読むので、`id_watermarks` は
`StringSteps` の中の ID を 1 つも予約しない。UI からは `DISK-3` が
トグルを塞いでいるので、到達するのは手編集した `.ravprj` だけ。

どちらも同じ形の欠陥で、同じ 1 つの規約で閉じる。

一方 `Document::id_watermarks` は `ParameterValue::static_identifier` 経由で
**保存された静的な値しか走査しない**。よって動的に駆動される ID は予約されず、
新規採番がその番号を引き当て、**参照が無関係なレイヤー / コンプ / 素材へ
繋がり直す**（REQ-LAYER-009 違反）。

UI 経路は `DISK-3`（#462）が塞いだが、塞いだのは公開する側だけで、
**手編集した `.ravprj` と既存文書は依然この状態を持てる**。

### 3. 2 件は同じ穴の別の口である

`HIGH-35` を「評価時にワイヤを無視する」で直すと、その事実をユーザーへ
届ける先が無い — **`HIGH-34` と同じ「警告をどこに出すか」に行き当たる**。
逆に `HIGH-34` を直すために評価時の警告を集めようとすると、
**キャッシュから返ったフレームは警告を出さない**という別の問題を抱える。
2 件は 1 つの設計で閉じる。

## 決定事項

### 識別子は静的な値しか持てない。読み口を 1 つに畳む

**`id_watermarks` が予約できるものだけが、評価から見える識別子である。**
これを不変条件にする。具体的には:

- 識別子パラメータの読み出しを**1 つの経路**に集約する。今は 2 つの綴りに
  分かれている（`ParameterValue::static_identifier` が Int 系の
  `layer.ref` / `precomp`、`composition::node_asset_reference` が
  `media` の `asset_id`）。どちらも「静的な保存値だけを読む」という同じ規約なので、
  その規約を名前のある 1 つの口にして、評価もそこを通す
- `param_port_overlay` は識別子パラメータのとき**ワイヤを無視して保存値を使う**
- 保存値が静的でない（ワイヤ / キーフレーム / `StringSteps` / 式 / ブレンド）
  ときは **「参照無し」として扱う** — `layer.ref` は何も参照せず、
  `media` はオフライン、`precomp` は空

この形にすると、**予約と評価が構造的に一致する**。「予約されていない ID が
評価から見える」状態が存在しなくなるので、`HIGH-35` の 3 段の連鎖
（予約漏れ → 採番の衝突 → 参照の繋ぎ直し）が**個別の検査なしに消える**。

代替案とその棄却理由（`HIGH-35` の修正方針より）:

- **`Graph::expose_param_port` で拒否する**: グラフは `from_parts` で再構築
  されるので、既存文書が開けなくなる可能性がある
- **`Document::validate` で拒否する**: 「保存できたものが開けなくなる」方向。
  `HIGH-26` の教訓に反する

**解除手段は残す。** 既に公開済みの識別子ポートは解除できる（`DISK-3` が
同じ理由でそうしている）。無視するだけで消さないので、ポートは見えたまま
「効いていない」状態になり、そのことを警告が言う。

### 警告は文書の静的な走査で出す。評価には集めさせない

評価時に警告を集める形（評価結果に診断を載せる）を**採らない**。理由:

- **キャッシュから返ったフレームは警告を出さない。** 同じフレームを 2 回
  評価すると 2 回目は無言になり、`--json` の内容が実行順に依存する
- 評価器に副作用のある収集器を通すのは、`ravel-review` の render 純粋性の
  検査項目と正面から衝突する

そして**上の決定によって、静的な走査で十分になる**。
`HIGH-34` が「評価しないと分からないオフライン」と書いた経路
（時間依存で素材が変わる）は、`asset_id` を `StringSteps` にできることに
由来していた。`WARN-1` がそれを「参照無し」に落とすので、
**オフラインは文書から完全に決まる**。2 件を一緒に設計する利点がここに出る。

`media` プロセッサの `tracing::warn!` は**そのまま残す**（GUI とライブラリの
利用者にとっては今もそれが唯一の口である）。消すと退行になる。

### GUI の見え方はこの計画の対象外

Outliner / Timeline のレイヤー行にオフライン印を出すのは
`media-import-plan.md` の**単位 7（`MEDIA-7`）**の担当。ここは
**`ravel-cli` の機械可読な出力**だけを埋める。境界を跨がない。

## 実装単位

| ID | 単位 | 依存 |
|---|---|---|
| WARN-1 | 識別子パラメータの解決を 1 経路に畳む（`ravel-core`） | — |
| WARN-2 | `ravel-cli render` の映像側 `Warning` と静的走査 | WARN-1 |
| WARN-3 | ロケール / 文書 / issue の決着 | WARN-1, WARN-2 |

### 単位 1: 識別子パラメータの解決を 1 経路に畳む

- 識別子パラメータの読み出しを 1 つの口に集約する。
  `is_identifier_parameter` / `static_identifier`（Int 系）と
  `node_asset_reference`（`asset_id`）が同じ規約の 2 つの綴りなので、
  **どちらも「静的でなければ参照無し」を返す**ことを型か関数で 1 度だけ言う
- `param_port_overlay` が識別子パラメータのとき**ワイヤを無視する**
  （到達するのは `layer.ref` の `layer` と `precomp` の `comp_id`）
- `asset_id` が `StringSteps` のとき**オフラインとして扱う**
  （`eval.rs` の `StringSteps` 解決から識別子パラメータを外す）
- **`Document::validate` は何も拒否しない。** 既存文書は開ける

**完了条件**

- `layer.ref` の `layer` と `precomp` の `comp_id` にワイヤを繋いだ文書で、
  評価が**保存値**を使う（ヘッドレステスト）
- `asset_id` が `StringSteps`（キーが 2 つ以上）の手編集文書が**開け**、
  評価が**オフライン**として扱い、**パニックしない**
- 識別子パラメータが `IntChannel` のキーフレームを持つ手編集文書が
  **開ける**。参照は解決しない
- `id_watermarks` が予約する集合と、評価から見える識別子の集合が
  **一致する**ことのテスト（この単位の要点。両方を同じ文書から取って比べる）
- 既存の識別子ポートを持つ文書のラウンドトリップ（ポートは残る）
- **`.ravprj` のフォーマットを上げない**（値の読み方だけが変わる）

### 単位 2: `ravel-cli render` の映像側 `Warning` と静的走査

`Warning` に 3 つ足す。**`docs/dev/render-cli.md` の `note` イベントの契約に
従う** — `id` は翻訳しない安定 ID、`message` は翻訳される文。ID は次の 3 つ:

| `id` | 意味 | 粒度と鍵 |
|---|---|---|
| `media_offline` | 参照している素材が解決できない（`HIGH-34`） | **素材ごとに 1 行**。鍵は `AssetId`。行は影響を受けたレイヤー名を**全部**持つ（1 つだけ持つと残りが消える） |
| `media_unreadable` | 素材は解決するが**開けない**（`HIGH-34` の同族） | 同じ。鍵は `AssetId` |
| `identifier_not_static` | 識別子パラメータが静的でないので参照が解決しない（`HIGH-35`） | **パラメータごとに 1 行**。鍵は `(NodeId, パラメータキー)`。ワイヤ / `IntChannel` / `StringSteps` / 式のどれだったかを `message` に出す |

- **`identifier_not_static` はポート経由に限らない。** `WARN-1` が「静的でない
  識別子は参照無し」に落とす**すべての形**（ワイヤ、キーフレーム、
  `StringSteps`、式、ブレンド）が同じ 1 行を出す。落として黙るのは
  `HIGH-34` と同じ欠陥を新しく作ることになる
- 収集はレンダー前の**文書の静的な走査**。`plan_render` が既に文書を
  走査しているので、そこに寄せる
- `media_unreadable` だけは走査で決まらないので、**参照されている素材ごとに
  1 回 probe する**（`MediaProber` はインポート経路が既に持っている）。
  **上限はここまで** — 開けたあとフレーム途中で壊れているファイルは
  レンダー中の `tracing::warn!` のままにする（非対象に理由を書いた）
- 素材の表示名 / レイヤー名は `AudioSourceSkipped` の綴りに揃える
  （素材が文書から消えていたら参照そのものを出す）
- レポート（`report.rs`）と `--json` の両方に出す

**完了条件**

- オフラインの素材を含む文書のレンダーで、レポートと `--json` の**両方**に
  素材ごとに 1 行出る
- 素材が実在するが開けない文書で `media_unreadable` が 1 行出る
- 識別子パラメータがワイヤ / `IntChannel` / `StringSteps` のそれぞれで
  駆動されている文書で、`identifier_not_static` が**形ごとに** 1 行出る
- **終了コードは変わらない**（警告は失敗ではない）
- 素材が全部解決する文書で 1 行も増えない（既存の出力が変わらないこと）
- 同じ素材を 3 レイヤーが参照しているとき、行が**素材ごとに 1 行**に畳まれ、
  その 1 行が**3 つのレイヤー名を全部持つ**
- `id` が翻訳されず、`message` だけが翻訳されること（`note` の契約）

### 単位 3: ロケール / 文書 / issue の決着

**完了条件**

- 3 つの警告の `message` のロケールが ja / en 揃っている
  （`id` は翻訳しない）
- `docs/dev/render-cli.md` の `note` の ID 一覧に 3 つが載っている
- `docs/specifications/architecture.md` の識別子パラメータの記述が追随
- `docs/agent-api-reference.md` の該当表が追随
- `issues/high/HIGH-34` と `issues/high/HIGH-35` が
  `issues/closed/` へ移り、`**解決済み**` 行が入る。
  `issues/README.md` と `issues/closed/README.md` の件数が合う

## 非対象

- **`--strict`（オフラインがあったら失敗させる）**。バッチ用途では欲しく
  なるはずだが、**終了コードの意味を変える**のはこの 2 件の欠陥とは別の判断で、
  要求も出ていない。警告が機械可読になれば `--json` を読む側で
  同じ判定ができる。要求が出たら足す
- **GUI 側のオフライン表示**。`MEDIA-7` の担当（上記の境界）
- **識別子パラメータをポートとして公開できないようにすること**。
  既存文書を壊さない側に倒す（`HIGH-26` の教訓）。無視して警告する
- **レンダー中のデコード失敗**（開けたファイルがフレーム途中で壊れている、
  コーデックが特定フレームで落ちる）。`media` プロセッサはこれも透明フレームに
  落とすが、**静的走査でも probe でも分からない**。評価時の収集を採らないという
  上の決定の代償で、ここだけは `tracing::warn!` が残る。
  拾うには「評価結果に診断を載せる経路」が要るので、要求が出たら単独で設計する
- **一括再リンク**。`media-import-plan.md` の非対象のまま
- **評価結果に診断を載せる汎用の経路**。キャッシュとの相性が悪く、
  ここで要らなくなった。要求が出たら単独で設計する
