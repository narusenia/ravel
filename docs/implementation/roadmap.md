# 実装ロードマップ

> 最終更新: 2026-07-29

`backlog.md` は全単位のフラットな一覧で、「何があるか」を引くためのもの。
**この文書は「どの順でやるか、なぜその順か」を決める**。

単位の内容と完了条件は各計画書、状態と依存は `backlog.md` が正。
ここは順序の根拠だけを持つ。片方だけ直さない。

## 並べる基準

順序は好みではなく、次の 4 つで決めている。上にあるものが強い。

### 1. 移行コストが時間で増える単位を先に

永続化フォーマットを触る単位は、**世に出た `.ravprj` が少ないうちが最も安い**。
後回しにすると移行対象が増え、マイグレーションのテスト行列も増える。

該当: `VEC-5`（Vec パラメータの `Channel2` 化）、`PARAM-1`（カーブ型と
文字列からの移行）。

### 2. 他を塞いでいる単位を先に

1 つ入れると複数の計画が動き出す単位。逆に後回しにすると、同じ概念の
実装が計画ごとに分裂する。

該当: `PARAM-1`（6 つの消費者）、`NETIF-1〜3`（`INFO` 全体）、
`SHEET-1`（`OVL-2` と `SIM-3`）、`VEC-5`（`OVL-5` と Properties の Vector 行）。

### 3. 挙動不変のリファクタは分岐が増える前に

後から入れるほど、載せ替える対象が増える。

該当: `OVL-1`（Viewer オーバーレイ機構）、`PANEL-1`（実効レイアウトの分離）。

### 4. 「評価はできるが編集できない」を優先

評価側が完成しているのに操作手段が無いものは、**残っている実装量に対して
得られる機能が最大**。

該当: `NETIF-*`（カスタムポートと Subnet）、`PARAM-2/4`（カーブとランプの
エディタ。ウィジェットは既にある）、`SHELL-1/2`（`time_remap` /
`track_matte` はデータモデルに存在して未配線）。

| 単位 | 内容 |
|---|---|

| `issues/high/HIGH-21` | NodeEditor の再生中フル再描画（閉じても残る） |

## フェーズ B: フォーマットを触る基盤

**目標**: 後になるほど高くつく移行を先に済ませる。

| 単位 | 内容 |
|---|---|
| `VEC-7a` | `vector.construct`（`VEC-5` の移行が挿入するので先に要る） |
| `VEC-5` | `_x` / `_y` パラメータを `Channel2` へ統合 + ロード時マイグレーション |
| `PARAM-1` | `ParameterValue::Curve` と文字列からの移行 |
| `3D-1` | **`Primitive::Mesh` の variant 追加と網羅規約**（レンダラなし） |

この 3 つは**ユーザーに見える変化がほとんど無い**。それでも先に置くのは
基準 1 と 2 のため。`VEC-5` は Properties の Vector 行を初めて到達可能にし、
`PARAM-1` は `FX-1` / `FX-3` / `STYLE-6` がカーブとランプの表現を
各自で発明するのを防ぐ。

`VEC-7a` が `VEC-5` より前にあるのは**依存の循環を切るため**。`VEC-5` の
移行は「`center_x` と `center_y` の両方に別ノードが繋がっている旧ファイル」で
`vector.construct` を挿入する必要があり、一方 `vector.construct` 自体は
Scalar 入力と Vec 出力だけで成立して `constant.vec*`（`VEC-6`）を要らない。
だから `construct` だけを切り出して先に入れる。

`3D-1` がここにあるのは基準 1 と 2 の両方に該当するため。**永続化フォーマット
ではなく「enum の網羅 match」が時間で高くつく**タイプ。`Primitive::Path` を
参照する箇所は現在 47 箇所 / 7 ファイルだが、`OPS-1〜13` / `PATH-1〜6` /
`TYPE-*` が入ると 100 箇所を超える。レンダラ（`3D-4`）は後から足しても
既存ノードに影響しないので、**variant だけを先に入れる**のが最も安い。

## フェーズ C: 塞がれているものを開ける

**目標**: 複数の計画が同時に動ける状態にする。

| 単位 | 内容 |
|---|---|
| `NETIF-1` | 出力ポートの再インデックス API |
| `NETIF-2` | In / Out のカスタムポート編集 API |
| `NETIF-3` | Properties の Ports セクション |
| `NETIF-5` | Subnet の生成と `sync_subnet_pins` |
| `SHEET-1` | `EvalRequest` の複数ターゲット化 |
| `OVL-1` | Viewer オーバーレイ機構の抽出（挙動不変） |
| `PANEL-1` | 実効レイアウトの分離（挙動不変） |
| `3D-2` | `orient` / `scale3` / `N` 標準属性と回転ユーティリティ |
| `3D-3` | `Scene` データ型とカメラ |
| `FRAC-1` | 多角形の三角形分割器（`PATH-0` の判断に含まれる） |

`SHEET-1` は `SIM-3` と `OVL-2` も同じ型を触る。**このフェーズで 3 者の
順序を決着させる**（`README.md` に記録がある）。

`NETIF-1〜3` が入った時点で、**カスタムポートがテストフィクスチャの外に
初めて存在できるようになる**。ここが今のいちばん大きな断絶。

## フェーズ D: 表現力の第一波

**目標**: 「作れるはずなのに作れない絵」を潰す。フェーズ B の基盤が
ここで回収される。

| 単位 | 内容 |
|---|---|
| `PARAM-2` / `PARAM-4` | カーブ / グラデーションのインラインエディタ |
| `PARAM-7` / `PARAM-8` | `math.curve` / `color.ramp`（値ドメイン） |
| `STYLE-1` | スタイル属性の読み出し（塗りと線で色が分かれる） |
| `STYLE-5` | `field.apply` の属性自動作成 + Color 既定マスク |
| `STYLE-6` | `field.ramp`（位置 → 色） |
| `VEC-1` | 二項合成の多相化（Color / Vec4 含む） |
| `VEC-6` / `VEC-7b` / `VEC-8` | 値ドメインのベクタノード（定数・分解・演算） |
| `OPS-11〜13` | `shape.line` / `geometry.connect` / `attribute.curveu` |

このフェーズの終わりに、**単独では作れなかった絵が繋がる**:

```text
線に沿ったグラデーション
  shape.line → attribute.curveu → field.attribute("u")
    → field.ramp → field.apply("Cd") → rasterize

塗りと線で別のグラデーション
  同じ経路の target を "stroke_color" にする

トーンカーブ・カラーランプが 3 ドメインで同じエディタ
  math.curve / field.curve_remap / comp.curves
  color.ramp / field.ramp        / comp.gradient
```

**目標**: グラフの中身が Viewer で見え、値を直接掴める。

| `OVL-4` | Field オーバーレイ（ヒートマップ / 等値線） |
| `OVL-5` | `ParamRole` とマニピュレータ（`center` を Viewer で掴む） |

`INFO-2` + `PARAM-8` で「レイヤー index に応じて色相をずらす」が
`layer.info(index) → color.ramp` として書ける。

## 未決: 書き出しをどこに置くか

`EXPORT-*` をフェーズ G に置いたのは依存関係の結果であって、
**製品としての優先度の判断ではない**。

現状 **何も書き出せない**（`README.md` の `render-export-plan.md` の説明が
「you cannot currently export anything」と明記している）。動画編集
アプリケーションとしては存在に関わる欠落で、依存だけで並べるとフェーズ G
まで下がってしまう。

判断が必要な問いはこれ:

- **作れる絵を増やすことを先にするか**（フェーズ D / E / F を通す）
- **少ない絵でも外に出せることを先にするか**（`EXPORT-1〜4` をフェーズ B か
  C に引き上げる）

前者は「自分で使って詰まった所を直す」順序、後者は「他人に見せられる
状態を作る」順序。`EXPORT-1`（エンコーダ抽象と実行時列挙）は依存が無く
**いつでも着手できる**ので、引き上げるコストは低い。

同じ性質の問いが `MOD-5` / `TYPE-*`（タイポグラフィ）にもある。
テキストが無いモーショングラフィックスツールの実用度をどう見るか。

## 順序を動かすときの基準

- **基準 1（移行コスト）に反する入れ替えはしない**。`VEC-5` / `PARAM-1` を
  後ろへ動かすと、移行の対象と検証行列が確実に増える
- **挙動不変のリファクタ（`OVL-1` / `PANEL-1`）を後ろへ動かすなら、
  その間に載せ替え対象を増やさない**こと
- 判断ゲート（`PATH-0` / `GPU-0` / `GPUCOMP-10` / `GPUCOMP-11`）は
  結果が出るまで後続を並べない
- 体感の修正（`issues/`）はどのフェーズにも割り込ませてよい。局所修正で
  依存が無い
