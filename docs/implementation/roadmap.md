## 並べる基準

順序は好みではなく、次の 5 つで決めている。上にあるものが強い。

### 0. 取り返せない損失と、出力の誤りを先に

**保存が壊れる / 保存できたか分からない / 出た音や絵が間違っている**は、
機能が増えるほど被害が増える。しかも「機能が足りない」と違って、ユーザーは
それを回避できない。

該当: `CRIT-02`〜`CRIT-04`（保存の不可視な失敗と非アトミック書き込み、
未コミットジェスチャーの焼き付き）、`HIGH-10`〜`HIGH-15`（音声の時間基準・
トリム・シーク・アンダーラン）、`HIGH-23` / `HIGH-24`（音声の編集が反映されない・
終端で止まらない）、`HIGH-18` / `HIGH-20`（開けない・読めないが
無言）、`MED-CORE-04` / `MED-GPU-03`（latent なクラッシュ）。

これらは**フェーズ A2 / A3 / A4**にまとめてある。いずれも局所修正か 1 エピックで、
他の単位を待たない。

### 1. 移行コストが時間で増える単位を先に

永続化フォーマットを触る単位は、**世に出た `.ravprj` が少ないうちが最も安い**。
後回しにすると移行対象が増え、マイグレーションのテスト行列も増える。

該当: **フェーズ B2**（`AID-1〜4` / `DISK-1〜6` / `PGRP-4` / `CPO-5`）。
`VEC-5`（Vec パラメータの `Channel2` 化）と `PARAM-1`（カーブ型と文字列からの
移行）はフェーズ B で済んだ。

### 2. 他を塞いでいる単位を先に

1 つ入れると複数の計画が動き出す単位。逆に後回しにすると、同じ概念の
実装が計画ごとに分裂する。

該当: `PARAM-1`（6 つの消費者）、`NETIF-1〜3`（`INFO` 全体）、
`SHEET-1`（`OVL-2` と `SIM-3`）、`VEC-5`（`OVL-5` と Properties の Vector 行）。

### 3. 挙動不変のリファクタは分岐が増える前に

後から入れるほど、載せ替える対象が増える。

該当: `OVL-1`（Viewer オーバーレイ機構）、`DOCK-1〜8`（フリードッキングへの
カットオーバー。旧 `PANEL-1` を吸収 — 旧 dock の上に UI を積むほど
載せ替え対象が増える）。

### 4. 「評価はできるが編集できない」を優先

評価側が完成しているのに操作手段が無いものは、**残っている実装量に対して
得られる機能が最大**。

該当: `NETIF-*`（カスタムポートと Subnet）、`PARAM-4`（ランプのエディタ。
カーブ側の `PARAM-2` は済）、`SHELL-1/2`（`time_remap` /
`track_matte` はデータモデルに存在して未配線）。

## issues の扱い

`issues/` の 102 件も**この文書が順序を決める**。`issues/README.md` は
「何が壊れているか」と「どれが互いに絡んでいるか」の台帳で、着手順を
持たない（同ファイルの「第1段〜第4段」は原因の分解であって順序ではない）。

- ロードマップには**クラスタ単位で 1 行**として載せる。個票は `issues/` へ
  リンクする。critical / high は ID を明記し、medium / low はクラスタ名と
  件数で示す。
- **計画書が引き受けた issue はクラスタから外す**（`cache-plan.md` が 7 件、
  `gpu-compositing-plan.md` が 5 件、`settings-screen-plan.md` が 2 件、
  完了した `done/ui-responsiveness-plan.md` が 3 件）。同じ関数を 2 方向から
  直して衝突させないため。
- クラスタ行に完了条件は書かない。issue 個票の「修正方針」と「検証」が正。

## フェーズ A4: 音声が編集に追いつくこと（完了）

**目標**: 音声レイヤーを 1 本置いて再生する、という最小の操作が成立する。

| クラスタ | 内容 |
|---|---|
| 準備の作り直し | `issues/high/HIGH-23`（リサンプル結果が未キャッシュ。配置・トリム編集ごとに全長やり直し → 初回は無音、再送は古い配置のまま鳴り続ける） |
| 停止の取りこぼし | `issues/high/HIGH-24`（Composition 終端の自動 Pause がエンジンへ転送されず、画が止まっても音が鳴り続ける） |
| 待ち時間の説明 | `issues/medium/media-audio.md` `MED-AUD-02`（デコード上限超過が無言で永久無音）、`MED-AUD-03`（準備中が UI に出ない） |

**A3 の直後に置く理由**は、A3 と同じ基準 0（出た音が間違っている）でありながら、
A3 の対象外だったから。A3 は「鳴っている音が正しい時刻か」を epoch 導入で
解いたが、実機で残ったのは**鳴り始めるまでと鳴り止むとき**だった。
2 件は無関係なコードだが、どちらも「音声を 1 本置いて再生する」だけで踏む。

`HIGH-23` は [`HIGH-15`](../../issues/closed/HIGH-15-settrack-resamples-on-prep-thread.md)
の続きでもある。A3 でリサンプルは prep スレッドから外れたが、**やり直しの回数**は
手つかずだった。修正は「出力レートへの変換をアセット単位に 1 回だけ、
ravel-app 側のキャッシュで持つ」で、エンジンからリサンプル経路が消える。
併せてリサンプラのコストも落とす（`rubato::FftFixedIn` か
`sinc_len` / `oversampling_factor` の削減）。これは `MED-MED-03`
（フィルタ遅延・テール欠落）と同じ関数なので一緒に触る。

`MED-AUD-03` を A4 に入れるのは、`HIGH-23` を直した後でも初回のデコードと
レート変換の待ちは残るから。ただし**進捗率を出す UI はここでは作らない** —
release では 4 分の曲で 1 秒未満に収まるので、必要なのは「準備中」の状態表示だけ。
モーダルな進捗表示は書き出し（`EXPORT-*`）の進捗基盤と一緒に設計する。

実施結果: デコード後の音声をバックグラウンドで出力レートへ変換し、
`asset_id + stream_index` 単位で `AudioService` にキャッシュするようにした。
engine の SRC worker は撤去され、配置・trim・mute・solo・fade の編集は完成済み
バッファを即時再利用する。終端 tick は frame 不変でも pause 状態を公開し、
Timeline / MediaBin は準備中を表示、準備失敗は workspace notification で通知する。

| 単位 | 内容 |
|---|---|
| `PTR-1` | 判定不要の静的カーソル（描画ツール中の Viewer、Timeline ルーラー、NodeEditor 空白） |
| `PTR-2` | ヒント機構とドラッグ中の保持（Timeline で導入） |

| `PTR-5` | Viewer の割り当て（レイヤー移動・パスハンドル・パン・ペン閉合） |
| `PTR-6` | Outliner の並べ替えと文書（`ui-spec.md` にポインタフィードバック節） |
| `INSP-1` | `Composition.background_color` の配線とチェッカーボード（`MED-CORE-09`） |

計画書は `done/pointer-feedback-plan.md` と `viewer-inspection-plan.md`。

`INSP-1` をここに入れるのは**設定できるのに効かないフィールド**だから。
`background_color` はコンプ設定フォームで編集でき、保存もされるのに、評価にも
合成にも現れない（Viewer は黒 quad をハードコードしている）。同時に「アルファ 0 と
黒を区別できない」も解消するので、チェッカーボード表示まで 1 単位で入れる。
検査系の残り（`INSP-2〜5`）はフェーズ E。

実施結果: Timeline / NodeEditor / Viewer の canvas は既存のヒットテストを再利用して
hover とドラッグ中の操作意図をカーソルで示し、Outliner のレイヤー並べ替えも
ドラッグ中の縦リサイズカーソルを出す。コンポジション背景色は synthetic な
`comp.background` として合成結果へ入り、Viewer はコンプ背景 / チェッカーボード /
単色をセッション内で切り替えられるようになった。（PR #213、2026-07-30）

**フェーズ A の目標（触っていて痛い箇所を消す）の続きとしてここに置く。**
3 パネルの主要な操作面が 1 枚の `canvas` で、要素が無いためカーソルが常に
`Arrow` のままになっている。特に Timeline のトリムエッジは左右 6px しかなく
（`TRIM_HANDLE_PX`）、1px 外すとバー全体の移動になるのに、その境界が画面に
出ていない。ロックされたレイヤーが無反応な理由も出ない。

**B より前に置く理由**は基準 0 でも基準 1 でもなく、**依存がゼロで B と
競合しないから**。B は永続化フォーマットとコア規約の単位で構成されており、
本フェーズは `ravel-app` のパネル入力経路だけを触る。逆に B を先に通しても
本フェーズのコストは変わらないので、順序を入れ替えても失うものは無い
（「体感の修正はどのフェーズにも割り込ませてよい」の適用例）。

hover 判定は**すべて既存のヒットテストの再利用**で足りる
（`bar_hit` / `row_at_content_y` / `keyframe_at_content_x` / `graph_hit_at` /
`node_at_local_pos` / `port_at_local_pos` / `edge_at_local_pos` /
`hit_test_shape_nodes` / `path_handle_hit`）。新しいレイアウト走査を
書かないので `MED-APP-13`（Timeline の行走査が 4 箇所）を悪化させない。
再描画も「ヒントが変化した時だけ notify」に閉じるので、フェーズ C3 の
`MED-UI-*` の前提を悪化させない。

**機能が無いものにカーソルを付けない**のがこのフェーズの制約。Hand / Zoom
ツール（`MED-APP-15`）と Viewer の bbox 8 ハンドルは操作が実装されていないので、
カーソルは**フェーズ E**で機能と同じ単位に入れる。ここで先に付けると
「掴めるのに動かない」状態を作る。

## フェーズ B: フォーマットを触る基盤

**目標**: 後になるほど高くつく移行を先に済ませる。

| 単位 | 内容 |
|---|---|
| `VEC-7a` | `vector.construct`（`VEC-5` の移行が挿入するので先に要る）**済** |
| `VEC-5` | `_x` / `_y` パラメータを `Channel2` / `Channel3` へ統合 + ロード時マイグレーション（format v5）**済** |
| `PARAM-1` | `ParameterValue::Curve` と文字列からの移行（format v6）**済** |
| `3D-1a` | **`P` の次元許容**（Vec2 \| Vec3。`as_vec2` 58 箇所）**済** |
| `3D-1b` | **`Primitive::Mesh` の variant 追加**（match 53 箇所。レンダラなし）**済** |
| `CACHE-1` | **`FrameBuffer` の精度多相化**（`.data[` 72 箇所。規約のみ）**済** |
| `CACHE-2` | `CacheIdentity` の抽出と時間基準化（旧 `BLUR-2` + `HIGH-03`）**済** |
| `CACHE-3` | `CacheBudget` と退避（`MED-CORE-06` / `07`）**済** |
| `CACHE-4` | スコープ無効化の粒度修正（`MED-CORE-02`）**済** |

この 3 つは**ユーザーに見える変化がほとんど無い**。それでも先に置くのは
基準 1 と 2 のため。`VEC-5` は Properties の Vector 行を初めて到達可能にし、
`PARAM-1` は `FX-1` / `FX-3` / `STYLE-6` がカーブとランプの表現を
各自で発明するのを防ぐ（カーブ側は済。ランプは `PARAM-3`）。

`VEC-7a` が `VEC-5` より前にあるのは**依存の循環を切るため**。`VEC-5` の
移行は「`center_x` と `center_y` の両方に別ノードが繋がっている旧ファイル」で
`vector.construct` を挿入する必要があり、一方 `vector.construct` 自体は
Scalar 入力と Vec 出力だけで成立して `constant.vec*`（`VEC-6`）を要らない。
だから `construct` だけを切り出して先に入れる。

`3D-1a` / `3D-1b` がここにあるのは基準 1 と 2 の両方に該当するため。ただし
**高くつくのは永続化フォーマットではなく「網羅すべき箇所の数」**。`as_vec2`
呼び出しが 58 箇所 / 12 ファイル、`Primitive::Path` の match が 53 箇所 /
7 ファイルあり、`OPS-1〜13` / `PATH-1〜6` / `TYPE-*` が入ると合わせて
100 箇所を大きく超える。レンダラ（`3D-4`）は後から足しても既存ノードに
影響しないので、**規約だけを先に確定させる**のが最も安い。

1a と 1b は独立した軸なので別単位にしてある（Vec3 の `P` + Path は
3D の折れ線、Vec2 の `P` + Mesh は平面の三角形分割で、どちらも単独で成立する）。

`CACHE-1` がここにあるのは `3D-1b` と同じ理由 — 高くつくのは永続化
フォーマットではなく**網羅すべき箇所の数**で、`FrameBuffer` は `Serialize` を
持たないので移行はコードだけ。`.data[` 直参照が 66 箇所、`FrameBuffer` 構築が
71 箇所あり、`FX-1`〜`FX-4`（カラー・ブラー・ディストーション・キーイング）は
全部 per-pixel ループを持つので、フェーズ F の後だと対象が倍以上になる。

**フェーズ B 完了（2026-07-31）。** `CACHE-3` / `CACHE-4` が入り、評価
キャッシュは単一の `CacheBudget` の下でバイト会計・LRU 退避されるようになった
（`MED-CORE-06`）。`register()` の全走査は逆引き索引で消え（`MED-CORE-07`）、

（#366 / #368 / #374）。

## フェーズ B2: フォーマットを触る残り

**目標**: フェーズ B の後に生まれた「永続化フォーマットを上げる単位」を、
世に出た `.ravprj` が少ないうちに片付ける。基準 1 はフェーズ B で終わって
いない — 移行を伴う単位はその後も増えた。

| 単位 | 内容 |
|---|---|
| `AID-1` / `AID-2` | `AssetId` 型と `MediaAssetEntry` の分離（`.ravprj` v9）と参照 3 系統の切り替え（`asset-identity-plan.md`）**済**（#456） |

**`AID-1` / `AID-2` が先頭で、基準 1 ではなく基準 0 で先頭。** 素材の識別子が
ファイル名から作った文字列（`"plate"`、衝突したら `"plate 2"`）で、それが
`media` ノード / `AudioSource` / 露出パラメータの 3 系統から参照される
キーそのものなので、**素材を削除して同名のファイルを再インポートすると、
古い参照が警告も無く別の素材へ繋がる**。オフラインになるなら気づけるが、

（消えるのは `AID-2` の完了条件）ので、2 単位で 1 組と見る。

**その間の深さの文書は保存に成功し、二度と開けない**。上限を 1 つにする

難しくなるので 1 つずつ入れた — 実際に `AID-*` が **v9**、`DISK-1` が **v10** を
取り、後から入った側が rebase で振り直している（`PGRP-4` / `CPO-5` も同じ手順に
なる）。`DISK-*` は「今できないことができるようになる」機能追加で、
後回しにしても既存プロジェクトは壊れないため `AID-*` の後。

## フェーズ CM: 色が正しいこと

**目標**: 合成がリニア空間で行われ、表示と書き出しが**共通の色空間へ

| `CM-5` | 文書更新（骨格） |
| `CM-6〜8` | `ocio-rs` 導入、`.ocio` 読み込みと GPU LUT、設定 UI（`SET-11`） |

**C4 の直後に置く理由**は基準 1（移行コストが時間で増える単位を先に）。
パイプラインを display-referred からリニアへ切り替えると、作者が指定した色の
意味が変わるので `.ravprj` の移行が要る。**リリースタグがゼロで CD も無い**
（`.github/workflows/` は `ci.yml` のみ、AGENTS.md も「パッケージング手順は
まだ無い」）が、それは配布していないことの証拠であって `.ravprj` が存在
しないことの証拠ではない。決めるのは在庫の推測ではなく**サポート方針**
（v7 は変換して開く / 変換できない構成は警告する。詳細は計画書）で、
**変換対象は後回しにするほど増える**から早いほど安い。

**C2 より前にする理由**は、フレームキャッシュが「どの色空間の絵を持って
いるか」を軸に持つことになるから。後から色変換を入れると `CacheIdentity` の
再検討が発生する（`BLUR-3` の `quality` 軸と同じ性質）。

**基準 0 との関係**: 現状は整数素材に限れば取り込み・Viewer・書き出しが
ほぼ同じ素朴変換（`clamp(0,1)*255`、伝達関数なし）で揃うので、「出た絵が
間違っている」の即時の実害は小さい（Viewer は最近接・動画は切り捨てで
1 LSB ずれている）。壊れているのは合成の数学（不透明度・ブレンド・ブラーが
非線形空間で行われる）で、これは機能が増えるほど被害が広がる種類の誤り。
だから C4（成果物が出せない）の次に置く。

**`EXPORT-*` は書き直しにならない。** 出力変換はエンコーダの手前に段を
挿すだけで、`Encoder` トレイトも連番の実装も変わらない。

**OCIO を後段に置く理由**は `color-management-plan.md` の決定事項に書いた。
要点は、難所が変換の数式ではなく構造の側にあること、`ocio-rs` が若い
クレート（初版 2026-05-13）なので `CM-6` の時点で採否を再判断できること、
`bundled` の C++ ソースビルドが CI キャッシュ予算（`#211`）を圧迫しうること。

>

### 実施結果（2026-08-20 時点、**完了**）

14 単位すべてが 3 本の PR でマージされた — `RESP3-1`〜`4`（#395）、
`RESP3-5`〜`11`（#397）、`RESP3-12`〜`14`（#396）。入ったものは次のとおり。

- **評価器（#395）**: 隣接インデックスを `Graph::ptr_eq` キーでスコープ単位に
  キャッシュし、1,000 ノード / 1,497 エッジで**コールドプル 18.7 → 0.8 ms、
  dirty 再プル 18.8 → 0.27 ms**。`changed_network_paths` は `Graph::ptr_eq` で

  （ルートスコープは空 `Vec` の clone だったので差が出ない）。
  `attribute_transfer` は一様グリッドで `Nearest` が厳密なまま
  **820 → 0.5 ms**、`DistanceWeighted` は 8 近傍打ち切りで **178 → 2.5 ms**。
  打ち切りは全域 IDW より**高精度**（線形場に対する最大誤差 0.46 対 9.63）
- **GPU（#396）**: `finalize` がビューアの Geometry 出力を GPU で
  ラスタライズする（**39.58 → 0.111 ms**）。残る CPU 経路はカバレッジマスク
  1 枚を再利用し `blend_coverage` を bbox に限定（**39.58 → 2.28 ms**）。
  `TexturePool` のアップロードスコープで同一 CPU フレームは評価 1 回に 1 度だけ
  上がる（4K RGBA32F で **3 → 1 回、398 → 133 MB / 評価**）
- **パネル（#397）**: `Params` ヒントでコンパイル済みシェルチェーンを保持、
  Timeline のヘッダ構築とキャンバス描画を可視 y 範囲に限定、
  `sync_from_project` の deep compare を `revision` + `MirrorEpoch` のゲートに
  置換、グローバル駆動 sync のあとに epoch を記録して対になる notify を吸収
  （ドラッグ 1 move あたりの Properties 再解決 **16 → 10 = 1 回 / move**、
  コンポジション切替の Timeline / Outliner **2 → 1**）

- **可視性（`VIS-1`〜`VIS-4`）**: フェーズを閉じた最後の 1 枚。`RESP3-7` の
  完了条件のうち唯一未達だった「パネルが非表示のとき `refresh_values` を
  走らせない」を、パネルへ可視性を届ける経路ごと入れた。

  MediaBin / NodeEditor が `is_instance_visible` で読む。**ゲートは飛ばすの
  ではなく遅らせる** — 裏では `MirrorEpoch` を記録しないので借りが残り、

  置いたドラッグ 10 move で **sync 合計 40 → 0 回**、Properties を裏に置いた
  再生 30 フレームで **30 → 0 回**（測定手順は
  [`perf-baseline.md`](perf-baseline.md)）。Viewer は対象外 — 裏でも評価要求を

**残った issue は無い。** `MED-UI-02` は `RESP3-7`（プレイヘッドの空振り）と

50 万要素超まで効かないので後ろへ下げた。

パーティクルの CPU ステップは 10 万点 0.2 ms 前後（予算の 1〜2%）、3D の毎フレーム

**sim とフィールド評価を GPU に移す必要は 10 万規模では無く、共通の前提は
`GPU-1` + `GPU-5`（描画側の常駐化と GPU 展開）だけ**。`PART-6` の位置づけと
`3D-4` の条件は各計画に反映済み。

3D は**フェーズ H に丸ごと置かれていたのを分割した**。`3D-1a` / `3D-1b`
（`P` の次元と `Primitive::Mesh` の規約）は基準 1 に該当するのでフェーズ B、
`3D-2` / `3D-3` はフェーズ C に上げてある。重いのは `3D-4`（第 2 のレンダラ）
だけで、それ以降が実際の 3D 機能。

## 決着: 書き出しをどこに置くか（2026-08-03）

**フェーズ C4 に引き上げた。** 「少ない絵でも外に出せることを先にする」を採った。

`EXPORT-*` がフェーズ G にあったのは依存関係の結果で、製品としての優先度の
判断ではなかった。現状 **何も書き出せない**（`README.md` の
`done/render-export-plan.md` の説明が「you cannot currently export anything」と
明記）。機能を足しても成果物が出ないので、ここが開くまで他の投資が回収されない。

引き上げのコストは低かった。`EXPORT-1`（エンコーダ抽象と実行時列挙）は依存が
無く、`EXPORT-0`（永続化の GUI 非依存クレートへの抽出）も gpui を import して
いないコードの機械的な移設。唯一の実質的な依存は `BLUR-3`（品質段階）と
`EXPO-1`〜`3`（公開パラメータ宣言。`NETIF-2` 経由でフェーズ C に依存）。

同時に **CLI を GUI ダイアログより先**にした。書き出し経路の全体がヘッドレスで
検証でき、GUI は薄い層として後から載る。詳細はフェーズ C4 の節。

同じ性質の問いが `MOD-5` / `TYPE-*`（タイポグラフィ）にもある。
テキストが無いモーショングラフィックスツールの実用度をどう見るか。

## 順序を動かすときの基準

- **基準 1（移行コスト）に反する入れ替えはしない**。`VEC-5` / `PARAM-1` を
  後ろへ動かすと、移行の対象と検証行列が確実に増える
- **挙動不変のリファクタ（`OVL-1`）とカットオーバー型の載せ替え（`DOCK-8`）を
  後ろへ動かすなら、その間に載せ替え対象を増やさない**こと
- 判断ゲート（`PATH-0a` / `PATH-0b` / `GPUCOMP-10` / `GPUCOMP-11`）は
  結果が出るまで後続を並べない（`GPU-0` は結果が出た）
- 体感の修正（`issues/` の perf 項目）はどのフェーズにも割り込ませてよい。
  局所修正で依存が無い
- **基準 0（損失と誤り）に反する入れ替えはしない**。フェーズ A2 / A3 を
  後ろへ動かすと、その間に作った成果物が壊れる / 間違った音のまま蓄積する
- **クラスタから issue を 1 件だけ抜き出して先に直さない**。同じ関数を触る
  ものを束ねてあるので、抜き出すと後続が rebase 衝突する（`HIGH-12`〜`15` の
  epoch 化がその典型）
- issue を計画書が引き受けたら、**クラスタ行から外して個票にも引受先を
  書く**。2 箇所で同じものを追わない

## フェーズ I: GPU バックエンドの内製化と拡張点

**独立したフェーズにして他を止めない**のがこのフェーズの制約。`GPUBK-1〜9` と
`GPULOSS-1〜5` は
バックエンドを 1 つも足さずに完結し、それぞれ単独でマージできる。

`GPUBK-4` が `GPUBK-5〜8` の後に来るのは、生ハンドルを閉じられるのが
**外から要る者が居なくなってから**だという理由。詳細は
[`gpu-backend-plan.md`](gpu-backend-plan.md) の「実装単位」節。

**`GPUBK-1〜2` を先頭に置く根拠**は、これが「脱却のためだけの投資」でないこと。
`MED-GPU-01`（ディスパッチごとにユニフォームバッファとバインドグループを新規作成、
`GpuTask` バッチング trait の実装ゼロ）と**同じ場所の同じ作業**で、
バックエンドを差し替えなくても性能が改善する。捨て札にならない単位から入る。

**この読みは当たった。そして同じ理屈が `GPUBK-10〜12` には効かない。**
`GPUBK-1〜8` の性能改善（`GPUBK-2` の submit 29 → 0.48、`GPUBK-6` の
リードバック −59〜77%）は**すべて wgpu の内側**で取れており、
バックエンドを 1 つも足さずに実現した。裏を返すと、**wgpu を外すこと自体の
取り分はまだ一度も測られていない** — `GPUCOMP-10` の分析が特定した唯一の
wgpu 由来のコストは「Metal のフェンス待ちの 1 ms 切り上げ」で、同じ分析が
「スピンでも拾える」と書いている。`GPUBK-10〜12` は先頭の単位群と違って
**判定次第で捨て札になりうる**ので、`GPUBK-14` で測ってから入る。

**測った結果、`GPUBK-10` は捨て札になった**（#295、2026-08-06）。
Metal で wgpu 経由と直叩きを比べると、**バックエンドを書かないと取れない分は
評価 1 回あたり 8.5 µs**（60 fps 予算 16.7 ms の 0.05%）。1.48 ms/評価 の
差の大半は「フェンス待ちの 1 ms 切り上げ」（`wgpu-hal` 側の問題で、上流修正でも
有界スピンでも取れる）と「ディスパッチごとに `begin_compute_pass` を開く
**我々のコードの構造**」で、どちらも wgpu の内側で回収できる。
`REQ-INFRA-009` の性能目的は**第一級から副次的・要再測定へ格下げ**した。
`GPUBK-11` / `GPUBK-12` は D3D12 / Vulkan で測るまで判定しない。

**`PLUG-1〜4` をここに入れる**のは、WGSL シェーダプラグインが `GPUBK-1` の
バインディング記述型に乗るから。2 つの記述型を作らないために同じフェーズで扱う。
`PLUG-1`（`ProcessorRegistry`）自体は依存が無く、いつでも着手できる。

**OFX（REQ-PLUGIN-001）が最後**。優先度は Must のままだが、`GPUBK-8`
（interop 出口）が無いと GPU 経路が CPU 往復に落ち、`HIGH-05` で 0 にした
リードバックを OFX ノードごとに再導入することになる。計画書も `GPUBK-8` の
形が決まってから書く（先に書くと腐る）。

その `GPUBK-8` が #287 で入ったので、**OFX ホストの計画書はいつでも書ける**。
バックエンド（`GPUBK-10`〜`13`）の完了を待つ必要は無い — OFX が要るのは
「抽象からバックエンド固有ハンドルを取り出せること」だけで、それは揃った。
計画を書くときに `gpu-backend-plan.md` の `GPUBK-8` 節の実装メモを読むこと。
**Metal コマンドキューは取れる** — `MED-GPU-07` で wgpu を crates.io の
29.0.4 へ揃えた際、その版が `wgpu_hal::metal::Queue::as_raw` を公開に戻していた
（当時固定していたフォークでは非公開だった）。したがって当初申し送りにあった
「ホストが別タイムラインのキューを作って同期する」前提は外れ、
**ホストは Ravel と同じキューに積める**。`interop` に取得口はまだ無いので、
消費者と一緒に計画書で足す。残る制約は **CUDA 経路しか持たないプラグインが
CPU 往復に落ちる**ことで、これは同じ節にある。

**フェーズ H との関係**: H は「重い基盤」で未使用サブシステムの昇格 / 削除判断。
I とは独立で、順序はどちらでもよい。
