## 並べる基準

順序は好みではなく、次の 5 つで決めている。上にあるものが強い。

### 0. 取り返せない損失と、出力の誤りを先に

**保存が壊れる / 保存できたか分からない / 出た音や絵が間違っている**は、
機能が増えるほど被害が増える。しかも「機能が足りない」と違って、ユーザーは
それを回避できない。

該当: `CRIT-02`〜`CRIT-04`（保存の不可視な失敗と非アトミック書き込み、
未コミットジェスチャーの焼き付き）、`HIGH-10`〜`HIGH-15`（音声の時間基準・
トリム・シーク・アンダーラン）、`HIGH-18` / `HIGH-20`（開けない・読めないが
無言）、`MED-CORE-04` / `MED-GPU-03`（latent なクラッシュ）。

これらは**フェーズ A2 と A3**にまとめてある。いずれも局所修正か 1 エピックで、
他の単位を待たない。

### 1. 移行コストが時間で増える単位を先に

永続化フォーマットを触る単位は、**世に出た `.ravprj` が少ないうちが最も安い**。
後回しにすると移行対象が増え、マイグレーションのテスト行列も増える。

該当: `VEC-5`（Vec パラメータの `Channel2` 化）、`PARAM-1`（カーブ型と
文字列からの移行）。

### 2. 他を塞いでいる単位を先に

1 つ入れると複数の計画が動き出す単位。逆に後回しにすると、同じ概念の
実装が計画ごとに分裂する。

該当: `PARAM-1`（6 つの消費者）、`NETIF-1〜3`（`INFO` 全体）、
`SHEET-1`（`OVL-2` と `SIM-3`）、`VEC-5`（`OVL-5` と Properties の Vector 行）。

### 3. 挙動不変のリファクタは分岐が増える前に

後から入れるほど、載せ替える対象が増える。

該当: `OVL-1`（Viewer オーバーレイ機構）、`PANEL-1`（実効レイアウトの分離）。

### 4. 「評価はできるが編集できない」を優先

評価側が完成しているのに操作手段が無いものは、**残っている実装量に対して
得られる機能が最大**。

該当: `NETIF-*`（カスタムポートと Subnet）、`PARAM-2/4`（カーブとランプの
エディタ。ウィジェットは既にある）、`SHELL-1/2`（`time_remap` /
`track_matte` はデータモデルに存在して未配線）。

## issues の扱い

`issues/` の 102 件も**この文書が順序を決める**。`issues/README.md` は
「何が壊れているか」と「どれが互いに絡んでいるか」の台帳で、着手順を
持たない（同ファイルの「第1段〜第4段」は原因の分解であって順序ではない）。

- ロードマップには**クラスタ単位で 1 行**として載せる。個票は `issues/` へ
  リンクする。critical / high は ID を明記し、medium / low はクラスタ名と
  件数で示す。
- **計画書が引き受けた issue はクラスタから外す**（`cache-plan.md` が 7 件、
  `gpu-compositing-plan.md` が 5 件、`settings-screen-plan.md` が 2 件、
  完了した `done/ui-responsiveness-plan.md` が 3 件）。同じ関数を 2 方向から
  直して衝突させないため。
- クラスタ行に完了条件は書かない。issue 個票の「修正方針」と「検証」が正。

## フェーズ B: フォーマットを触る基盤

**目標**: 後になるほど高くつく移行を先に済ませる。

| 単位 | 内容 |
|---|---|
| `VEC-7a` | `vector.construct`（`VEC-5` の移行が挿入するので先に要る） |
| `VEC-5` | `_x` / `_y` パラメータを `Channel2` へ統合 + ロード時マイグレーション |
| `PARAM-1` | `ParameterValue::Curve` と文字列からの移行 |
| `3D-1a` | **`P` の次元許容**（Vec2 \| Vec3。`as_vec2` 55 箇所） |
| `3D-1b` | **`Primitive::Mesh` の variant 追加**（match 47 箇所。レンダラなし） |
| `CACHE-1` | **`FrameBuffer` の精度多相化**（`.data[` 66 箇所。規約のみ） |
| `CACHE-2` | `CacheIdentity` の抽出と時間基準化（旧 `BLUR-2` + `HIGH-03`） |
| `CACHE-3` | `CacheBudget` と退避（`MED-CORE-06` / `07`） |
| `CACHE-4` | スコープ無効化の粒度修正（`MED-CORE-02`） |

この 3 つは**ユーザーに見える変化がほとんど無い**。それでも先に置くのは
基準 1 と 2 のため。`VEC-5` は Properties の Vector 行を初めて到達可能にし、
`PARAM-1` は `FX-1` / `FX-3` / `STYLE-6` がカーブとランプの表現を
各自で発明するのを防ぐ。

`VEC-7a` が `VEC-5` より前にあるのは**依存の循環を切るため**。`VEC-5` の
移行は「`center_x` と `center_y` の両方に別ノードが繋がっている旧ファイル」で
`vector.construct` を挿入する必要があり、一方 `vector.construct` 自体は
Scalar 入力と Vec 出力だけで成立して `constant.vec*`（`VEC-6`）を要らない。
だから `construct` だけを切り出して先に入れる。

`3D-1a` / `3D-1b` がここにあるのは基準 1 と 2 の両方に該当するため。ただし
**高くつくのは永続化フォーマットではなく「網羅すべき箇所の数」**。`as_vec2`
呼び出しが 55 箇所 / 11 ファイル、`Primitive::Path` の match が 47 箇所 /
7 ファイルあり、`OPS-1〜13` / `PATH-1〜6` / `TYPE-*` が入ると合わせて
100 箇所を大きく超える。レンダラ（`3D-4`）は後から足しても既存ノードに
影響しないので、**規約だけを先に確定させる**のが最も安い。

1a と 1b は独立した軸なので別単位にしてある（Vec3 の `P` + Path は
3D の折れ線、Vec2 の `P` + Mesh は平面の三角形分割で、どちらも単独で成立する）。

`CACHE-1` がここにあるのは `3D-1b` と同じ理由 — 高くつくのは永続化
フォーマットではなく**網羅すべき箇所の数**で、`FrameBuffer` は `Serialize` を
持たないので移行はコードだけ。`.data[` 直参照が 66 箇所、`FrameBuffer` 構築が
71 箇所あり、`FX-1`〜`FX-4`（カラー・ブラー・ディストーション・キーイング）は
全部 per-pixel ループを持つので、フェーズ F の後だと対象が倍以上になる。

`CACHE-2〜4` は**フェーズ B の末尾**。ユーザーに見える変化は無く、
`MED-CORE-06`（上限なしキャッシュ）と `HIGH-03` を回収し、`BLUR-3〜5` の
ゲートを開ける。ここを飛ばしてモーションブラーに進むと「実装したのに
ブレない」形で静かに壊れる。

```text
塗りと線で別のグラデーション

トーンカーブ・カラーランプが 3 ドメインで同じエディタ

  color.ramp / field.ramp        / comp.gradient
```

| クラスタ: 操作の正しさ（13 件） | 選択とターゲットの取り合い（`MED-APP-04`〜`06`）、ドラッグの復帰なし（`MED-APP-03`）、no-op undo の記録（`MED-APP-07` / `LOW-APP-02` / `LOW-APP-07` / `LOW-APP-10`）、`HIGH-19`（Timeline ズームのアンカーがウィンドウ空間）、ボックス選択とラバーバンド（`LOW-APP-03` / `LOW-APP-04`）、`MED-APP-08`（サムネイルが Open を越えて stale）、`MED-APP-15`（Hand / Zoom が dead UI） |
| クラスタ: 表示の欠落（4 件） | `MED-APP-17`（カーブエディタの縦ズーム未実装 = `PARAM-5`）、`MED-APP-19`（`Channel4` が常に Color 描画）、`MED-APP-20`（Vector に成分ラベルとリンクトグルなし = `VEC-5` の受け皿）、`MED-APP-21`（Viewer bbox の `type_key` 固定 match = `OVL-3` が同時に消す） |

`OVL-3` は既存の負債（`type_key` の固定 match）を**同時に消す**。
新しい shape ノードを足すたびに Viewer を編集する状況がここで終わる。

「操作の正しさ」クラスタをここに置く理由は、**同じ場所を触るから**。
`OVL-*` が Viewer の入力経路を、`SHEET-*` が選択とターゲットの流れを
書き換えるので、選択の取り合い（`MED-APP-04`〜`06`）を先に個別修正すると
二度手間になる。`MED-APP-17` / `MED-APP-20` / `MED-APP-21` は
`PARAM-5` / `VEC-5` / `OVL-3` が**そのまま解消する**ので、issue 側に
「単位が引き受けた」と記録して個別には着手しない。

`INFO-2` + `PARAM-8` で「レイヤー index に応じて色相をずらす」が
`layer.info(index) → color.ramp` として書ける。

## フェーズ H: 重い基盤

**目標**: 単発では入らない、前提の大きいもの。

| 単位 | 内容 |

**「未使用サブシステムの判断」は昇格か削除かを決める単位**で、実装の単位では
ない。ジャーナル（`MED-CORE-08` / `MED-APP-11`）は REQ-PROJ-002 が要求する
機能なので、`SET-9`（自動保存）と一緒に「実装する」判断をするか、

の設計コメントを縛り続ける）。

`PATH-0a` と `GPU-0` は**判断の単位**で、実装の単位ではない。結果によって
後続が消えることを前提に置いてある。`PATH-0b`（三角形分割器）は結果が

`3D-2` / `3D-3` はフェーズ C に上げてある。重いのは `3D-4`（第 2 のレンダラ）
だけで、それ以降が実際の 3D 機能。

## 未決: 書き出しをどこに置くか

`EXPORT-*` をフェーズ G に置いたのは依存関係の結果であって、
**製品としての優先度の判断ではない**。

現状 **何も書き出せない**（`README.md` の `render-export-plan.md` の説明が
「you cannot currently export anything」と明記している）。動画編集
アプリケーションとしては存在に関わる欠落で、依存だけで並べるとフェーズ G
まで下がってしまう。

判断が必要な問いはこれ:

- **作れる絵を増やすことを先にするか**（フェーズ D / E / F を通す）
- **少ない絵でも外に出せることを先にするか**（`EXPORT-1〜4` をフェーズ B か
  C に引き上げる）

前者は「自分で使って詰まった所を直す」順序、後者は「他人に見せられる
状態を作る」順序。`EXPORT-1`（エンコーダ抽象と実行時列挙）は依存が無く
**いつでも着手できる**ので、引き上げるコストは低い。

同じ性質の問いが `MOD-5` / `TYPE-*`（タイポグラフィ）にもある。
テキストが無いモーショングラフィックスツールの実用度をどう見るか。

## 順序を動かすときの基準

- **基準 1（移行コスト）に反する入れ替えはしない**。`VEC-5` / `PARAM-1` を
  後ろへ動かすと、移行の対象と検証行列が確実に増える
- **挙動不変のリファクタ（`OVL-1` / `PANEL-1`）を後ろへ動かすなら、
  その間に載せ替え対象を増やさない**こと
- 判断ゲート（`PATH-0a` / `PATH-0b` / `GPU-0` / `GPUCOMP-10` / `GPUCOMP-11`）は
  結果が出るまで後続を並べない
- 体感の修正（`issues/` の perf 項目）はどのフェーズにも割り込ませてよい。
  局所修正で依存が無い
- **基準 0（損失と誤り）に反する入れ替えはしない**。フェーズ A2 / A3 を
  後ろへ動かすと、その間に作った成果物が壊れる / 間違った音のまま蓄積する
- **クラスタから issue を 1 件だけ抜き出して先に直さない**。同じ関数を触る
  ものを束ねてあるので、抜き出すと後続が rebase 衝突する（`HIGH-12`〜`15` の
  epoch 化がその典型）
- issue を計画書が引き受けたら、**クラスタ行から外して個票にも引受先を
  書く**。2 箇所で同じものを追わない
