# ビューアのプレビュー解像度 実装計画（REQ-UI-004）

> **Status**: Planned — 2026-08-06

対象要件: REQ-UI-004（スコープ付きビューア）。
関連: REQ-GPU-001（デバイス共有）、REQ-INFRA-009（バックエンド内製化）、
REQ-RENDER-001（レンダーキュー）。
前提計画: `gpu-backend-plan.md`（`GPUBK-9` の計測）、`gpu-compositing-plan.md`。

## 問題

**フル解像度で結果を確認する手段が無い。**

`crates/ravel-app/src/project_state.rs` の `VIEWER_MAX_DIM = 1024` が対話評価の
長辺を上限で切る（`viewer_resolution()`、呼び出しは 1 箇所）。1920x1080 の
コンポジションはビューアでは常に `1024x576` で評価・表示され、**等倍で見る手段が
無い**。ズームしても 1024 幅の結果を拡大するだけ。

これは「速度の問題」ではなく**品質確認の能力の問題**。文字の可読性、細い線、
グレイン、シャープの効き具合は 1024 幅のプレビューでは判断できない。
書き出し（`EXPORT-0`〜`3`）が未実装なので、**現時点ではフル解像度の出力経路が
どこにも無い**。

`VIEWER_MAX_DIM` が入った理由（シェル合成が CPU でレイヤーごとに readback する）は
**既に消えている**（`GPUCOMP-2/3/4/9`、`GPUBK-6`）。定数だけが残っている。

### 計測が示したこと（`GPUBK-9`、2026-08-06）

`perf-baseline.md` の「ビューア経路の表示解像度」節。1080p / 10 レイヤーの内訳:

| 成分 | ms | 割合 |
|---|---|---|
| CPU 評価 | 約 3.1 | 20% |
| **GPU 計算** | **約 9.1** | **58%** |
| GPU→CPU 転送 | 2.04 | 13% |
| BGRA 変換（`ViewerImage::from_frame_buffer`） | 1.63 | 10% |
| GPUI 再アップロード / present | 未測定 | — |
| 測定済み合計 | 約 15.8 | |

`1024x576` は同じ分解で約 5.7 ms。

ここから 3 つ言える。

1. **1080p 常時 60 fps は届かない。** 15.8 ms で予算 16.7 ms の残りは 0.9 ms、
   そこに GPUI のアップロードと present は入らない。**ただし 30 fps 予算
   33.3 ms なら大きく余る**
2. **ゼロコピー表示だけでは解決しない。** 消えるのは転送 + 変換 = 3.7 ms +
   未測定のアップロードで合計の約 23%。支配項は GPU 計算 9.1 ms
3. **読み戻しの回数はもう減らせない**（`readbacks/frame` = 1.00）

**だから「常時フル解像度」を目標に置かない。** 隠し定数をユーザー制御の
解像度係数に置き換え、**編集中は落とし、手を止めたらフル解像度で描き直す**。
After Effects / Nuke / Fusion が全部この形をとっているのは同じ理由。

## 決定事項（2026-08-06 設計セッション）

### 解像度は係数で、絶対値ではない

`Full` / `1/2` / `1/4` の係数をコンポジション解像度に掛ける。`VIEWER_MAX_DIM`
のような絶対上限は**持たない** — コンポが 4K でも 8K でも同じ係数の意味になり、
「今どのくらい粗いのか」がユーザーに予測できる。

`1/3` は入れない（AE は持つが、`1/2` と `1/4` の間の刻みに実益が薄く、
選択肢が増えるほど「どれを選ぶべきか」が曖昧になる）。必要なら後で足せる。

### 適応解像度のトリガは入力の有無で、負荷ではない

**スクラブ・ドラッグ・パラメータ操作の最中は係数を落とし、入力が止まってから
一定時間で選択係数に戻して再評価する。**

負荷を見て自動調整する形（AE の Adaptive Resolution に近い）は採らない。
理由は**予測可能性**:

- バックグラウンドのビルドや他アプリで画質が勝手に変わる。`GPUBK-9` の計測で
  実際にこれを踏んだ（同じベンチが loadavg 次第で 14.2 ms と 20.1 ms になり、
  判断を誤らせた）
- ヒステリシスと震えの対策が要る
- テストが時間依存になる

入力駆動なら**挙動が常に同じ**で、既存の latest-wins 合併にそのまま乗る。

### 係数はコンポジションではなく UI 状態

プロジェクトの内容ではなく「今どう見ているか」なので、`.ravprj` の
`document/main.ron` には入れない。**`ui_state.json`**（REQ-UI-013 の
アクティブコンプと同じ層）に置く。プロジェクトを共有したときに相手の
プレビュー設定を上書きしない。

**`format_version` は上げない**（`ui_state.json` の任意エントリ追加。
`docs/dev/persistence.md` の判断表どおり）。

### 評価結果のキャッシュは係数を含む

解像度が違う評価結果は別物なので、キャッシュキーに係数（または実解像度）が
入っていなければ `1/4` の結果が `Full` として表示される。**既存の
`EvalContext.resolution` がキーに入っているかを最初の単位で確認する**（入って
いれば追加作業は無い。入っていなければそれが本計画の最初の修正になる）。

### 非対象

- **ゼロコピー表示**。計測から優先度が下がった（約 23%、支配項ではない）うえ、
  GPUI 側がデバイスを渡せない（`architecture.md` の「UI フレームワークの
  フォーク方針」）。別計画
- **GPU 計算そのものの短縮**。支配項だが本計画の範囲外。
  `GPUBK-14` が出した「ディスパッチを 1 コンピュートパスに畳む」
  （149.5 µs/評価）が最初の候補で、別単位として起票する
- **プロキシ / 低解像度素材への差し替え**（REQ-MEDIA 系）。解像度係数は
  評価解像度の話で、素材の差し替えとは別機構
- **書き出し解像度**。係数はビューアにしか掛からない（`EXPORT-*` は
  コンポ解像度で評価する）

## 目標構成

```text
ViewerResolution { Full, Half, Quarter }        ← UI 状態（ui_state.json）
        │
        │  interacting? → 一段落とす（適応）
        ▼
effective_factor
        │  × コンポジション解像度
        ▼
EvalContext.resolution   ← 既存。評価はこれだけを見る
        │
        ▼
評価 → FrameBuffer → ViewerImage（BGRA）→ GPUI
        ▲
        └ ビューアは表示時にコンポ座標へスケールする（既存の仕組み。
          `done/viewer-comp-coordinate-scale-plan.md`）
```

**`viewer_resolution()` は係数の適用に置き換わり、`VIEWER_MAX_DIM` は消える。**

### VRES-1 係数モデルと評価経路

- `ViewerResolution`（`Full` / `Half` / `Quarter`）を `ravel-ui` に置く。
  GUI 非依存の層（コマンドとキーバインドがそこにあるので）
- コンポジション解像度に係数を掛けて評価解像度を出す。**奇数を安全に扱う**
  （1 未満に潰さない、アスペクトを保つ、`div_ceil` か `max(1)` のどちらを
  採るか決めて理由を書く）
- `viewer_resolution()` と `VIEWER_MAX_DIM` を撤去し、係数の適用に置き換える
- **評価キャッシュのキーに解像度が入っていることを確認する。** 入っていなければ
  入れる。`1/4` の結果が `Full` として再利用されないこと

**完了条件**

- 係数から評価解像度が出るテスト（`Full` = コンポ解像度、`Half` / `Quarter`、
  奇数解像度、極小解像度で 0 にならないこと）
- **`VIEWER_MAX_DIM` がリポジトリから消えていること**（`grep` で 0 件）
- 係数を変えると `EvalContext.resolution` が変わるテスト
- **解像度の違う評価結果が互いに再利用されないテスト**
- 既定は `Half`（現行 1024x576 相当のコストを 1080p で維持する）。
  **その根拠を計画書かコードのコメントに書く**

### VRES-2 係数の UI とコマンド

- ビューアに係数の選択を出す（下部のセレクトが自然。`ui-spec.md` の
  ビューア節に合わせる）
- `CommandId` を追加し、`for_each_command!` の表に載せる。キーバインドも
- ロケール（`assets/locales/{en,ja}.toml`）
- **現在の係数と実効係数（適応で落ちている最中）が区別して見えること**

**完了条件**

- セレクトとコマンドの両方から係数が変わる
- `assets/locales/{en,ja}.toml` にキーが揃っている
- キーバインドが `docs/dev/add-command.md` の手順どおり登録されている
- 実機で `Full` に切り替えて、文字の細部が `Quarter` と違って見えることの確認

### VRES-3 UI 状態の永続化

- `ui_state.json` に係数を持つ。**任意エントリで、欠落時は既定（`Half`）**
- `format_version` は上げない

**完了条件**

- 係数が保存・復元されるテスト
- **係数を持たない既存の `ui_state.json` が既定で読めるテスト**
- `docs/dev/persistence.md` の `ui_state.json` の記述を更新

### VRES-4 適応解像度（入力中は落とす）

- スクラブ・ドラッグ・パラメータ操作の**開始で一段落とし、停止から N ms で
  選択係数に戻して再評価する**
- N は定数から始める（設定化は非対象）。**値の根拠を書く**
- 落とす段数は 1 段（`Full` → `Half`、`Half` → `Quarter`、
  `Quarter` → `Quarter`）
- 既存の latest-wins 合併に乗せる。**入力が止まる前の中間フレームを
  フル解像度で評価しない**こと

**完了条件**

- 入力開始で実効係数が落ちるテスト
- 停止から N ms で選択係数に戻り、**再評価が 1 回だけ走る**テスト
  （latest-wins が効いていること）
- 入力が連続している間は再評価が走らないテスト
- **`Quarter` を選んでいるときに適応で更に落ちないテスト**
- 実機でスクラブ中の応答が `Full` 選択時にも保たれることの確認

## 検証

- `VRES-1` / `VRES-3` / `VRES-4` の判定ロジックはヘッドレス
- `VRES-2` と `VRES-4` の体感は実機（`cliclick` でのドラッグ確認）
- **`perf-baseline.md` への追記は係数ごとに。** 測定は
  `GPUBK-9` の節に書いた作法に従う（同一機体・交互・中央値・loadavg を記録）。
  **この機体の loadavg 平常値は 3 前後**で 2 以下は待っても来ないので、
  絶対値ではなく係数間の比を見る

## 落とし穴

- **`VIEWER_MAX_DIM` の撤去はビューアのスケール表示に触る。**
  `done/viewer-comp-coordinate-scale-plan.md` が入れた「評価バッファ解像度と
  コンポ座標の変換」がそのまま効くはずだが、上限が消えて評価解像度が
  コンポ解像度と一致しうる（`Full`）ので、**スケール 1.0 の経路を確認する**
- **`ViewerImage::from_frame_buffer` は毎ピクセルの CPU ループ**で、
  `Full` の 1080p で 1.63 ms、4K で 6.44 ms 掛かる。`Full` を選ぶと
  ここが効いてくるので、係数ごとの実測に含める
- **適応解像度は「入力中」の定義がパネルごとに違う。** タイムラインのスクラブ、
  ビューアのドラッグ、Properties のスクラブ値、カーブエディタの操作が
  それぞれ入力源になる。**1 箇所で判定できる形にする**（各パネルが
  個別に落とす実装にすると必ず抜ける）
- 4K コンポで `Full` は転送 5.54 + 変換 6.44 = 12 ms が出口だけで掛かる。
  **`Full` は「止めて確認する」用途だと文書に書く**
