# スコープ 4 種（波形 / ベクトル / ヒストグラム / パレード）実装計画

> **Status**: 計画のみ — 2026-08-25（`done/viewer-inspection-plan.md` の `INSP-5` が
> 引き取りを判断してこの計画に切り出した）

対象: REQ-UI-004 が Must で要求する波形モニタ / ベクトルスコープ /
ヒストグラム / パレードの 4 パネル。関連要件: REQ-UI-004、REQ-UI-005
（多重インスタンスと Document / View 分離）。

## なぜ `done/viewer-inspection-plan.md` から切り出したか

`INSP-5` は「本計画で引き取るか、別計画に切るか」を決める単位だった。
別計画にした理由は 3 つある。

1. **UI 側に測るデータが無い。** `GPUCOMP-9` / `CM-7` で f32 → 表示バイト列の
   変換が評価ワーカーへ移ったので、UI が持つのは BGRA u8 の表示画像
   （または GPU テクスチャ）だけ。`INSP-3` はリニアフレームの CPU コピーを
   **読み取りが有効な間だけ**フレームに添える仕組みを入れたが、あれは
   消費者が 1 つである前提の `Arc<AtomicBool>` 1 本。スコープは消費者が
   最大 4 種 ×（多重インスタンス）なので、**添付の要求を数える**仕組みが要る。
   これは検査系の表示オプションではなく評価パイプラインの話
2. **毎フレームの統計計算が入る。** 1080p は 200 万画素で、4 パネルが
   それぞれ全画素を走査すると UI スレッドで確実に破綻する。
   間引き幅・共有・（必要なら）GPU への移動という段取りが要る
3. **OCIO が REQ-UI-004 に含まれている。** 色管理は評価パイプライン全体の
   話で、計画が 1 つも無い。この計画は**リニア値を測る**ところまでで区切り、
   表示参照の測り方は色管理の計画へ送る（下の「非対象」）

つまり AGENTS.md の Design gate に当たる規模（複数クレート・複数パネル・
評価経路）なので、`done/viewer-inspection-plan.md`（Viewer の表示オプション）に
足すのではなく独立した計画にした。

## すでにあるもの

**トグルとレイアウトは済んでいる。** `PanelKind::{Waveform, Vectorscope,
Histogram, Parade}` は存在し、`View ▸ スコープ`（`Alt+6`）が
`ravel_ui::shell::SCOPE_PANELS` の 4 枚をまとめて開閉し、ワークスペース
プリセット `assets/workspaces/color.toml` が 4 枚を配置する。
足りないのは**中身**だけ — パネル工場（`crates/ravel-app/src/panels/mod.rs`）が
この 4 種に `PlaceholderPanel` を返している。

したがって REQ-UI-004 の受入条件のうち「メニューから各スコープパネルを
トグルできる」は実質満たしており、残るのは 4 つの「表示される」と
「OCIO を反映」。

## 問題

### 1. 測る値が UI に無い

`panels::ViewerFrame` は `Frame { image, composition_resolution, linear }` /
`GpuFrame { frame, composition_resolution, linear }` で、`linear:
Option<Arc<FrameBuffer>>` は**ピクセル読み取りが有効な間だけ**入る
（`INSP-3`）。ゲートはホストの `Arc<AtomicBool>` 1 本
（`ProjectState::set_pixel_readout` → `GpuEvalHooks::with_display_pixel_readout`）
で、`bool` なので**消費者が 2 つ以上になった瞬間に壊れる** — 読み取りを
off にするとスコープの入力も消える。

### 2. 全画素走査を 4 パネル分は払えない

スコープは 4 種とも「フレーム全体の統計」であって、パネルごとに別の値を
見るわけではない（ヒストグラムとパレードは同じ画素集合の別の見せ方）。
パネルごとに走査すると同じ仕事を 4 回払う。さらに REQ-UI-005 は
同一パネルの多重インスタンスを許すので、上限は 4 ではない。

### 3. 何色空間の値を測るのかが決まっていない

REQ-UI-004 は「OCIO カラースペースを反映」と書くが、色管理の実装が無い。
今測れるのは**評価結果のリニア値**だけで、それは `INSP-3` のピクセル読み取りが
報告している値と同じもの。ここを曖昧にすると「Viewer の絵と波形が合わない」
という報告が出る。

## 目標アーキテクチャ

```text
評価ワーカー                          UI スレッド
────────────                          ──────────
DisplayTransform                      ScopeSummary（Global、1 フレーム 1 回）
  ├─ 表示バイト列 ─────────────────▶  ViewerFrame（絵）
  └─ linear コピー ─────────────────▶  ├─ ピクセル読み取り（INSP-3）
     （要求が 1 つ以上ある間だけ）        └─ scope_summary()（MON-2）
                                              │
                                    ┌─────────┴──────────┐
                                 Histogram  Waveform  Parade  Vectorscope
                                 （各パネルは要約を描くだけ）
```

決め事は 3 つ。

- **リニアフレームの添付は「要求の数」で決まる。** `bool` を数（または
  消費者集合）に替え、ピクセル読み取りとスコープが同じ 1 本のコピーを共有する。
  要求が 0 になったら添付を止める（`GPUCOMP-9` が外した読み戻しを、
  誰も見ていないのに払い続けない）
- **統計はフレームが届いたときに 1 回だけ計算し、Global で共有する。**
  パネルの `render` では計算しない（`HIGH-21` と同型の負荷になる）。
  間引き幅で**サンプル数に上限を置く**ので、コストは解像度に依らない
- **測るのは評価結果のリニア値。** 目盛りは 0–1 を基準にし、それを超える値
  （HDR / 露出オーバー）は切り捨てずに範囲外として示す。表示参照の測定は
  色管理が来てから

### 採らない案

- **パネルごとにサンプルする。** 同じ仕事を N 回払う。値がパネル間で
  食い違う余地も生む（間引きの位相がずれる）
- **最初から GPU コンピュートで集計する。** 正しい最終形の可能性はあるが、
  間引きした CPU 走査で足りるかを測る前に `ravel-gpu` のパイプラインを
  1 本増やすのは順序が逆。**測ってから**移す（`MON-2` の完了条件に上限を置く）
- **表示バイト列（BGRA u8）を測る。** リニアフレームの添付が要らなくなるが、
  測っているのは LUT 込みの表示値なので、カラコレの判断には使えないうえ
  `INSP-3` の読み取りと数字が食い違う

## 実装単位

### MON-1: リニアフレームの要求を数える

`INSP-3` の `Arc<AtomicBool>` を**要求カウント**に替え、ピクセル読み取りと
スコープが 1 本の CPU コピーを共有する。

- `ProjectState` に「リニアフレームを要求している消費者」の集合を持たせる
  （読み取り / スコープ、将来の消費者を足せる形）
- 0 → 1 と 1 → 0 の遷移でだけ、出力段フレームキャッシュを捨てて
  `InvalidationHint::None` で 1 回要求する（`INSP-3` と同じ理由 —
  キャッシュ済みの完成フレームは f32 を持たない）
- 遷移でないとき（2 → 1 など）は何もしない

**完了条件**

- 読み取りだけ on → `linear` が付くテスト
- スコープだけ on → `linear` が付くテスト
- 両方 on → 添付は 1 つ（コピーが 2 本にならない）テスト
- 片方を off → まだ付いている、両方 off → 付かないテスト
- 0 → 1 と 1 → 0 でだけキャッシュを捨てるテスト（回数を数える）

### MON-2: 要約の計算（ヘッドレス）

`FrameBuffer` から 4 種のスコープが必要とする要約を 1 回で作る純粋関数を
`ravel-ui` に置く（`ravel-core` ではない — 評価ではなく読み取りの語彙）。

- ヒストグラム: チャンネルごとの度数分布（ビン数は固定）
- 波形 / パレード: **列ごと**の輝度分布（画面 X = 画像列、Y = 値）
- ベクトルスコープ: 彩度平面の散布（極座標のビン）
- **間引き幅はサンプル数の上限から決める**（例: 上限を N とし、
  `stride = ceil(sqrt(w*h / N))`）。4K でも 1080p でも走査するサンプル数が
  同じになる
- 0–1 の外の値は clamp せず、範囲外として数える（露出オーバーが
  「上端に張り付いた正常値」に見えないように）

**完了条件**

- 既知の画像（黒 / 白 / 単色 / 縦グラデーション）で各要約の値を固定する単体テスト
- 解像度を 4 倍にしてもサンプル数が上限を超えないテスト
- 1 を超える値・負の値が範囲外として数えられるテスト
- 1080p / 4K での計算時間の実測を `perf-baseline.md` に記録し、
  **UI スレッドで払える範囲に収まっていること**（超えていたら
  評価ワーカー側へ移す判断をこの単位でする）

### MON-3: ヒストグラムパネル

`PlaceholderPanel` を置き換える最初の 1 枚。要約の共有経路
（Global + フレーム到着時 1 回計算）はここで通す。

**完了条件**

- 要約が無い（評価前）ときに空の枠だけ描くテスト
- パネルの `render` が要約を計算しないこと（計算は到着時 1 回）を
  固定するテスト
- 目盛り（0 / 0.5 / 1.0）が出ること

### MON-4: 波形モニタ

**完了条件**

- 縦グラデーションの画像で、波形が斜めの帯になることを固定するテスト
- 列数がパネル幅より多い / 少ない両方で潰れないこと

### MON-5: パレード

`MON-4` の描画を 3 チャンネル分横に並べる。**新しい計算は足さない**
（同じ要約の別の見せ方）。

**完了条件**

- 単色画像で 3 つの帯の高さが色成分どおりになるテスト
- `MON-4` と同じ要約から描いていること（別経路を作らない）

### MON-6: ベクトルスコープ

**完了条件**

- グレー画像で中心に集まる、原色で対応する方向へ伸びるテスト
- 目安の枠（グラティクル）が出ること

### MON-7: 受入条件と文書

**完了条件**

- REQ-UI-004 の受入条件 4 つ（波形 / ベクトル / ヒストグラム / パレードが
  表示される）にチェックが入る
- `docs/ui-impl-status.md` に 4 行、`docs/specifications/ui/` に仕様
- ワークスペースプリセット `color.toml` の 4 枚が実機で埋まることの確認
- OCIO が未対応であること（測っているのはリニア値）を仕様に明記

## 非対象

- **OCIO / 表示参照の測定**。REQ-UI-004 が要求しているが、色管理の計画が
  無い。この計画はリニア値の測定で区切り、表示参照のモードは色管理の計画が
  できた時点で単位を足す
- **GPU コンピュートでの集計**。`MON-2` の実測が UI スレッドの予算を超えた
  ときに初めて検討する
- **スコープからの操作**（波形をドラッグしてリフト / ゲインを動かす等）。
  カラコレノードが揃ってからの話
- **スコープ専用の ROI**。部分評価が無いので枠だけ描いても使われない
  （`done/viewer-inspection-plan.md` の非対象と同じ理由）
