# Wrangle とユーザー定義パラメータ 実装計画

> **Status**: Planned（リリース後） — 2026-08-08

対象: `ravel-core` の式言語（`expression/`）とノードのパラメータ、
`ravel-nodes` の属性ノード、`ravel-app` の Properties。
要件は `REQ-CORE-010`（属性）、`REQ-CORE-015`（フィールド式）、
`REQ-PLUGIN-005`（サブグラフテンプレート = HDA 相当）。

**この計画書はリリース後に着手する。** リリース前に済ませておく必要が
あるのは `HIGH-30`（Subnet のポート改名が外側のエッジを落とす）だけで、
その理由は下の決定事項に書いた。

## 問題

### 1. 属性を 1 つ書き換えるのにノードが 2 個要る

`field.expression` と `attribute.set` を繋げば、単一属性の Wrangle 相当は
**もう組める**。属性を 3 つ書き換えるならノードが 6 個並ぶ。
「点の色を位置から決めて、ついでにサイズも決める」程度でグラフが埋まる。

### 2. ユーザー定義パラメータが Subnet の境界にしか生やせない

現在ユーザーがパラメータを足せるのは
`add_custom_port`（`crates/ravel-core/src/network.rs:454`）**だけ**で、
`interface_side`（同 `:387`）が `net.in` / `net.out` 以外の
ノードを弾く。つまり**ネットワークインターフェースの上にしか生えない**。

`REQ-PLUGIN.md` の REQ-PLUGIN-005 は、サブグラフテンプレート（Houdini の
HDA / Nuke の Gizmo / Blender の Node Group 相当）を「最も早く、最も安全に
出せる拡張形態」と位置づけている。だが**その形が成立するのは、Subnet の
昇格と任意ノードのユーザー定義パラメータが揃ったときだけ**。片方だけでは、
公開できるのは境界に直接生やしたパラメータに限られる。

### 3. `backlog.md` の現状認識が古い

`backlog.md` の実機フィードバック表は Wrangle を
「式言語（`EXPR-*`）と WGSL シェーダノード（`PLUG-3`）の交差点。要設計」と
書いていた。**`PLUG-3` は要らない**（下の決定事項）。この計画書が
その行を引き取る。

## 調査で分かったこと

計画の前提が変わるので先に置く。

### 式言語は属性を既に要素ごとに読む

`ExpressionFieldProcessor`（`crates/ravel-nodes/src/field/mod.rs:122`。
登録は `crates/ravel-nodes/src/lib.rs:190`）は
`Scope::field_context()` の語彙で式をコンパイルする。
`STANDARD_ATTRIBUTES`（`crates/ravel-core/src/expression/scope.rs:70`）が
`P` / `N` / `Cd` / `index` を宣言し、**それ以外の名前も受ける**
（属性の存在はコンパイル時に決まらないので、既定値へ落として
サンプル時に警告する）。`@P.x`、`@Cd.r`、`@index` が通ることは
`crates/ravel-core/src/expression/tests.rs:583` 以降に固定されている。

**時間依存の判定も入っている** — `expression_field_reads_the_clock`
（`field/mod.rs:142`）が `frame` / `time` を読む式かどうかを構築時に
判定し、読まない式はフレームをまたいでキャッシュされる。

### 属性を書く側も揃っている

`attribute.set` が属性を書く。`VEC-5` で `value` は**型駆動**になっており、
`type` を変えると値の形とパラメータポートの型が 1 コマンドで付け替わる
（`Graph::set_params` と `registry::builtin::dependent_param_updates`）。

### つまり足りないのは言語の側面だけ

「`field.expression` → `attribute.set`」で**単一属性の Wrangle 相当は
既に組める**。足りないのは:

- **複数の文**（`;` 区切り）
- **複数の属性への書き戻し**（`@Cd = …` という左辺）
- **ローカル変数**（中間結果に名前を付ける）

パーサは現状これを持たない — `crates/ravel-core/src/expression/parser.rs:28`
が「文も代入もループも定義形式も無い」と明言している。

### 変数名前空間の拡張は最初から想定されている

`Scope::declare_variable`（`scope.rs:108`）と
`Scope::with_variables`（同 `:127`）は public で、
`Scope::parameter_context()`（同 `:89`）と `field_context()`（同 `:97`）が
その実例になっている。

**カスタムパラメータを式から名前で引くのは、ノードのパラメータ名を
`with_variables` に渡し、値をスロット順で渡すだけ。** 言語側の工事はほぼ無い。

## 決定事項

### Wrangle は「複数の文で複数の属性を書く 1 つの CPU ノード」

型キーは `attribute.wrangle` のような形。**GPU は含めない。**

`PLUG-3`（WGSL シェーダノード）を交差させない理由は 2 つ。第 1 に、
`field.expression` の CPU 経路が既に動いており、そこから連続的に伸ばせる。
第 2 に、GPU を混ぜると「同じ式が CPU と GPU で違う答えを出さないこと」を
最初から背負うことになり、言語の設計とバックエンドの設計が同時に動く。
**GPU への移行は `gpu-resident-geometry-plan.md` の測定基準に従って
後から判断する**（各モーショングラフィックス計画の「GPU 方針」と同じ扱い）。

**要素の追加・削除も含めない。** `addpoint` / `removepoint` 相当は
`OPS-1`（`geometry.blast`）の領分で、要素数が変わるとスコープ
（`evaluation-scope-plan.md` の `PathSegment`）の話になる。言語の話ではない。

### カスタムスライダーは任意のノードに一般化する。Wrangle はその一利用者

Wrangle 専用のパラメータ機構を作らない。**任意のノードにユーザー定義
パラメータ（spare parameter）を足せるようにし、Wrangle はそれを使う。**

理由は `MED-APP-25` の「採番規則を 2 つ置かない」と同じ。ユーザー定義
パラメータの機構が 2 本あると、永続化・undo・改名伝播・式からの参照が
それぞれ 2 通りになる。片方だけ直したバグが残り続ける。

一般化すると `add_custom_port` の `interface_side` 制限が外れ、
**REQ-PLUGIN-005 の HDA 相当が成立する**（Subnet の昇格と組み合わせて）。

### `HIGH-30` を先に直すのが前提

[`HIGH-30`](../../issues/high/HIGH-30-subnet-port-rename-drops-outer-edges.md)
は Subnet のポート改名が外側のエッジを落とす。**カスタムパラメータを
持てるノードが増えるほど、リネーム伝播の穴が広がる。**今は境界ノードだけの
問題だが、任意のノードが改名対象になれば同じ穴が全ノードに開く。

だから `HIGH-30` は**リリース前**に塞ぐ。この計画書自体はリリース後だが、
前提だけは先に片付ける。

### `PGRP` と `MED-APP-26` への波及

- **`PGRP`（パラメータグループ）** — グループ化の対象が増える。
  `parameter-groups-plan.md` は「グループはノード型が宣言する。インスタンスに
  持たせるのは In ノードだけ」と決めており、**spare parameter は型が知らない
  パラメータ**なので、In ノードと同じ扱い（インスタンス側のグループ）に
  なる。`PGRP-4` が持っている形をそのまま広げれば足りる
- **`MED-APP-26`（露出トグルが片道）** — 下の未決定を参照

## 未決定の分岐: spare parameter は既存の露出モデルに乗るか

**この計画書では決めない。** 判断材料だけ置く。

現在の「プロジェクトへ露出」（`done/exposed-parameters-plan.md` の `EXPO-*`）は
**既にあるパラメータをプロジェクト境界の外へ名前で出す宣言**で、
`MED-APP-26` はそのトグルが片道になっているというバグ。

spare parameter は**ノードに新しいパラメータを生やす**操作で、方向が逆。
2 つの繋ぎ方がある:

| 案 | 形 | 得 | 損 |
|---|---|---|---|
| A. 2 段 | spare parameter を生やす → 既存の `EXPO-*` で露出する | 露出の機構が 1 つのまま。`MED-APP-26` の修正がそのまま効く | ユーザーの操作が 2 段になる。「スライダーを作る」だけのつもりで 2 回操作する |
| B. 兼用 | spare parameter の宣言が露出宣言を兼ねる | 操作が 1 段 | 露出の宣言が 2 経路になる。`EXPO-3`（宣言の機械可読な列挙）と CLI の `--param` が両方を見る必要が出る |

**判断は `WRG-4` の着手前に要る**（宣言の置き場所が変わるため）。
決めるときは `MED-APP-26` の修正が入った後の形を見ること — 片道トグルが
直っていない状態で兼用にすると、解除できない宣言が増える。

## 実装単位

| ID | 単位 | 依存 |
|---|---|---|
| WRG-1 | 式言語の複数文とローカル変数（`;` と代入） | — |
| WRG-2 | 属性への書き戻し（`@attr = …` の左辺） | WRG-1 |
| WRG-3 | `attribute.wrangle` ノード | WRG-2 |
| WRG-4 | spare parameter の機構（任意ノードのユーザー定義パラメータ） | `HIGH-30`、上の分岐の決着 |
| WRG-5 | spare parameter の編集 UI | WRG-4 |
| WRG-6 | spare parameter を式から名前で引く | WRG-3, WRG-4 |
| WRG-7 | ロケール / 文書 | WRG-1〜6 |

### 単位 1: 式言語の複数文とローカル変数

- `;` 区切りの文列と `name = expr` の代入をパーサへ足す。
  **ループも関数定義も足さない**（`parser.rs:28` の「ループ無し」は
  評価コストの上限を保証している性質で、崩さない）
- ローカル変数は `Scope::declare_variable` のスロットに乗る。
  **新しい記憶域を作らない**
- 最後の文の値が式全体の値になる。**既存の 1 式のソースは 1 文の
  文列として同じ結果を返す**（互換）

**完了条件**

- 既存の式のテストが 1 つも変わらずに通る
- `a = @P.x * 2; a + 1` が評価できる
- **未定義の「変数」が従来どおりコンパイルエラーになる。**
  `@attr` はこれに含まれない — 属性の存在はコンパイル時に決まらないので、
  未知の `@attr` は**通したうえで既定値へ落とし、サンプル時に警告する**
  （`field.expression` の現在の挙動。単位 0 の記述と同じ規則）。
  両方をテストで固定する
- ループの構文が無いことがテストで固定されている

### 単位 2: 属性への書き戻し

- `@Cd = …` を左辺として受け、**書き込まれた属性の集合**を
  `Program` から取り出せるようにする
- 型（幅）は右辺の値から決まる。`STANDARD_ATTRIBUTES` に無い名前も書ける
- **読みと書きが同じ式の中で混ざる場合の順序**を決める:
  文の順に評価し、後の文は前の文の書き込みを読む

**完了条件**

- 書き込まれた属性の一覧が取れる
- `@Cd.r = @P.x; @Cd.g = @Cd.r` が期待どおりの値になる
- 読み専用の式（既存のフィールド式）が書き込み集合を空で返す

### 単位 3: `attribute.wrangle` ノード

- ジオメトリを受け、要素ごとに式を評価し、書き込まれた属性を更新して返す
- 属性が無ければ**作る**（`STYLE-5` の「`field.apply` の属性自動作成」と
  同じ規則に合わせる。規則を 2 つ持たない）
- **時間依存の判定は `expression_field_reads_the_clock` と同じ形**で行う。
  読まない式はフレームをまたいでキャッシュされる
- `field.expression` は残す。**Wrangle は置き換えではなく上位であり**、
  フィールドを値として渡す用途は `field.expression` のまま

**完了条件**

- 複数属性を 1 ノードで書き換えられる
- 時間を読まない式でフレーム間キャッシュが効く（`field/mod.rs:764` の
  テストと同型のテスト）
- 式が壊れているとき、評価は止まらずエラーがノードに出る

### 単位 4: spare parameter の機構

- `interface_side` の制限を外し、**任意のノードにパラメータを足せる**形へ
  一般化する。`add_custom_port` の予約名検査と重複検査はそのまま効かせる
- 永続化は `.ravprj` のフォーマットを 1 つ上げる。**採番はマージ順**
  （着手時に `manifest.rs` の `CURRENT_FORMAT_VERSION` を見る。
  `discrete-keyframes-plan.md` / `asset-identity-plan.md` /
  `parameter-groups-plan.md` / `CM-2` と競る）
- **改名は既存の伝播経路に乗せる**（`HIGH-30` の修正後の形）。
  新しい伝播を書かない
- グループ割り当ては `PGRP-4` のインスタンスグループに乗る

**完了条件**

- 任意のノードにパラメータを足せて、`.ravprj` を往復しても残る
- 改名で式・ポート・宣言の参照が追随する（`HIGH-30` の回帰テストが
  任意ノードでも通る）
- 旧バージョンの `.ravprj` が読め、spare parameter 無しとして扱われる
- 予約名（組み込みパラメータと同名）が拒否される

### 単位 5: spare parameter の編集 UI

- Properties から追加・削除・改名・型変更ができる
- 型は `CustomPortType` の既存の集合に合わせる。**新しい型体系を作らない**
- 追加・削除は 1 undo

**完了条件**

- 追加したパラメータが Properties に出て、値が編集できる
- 削除すると参照していた式がエラーを出す（黙って既定値へ落ちない）
- 各操作が 1 undo

### 単位 6: spare parameter を式から名前で引く

- ノードのパラメータ名を `Scope::with_variables` に渡し、値をスロット順で
  渡す。**言語側の変更は無い**
- 名前の衝突（`frame` / `time` / `elem.count` などの組み込み名）は
  **パラメータの追加時に拒否する**。式のコンパイル時に静かに勝敗を
  決めない

**完了条件**

- Wrangle のカスタムスライダーが式から名前で読める
- 組み込み名と同じ名前のパラメータが追加時に拒否される
- パラメータをアニメートすると式の結果が時間で変わる

### 単位 7: ロケール / 文書

**完了条件**

- 追加した文言が ja / en 揃っている
- `docs/specifications/data-model.md` のパラメータの記述が追随
- `docs/dev/` のノード追加手順と永続化変更手順が追随
- REQ-PLUGIN-005 の受入条件のうち、spare parameter で満たせるものに印が付く

## 非対象

- **GPU（WGSL）版の Wrangle。** 上記のとおり `PLUG-3` とは交差させない
- **要素の追加・削除。** `OPS-1` の領分
- **ループと関数定義。** 評価コストの上限が壊れる
- **`field.expression` の廃止。** フィールドを値として渡す用途が残る
- **他のノードの式化**（既存ノードを Wrangle で置き換える）。
  組み込みノードは組み込みのまま速い
