# REQ-CORE — コアエンジン

## REQ-CORE-001: ノードグラフトップレベルアーキテクチャ + Composition/Layer モデル

- **優先度**: Must
- **ステータス**: Revised (v3 — レイヤーネットワークモデル。詳細は REQ-LAYER)
- **説明**: Ravelの内部表現はノードグラフ（DAG）を基盤とする。Composition は独自の解像度・FPS・尺を持ち、Layer の順序付きリストを保持する。タイムラインUIは選択中の Composition 内の Layer 群を表示する「ビュー」として機能する。全てのデータフロー、エフェクト適用、合成はDAG上のノード接続で表現される。
- **Compositionモデル（AEモデル）**:
  - Composition は独自の解像度・FPS・尺を持つ（AEプリコンプ相当）
  - Layer は下から上への合成順序を持つ（AE標準）
  - **v3: 各 Layer は「殻」（ビルトインTransform、opacity、blend_mode、時間配置、親子付け等の汎用プロパティ）+「1つのノードネットワーク」で構成される（1レイヤー = 1ネットワーク、Houdini 的。REQ-LAYER-001）**
  - **v3: 従来の LayerSource 構造分岐とエフェクトサブグラフの二重構造は廃止。レイヤー種は作成時テンプレートに降格（REQ-LAYER-008）**
  - Layer の親子関係（Parenting）をサポート。Null Layer による制御。Transform継承（Null Layer は REQ-LAYER-005 で再定義）
- **評価方式（v3）**: 殻の合成チェーン（時間変換 → Transform → Opacity → Merge）は従来通り synthetic ノードへコンパイルするが、**v2 の「Composition 全体を平坦な DAG ノード列に展開し Evaluator 変更不要」方式は撤回**。レイヤーネットワークは平坦化せず、ネットワーク境界ノードを介した再帰評価とし、Evaluator は Document-aware 化・スコープ付き EvalContext・評価時パラメータ解決の変更を受け入れる（REQ-LAYER-006, REQ-LAYER-007）。殻の決定論的 ID による dirty 追跡・キャッシュ維持は継続して機能する。
- **受入条件**:
  - [ ] ルートノードグラフが存在し、全処理がDAG上のノードとして表現される
  - [ ] Composition が Layer の順序付きリストを保持する
  - [ ] 殻の合成チェーンが synthetic ノード列にコンパイルできる
  - [ ] タイムラインUIが Composition 内の Layer の in/out + キーフレームを表示する
  - [ ] Layer のノードネットワークをノードエディタで開いて編集できる（REQ-LAYER-011）
  - [ ] ノードグラフの変更がタイムライン表示に反映される
  - [ ] PreComp（入れ子 Composition）が動作する

- **優先度**: Must
- **ステータス**: Draft

  - [ ] トポロジカルソートに基づく評価順序が保証される

## REQ-CORE-006: 三層キャッシュ (VRAM/RAM/Disk)

- **優先度**: Must
- **ステータス**: Revised (v2)
- **説明**: **出力段（Composition / レイヤー出力）のフレームを**三層でキャッシュ。
  GPU VRAM（最速、容量小）→ RAM（中速、中容量）→ ディスク（低速、大容量）と
  段階的にエビクトする。プレビュー再生時は VRAM キャッシュから直接表示し
  ゼロコピー。キーは所有パスと、量子化した時間・解像度・フレームレート・
  品質・**精度**・bypass からなる同一性の組。**精度以外の軸は厳密一致**で
  照合し、**精度だけは順序比較**とする — 要求側が受け入れ可能な最低精度を
  宣言し、保存精度がそれ以上なら（変換せずそのまま渡せるので）ヒット、
  下回ればミス。書き出しは常に f32 を要求するので、キャッシュの有無で
  成果物が変わらない。エントリを縮小・降格して流用する近似ヒットは行わない。
  ノード単位の評価キャッシュは 1 ノード 1 値のまま同一性照合で運用し、
  多エントリ化は将来の判断とする。バイト予算は層をまたいで単一の権威が会計し、
  シミュレーションキャッシュ（REQ-CORE-011）には保護枠を与える。ディスク層は
  グローバルなキャッシュディレクトリに置き、格納先は設定で変更できる
  （未保存プロジェクトでも効かせるため。REQ-PROJ-001 の zip コンテナ内には
  置かない）。
- **受入条件**:
  - [ ] 三層キャッシュが動作しVRAMヒット時にGPU→CPU転送が発生しない
  - [x] 単一のバイト予算が層をまたいで会計し、上限超過でエビクトされる
        （`CacheBudget`。VRAM は評価キャッシュの GPU 常駐値とテクスチャ
        プールのアイドル枠を 1 つの総額で会計し、アイドル枠は残余）
  - [ ] シミュレーションキャッシュの保護枠が通常エントリの圧力で削られない
        （`CacheBudget` 側の予約枠の会計とテストは済み。sim は通常エントリの
        圧力では退避されず、sim 単独が層の上限を超えたときだけ sim 同士で
        退避する。ただし**シミュレーションキャッシュ本体が未実装**なので
        条件は未達。担当は `stateful-eval-plan.md` の `SIM-1`）
  - [ ] 要求精度を下回るエントリがヒットせず、上回るエントリは変換なしでヒットする
  - [ ] ディスクキャッシュがグローバルなキャッシュディレクトリに永続化され、格納先を設定で変更できる
  - [ ] キャッシュヒット率がモニタリング可能で、キャッシュ済み範囲を UI から参照できる
        （ヒット率は `Evaluator::cache_stats()` で読める。キャッシュ済み
        範囲の UI は `cache-plan.md` の `CACHE-6`）
- **依存**: REQ-GPU-001, REQ-CORE-002
- **v2 改訂の理由**: 三層をノード単位の評価結果に対して定義していたが、
  現行の評価キャッシュは 1 ノードにつき値を 1 つしか持てず（`NodeKey` が
  path + node のみ）、多エントリ化は無効化経路の全面再検証を伴う。一方で
  体感（スクラブ・再生・キャッシュ済み範囲の表示）に効くのは出力段だけなので、
  三層の定義を出力段に移した。ディスク層の格納先は、実装が
  「未保存プロジェクトでも効く」ことを理由に既にグローバルを選んでいた
  （`docs/implementation/media-import-plan.md`）ことと、`.ravprj` の展開
  ディレクトリ運用が未実装であることから、要件側を実装に合わせた。
  設計は `docs/implementation/cache-plan.md`。

## REQ-CORE-009: 制限なし解像度/FPS/32bit float内部処理

- **優先度**: Must
- **ステータス**: Revised (v2)
- **説明**: **画素演算は常に32bit floatで実行**。入出力の解像度・フレームレートに人工的な上限を設けない。パフォーマンスはハードウェア依存。OCIO（REQ-RENDER-003）も32bit floatリニア空間での処理を前提。
  **保存表現は演算精度と区別する**: GPU 常駐フレームとキャッシュエントリは
  縮約形式（f16 等）で保持してよく、その場合も演算に入る前に f32 として
  読み出す（精度が演算へ漏れない境界を 1 箇所に置く）。書き出しは f32 の
  保存精度を要求する（REQ-CORE-006）。
- **受入条件**:
  - [ ] 画素演算が32bit floatで行われる
  - [ ] 8K以上の解像度で動作する（パフォーマンスはハードウェア依存）
  - [ ] 120fps以上のフレームレートで動作する
  - [ ] 縮約形式の保存表現が、演算へ渡る境界で f32 として読み出される
  - [ ] 表示・書き出し以外でビット深度変換が絵に影響しない
- **v2 改訂の理由**: 「内部フレームバッファは常に 32bit float」「ビット深度
  変換は入出力時のみ」という記述は、**GPU 経路が既に `Rgba16Float` で
  レンダリングしている**実装と乖離していた。加えて REQ-CORE-006 v2 の
  フレームキャッシュは縮約形式で保持することで初めて実用的な枚数が乗る。
  そこで「演算精度」と「保存表現」を分け、前者を f32 に固定したまま後者の
  縮約を許す形に改めた。設計は `docs/implementation/cache-plan.md`。

## REQ-CORE-010: ジオメトリ属性システム

  - [ ] 任意名・任意型の属性を point / instance ドメインに付与できる
  - [ ] 標準属性（P/index 等）が全ジオメトリ生成ノードで設定される
  - [ ] 複製・変形・変換ノードを通過しても属性が保持・伝播される
  - [ ] 属性の転送・昇格・サンプリング操作がノードとして提供される
  - [ ] 式から属性値を参照できる（`@attr` 相当のアクセス。REQ-CORE-015）
  - [ ] GeometricData トレイト（REQ-CORE-003）配下に統合される
- **依存**: REQ-CORE-003, REQ-CORE-004

## REQ-CORE-011: ステートフル評価とシミュレーションキャッシュ

- **優先度**: Must
- **ステータス**: Draft
- **説明**: パーティクル・物理・トレイル等、**前フレームの結果に依存するノード**を Hybrid Pull 評価（REQ-CORE-002）と整合する形でサポートする。ステートフルノードは「フレーム逐次評価」を宣言し、評価エンジンはフレーム t の要求に対し未計算区間 [last_cached+1, t] を順に評価してシミュレーションキャッシュに蓄積する。上流パラメータ/グラフ変更時はキャッシュを影響フレーム以降で破棄し再計算する。タイムラインスクラブ時は最後にキャッシュされたフレームまでの結果を表示し、再計算をバックグラウンドで進行する。同一シード・同一入力での評価は決定的であること。
- **受入条件**:
  - [ ] ステートフルノードがフレーム逐次で評価され前フレーム状態を参照できる
  - [ ] シミュレーション結果がフレーム範囲でキャッシュされる
  - [ ] 上流変更でキャッシュが影響フレーム以降のみ破棄される
  - [ ] 後方スクラブ（t が既キャッシュ範囲内）が再計算なしで表示される
  - [ ] 前方ジャンプ時に未計算区間が順次評価される（UI は非ブロック、REQ-CORE-005）
  - [ ] 同一シードで再現可能（決定的評価）
  - [ ] ステートレスノードの評価パス（REQ-CORE-002）に性能退行がない
- **依存**: REQ-CORE-002, REQ-CORE-006

## REQ-CORE-013: グラフ内反復

- **優先度**: Should
- **ステータス**: Revised (v2 — 2026-07-27 に「v1 では採用しない」を撤回)
- **説明**: Houdini for-each / Geometry Nodes repeat zone 相当のグラフ内ループ。**ピース単位**（整数属性の値ごとにジオメトリを分割し、値の種類数だけ内部ネットワークを評価する）で提供する。要素単位の反復（1 要素ごとに評価）は採用しない — 全要素同時変調は従来どおり属性システム + フィールドが担い、反復は「属性では書けない構造的な操作を部分集合ごとに適用する」ためのものと位置づける。実装計画は `docs/implementation/evaluation-scope-plan.md`。
- **v1 撤回の理由**: 当初の不採用判断は「評価エンジンの静的 DAG 前提を維持する」ためだったが、(1) 本機能は動的なグラフ書き換えではなく静的 DAG を異なるスコープで複数回 pull するだけで、REQ-LAYER-003 の subnet が既に行っていることの一般化にすぎず前提を壊さない。(2) 現行の評価キャッシュは 1 ノードにつき値を 1 つしか保持できず（`NodeKey` が path + node のみ、frame はキーではなく検証条件）、REQ-CORE-011 のシミュレーションキャッシュと REQ-MOGRAPH-005 のタイムリマップが**同じ制約に別々の回避策で当たっていた**。共通のスコープ軸（`PathSegment` の拡張）を先に決めれば反復は追加機構なしで載るため、後回しにするほど統合コストが上がる。
- **受入条件**:
  - [ ] 整数属性のピースごとに内部ネットワークが評価される
  - [ ] 反復インデックスとピースジオメトリを内部ネットワークが受け取れる
  - [ ] 結果の結合が要素数・属性列ともに正しい
  - [ ] 反復回数の上限超過が黙って切り捨てられずエラーになる
  - [ ] 反復のネストが評価エラーになる
  - [ ] 同一入力での評価が決定的（ピース分割順がハッシュ順に依存しない）
  - [ ] 上流編集で全反復スコープのキャッシュが破棄される
- **依存**: REQ-CORE-002, REQ-CORE-010, REQ-CORE-012

## REQ-CORE-014: パラメータ式

- **優先度**: Must
- **ステータス**: Draft（2026-08-03 新設。REQ-CORE-007 と REQ-PLUGIN-003 から分離）
- **説明**: パラメータ 1 つの値を式で計算する。統一アニメーションチャネル
  （REQ-CORE-007）の値ソースの 1 つで、評価 1 回につき 1 値を返す。
  `frame` / `time` / `fps` / コンポジション寸法などのコンテキスト変数と、
  数学関数（三角・指数・`noise`・`clamp`・`mix`・条件）が使える。

  **言語はループを持たない軽量式言語とし、Lua は使わない。** 判断の根拠:

  1. **他ノードの参照は式の仕事ではない。** チャネルは `NodeOutput` ソースを
     独立に持ち、ブレンドで合成できる（REQ-CORE-007）。After Effects の
     `thisComp.layer("X").position` に当たるものは Ravel ではグラフのエッジで
     表現される。したがって式が担うのは自分のコンテキストと入力から値を作ることだけで、
     汎用言語の表現力を要らない。
  2. **式ソースは永続化される。** 移行コストが非対称で、狭い式言語から
     後で汎用言語を足すのはチャネルのソース種別を増やすだけだが、逆向きは
     保存済みのコードを機械変換できない。狭い方から始めるのが安全側。
  3. **停止性が構文で保証される。** ループが無いので、命令数フックや
     メモリ上限といった実行時のサンドボックス機構が要らない（REQ-INFRA-007）。
  4. **フィールド式（REQ-CORE-015）と同じ言語を共有できる。** そちらは
     要素ごとの評価になるため、AST を持てること（ベクトル化・将来の
     シェーダ変換）が効く。

  **決定的かつ副作用なし**でなければならない。三層キャッシュ（REQ-CORE-006）は
  「同じ入力なら同じ出力」を前提にキーを作るので、式が参照するものは
  すべてキャッシュキーに入る必要がある。式言語のパーサが依存を静的に列挙できることが
  この要件の前提。

  **式言語は全域関数とする。** すべての演算をすべての入力に対して定義し
  （`1/0` → 無限、`sqrt(-1)` → NaN 等）、**実行時エラーが存在しない**言語にする。
  構文エラーと未定義変数は**編集時に**検出できる（変数集合が静的に決まるため）。
  これにより「評価中に失敗しうる」経路が消え、値ソースの評価は値を返すだけの
  シグネチャを保てる。有限でない結果はチャネル境界で既定値に落とす。

  **失敗はそのパラメータに閉じる。** 編集時のエラーは位置付きで表示し、
  不正な式は保存されても評価には使われない（既定値のまま）。評価全体を落とさない。

- **受入条件**:
  - [ ] パラメータに式を設定でき、フレームごとに評価される
  - [ ] `frame` / `time` / `fps` とコンポジション寸法にアクセスできる
  - [ ] 数学関数（sin / cos / exp / noise / clamp / mix / 条件）が使える
  - [ ] 構文エラーと未定義変数が編集時に位置付きで表示される
  - [ ] 不正な式が評価に使われず、該当パラメータが既定値のままになる
  - [ ] 有限でない結果（NaN / 無限）が既定値に落ちる
  - [ ] 失敗したパラメータと式がユーザーに届く
  - [ ] 同一の式・同一フレームの評価が決定的で、キャッシュキーが式ソースと
        参照集合を含む
  - [ ] 式が参照する依存が静的に列挙でき、dirty 伝播に使える
  - [ ] 式ソースが `.ravprj` に永続化され、往復する
  - [ ] ループを書けない（言語仕様として）
- **依存**: REQ-CORE-002, REQ-CORE-006, REQ-CORE-007

## REQ-CORE-015: フィールド式

- **優先度**: Should
- **ステータス**: Draft（2026-08-03 新設。REQ-CORE-012 から分離）
- **説明**: フィールド（REQ-CORE-012）の 1 種として、位置と属性から要素ごとの値を
  式で計算する。言語は REQ-CORE-014 と同一。Houdini の VEX に当たる位置づけで、
  ジオメトリ属性の変調・パーティクルフォース・per-instance パラメータ変調
  （REQ-MOGRAPH-001）に接続する。標準属性（`P` / `index` / 法線 / 色）と
  任意名の属性を参照できる。

  **評価はバッチである。** フィールドのサンプルは位置の配列を受けて値の配列を
  返す契約なので、要素ごとに評価器を呼び出す実装に縛られない。パラメータ式
  （数百回 / フレーム）と違って要素数は数万オーダーになりうるため、性能特性が
  2 桁以上違う。**要素数に対して線形で、要素ごとの固定オーバーヘッドが
  支配的にならない**ことを要件とする。

  将来 GPU 側で評価する余地を残す。AST を持つ言語を選んだ理由の 1 つがこれで、
  式を WGSL などのシェーダ言語へ落とす経路が閉じない（REQ-GPU-001）。

- **受入条件**:
  - [ ] フィールドノードとして式を書き、任意のジオメトリ属性を変調できる
  - [ ] 位置（`P`）と任意名の属性を式から参照できる
  - [ ] 他のフィールドと合成（加算・乗算・最大等）できる
  - [ ] 評価が要素数に対して線形で、要素ごとの固定オーバーヘッドが支配的でない
  - [ ] 同一入力の評価が決定的で、要素の順序に依存しない
  - [ ] エラーがフィールド単位に閉じ、評価全体を落とさない
  - [ ] パラメータ式（REQ-CORE-014）と同一の構文・関数群が使える
- **依存**: REQ-CORE-010, REQ-CORE-012, REQ-CORE-014
