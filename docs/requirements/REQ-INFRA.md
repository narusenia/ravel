## REQ-INFRA-007: 拡張の信頼モデル（段階分け）

- **優先度**: Must
- **ステータス**: Revised (v2 — 2026-08-03 に段階を明示)
- **説明**: 拡張点ごとに必要な隔離の強さが違う。**一律に「サンドボックス」と
  呼ぶと、実行時機構が要らないものに要らない機構を付け、要るものに足りない
  機構で済ませることになる**ので、段に分けて定義する。

  | 段 | 対象 | 必要な機構 | 根拠 |
  |---|---|---|---|
  | **0: 隔離不要** | 式（REQ-CORE-014 / -015） | なし | ループが文法に無く I/O を持たない。停止性が構文で保証される |
  | **0: 隔離不要** | サブグラフテンプレート（REQ-PLUGIN-005） | なし | コードを実行しない。既存ノードの組み合わせ |
  | **1: ホストは安全、GPU は止められる** | WGSL シェーダ（REQ-GPU-003, REQ-PLUGIN-002） | naga による検証 + **ループ境界の扱いの決定** | ホスト側の capability が空（ファイル・ネットワーク・ホストメモリに到達しない）。**ただし WGSL は `for` / `while` / `loop` を持つ**ので、長すぎるループは GPU ハング / TDR を起こせる。`MED-GPU-03`（ブラー半径未クランプで per-pixel ループが無限膨張し GPU ハング）が実例で、`blur.wgsl` も `rasterize.wgsl` も実際にループを使う |
  | **2: 実行時制限** | Lua（REQ-PLUGIN-003 / REQ-CODE-001） | `io` / `os` 除外 + **命令数フック** + **メモリ上限** | 汎用言語なので停止性を言語で保証できない。`while true do end` も `string.rep("x", 1e9)` も書ける |
  | **3: capability** | WASM（REQ-PLUGIN-002 / REQ-CODE-004） | ホストが与えた機能のみ到達可能 | ABI とサンドボックスが処理系側に揃っている |
  | **4: プロセス分離** | OFX（REQ-PLUGIN-001） | 子プロセス（REQ-PROJ-002） | 目的はセキュリティではなく**クラッシュ耐性**。他者のネイティブコードを落とさせない |
  | **信頼（隔離しない）** | Rust ネイティブ（REQ-PLUGIN-002 の補助形態） | なし。**ユーザーへの明示が要件** | 任意コード実行。配布対象にしない |

  **段 0 と段 1 の違いが設計上の意味を持つ。** 式とサブグラフテンプレートは
  実行時のサンドボックス機構なしで安全に出せる。WGSL は**ホストに対しては
  同じく安全**（capability が空）だが、**GPU を止められる**点だけが違う。
  したがって WGSL プラグインを出すには、ホスト側の隔離機構ではなく
  「ループ境界をどう扱うか」の判断だけが必要になる。選択肢は (a) 静的解析で
  非有界ループを拒否する、(b) ループ回数を決めるパラメータをクランプする
  （`MED-GPU-03` が blur で採った方法）、(c) TDR リスクを受け入れて
  ドライバのリセットに任せる。**実装計画で決める。**

- **受入条件**:
  - [ ] 式とサブグラフテンプレートにループを書けない / コードを実行しない
  - [ ] WGSL が naga の検証を通り、失敗が理由付きで表示される
  - [ ] WGSL シェーダがホストのファイル・ネットワーク・メモリに到達できない
  - [ ] WGSL のループ境界の扱いが決まっており、非有界ループの帰結
        （拒否 / クランプ / TDR 受容）が文書化されている
  - [ ] Luaスクリプトからファイルシステムにアクセスできない
  - [ ] Luaスクリプトからネットワークにアクセスできない
  - [ ] Lua の無限ループが命令数フックで中断され、UI が固まらない
  - [ ] Lua のメモリ確保が上限で止まり、プロセスが落ちない
  - [ ] OFXプラグインが別プロセスで実行される
  - [ ] プラグインクラッシュ時にメインプロセスが生存する
  - [ ] 信頼モデルが拡張の種別ごとに UI に表示される（REQ-PLUGIN-004）

## REQ-INFRA-009: GPU バックエンドと UI 依存の内製化

- **優先度**: Must
- **ステータス**: Revised（v2 — 2026-08-06。性能目的を第一級から**副次的・
  要再測定**へ格下げ）
- **目的 1（第一級）: OFX 対応（REQ-PLUGIN-001）とデバイス共有
  （REQ-GPU-001）。** OFX GPU Render Suite は OpenGL / CUDA / Metal を前提と
  する。wgpu の内側にあるデバイスをこれらの API の語彙で外に出す道が無いので、
  wgpu のままでは OFX の GPU 経路が CPU バッファ往復に落ちる。**Must の要件
  （OFX）が別の Must（wgpu 固定）に阻まれている**ので、後者を動かす。

- **目的 2（副次的・要再測定）: 性能。** v1 はこれを第一級としていたが、
  **測ったら Metal では成立しなかった**ので格下げする。macOS / Metal で
  wgpu 経由とプラットフォーム API 直叩きを比べた実測
  （`docs/implementation/perf-baseline.md` の「wgpu 抽象の取り分」節、
  判定は `docs/implementation/gpu-backend-plan.md` の `GPUBK-14`）:

  | 容疑 | wgpu の取り分 | バックエンドが必要か |
  |---|---|---|
  | フェンス待ちの粒度 | 約 1.32 ms / 待ち 1 回 | 不要（`wgpu-hal` の 1 ms sleep。上流修正か有界スピンで取れる） |
  | ディスパッチ単位の記述 | 158 µs / 評価 | ほぼ不要（95% は wgpu 内でディスパッチを 1 パスに畳めば取れる） |
  | バリアの粒度 | 測定誤差内（0） | — |

  **バックエンドを書いて初めて取れるのは約 20 µs / 評価**（60 fps 予算の
  0.1%）。**この数字を根拠にバックエンド着手を正当化しない** — 性能の取り分は
  まず wgpu の内側で取る。

  格下げであって取り下げではないのは、上表が **Metal のみの実測**だから。
  wgpu が積むコストはバックエンドごとに違う（D3D12 は記述子ヒープとリソース
  状態遷移、Vulkan は明示バリアとディスクリプタセットで、wgpu の抽象が
  吸収している量が Metal と同じ保証は無い）。**D3D12 / Vulkan は未測定**で、
  そちらで取り分が出れば性能はその範囲で再び目的として立つ。
  **立てるには各プラットフォームでの実測を先に出すこと**（Metal の結果を
  横流ししない、`GPUBK-14` と同じ規律）。

- **説明**: GPU バックエンドを内製の抽象に置き換え、Metal（macOS）/ D3D12
  （Windows）を直接叩き、Linux は Vulkan とする。UI フレームワーク（GPUI）は
  ハードフォークして同じバックエンドに載せ、UI 描画とコンピュートの
  デバイス共有（REQ-GPU-001）を維持する。

  **WGSL は資産として維持する。** シェーダは 11 ファイルで、`naga` は wgpu とは
  独立したクレートとしてすでにワークスペースの直接依存にある。バックエンド feature
  （MSL / HLSL / SPIR-V 出力）を追加すれば、WGSL ソースを各プラットフォームの
  シェーダ言語へ落とせる。**ユーザーが書く WGSL（REQ-GPU-003）とシェーダ
  プラグイン（REQ-PLUGIN-002）の契約は、この移行を越えて変わらない。**

- **前提となる現状（2026-08-03 実測）**: 移行の難所は「クレート分離」ではなく
  「型の隠蔽」にある。

  | 事実 | 含意 |
  |---|---|
  | `wgpu::` の出現は **334 箇所 / 324 行 / 18 ファイル**、**`ravel-gpu` と `ravel-nodes` の 2 クレートのみ**（`find crates -name '*.rs' \| xargs grep -o 'wgpu::' \| wc -l`。テストと examples を含む） | `ravel-app` / `ravel-ui` / `ravel-dock` / `ravel-core` / `ravel-media` / `ravel-audio` は無変更 |
  | `ravel-core` は GPU 型を名前で知らない（`NodeData` が `is_gpu_resident()` を持つだけ） | 評価器・キャッシュ・グラフ・Composition は無変更 |
  | `ravel-app` は GPU フレームを不透明ハンドルとしてのみ触る | パネル層は無変更 |
  | ノードプロセッサの GPU 依存は引数 3 つに集約されている | 差し替え点が 1 箇所 |
  | だが `ravel-gpu` が生の wgpu ハンドル（device / queue / adapter / instance / pipeline / texture / view）を公開している | **façade になっていない** |
  | テクスチャプールのキー型に wgpu の enum（format / usage）が埋まっている | プールの同一性判定が wgpu の語彙で書かれている |
  | バインドグループ**レイアウト**は `gpu_util.rs` の 3 ヘルパに factor 済み（入力テクスチャ / 出力ストレージ / ユニフォーム）。ただし戻り値の型が wgpu | 抽象化は戻り値の型を差し替えることから始められる |
  | 各ノードが手書きしているのは**ディスパッチ側**（ユニフォームバッファ生成・テクスチャビュー生成・バインドグループ実体・コマンドエンコーダ）で、7 つのコンピュートノードで**形が同一** | 宣言的なディスパッチ API 1 つで 7 ノードを畳める。これは `MED-GPU-01`（ディスパッチごとのバッファ / バインドグループ再作成）の修正と同じ作業 |
  | 外れ値は 2 つだけ — `rasterize/mod.rs`（ストレージバッファで頂点データを渡し、`gpu_util.rs` のレイアウトヘルパを複製している）と `raster.rs`（唯一のレンダーパイプライン） | 例外は個別に扱えば足りる。複製の解消は抽象化の副産物 |

- **設計制約（この要件の本体）**:
  - **常に動く状態を保つ。** バックエンドを差し替える前に、抽象を挟んで
    **wgpu を「抽象の下の 1 実装」に押し込む**。抽象なしで書き換え始めると
    その間ビルドが通らない。
  - **抽象化それ自体が性能改善と重なる形にする。** バインドグループの記述を
    宣言的にすると、バインドグループのキャッシュとコマンドバッファのバッチングが
    同時に入る（`issues/medium/gpu-nodes.md` の `MED-GPU-01` が同じ場所の問題）。
    **バックエンドを差し替えなくても価値が出る**単位から始める。
  - **UI とコアを巻き込まない。** 上の表の「無変更」列を壊す変更は、
    抽象の切り方が間違っている兆候として扱う。
  - **デバイス共有の経路を壊さない。** 現行は外部から wgpu インスタンスを
    受け取って UI と共有する形。抽象化後も「外からデバイスを受け取れる」形を
    保ち、GPUI フォークを後から独立に進められるようにする。
  - **OFX が要求する形で外に出せる。** 抽象は Metal テクスチャ / デバイス
    ポインタを取り出せる出口を持つ（REQ-PLUGIN-001 の前提）。

- **受入条件**:
  - [ ] `ravel-gpu` の公開 API に特定バックエンドの型が現れない
  - [ ] テクスチャの形式と用途がバックエンド非依存の型で表現される
  - [ ] ノードプロセッサがバインディングを宣言的に記述し、バックエンド固有の
        記述子を組まない
  - [ ] 宣言的バインディングによってバインドグループが再利用され、
        ディスパッチごとの再作成が消える
  - [ ] WGSL ソースが naga 経由で各プラットフォームのシェーダ言語へ落ちる
  - [ ] 既存の全 GPU ノードがゴールデンテストで移行前と一致する
  - [ ] macOS で Metal バックエンドが動作する
  - [ ] Windows で D3D12 バックエンドが動作する
  - [ ] Linux で Vulkan バックエンドが動作する
  - [ ] UI 描画とコンピュートがデバイスを共有する（REQ-GPU-001 の条件を維持）
  - [ ] `ravel-core` / `ravel-ui` / `ravel-app` にバックエンド固有の依存が入らない
  - [ ] 抽象が OFX GPU Render Suite に渡せる形でテクスチャ / デバイスを露出できる
  - [ ] 移行の各段階でワークスペースのビルドとテストが通る
- **依存**: REQ-GPU-001, REQ-GPU-002, REQ-UI-001
- **これを前提とするもの**: REQ-PLUGIN-001（OFX）
