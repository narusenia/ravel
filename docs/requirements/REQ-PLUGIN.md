# REQ-PLUGIN — プラグインシステム

## REQ-PLUGIN-001: OpenFX統合 (C/C++ Shim、B→Aフル準拠)

- **優先度**: Must
- **ステータス**: Revised (v2 — 2026-08-03 に着手順を後置)
- **説明**: OpenFXプラグインをC/C++ Shimレイヤー経由で統合。初期はコアSubset（Image Effect + Parameter + GPU Render Suite）をサポートし、主要フィルタ系プラグイン（Sapphire、BorisFX、Neat Video等）の基本機能が動作。段階的にMulti-clip、Temporal Access、Interact Suiteを追加しOFX 1.4フル準拠を目指す。未実装Suiteは`kOfxStatErrUnsupported`を返す。OFXプラグインはREQ-PROJ-002のプロセス分離で隔離実行。
- **着手順（v2 で明示）**: 優先度は Must のまま維持する（映像制作ソフトとして
  既存の商用プラグイン資産が動くことは要件）。ただし**着手は REQ-INFRA-009
  （GPU バックエンドの内製化）の後**に置く。理由:

  1. **OFX GPU Render Suite は OpenGL / CUDA / Metal を前提とする。** 現行の
     GPU 基盤は wgpu 固定（REQ-GPU-001）で、これらとの相互運用が自明でない。
     wgpu のままだと実質 CPU バッファ経由に落ちるので、OFX ノードを 1 つ挟む
     ごとに毎フレームのリードバックが増える（`issues/closed/HIGH-05` と
     `issues/high/HIGH-04` で潰した / 潰している経路をそのまま再導入する）。
  2. REQ-INFRA-009 は Metal / D3D12 を直接触る抽象を作るので、**その抽象が
     OFX が要求する texture / device pointer をそのまま露出できる**。
     先に抽象を決めれば OFX ホストは自然に載る。逆順にすると、wgpu 前提の
     shim を書いてから捨てることになる。

  **着手できるのは `GPUBK-8`（interop 出口）の完了後**で、REQ-INFRA-009 の
  全体完了（`GPUBK-10`〜`13` の各バックエンド）を待つ必要はない。OFX が必要と
  するのは「抽象からバックエンド固有ハンドルを取り出せること」だけなので、
  `GPUBK-8` が契約を固めた時点で計画を書ける。実装計画をそれより前に書かないのは、
  前提が動いて腐るため（`docs/implementation/` には置かない）。
- **範囲の限界（v2 で明示）**: OFX の画像モデルは矩形 RGBA バッファ + RoD / ROI
  なので、OFX ノードは FrameBuffer → FrameBuffer に閉じる。ジオメトリ
  （REQ-CORE-010）・属性・フィールドを OFX から扱う道は無い。Ravel 独自の
  プロシージャル機能は REQ-PLUGIN-002 の経路が担う。
- **初期サポート (Phase B)**:
  - Image Effect Suite
  - Parameter Suite
  - GPU Render Suite (OpenGL/Metal/CUDA)
- **将来追加 (Phase A)**:
  - Multi-clip Suite
  - Temporal Access Suite
  - Interact Suite (ビューポートオーバーレイUI)
- **受入条件**:
  - [ ] OFXプラグインをスキャン・ロードできる
  - [ ] Image Effectプラグインが動作する
  - [ ] プラグインパラメータがRavel UIに表示される
  - [ ] GPU Renderが動作する
  - [ ] プラグインが別プロセスで隔離実行される
  - [ ] 未対応Suiteに対して`kOfxStatErrUnsupported`が返される
- **依存**: REQ-INFRA-009, REQ-PROJ-002, REQ-INFRA-007

## REQ-PLUGIN-002: ネイティブプラグインAPI (WGSL / WASM / Rust)

- **優先度**: Should
- **ステータス**: Revised (v2 — 2026-08-03 に形態と着手順を確定)
- **説明**: Ravelネイティブのプラグインシステム。OFXのC API制約に縛られず、Ravelのトレイトベース型システム（REQ-CORE-003）と直接統合。
- **拡張点は 1 箇所に作る（v2）**: 現状の解決経路は**閉じた `match` で、
  末尾が `_ => None`**。未知の `type_key` は黙って解決されないだけで、
  プラグイン空間は doc コメントが名前を付けているだけの空所。差し替え点が
  1 箇所（呼び出し元も 1 箇所）なので、そこをレジストリにする。
  **組み込みノードも同じ経路に寄せる** — 組み込みだけを特別扱いすると、
  プラグイン経路が恒久的に二級市民になり検証もされない。
  併せて**未知の `type_key` が黙って無視されず明示的なエラーになる**ようにする。
- **形態は 3 つで、扱うデータの種類ごとに使い分ける（v2）**:

  | 形態 | 第一級か | GPU | 適する対象 | 配布 |
  |---|---|---|---|---|
  | **WGSL シェーダ + manifest** | **v1 の主形態** | ○ | ピクセル効果 | ○ |
  | WASM（Component Model） | v2 | × | **ジオメトリ処理・属性演算** | ○ |
  | Rust ネイティブ（`cdylib`） | 補助 | ○ | 何でも | ×（自分用 / 社内用） |

  **WGSL を第一形態にする理由**: (1) ABI の問題がゼロ（配布物はテキスト）、
  (2) GPU で動くので CPU 往復が発生しない、(3) **ホスト側の capability が空**
  なのでホストのサンドボックス機構を作らずに出せる（ファイル・ネットワーク・
  ホストメモリに到達しない。REQ-INFRA-007 の段 1。**ただし WGSL は
  ループを持つので GPU ハングは起こせる** — ループ境界の扱いは実装計画で決める）、
  (4) ノードの形（入出力ポート・パラメータ）は
  REQ-PROJ-006 の公開パラメータ宣言をそのまま使えるので新しい概念が要らない、
  (5) 効果プラグインの需要の大半がピクセルシェーダ。REQ-GPU-003 の
  WGSL カスタムシェーダノードと同じ実行機構を、manifest で配布可能にしたもの。

  **WASM はジオメトリ側**: ジオメトリ処理は CPU 側（属性配列の変形）なので、
  WASM が GPU を使えないことが制約にならない。属性配列を線形メモリで渡す形は
  Component Model と相性がよい。

  **Rust ネイティブは信頼モデルかつ配布非対応**: Rust に安定 ABI が無く、
  `Arc<dyn NodeProcessor>` を dylib 境界で渡せない。同一コンパイラ前提でしか
  成立しないので、「自分用・社内用の拡張」として位置づけ、公開レジストリ
  （REQ-PLUGIN-004）の配布対象にはしない。

- **受入条件**:
  - [ ] ノードプロセッサの解決がレジストリ経由になり、組み込みも同じ経路を通る
  - [ ] WGSL シェーダと manifest だけでノードを追加できる
  - [ ] シェーダの入出力ポートとパラメータを manifest で宣言できる（REQ-PROJ-006）
  - [ ] 宣言したパラメータが Properties に出て統一チャネル（REQ-CORE-007）に接続できる
  - [ ] シェーダのコンパイルエラーが理由付きで表示され、アプリが落ちない
  - [ ] プラグインAPIドキュメントが提供される
  - [ ] プラグインがRavelの型システムと統合される
  - [ ] （v2）WASM プラグインがサンドボックス内でジオメトリを処理する
  - [ ] （補助）Rust ネイティブプラグインをロードでき、信頼モデルであることが
        ユーザーに明示される
- **依存**: REQ-CORE-003, REQ-PROJ-006, REQ-GPU-002, REQ-GPU-003, REQ-INFRA-007

## REQ-PLUGIN-003: Lua ランタイム (mlua)

- **優先度**: Must
- **ステータス**: Revised (v2 — 2026-08-03 に用途を限定)
- **説明**: `mlua` クレートで Lua を組み込む。**用途は REQ-CODE-001 のコード
  Layer / コードノードのみ**。サンドボックス内で実行する（REQ-INFRA-007）。
- **v2 で削った 2 つの用途とその理由**:

  1. **パラメータエクスプレッション → REQ-CORE-014 / REQ-CORE-015 へ。**
     当初は「Lua でエクスプレッション」としていたが、設計として逆向きだった。
     式に必要な表現力は狭く（他ノード参照はチャネルが構造的に持つ）、一方で
     フィールド式は要素ごとの評価になるため AST を持てる言語が要る。詳細な
     根拠は REQ-CORE-014 に書いた。**mlua はコード Layer のためのものであり、
     式のためのものではない。**
  2. **バッチ処理スクリプト・操作自動化 → REQ-PLUGIN-006 へ。** これは
     Document を書き換える側で、DAG 内部の純関数とは契約が正反対
     （前者は本質的に副作用を持ち、後者は決定的でなければキャッシュが壊れる）。
     同一のサンドボックスで括れないので分離し、言語選択も別に決める。

  結果として Lua の契約は 1 つになる: **DAG の内側で走る時間純関数**。
  `render(ctx) -> Geometry | FrameBuffer`（REQ-CODE-001）。決定性は言語で
  保証できないので契約として要求し、実行時のサンドボックス（`io` / `os` 除外 +
  命令数フック + メモリ上限）で守る。

- **受入条件**:
  - [ ] Lua スクリプトが REQ-CODE-001 の契約で評価される
  - [ ] `frame`, `time`, `fps` 等のコンテキスト変数にアクセスできる
  - [ ] 数学関数（sin/cos/noise等）が利用できる
  - [ ] ジオメトリ API（REQ-CORE-010 の属性読み書き）を利用できる
  - [ ] スクリプトエディタ / コンソールが提供される
  - [ ] ファイルシステム/ネットワークアクセスが制限される
  - [ ] 無限ループが命令数フックで中断され、UI が固まらない
  - [ ] メモリ確保が上限で止まり、プロセスが落ちない
- **依存**: REQ-CODE-001, REQ-INFRA-007

## REQ-PLUGIN-004: プラグインマネージャUI → オンラインレジストリ

- **優先度**: Should
- **ステータス**: Draft
- **説明**: アプリ内プラグインマネージャUI。インストール済みプラグイン（OFX/ネイティブ/WGSL/Lua/テーマ/テンプレート）の一覧表示、有効/無効切り替え、バージョン管理。パッケージmanifest仕様を初期から定義。将来的にオンラインレジストリ（`ravel install <package>`）に拡張。
  manifest がノードの形（入出力ポート・パラメータ）を宣言する部分は
  REQ-PROJ-006 の公開パラメータ宣言と**同じスキーマを使う**（`shader` /
  `node-pack` / `template` で 3 回発明しないため）。**信頼モデルを種別ごとに
  表示する**（REQ-INFRA-007 の段）。`rust-native` は配布対象にせず、手動配置のみ。
- **パッケージmanifest形式**:
  ```toml
  [package]
  name = "glitch-effects"
  version = "1.0.0"
  type = "node-pack"  # node-pack | ofx-bundle | template | shader | lua-script | theme
  ravel_compat = ">=0.1.0"
  ```
- **受入条件**:
  - [ ] インストール済みプラグインの一覧が表示される
  - [ ] プラグインの有効/無効を切り替えられる
  - [ ] パッケージmanifest仕様が定義されている
  - [ ] 手動インストール（ディレクトリ配置）でプラグインが認識される

## REQ-PLUGIN-005: プリセット/テンプレートシステム + コミュニティ配布

- **優先度**: Should
- **ステータス**: Draft
- **説明**: 3粒度のプリセット。(1)ノード単位プリセット（パラメータ保存/復元）、(2)サブグラフテンプレート（複数ノードの再利用、公開パラメータ定義）、(3)プロジェクトテンプレート（SNS向け縦動画、MV用等）。テンプレートパッケージはREQ-PLUGIN-004のmanifest形式に準拠。ローカルインポート/エクスポートで初期運用。
- **(2) は Houdini の HDA / Nuke の Gizmo / Blender の Node Group に当たる
  （2026-08-03 追記）**: 実際のプラグイン生態系では、**コードでない拡張**が
  主力になっている（Nuke で流通しているものの大半は C++ プラグインではなく
  Gizmo）。Ravel は評価側の土台をすでに持っている — `subnet` ノードが内部グラフを
  再帰評価し、`net.in` / `net.out` がカスタムポートを扱える（REQ-LAYER-003）。
  公開パラメータの宣言は REQ-PROJ-006 の機構をそのまま使うので、**この粒度が
  最も早く、最も安全に出せる拡張形態**になる。コード実行を伴わないので
  サンドボックスの議論も要らない。
- **受入条件**:
  - [ ] ノード単位のプリセットを保存/適用できる
  - [ ] サブグラフをテンプレートとして保存/インポートできる
  - [ ] サブグラフテンプレートの公開パラメータが REQ-PROJ-006 の宣言で表現される
  - [ ] プロジェクトテンプレートから新規プロジェクトを作成できる
  - [ ] テンプレートのエクスポート/インポートが可能
- **依存**: REQ-PLUGIN-004, REQ-PROJ-006, REQ-LAYER-003, REQ-UI-002

## REQ-PLUGIN-006: 操作自動化 / バッチスクリプト

- **優先度**: Could
- **ステータス**: Draft（2026-08-03 新設。REQ-PLUGIN-003 から分離）
- **説明**: エディタの操作を外部から駆動する経路。プロジェクトの一括変換、
  複数バリエーションの生成、定型作業の自動化。**DAG の内側で走るコード
  （REQ-CODE-001）とは契約が正反対**で、こちらは Document を書き換える
  副作用が本質。
- **言語は未定**: Lua には**しない**。理由は、DAG 内部の Lua（REQ-PLUGIN-003）と
  同じ処理系を共有すると「純粋でなければならない側」と「副作用が本質の側」が
  同じサンドボックスに乗ってしまい、境界が守れなくなるため。候補は別途評価する
  （自作 DSL も視野に入れる）。
- **急がない理由**: テンプレートレンダリング（複数バリエーションの生成）は
  REQ-RENDER-005 の CLI と REQ-PROJ-006 の公開パラメータ宣言で成立するので、
  自動化スクリプトが無くても主要な用途が埋まる。
- **設計上の前提（言語が決まる前に確定しておくもの）**:
  - 変更は既存の Command 経路を通る（`.agents/rules/` の「Command 経路単一性」）。
    スクリプトが独自にドキュメントを書き換える裏口を作らない。
  - 1 スクリプトの実行が undo の 1 単位、または明示的にグループ化できる。
  - GUI を起動せずに実行できる（REQ-RENDER-005 と同じヘッドレス層に乗る）。
- **受入条件**:
  - [ ] スクリプトからプロジェクトを開き、変更し、保存できる
  - [ ] 変更が既存の Command 経路を通り、undo で戻せる
  - [ ] GUI なしで実行できる
  - [ ] 失敗が分類された終了コードになる
- **依存**: REQ-RENDER-005, REQ-PROJ-006, REQ-UI-003
