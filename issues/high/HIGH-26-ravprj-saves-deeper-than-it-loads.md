# [HIGH-26] `.ravprj` は自分で読めない深さまで保存できる — サブネットを深く入れ子にしたプロジェクトが二度と開かない

| 項目 | 内容 |
| --- | --- |
| 深刻度 | high |
| 種別 | bug |
| 領域 | ravel-project / 永続化 |
| 該当 | `crates/ravel-project/src/graph_doc.rs:67`, `crates/ravel-core/src/composition/mod.rs:599` |

## 現状

**保存側と読み込み側で有効な上限が違う。**

- 文書が許すサブネットの入れ子は `MAX_SUBNET_DEPTH = 64`
  （`composition/mod.rs:599`）。保存はこの上限で検証される
- 読み込みは `ron::from_str`（`graph_doc.rs:67`）を既定設定で呼ぶ。**RON の
  デシリアライザは自前の再帰上限を持ち**、サブネット 1 段が RON の入れ子を
  複数段消費するため、**サブネット深さ 20 前後で `ExceededRecursionLimit`** に
  達する

つまり深さがこの 2 つの上限の間にある文書は、**保存に成功し、開くときに失敗する**。

`.ravtpl`（`EXPO-6` で追加したサブグラフテンプレート）も同じ `ron::from_str` を
通るので同条件。

## 影響

**保存できたプロジェクトが二度と開けない。** 警告も出ず、保存時点では成功して
いるので、ユーザーは失うまで気づけない。復旧手段はファイルを手で編集して
入れ子を浅くすることだけで、実質的なデータ損失。

引き金は「サブネットを 20 段近く入れ子にすること」で、現状の到達経路は
Collapse to Subnet の繰り返しに限られるため頻度は低い。ただし
`plugin-system-plan.md` のサブグラフテンプレートや `EXPO-6` の入れ子が広まると
到達しやすくなる。

## 修正方針

**上限を 1 つにする。** 選択肢は 2 つで、どちらを採るかは決めが要る。

1. **読み込み側を文書の上限に合わせる。** `ron::Options` の
   `recursion_limit` を `MAX_SUBNET_DEPTH` が要求する RON 段数まで引き上げる。
   このとき**スタック消費が上限になる**ので、深い入力でスタックを溢れさせない
   ことを fuzz で確かめる必要がある（`crates/ravel-project/tests/fuzz_parser.rs`
   が既に 100,000 件の不正入力を流している）
2. **保存側を読み込みの実力に合わせる。** `MAX_SUBNET_DEPTH` を RON が確実に
   読める深さまで下げる。保存できたものは必ず開けるようになるが、
   **既存の深い文書が保存できなくなる**ので移行の検討が要る

**どちらにせよ「保存できたものは開ける」を不変条件として明示し、テストで
固定すること。** 現状はその不変条件がどこにも書かれていない。

`.ravtpl` 側だけ先に上限を上げるのは**やってはいけない** — 「貼り付けた文書が
再読込できないテンプレート」を作れるようになり、非対称が悪化する。

## 備考

`EXPO-6`（サブグラフテンプレート）の実装中に発見した。**この欠陥自体は
`.ravprj` に元からあり、`EXPO-6` が持ち込んだものではない。**
`crates/ravel-project/src/subgraph_template.rs` の
`a_template_nested_past_the_document_limit_does_not_load` が、2 つの上限が
併存している事実をテストのコメントに記録している。
